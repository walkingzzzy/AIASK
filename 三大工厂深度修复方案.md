# 三大工厂深度修复方案

> 来源：基于 2026-05-19 深度代码审查（策略工厂 / 因子挖掘工厂 / 孵化工厂），发现 12 个具体问题。
> 方法：每个修复都落到具体文件 + 行号 + diff，不写"建议优化"类无操作语言。
> 范围：本方案只覆盖审查中实测到的差距，不引入新功能。

---

## 0. 背景与判断

三大工厂的**架构已经成形**，核心问题不是缺模块，而是**关键回环没接通**：

- 因子挖掘工厂产物只输出"因子名字"，DSL / fitness / IC 都没进策略工厂的 spawn 路径。
- 孵化工厂 runner 路径的 metric 写入和 schema 字段名错位，`incubation_factory/metrics_recorder.py` 写出的部分指标列恒为 NULL（注意：`incubation_parts/runtime.py` 的另一条记录路径已经写对字段）。
- DecayTracker 完整写好但**全仓库零调用**，衰减监控形同虚设。
- IncubationAccelerator 只写事件不晋升，加速孵化只是日志。
- `report_factor_performance` 通道开了无人调，因子→策略实盘反馈断链。

修复的核心目标是**让现有代码真的跑起来**，而不是新增能力。

### 2.1 修复 #1：接通 DecayTracker 衰减闭环

**根因**：
- [pool/decay_tracker.py:80-118](packages/akshare-mcp/src/akshare_mcp/services/factor_mining_factory/pool/decay_tracker.py#L80-L118) 实现了双曲衰减估计，但**全仓库零调用**。

```python
"""Adapter that pulls factor IC snapshot from factor_ic_history."""
from __future__ import annotations

from datetime import datetime, timezone
from typing import Any


async def compute_factor_ic_snapshot(db: Any, factor_id: str, factor_name: str | None) -> dict[str, Any]:
    """Return {current_ic, days_since_admission}.

    Reads recent rolling IC from factor_ic_history table; falls back to 0.0
    when the table is empty or unavailable.
    """
    if not hasattr(db, "fetch"):
        return {"current_ic": 0.0, "days_since_admission": 0}
    try:
        # Use factor_name when available, otherwise factor_id (storage key
        # variability — both are exercised in the codebase).
        key = factor_name or factor_id
        rows = await db.fetch(
            """
            SELECT ic_value, ic_date
              FROM factor_ic_history
             WHERE factor_name = $1
             ORDER BY ic_date DESC
             LIMIT 20
            """,
            key,
        )
        if not rows:
            return {"current_ic": 0.0, "days_since_admission": 0}

        # 简单 EMA(20)
        weights = [(0.85 ** i) for i in range(len(rows))]
        total_weight = sum(weights) or 1.0
        current_ic = sum(float(r["ic_value"] or 0.0) * w for r, w in zip(rows, weights)) / total_weight

        latest = rows[0]["ic_date"]
        oldest = rows[-1]["ic_date"]
        try:
            days = (
                datetime.fromisoformat(str(latest)).date()
                - datetime.fromisoformat(str(oldest)).date()
            ).days
        except Exception:
            days = 20
        return {"current_ic": float(current_ic), "days_since_admission": max(days, 0)}
    except Exception:
        return {"current_ic": 0.0, "days_since_admission": 0}
```

### 3.1 修复 #4：把 IC/IR 真正反馈进进化循环

**根因**：所有引擎的 fitness 都基于"编译有效性 + 字段多样性 + 复杂度"等结构性指标 ([gp_engine.py:246-288](packages/akshare-mcp/src/akshare_mcp/services/factor_mining_factory/engines/gp_engine.py#L246-L288), [rl_engine.py:250-280](packages/akshare-mcp/src/akshare_mcp/services/factor_mining_factory/engines/rl_engine.py#L250-L280), [evolution/optimizer.py:67-91](packages/akshare-mcp/src/akshare_mcp/services/factor_mining_factory/evolution/optimizer.py#L67-L91))，**进化阶段感知不到 IC**。预测力反馈只在最末端的 `_validate_batch` 出现。

**修复策略**：
1. 在 `EvolutionaryOptimizer.evolve` 的每一代结束时跑一次"轻量 IC 评估"（用 `validation_codes` 子集 + 短 lookback），把 IC 注入 fitness。
2. 把 `validation_result.ic_mean` 也回传到 raw_candidates 的 fitness，让下一轮搜索能复用经验（meta_learner.record_cycle 已经接收 candidates，但没读 IC）。

文件：`packages/akshare-mcp/src/akshare_mcp/services/factor_mining_factory/evolution/optimizer.py`

### 4.1 修复 #7：用 Wilson 区间替换 skill_lcb 的样本方差近似

**根因**：[forward_verifier.py:219-234](packages/akshare-mcp/src/akshare_mcp/services/incubation_factory/forward_verifier.py#L219-L234) 在 0/1 命中序列上用 `np.std(ddof=1)` 估方差再做 Wald 正态近似。该近似在小样本（n<30）和极端命中率下不稳定，可能偏高也可能偏低；Wilson 区间更适合作为二项命中率下界。

**修复**：

```diff
-    def _compute_skill_lcb(self, hits: list[float]) -> float:
+    def _compute_skill_lcb(self, hits: list[float]) -> float:
+        """Wilson 95% lower bound for proportion (hit_rate), then subtract 0.5.
+
+        Replaces the previous Wald approximation, which is unstable for
+        n < 30 / extreme hit_rate values.
+        """
         if len(hits) < 5:
             return 0.0
-        arr = np.array(hits, dtype=np.float64)
-        hit_rate = float(np.mean(arr))
-        skill = hit_rate - 0.5
-        std = float(np.std(arr, ddof=1))
-        n = len(arr)
-        lcb = skill - 1.96 * std / np.sqrt(n)
-        return float(lcb)
+        n = len(hits)
+        p = float(np.mean(hits))
+        z = 1.96
+        denom = 1 + z * z / n
+        center = (p + z * z / (2 * n)) / denom
+        margin = (z * np.sqrt(p * (1 - p) / n + z * z / (4 * n * n))) / denom
+        wilson_lower = center - margin

```

### 4.2 修复 #8：修正 forward_sharpe 的持有期年化

**根因**：[forward_verifier.py:269-279](packages/akshare-mcp/src/akshare_mcp/services/incubation_factory/forward_verifier.py#L269-L279) 输入的 `all_returns` 实际上已经等价于按方向调整后的持有期收益（`hit ? abs(r) : -abs(r)` 等价于 `primary_return * direction`），但 `_compute_forward_sharpe` 按日频 `√252` 年化；当 primary horizon 是 5/10 日时，频率与收益周期不匹配。

**修复**：把 `all_returns.append(abs(primary_return) if hit else -abs(primary_return))` 改成语义更直接的 `all_returns.append(primary_return * direction)`；同时把 `√252` 改成 `√(252/primary_horizon)`，按持有期频率年化。

```diff
-    def _compute_forward_sharpe(self, returns: list[float]) -> float:
+    def _compute_forward_sharpe(self, returns: list[float], horizon_days: int = 5) -> float:
         if len(returns) < 5:
             return 0.0
         arr = np.array(returns, dtype=np.float64)
         mean_return = float(np.mean(arr))
         std_return = float(np.std(arr, ddof=1))
         if std_return < 1e-10:
             return 0.0
-        return float(mean_return / std_return * np.sqrt(252))
+        # 每年的独立持有期数 = 252 / horizon_days
+        periods_per_year = max(1.0, 252.0 / max(horizon_days, 1))
+        return float(mean_return / std_return * np.sqrt(periods_per_year))
```

并修改 `verify` 中 `all_returns.append(...)` 的逻辑：把 `abs(primary_return) if hit else -abs(primary_return)` 改成 `primary_return * direction`（方向调整后的持有期收益，语义更直接但数值基本等价），并调用 `self._compute_forward_sharpe(all_returns, horizon_days=primary_horizon)`。
