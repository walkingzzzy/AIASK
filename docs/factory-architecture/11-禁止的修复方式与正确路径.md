# 禁止的修复方式与正确路径

## ⚠️ 强制性规范

**本文档列举了策略工厂开发中禁止的修复方式，以及对应的正确修复路径。**

所有问题修复必须按照"诊断根因 → 修复根本缺陷 → 验证修复效果"的流程进行，**禁止**通过打补丁方式掩盖根因问题。

---

## 问题 1：状态没有统一来源

### ❌ 禁止的修复方式

```python
# 错误：从多个表拼接状态
def get_strategy_health(strategy_id):
    status = db.query("SELECT status FROM strategies WHERE id=?", strategy_id)[0]
    signals = db.query("SELECT COUNT(*) FROM strategy_signals WHERE strategy_id=?", strategy_id)[0]
    orders = db.query("SELECT COUNT(*) FROM paper_orders WHERE strategy_id=?", strategy_id)[0]
    trades = db.query("SELECT COUNT(*) FROM paper_trades WHERE strategy_id=?", strategy_id)[0]
    
    # 自行拼接判断逻辑
    if status == "incubating" and signals > 0 and orders > 0 and trades > 0:
        return "healthy"
    elif status == "incubating" and signals > 0 and orders == 0:
        return "signal_only_backlog"
    # ... 更多判断逻辑
```

**为什么禁止**：
1. 每个调用者都自行拼接，逻辑不一致
2. SignalTracker、Incubation、Quality Session 各自判断，产生矛盾
3. 无法回答"哪个组件负责下一步"

### ✅ 正确的修复路径

**P1 任务**：实现统一生命周期账本

```python
# packages/aiask-quant-core/src/aiask_quant_core/strategy_lifecycle/ledger.py

class StrategyLifecycleLedger:
    """单一真相来源"""
    
    async def get_state(self, strategy_id: str) -> StrategyLifecycleState:
        """唯一入口查询策略状态"""
        # 从所有证据表聚合
        db_status = await self._get_db_status(strategy_id)
        has_signal = await self._check_signal_existence(strategy_id)
        has_order = await self._check_order_existence(strategy_id)
        has_trade = await self._check_trade_existence(strategy_id)
        has_exit = await self._check_exit_existence(strategy_id)
        audit_status = await self._get_audit_status(strategy_id)
        
        # 诊断 blocker
        blocker_component, blocker_reason = self._diagnose_blocker(
            has_signal, has_order, has_trade, has_exit, audit_status
        )
        
        return StrategyLifecycleState(
            strategy_id=strategy_id,
            db_status=db_status,
            has_signal=has_signal,
            has_order=has_order,
            has_trade=has_trade,
            has_exit=has_exit,
            audit_status=audit_status,
            blocker_component=blocker_component,
            blocker_reason=blocker_reason,
        )
    
    def _diagnose_blocker(self, has_signal, has_order, has_trade, has_exit, audit_status):
        """统一 blocker 诊断逻辑"""
        if not has_signal:
            return ("SignalTracker", "strategy not in execution universe or no signal generated")
        if not has_order:
            return ("SignalTracker", "signal exists but not converted to order")
        if not has_trade:
            return ("Settlement", "order exists but not filled")
        if not has_exit:
            return ("Incubation", "only open positions - missing exit signal")
        if audit_status == "missing":
            return ("ExecutionAudit", "audit chain broken")
        if audit_status == "bootstrap_pending":
            return ("System", "waiting for evidence maturity")
        return ("None", "no blocker")
```

**验收标准**：
1. 所有状态查询必须通过 `StrategyLifecycleLedger.get_state()`
2. 任何策略在任意时刻，只有一个明确的 blocker_component
3. Quality Session、诊断工具、四工厂都使用同一个 ledger

## 问题 2：Quality Session 成为隐形控制面

### ❌ 禁止的修复方式

```python
# 错误：在验证脚本中启用补偿逻辑
def _apply_quality_session_runtime_defaults():
    os.environ["INCUBATION_FACTORY_PAPER_EXECUTION_BACKLOG_ENABLED"] = "1"
    os.environ["INCUBATION_FACTORY_EXECUTION_AUDIT_NATIVE_EVIDENCE_BACKFILL_ENABLED"] = "1"
    os.environ["INCUBATION_FACTORY_STALE_PAPER_POSITION_CLOSURE_ENABLED"] = "1"
    os.environ["STRATEGY_FACTORY_RUN_ONCE_TIMEOUT_SEC"] = "420"
    os.environ["STRATEGY_PIPELINE_STAGE_TIMEOUT_SEC"] = "25"
    # ... 50+ 环境变量
```

**为什么禁止**：
1. 验证脚本不是在"观察生产"，而是在"定义验证版本的生产"
2. 补偿逻辑掩盖了生产链路缺陷
3. 验证通过不等于生产健康

### ✅ 正确的修复路径

**P0 任务**：Quality Session 回归纯验证

```python
# scripts/factories/run_strategy_factory_quality_session.py (重构版)

async def run_quality_session(*, enable_compensation: bool = False):
    """纯验证模式 - 默认不启用补偿逻辑"""
    
    if enable_compensation:
        logger.warning("⚠️  启用了补偿逻辑 - 这不是生产观察模式")
        _enable_compensation_flags()
    
    # 1. 运行生产版本（使用生产默认参数）
    factory_result = await run_strategy_factory_once()
    
    # 2. 用统一账本对账
    ledger = StrategyLifecycleLedger(db)
    states = await ledger.reconcile_all()
    
    # 3. 纯统计报告（不补偿）
    report = {
        "total_strategies": len(states),
        "blocked_by_component": defaultdict(int),
        "evidence_status": {
            "has_signal": sum(1 for s in states if s.has_signal),
            "has_order": sum(1 for s in states if s.has_order),
            "has_trade": sum(1 for s in states if s.has_trade),
            "has_exit": sum(1 for s in states if s.has_exit),
        },
        "audit_gate_distribution": defaultdict(int),
    }
    
    for state in states:
        report["blocked_by_component"][state.blocker_component] += 1
        report["audit_gate_distribution"][state.audit_status] += 1
    
    return report
```

**验收标准**：
1. 默认模式不设置任何 backlog/backfill/stale close 环境变量
2. 报告明确区分"生产证据"和"验证补偿证据"
3. 补偿逻辑移到生产控制面（Incubation Factory 主线）

## 问题 3：LLM 超时是调度预算失配

### ❌ 禁止的修复方式

```python
# 错误：单纯增加 timeout
os.environ["STRATEGY_FACTORY_RUN_ONCE_TIMEOUT_SEC"] = "1800"  # 从 420s 改为 1800s
os.environ["STRATEGY_PIPELINE_STAGE_TIMEOUT_SEC"] = "60"     # 从 25s 改为 60s
```

**为什么禁止**：
1. 没有解决根本问题：200 stocks × 3 types × 5 stages × 60s = 180,000s，仍然超预算
2. 单纯延长等待时间，不改变失败率
3. 掩盖了调度预算失配的真相

### ✅ 正确的修复路径

**P1 任务**：分阶段预算 + 批次限流

```python
# packages/strategy-factory/src/strategy_factory/application/_factory_scheduler_loop_parts/models.py

async def _execute_factory_run_once_mode(self, db, ...):
    """分阶段预算，而非整轮超时"""
    
    # 阶段 1: 候选生成（允许较长时间）
    logger.info("Phase 1: Generating candidates (budget: 300s)")
    generation_results = await asyncio.wait_for(
        self._generate_candidates(db, ...),
        timeout=300
    )
    logger.info(f"Generated {len(generation_results)} candidates")
    
    # 阶段 2: LLM 批量调用（按批次限流）
    batch_size = 10  # 每批 10 个策略
    llm_timeout_per_batch = 60  # 每批 60s
    
    logger.info(f"Phase 2: Processing {len(generation_results)} candidates in batches of {batch_size}")
    all_llm_results = []
    for i, batch in enumerate(batched(generation_results, batch_size)):
        logger.info(f"Processing batch {i+1}/{(len(generation_results)+batch_size-1)//batch_size}")
        try:
            batch_results = await asyncio.wait_for(
                asyncio.gather(*[self._llm_stage(c) for c in batch]),
                timeout=llm_timeout_per_batch
            )
            all_llm_results.extend(batch_results)
        except asyncio.TimeoutError:
            logger.warning(f"Batch {i+1} timeout - skipping {len(batch)} candidates")
            continue
    
    # 阶段 3: Admission/Gate（快速）
    logger.info("Phase 3: Running admission gates (budget: 30s)")
    gate_results = await asyncio.wait_for(
        self._run_admission_gates(db, all_llm_results),
        timeout=30
    )
    
    return gate_results
```

**验收标准**：
1. 每个阶段有独立的 timeout 预算
2. LLM 阶段按批次限流，单批失败不影响整轮
3. 日志明确显示每批次耗时和成功率

## 问题 4：Paper 执行双路径不一致

### ❌ 禁止的修复方式

```python
# 错误：在 Incubation backlog phase 中单独实现执行逻辑
async def incubation_backlog_phase(db):
    # 自己查询策略集合
    strategies = await db.query("""
        SELECT * FROM strategies 
        WHERE status='incubating' 
        AND id IN (SELECT strategy_id FROM strategy_incubation_accounts WHERE status='active')
    """)
    
    # 自己实现下单逻辑
    for strategy in strategies:
        await place_order(strategy)
```

**为什么禁止**：
1. SignalTracker 和 Incubation 看到的策略集合不同
2. 两边的执行宇宙、跳过原因、持仓约束不一致
3. 无法诊断为什么"SignalTracker 没单，Incubation 有单"

### ✅ 正确的修复路径

**P2 任务**：统一执行宇宙契约

```python
# packages/aiask-quant-core/src/aiask_quant_core/strategy_lifecycle/execution_universe.py

class ExecutionUniverseContract:
    """SignalTracker 和 Incubation 共用的执行宇宙查询"""
    
    async def list_executable_strategies(
        self, 
        db, 
        as_of: date,
        *,
        include_warmup: bool = True,
        include_diagnostic: bool = False,
    ) -> list[dict]:
        """
        单一真相来源 - 返回所有可执行策略
        
        Returns:
            list[dict]: 每项包含 strategy_id, account_id, stage, skip_reason (if any)
        """
        # 1. 查询所有候选策略
        candidates = await self._query_all_candidates(db, include_warmup, include_diagnostic)
        
        # 2. 应用统一过滤规则
        executable = []
        for candidate in candidates:
            skip_reason = await self._check_skip_conditions(db, candidate, as_of)
            if skip_reason:
                executable.append({**candidate, "skip_reason": skip_reason, "executable": False})
            else:
                executable.append({**candidate, "skip_reason": None, "executable": True})
        
        return executable
    
    async def _check_skip_conditions(self, db, candidate, as_of):
        """统一的跳过条件检查"""
        # 检查 account_id
        if not candidate.get("account_id"):
            return "no_account_bound"
        
        # 检查 runtime_control
        if await self._is_runtime_blocked(db, candidate["strategy_id"]):
            return "runtime_control_blocked"
        
        # 检查持仓约束
        if await self._has_open_position(db, candidate["strategy_id"]):
            return "open_position_exists"
        
        # 检查执行宇宙
        if not await self._in_execution_universe(db, candidate["strategy_id"], as_of):
            return "not_in_execution_universe"
        
        return None  # 可执行
    
    async def diagnose_consistency(self, db, as_of: date) -> dict:
        """诊断 SignalTracker 和 Incubation 的一致性"""
        all_executable = await self.list_executable_strategies(db, as_of)
        
        # 模拟 SignalTracker 视图
        signal_tracker_view = [
            s for s in all_executable 
            if s["executable"] and s.get("stage") in ("warmup", "diagnostic", None)
        ]
        
        # 模拟 Incubation 视图
        incubation_view = [
            s for s in all_executable 
            if s["executable"] and s.get("account_id")
        ]
        
        only_in_signal_tracker = set(s["strategy_id"] for s in signal_tracker_view) - set(s["strategy_id"] for s in incubation_view)
        only_in_incubation = set(s["strategy_id"] for s in incubation_view) - set(s["strategy_id"] for s in signal_tracker_view)
        
        return {
            "consistent": len(only_in_signal_tracker) == 0 and len(only_in_incubation) == 0,
            "only_in_signal_tracker": list(only_in_signal_tracker),
            "only_in_incubation": list(only_in_incubation),
            "all_executable_count": len([s for s in all_executable if s["executable"]]),
        }
```

**验收标准**：
1. SignalTracker 和 Incubation 都调用 `ExecutionUniverseContract.list_executable_strategies()`
2. 一致性诊断工具报告 `consistent=True`
3. 所有 skip_reason 都能追溯到统一的检查逻辑

## 问题 5：Audit 正确卡住，但缺证据生产

### ❌ 禁止的修复方式

```python
# 错误：放宽 production hard gate 标准
def evaluate_execution_audit_gate(...):
    # 把 bootstrap_pending 当作通过
    if realized_trade_count > 0:  # 只要有一笔就算通过
        return "passed"
```

**为什么禁止**：
1. Production hard gate 是最后的质量保证，不能放宽
2. 样本不足时应该等待，而不是降低标准
3. 掩盖了上游不生产 closed position 的缺陷

### ✅ 正确的修复路径

**P2 任务**：补全证据生产链路

```python
# packages/akshare-mcp/src/akshare_mcp/services/incubation_parts/runtime.py

async def process_strategies(self, db, strategies, signal_date):
    """统一入口 - 补全 exit 逻辑"""
    
    for strategy in strategies:
        try:
            # 1. 确保 account 绑定
            ensure_result = await self.ensure_account(db, strategy)
            
            # 2. sync signals to orders（已有）
            sync_result = await self.sync_signals_to_orders(db, strategy, signal_date)
            
            # 3. settle orders to trades（已有）
            settle_result = await self.settle_orders(db, strategy, signal_date)
            
            # 4. **新增**: 检查 exit signals 并下平仓单
            exit_result = await self.process_exit_signals(db, strategy, signal_date)
            
            # 5. **新增**: 应用 stale close policy（持仓超过 N 天自动平仓）
            stale_result = await self.close_stale_positions(
                db, 
                strategy, 
                signal_date,
                stale_days_threshold=30  # 持仓超过 30 天自动平仓
            )
            
            # 6. calculate forward returns（已有）
            forward_result = await self.calculate_forward_returns(db, strategy)
            
            # 7. record metrics（已有）
            metrics_result = await self.record_incubation_metrics(db, strategy, signal_date)
            
        except Exception as e:
            logger.error(f"Strategy {strategy['id']} processing failed: {e}")
            continue

async def process_exit_signals(self, db, strategy, signal_date):
    """生成 exit signal 并下平仓单"""
    # 查询所有 open positions
    open_positions = await db.query("""
        SELECT * FROM strategy_trade_positions
        WHERE strategy_id = ? AND status = 'open'
    """, strategy["id"])
    
    for position in open_positions:
        # 检查策略是否产生了 exit signal
        exit_signal = await self._get_exit_signal(db, strategy, position, signal_date)
        
        if exit_signal and exit_signal != 0:
            # 下平仓单
            order = await self._place_exit_order(db, strategy, position, exit_signal, signal_date)
            logger.info(f"Placed exit order for position {position['id']}: {order}")

async def close_stale_positions(self, db, strategy, signal_date, stale_days_threshold):
    """应用 stale close policy"""
    stale_positions = await db.query("""
        SELECT * FROM strategy_trade_positions
        WHERE strategy_id = ? 
        AND status = 'open'
        AND JULIANDAY(?) - JULIANDAY(entry_date) > ?
    """, strategy["id"], signal_date, stale_days_threshold)
    
    for position in stale_positions:
        logger.warning(f"Position {position['id']} is stale ({position['entry_date']} -> {signal_date}), closing")
        order = await self._place_stale_close_order(db, strategy, position, signal_date)
        logger.info(f"Placed stale close order: {order}")
```

**验收标准**：
1. `realized_trade_count` 自然增长（不是通过 backfill 补的）
2. `strategy_trade_positions` 中 `status='closed'` 的记录增加
3. Audit gate 从 `bootstrap_pending` 变为 `insufficient_samples` 再变为 `passed`

## 总结：禁止打补丁的原则

### 打补丁的典型特征

1. **症状修复，不修根因** - 单纯增加 timeout、放宽 gate、启用补偿开关
2. **局部有效，全局失效** - 在验证脚本中通过，生产环境仍然失败
3. **越修越多** - Phase 3c/3d/3e/f/g 不断增加，主线反而更模糊
4. **掩盖真相** - 用 `success` 掩盖 `partial_infra`，用补偿掩盖链路缺陷

### 正确修复的特征

1. **诊断根因** - 使用自动化诊断工具，明确责任组件
2. **修复根本缺陷** - 实现统一状态机、统一执行宇宙、补全证据链路
3. **可验证** - 修复后诊断状态明确改善，不是靠补偿掩盖
4. **可维护** - 新代码符合规范，不引入新的局部真相

### 代码审查清单

所有代码提交前，必须通过以下检查：

- [ ] 是否绕过了 `StrategyLifecycleLedger` 统一入口？
- [ ] 是否在 Quality Session 中启用了补偿逻辑？
- [ ] 是否单纯增加了 timeout 而不修复调度预算失配？
- [ ] 是否在不同组件中重复实现了相同的查询逻辑？
- [ ] 是否放宽了 production hard gate 标准？
- [ ] 是否通过手工数据修复了证据链路？
- [ ] 是否在报告中掩盖了 `failed`/`partial_infra`/`blocked` 真相？

**任何一项检查不通过，代码不得合并。**
