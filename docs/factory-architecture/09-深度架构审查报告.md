# 深度架构审查报告

## 审查结论

策略工厂长期修不完的原因，不是单点代码质量差，而是系统在控制面、生命周期、证据链和验证入口之间没有统一裁决。四工厂职责已经逐步形成，但仍存在“生产线跑起来”和“证据闭环健康”之间的架构落差。

最核心的判断：

- 四工厂进程健康不等于策略生产线健康。
- Strategy Factory 生成/准入健康不等于 Incubation 晋级健康。
- SignalTracker sidecar 缺席会让孵化证据断链，但它又不在四工厂 supervisor 内。
- quality session 能暴露问题，也可能掩盖生产控制面缺位。
- 当前 `hard_gate_passed=0` 不能被强修；没有真实 paper closed round-trip 时，这是正确结果。

## 审查限制

当前会话未暴露 `thinking` MCP server/resource/tool，因此本报告不能声称调用了 thinking MCP。已使用的深度审查来源包括：

- 当前源码和启动脚本。
- Graphify 代码图谱。
- `akshare-mcp` resources/templates。
- AKShare MCP server capability 和 tool catalog。

## 为什么不能只按 MCP tool 数量估算边界

本轮深审确认，四工厂对 `akshare-mcp` 的依赖并不主要发生在 FastMCP tool catalog，而是发生在四层能力面：

1. `MCP host surface`：server/tool/resource/prompt/manager facade
2. `Runtime provider surface`：`configure_strategy_factory_runtime_services()` 注入的 provider
3. `Runtime adapter surface`：repository/vector/autonomy/factor_research/incubation/validation/risk
4. `Factory implementation surface`：`factor_mining_factory`、`incubation_factory`、`signal_tracker_parts`、`market_event_sources`、`strategy_lifecycle_shared`、`matching_engine`、`nav_engine`

当前真实代码已经确认：

- Strategy Factory 默认 host bridge 注入 20 个 provider。
- `MCPRuntimeAdapters` 当前暴露 7 条 adapter 通道；若只算 gateway 通道则为 6 条，另加 1 条 repository 通道。
- 共享存储层还额外接入 signal evidence、execution audit snapshot、event extraction、text embedding 等 runtime hook。

这也是为什么：

- 只看 `179 tools` 会低估四工厂真正吃掉的运行实现。
- 只看 `strategy-factory` 目录又会高估当前运行迁移进度。
- 必须把 provider、adapter、service、storage hook、sidecar 都纳入同一审计口径。

- `12-四工厂真实流程与MCP依赖审计.md`
- `13-四工厂-MCP能力占用台账.md`

若要看 target-state 的正式拆分路线，而不是 current-state 审查结论，请读根目录主方案：

## 核心问题

### 1. 多套局部真相

系统同时有 Strategy Factory run result、SignalTracker result、Incubation result、Quant Core audit summary、quality session snapshot。它们都有自己的 status/healthy/partial 字段，但没有一个统一的 Lifecycle Ledger 裁决。

后果：

- 外层 `success=True` 可能弱化底层 `partial_infra`。
- `submitted=0` 可能掩盖 observe/paper/audit-only 的实际入口。
- `hard_gate_passed=0` 可能被误认为代码坏了，也可能被误修成假通过。

根治方向：建立 `LifecycleLedgerContract` 和 `FactoryRunContract`。

### 2. quality session 补偿化

quality session 原本应该是验证工具，但随着多轮修复，它开始承载 SignalTracker 调用、Incubation 调用、factor evidence 标注、runtime health augmentation 等能力。

风险：

- 验证会话能生成证据，不代表生产四工厂自然生成同样证据。
- 运维容易把 quality session 的健康当成生产 supervisor 的健康。
- 修复容易落在验证脚本，而不是生产 control plane。

根治方向：quality session 只允许读取、触发验证、报告；生产补偿逻辑必须迁回 sidecar/runner/control plane。

### 3. SignalTracker sidecar 缺位风险

当前四工厂 supervisor 不启动 SignalTracker，但孵化 hard gate 又依赖它产生 signal、order、forward return 和 evidence。这个架构是合理的，但必须把 sidecar 作为显式运行依赖，而不能靠记忆。

风险：

- Strategy 已进入 observe/paper，但没有信号。
- Incubation intake 工作，却没有 paper evidence。
- execution audit 长期 `missing`。

根治方向：四工厂健康报告必须显示 SignalTracker sidecar last run、phase status、evidence delta。

### 4. paper evidence 未形成足够 round-trip

最近运行事实显示：有信号、有少量 paper orders/trades、有大量 open positions，但 closed positions 和真实 round-trip 仍不足。在“不用 bootstrap 计入 hard gate”的前提下，不能诚实地立即让 hard gate 通过。

风险：

- 只看到 order/trade 增长就误判可晋级。
- open positions 堆积，没有 stale close/exit policy。
- execution audit acceptance 停在 `insufficient_samples` 或 `pending_evidence`。

根治方向：继续生产真实 paper round-trip，明确 sample debt，禁止 bootstrap 晋级。

### 5. factor mining 健康未进入统一证明

如果验证会话跳过 factor mining，却仍报告策略工厂健康，就会让“新因子生成/消费链路”未验证。

风险：

- Strategy Factory 只靠旧因子或 LLM 生成。
- active factor pool 过期却未被识别。
- factor_mining_not_run 长期存在。

根治方向：quality session 和 supervisor health 必须把 factor mining 作为独立验证维度。

### 6. MCP governance 可观测性不足

AKShare MCP capability resource 可读，但 governance system report resource 当前读取失败。治理资源本身是系统健康入口，读取失败不能被视为无关错误。

风险：

- Agent/Desktop 看到的治理状态与工厂实际状态脱节。
- resource failure 被调用方吞掉。

根治方向：MCP resource health 进入 `degraded`，并有 owner 与修复路径。

## 架构根治方向

| 优先级 | 方向 | 产物 |
| --- | --- | --- |
| P0 | 统一生命周期账本 | per-strategy state、evidence、blocker、owner |
| P0 | SignalTracker 显式 sidecar health | last run、phase status、evidence delta |
| P0 | audit gate 语义统一 | missing/needs_remediation/bootstrap_pending/insufficient_samples/passed |
| P1 | quality session 瘦身 | 只验证，不生产补偿 |
| P1 | factor mining 验证维度 | raw/validated/accepted/pool/freshness |
| P1 | governance resource health | resources/read failure 可见 |
| P2 | Desktop/Agent 控制面 | 同一健康枚举和诊断入口 |

## 判断标准

后续任何修复都应先回答：

1. 这个问题属于哪个生命周期状态。
2. 缺的是信号、订单、成交、持仓、前向、evidence、audit，还是样本成熟度。
3. 责任组件是谁。
4. 修复后能否由证据表独立复核。
5. 是否把 quality session 的能力误当成生产能力。
6. 是否保持 bootstrap/backtest 不进入 production hard gate。

答不上这些问题，就不是根治，是继续补洞。
