## 1. 功能设计

### 1.1 需求背景与价值

| 项 | 内容 |
|---|---|
| 问题陈述 | 策略生成、验证、孵化、晋级涉及多个工厂、证据链和生命周期状态，缺少统一规范导致状态混淆、证据断链和验收标准不一致 |
| 解决方案 | 建立四工厂体系标准化规范，明确职责边界、证据链完整性、状态机映射规则和验收标准 |
| 业务价值 | 1. 确保策略质量和风险控制<br>2. 提供可审计的证据链<br>3. 支持从生成到上线的全生命周期管理<br>4. 建立诚实的Hard Gate标准 |

### 1.2 用户故事

| 编号 | 优先级 | 用户故事 | 成功标准 |
|---|---|---|---|
| SF-US-001 | P0 | 作为量化研究员，我需要看到策略从生成到上线的完整生命周期状态 | 能通过统一接口查询策略当前处于哪个业务阶段，有哪些证据，有哪些阻塞项 |
| SF-US-002 | P0 | 作为风控人员，我需要确认策略通过了真实paper交易验证才能上线 | Hard Gate只认可≥20个真实closed round-trip，拒绝bootstrap/backtest数据 |
| SF-US-003 | P0 | 作为运维人员，我需要快速诊断四工厂健康状态和证据链完整性 | 诊断脚本能显示整体状态、通过项/警告项/阻塞项，并定位具体问题 |
| SF-US-004 | P1 | 作为开发人员，我需要理解四工厂职责边界和数据流向 | 文档清晰定义每个工厂的职责、输入输出、依赖关系 |

### 1.4 业务规则与边界

| 规则 | 说明 | 验收 |
|---|---|---|
| Hard Gate不可放宽 | production_trade_floor=20是最低要求，不接受bootstrap/backtest | 审计gate status分布 |
| 四工厂独立运行 | 每个工厂可独立启动、监控、失败 | supervisor进程分离 |
| SignalTracker是sidecar | 不在四工厂supervisor内，但是孵化必需依赖 | 健康检查显示sidecar状态 |
| Quality Session只读 | 验证会话不生成生产补偿数据 | 代码审查Quality Session职责 |
| 证据链完整性 | 信号→订单→成交→持仓→前向收益→审计，每个环节可追溯 | SQL验证转换率 |
| V1 Deferred | 四工厂不进入V1前端产品入口 | 前端路由和导航负向测试 |

## 8. 架构警告项

基于 [09-深度架构审查报告](../09-深度架构审查报告.md) 的当前审查结论：

### 8.1 多套局部真相问题

**问题**: 系统同时存在多套局部健康判断，缺少统一裁决机制

**影响**: 外层成功可能掩盖底层失败，状态不一致，Gate状态混淆

**根治方向**: 建立统一的生命周期账本契约（详见上级目录的 [09-深度架构审查报告](../09-深度架构审查报告.md) 与 [05-技术治理与修复路线图](../05-技术治理与修复路线图.md)）

### 8.2 Quality Session补偿化风险

**问题**: Quality Session原本是验证工具，但随着修复开始承载生产补偿逻辑

**影响**: 验证会话健康≠生产健康，修复路径偏差

**根治方向**: Quality Session只读取验证，生产补偿回归sidecar/runner/control plane（详见上级目录的 [09-深度架构审查报告](../09-深度架构审查报告.md) 与 [05-技术治理与修复路线图](../05-技术治理与修复路线图.md)）

### 8.3 SignalTracker Sidecar缺位风险

**问题**: SignalTracker是孵化必需sidecar，但不在四工厂supervisor内

**影响**: 隐式依赖，证据断链，运维记忆依赖

**根治方向**: 健康检查显示SignalTracker状态，Incubation启动前preflight检查（详见上级目录的 [09-深度架构审查报告](../09-深度架构审查报告.md) 与 [03-四工厂运行规范](../03-四工厂运行规范.md)）

## 9. 开发规范

### 9.1 代码组织

- 四工厂代码独立package，共享策略生命周期管理
- 每个工厂有独立的domain、application、infrastructure层
- 证据表通过CRUD层访问，不允许直接SQL

### 9.2 提交规范

- 使用 `feat(factory):`、`fix(factory):`、`refactor(factory):` 前缀
- 关联issue和功能编号
- 修改状态机或证据表必须同步更新规范文档

### 9.3 测试要求

- 单元测试覆盖率 >80%
- 集成测试覆盖证据链转换
- E2E测试覆盖完整生命周期

### 12.3 查询策略状态

```sql
-- 连接数据库
sqlite3 data/db/akshare_mcp.sqlite3

-- 查询策略状态分布
SELECT status, COUNT(*) as count
FROM strategies
GROUP BY status
ORDER BY count DESC;

-- 查询证据链完整性
SELECT 
    COUNT(DISTINCT s.strategy_id) as strategies_with_signals,
    COUNT(DISTINCT o.strategy_id) as strategies_with_orders,
    COUNT(DISTINCT t.strategy_id) as strategies_with_trades
FROM strategy_signals s
LEFT JOIN paper_orders o ON s.strategy_id = o.strategy_id
LEFT JOIN paper_trades t ON o.id = t.order_id;
```
