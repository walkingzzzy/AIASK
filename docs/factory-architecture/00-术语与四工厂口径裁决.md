# 术语与四工厂口径裁决

## 裁决

以后在工程规范、运维手册、启动脚本说明和问题诊断中，“四工厂”默认指 supervisor 管理的四个运行体：

1. `Strategy Factory`
2. `Factor Mining Factory`
3. `Incubation Factory`
4. `Market Event Ingest`

`SignalTracker` 不再被称为第四工厂。它是策略孵化闭环的必需 sidecar，可以独立运行，也可以被验证会话调用，但不属于 `run_three_factories.py` 的四运行体集合。

**重要说明**：启动脚本 `run_three_factories.py` 文件名是历史遗留命名；其默认拓扑**最多**可拉起四个运行体，但并非不可变集合。CLI 的 `--no-strategy/--no-factor/--no-incubation/--no-event-ingest`，以及 `MARKET_EVENT_INGEST_ENABLED` 等环境开关，都可能使实际子进程少于四个。这个命名债务源于早期只有三个工厂时的设计，后续增加 Market Event Ingest 时未同步更新文件名。文件内部 `REQUIRED_SCRIPTS` / `_build_specs` 已按“默认最多四运行体”工作。

## 为什么要裁决

历史上存在两套口径：

- 历史闭环口径：Strategy Factory、Factor Mining Factory、Incubation Factory、SignalTracker。
- 当前 supervisor 口径：Strategy Factory、Factor Mining Factory、Incubation Factory、Market Event Ingest。

历史闭环口径强调”信号产生与孵化证据闭环”，但会误导运维以为 `run_all_factories.py` 或 `run_three_factories.py` 已经启动 SignalTracker。当前代码实际情况是：`run_all_factories.py` 委托 `run_three_factories.py`，而 `run_three_factories.py` **默认最多**监督四个运行体（尽管文件名仍为 three_factories；可被 CLI/环境变量裁剪），SignalTracker 需要通过 `run_signal_tracker.py` 单独运行或被 quality session 显式调度。

## 为什么 Market Event Ingest 是第四运行体

Market Event Ingest 不是“数据同步脚本的附属品”，而是策略生产线的外生事件入口。它负责把公告、交易所披露、官方事件和可信来源归一化为可审计事件，再桥接到 Strategy Factory 的 event candidate / theme / research task。

它成为第四运行体有三个设计理由：

1. 业务上，它提供策略创意的事件触发器，让策略工厂不仅依赖 LLM 自发生成或因子池扫描。
2. 工程上，它有独立 source adapter、source tier、degraded reason、bridge 状态和运行节奏，适合由 supervisor 管理。
3. 治理上，它把 source reliability 与 strategy generation 分离，避免 Tier C/news/media 直接冒充可晋级策略证据。

因此“四工厂”是策略生产线的四个生产单元：事件输入、因子生产、策略生产、孵化验证。

## 为什么 SignalTracker 是 sidecar

SignalTracker 横跨策略、paper execution、forward returns、execution audit，不是某个单一工厂的上游或下游。它的职责是把“策略已进入观察/孵化”推进成“有可审计 paper evidence”。这是一条证据闭环，不是一个独立策略生产工厂。

把 SignalTracker 定义为 sidecar 的原因：

- 它不由 `run_three_factories.py` 默认管理；当前规范不能假设四工厂 supervisor 已经启动它（注意：文件名 run_three_factories.py 是历史命名；默认最多管理四个运行体，且不包括 SignalTracker）。
- 它处理跨组件证据：`strategy_signals`、`paper_orders`、`paper_trades`、`signal_forward_returns`、`strategy_signal_evidence` 和 audit snapshots。
- 它的失败应该被健康检查识别为“闭环不完整”，而不是被误归因给 Incubation Factory。
- 它现在已经与 Incubation / sidecar runtime 共用 `strategy_factory.contracts.execution_universe.ExecutionUniverseContract` 这套公开契约；剩余工作主要是继续压缩 legacy fallback 和旧 compat 使用面，避免再次出现多条查询路径并存的双真相。

## 标准术语

| 术语 | 标准含义 | 目标 |
| --- | --- | --- |
| 四工厂 | supervisor 管理的 Strategy、Factor Mining、Incubation、Market Event Ingest | 形成可连续运行的策略生产线 |
| Strategy Factory | 策略工厂，拥有策略生成、准入、状态解析、提交和生命周期编排契约 | 持续发现、生成和筛选策略候选 |
| Factor Mining Factory | 因子挖掘工厂，负责因子搜索、验证、QC、活跃池治理和因子反馈 | 持续生产可验证、可复用的 alpha/factor 原料 |
| Incubation Factory | 孵化工厂，负责观察/孵化 intake、信号验证、paper 证据、指标、反馈和晋级 gate | 持续把候选策略变成可审计的 paper 证据 |
| Market Event Ingest | 市场事件摄取，负责官方/可信事件归一化，并桥接到策略工厂事件任务 | 持续吸收外部事件并产生可追溯策略触发器 |
| SignalTracker | 闭环 sidecar，负责策略信号、paper execution universe、forward returns 和证据链推进 | 让孵化晋级拥有真实 paper evidence |
| Quality Session | 短验证或 24h 质量会话，只用于验证当前生产契约，不是生产 supervisor | 发现链路退化，不制造生产真相 |
| Bootstrap Evidence | 回测或 bootstrap 证据，只能用于诊断，不能纳入 production hard gate | 验证代码路径或辅助定位样本债 |
| Real Paper Round-trip | paper 买入、持仓、退出、closed position 和 realized evidence 的完整回合 | production hard gate 的唯一执行样本来源 |

## 命名规则

- 文档、issue、运行记录中写“四工厂”时，必须指当前 supervisor 口径。
- 需要讨论 SignalTracker 时，使用“SignalTracker sidecar”或“信号闭环 sidecar”。
- 需要讨论质量验证时，使用“quality session”或“质量会话”，不得写成生产四工厂。
- 需要讨论旧口径时，必须显式写“历史闭环口径”，并注明已经废弃。

## 禁止混用

| 禁止写法 | 正确写法 |
| --- | --- |
| “把 SignalTracker 写进四工厂成员列表” | “四工厂 + SignalTracker sidecar” |
| “run_all_factories 启动完整闭环” | “run_all_factories 启动四运行体兼容入口，SignalTracker 需单独启动” |
| “quality session 修好了生产链路” | “quality session 验证/暴露了生产链路状态” |
| “用 bootstrap 代替真实 paper 样本” | “bootstrap 只能作为诊断证据，hard gate 等待真实 paper closed round-trip” |

## 工程约束

- `run_three_factories.py` 的职责是进程生命周期管理，不拥有业务补偿逻辑。
- `run_all_factories.py` 是兼容入口，不应重新引入 SignalTracker 混合启动语义。
- `start_four_factories_24h.sh` 这类历史脚本不能作为规范来源；若继续保留，只能作为兼容包装或迁移对象。
- SignalTracker 的缺席必须被健康检查识别为闭环不完整，而不能由孵化或质量会话静默掩盖。
