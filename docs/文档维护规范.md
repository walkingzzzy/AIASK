# 文档维护规范

本文用于防止 `docs/` 再次回到“所有材料平铺堆积”的状态。

## 文档状态

| 状态 | 放置位置 | 用途 |
| --- | --- | --- |
| 当前规范 | `docs/` 或 `docs/plans/` | 协议、接入规范、稳定约束 |
| 当前方案 | `docs/plans/` | 仍会被直接执行、拆任务、做评审的方案 |
| 历史方案 | `docs/plans/archive/` | 某一时间点的开发方案、审计结果、排期材料 |
| 研究蓝图 | `docs/plans/archive/` | 理念推演、愿景设计、远期架构构想 |
| 静态资源 | `docs/screenshots/` 等资源目录 | 截图、JSON 审计输出等附件 |

## 新文档准入规则

只有满足下面任一条件，才建议新建独立文档：

1. 需要沉淀稳定协议或跨团队约束。
2. 需要承载一条可执行的独立实施主线。
3. 需要留存可复核的审计/盘点证据。
4. 现有文档无法通过增量更新覆盖该主题。

以下情况不要新开文档：

1. 只是某次临时讨论记录。
2. 只是把已有方案换种说法再写一遍。
3. 只是某个 PR 的局部 TODO，适合留在 issue、PR 描述或代码注释里。

## 新文档必须具备的信息

建议每篇文档开头至少包含以下信息：

1. 文档角色：规范、方案、审计、研究蓝图中的哪一种。
2. 适用范围：面向哪个模块、哪个目录、哪个时间窗口。
3. 校准说明：是否为时点性材料，哪些结论需要和当前代码重新核实。
4. 阅读方式：谁应该读，先读什么，再读什么。

当文档超过约 400 行时，必须在开头给出 5 到 10 行“先看摘要”，不要让读者先扎进长文细节。

## 放置规则

1. `docs/README.md` 负责全局导读，不承载大段方案细节。
2. `docs/plans/README.md` 负责开发方案导航，不承载完整实施内容。
3. 当前仍要执行的方案留在 `docs/plans/`。
4. 已经过时、但仍值得保留的方案一律放到 `docs/plans/archive/`。
5. 截图、JSON 输出、自动生成材料放资源目录，不和主文档混排。

## 归档触发条件

出现以下任一情况时，应考虑归档：

1. 文档已经被新方案替代。
2. 文档内容明显依赖某个历史代码快照或审计时间点。
3. 文档不再作为当前任务拆解入口，但保留背景价值。
4. 文档所在目录出现“新同学不知道先看哪份”的现象。

## 链接规则

1. 被其他目录广泛引用的文档，移动前先核对引用方。
2. 如果某个历史文档因为外部引用必须保留原路径，可以留在原位，但必须在导读中明确标记其“历史材料”身份。
3. 路径变更后，要优先更新导读文档，避免入口失效。
