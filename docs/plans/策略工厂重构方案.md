# 策略工厂重构方案

> 基线：仓库当前代码实况 | 编制日期：2026-03-24
>
> 目标：在不打断现有 `strategy_manager` / BFF / Web 使用面的前提下，把策略工厂从“可运行但高度耦合的编排系统”重构为“边界清晰、状态可信、可逐步裁剪兼容层”的稳定产品底座。

> 校准说明：本文基于当前仓库代码实况编制，重点不是重新设计一套理想化系统，而是给出现有实现上可落地的拆分路径。若后续代码实况变化，应以新代码和运行审计结果为准。
>
> 阅读提醒：本文中的 P0 / P1 / P2 / P3 / P4 是建议推进顺序与拆分方案，不等价于已经确认的版本排期，也不代表这些阶段已经完成。

## 一、为什么现在要重构

策略工厂已经单独拆成了 `packages/strategy-factory`，这说明“代码目录”已经独立；但它还没有做到“运行边界”和“依赖边界”独立。

当前核心问题不是“代码放在哪”，而是以下四件事：

1. 新包仍显著依赖旧 `akshare_mcp.services.strategy_factory` 的兼容层、patch surface 和运行时代理。
2. `StrategyFactoryScheduler` 承担了过多职责，既负责循环调度，又负责快照采集、因子刷新、自治任务、门禁、提交、淘汰和运行摘要。
3. 多个阶段使用“降级继续跑”的策略，导致 `success` 更接近“主流程没崩”，不完全等于“关键环节都健康完成”。
4. 调度、状态、证据、持久化和产品读接口之间还没有形成足够稳定的契约，后续继续迭代时容易产生静默回归。

这类系统如果不继续收口，短期看还能维护，长期会出现三个典型问题：

- 改一个子阶段，整条主链都要回归。
- 出现异常时，很难快速判断是兼容层、运行时代理、DB、自治服务还是门禁逻辑出了问题。
- 兼容层会越来越难删除，系统会长期停留在“迁移完成一半”的状态。

## 二、重构目标

本次重构不追求“推翻重写”，而是追求四个结果：

1. 调度层和业务流水线分离。
2. 阶段状态语义真实、可观测、可审计。
3. 应用层只依赖显式合同，不再直接感知旧 patch surface。
4. 兼容层从“运行主路径的一部分”退化成“少量旧调用方的薄壳”。

对应的验收口径是：

- 主执行路径可在不依赖旧根包 patch surface 的情况下运行。
- `factory_status` / `factory_runs` / `factory_run_detail` 看到的状态与真实运行状态一致。
- 自治任务失败、因子刷新失败、持久化失败不再被宽泛地包装成“成功运行”。
- 可以明确知道哪些能力是硬依赖，哪些能力是可选增强。

## 三、重构原则

### 3.1 不做大爆炸式迁移

不直接删除 compat 层，不一次性替换全部入口。每一阶段都保持：

- `strategy_manager` 对外 contract 不变
- BFF `/strategy-market/*` 接口不变
- 旧导入路径可继续工作

### 3.2 先收口状态，再收口依赖

先把“运行状态说真话”做好，再逐步删兼容桥和动态代理。否则会出现“代码看起来更整洁，但线上更难排障”的反效果。

### 3.3 以证据模型驱动，而不是以函数堆叠驱动

策略工厂本质是一个多阶段流水线，不应该只靠 `run_once()` 里堆叠函数调用。应明确：

- 输入是什么
- 每阶段产出是什么
- 哪些字段是面向持久化
- 哪些字段是面向产品读接口
- 哪些失败会阻断，哪些失败只降级

### 3.4 兼容层只保留在边界

兼容逻辑应放在最外层，不应继续深度进入应用服务内部。应用层应该只依赖：

- repository contract
- gateway contract
- 明确的数据模型

## 四、目标架构

建议把现有实现拆成 5 层。

### 4.1 Control Plane

负责调度与外部触发，不直接处理候选策略业务。

建议保留：

- `StrategyFactoryScheduler`
- `factory_status`
- `factory_run_once`
- `factory_runs`

但职责缩小为：

- 计算何时跑
- 调用一次 cycle runner
- 记录最近一次结果
- 管理循环状态

### 4.2 Cycle Runner

新增一个单独的“单次工厂运行器”，例如：

- `application/cycle_runner.py`

它负责顺序执行阶段，但不负责循环调度。输入输出明确化：

- 输入：`db`, `runtime_adapters`, `run_context`
- 输出：`FactoryRunResult`

### 4.3 Stage Services

把当前 scheduler 内的重逻辑拆成独立服务：

- `SnapshotService`
- `FactorResearchService`
- `ReadinessService`
- `ResearchTaskOrchestrator`
- `CandidatePipelineService`
- `SubmissionService`
- `EliminationService`

每个 stage service 只做一件事，并返回统一的 stage result。

### 4.4 Infrastructure Gateways

应用层只依赖显式 gateway：

- `StrategyFactoryRepository`
- `AutonomyGateway`
- `FactorResearchGateway`
- `ValidationGateway`
- `RiskGateway`
- `IncubationGateway`
- `VectorSearchGateway`

兼容旧包、MCP 服务、动态 import 的逻辑全部限制在 infrastructure 层。

### 4.5 Compatibility Shell

保留：

- `akshare_mcp.services.strategy_factory`
- facade 导出
- 必需 patch-point

但不让 compat shell 再驱动主业务逻辑，只做：

- 旧 import 转发
- 测试 patch 兼容
- 少量运行时 fallback

## 五、优先级排序

建议按以下顺序推进，而不是同时动所有东西。

### P0：状态收口与运行可信度

目标：让工厂“说真话”。

实施项：

1. 引入统一的 `StageStatus` 和 `FactoryRunStatus` 语义。
2. 自治阶段不要再固定 `ok=True`，而是根据 `failed_task_count`、`external_llm_status` 和关键产物来判定。
3. 明确哪些异常导致：
   - 阶段失败但 run 可继续
   - run 跳过
   - run 失败
4. 给 `summary` 增加“硬失败数 / 降级数 / 跳过原因 / 持久化失败数”。
5. 统一 stage 结果结构，避免有的 stage 用 `ok/status`，有的 stage 只塞自由字段。

建议文件拆分：

- 从 `application/factory_scheduler.py` 提取 `stage_result.py` 或 `run_models.py`

验收标准：

- `factory_run_detail` 能一眼区分 `success / partial / skipped / failed`
- 自治失败不再在 stage 上显示为成功
- 运行摘要能解释“为什么跳过/为什么成功”

### P1：把单次运行逻辑从 Scheduler 中剥离

目标：把“调度”和“业务流水线”拆开。

实施项：

1. 新建 `FactoryCycleRunner`。
2. `StrategyFactoryScheduler.run_once()` 只负责组装上下文并调用 runner。
3. `_run_autonomy_batches()`、`_build_factory_readiness()`、`_build_factor_research_artifact()`、`_persist_enriched_snapshot()` 等迁移到 runner 或对应 service。
4. scheduler 保留：
   - `_loop`
   - `start/stop/shutdown`
   - `status`
   - 最近一次运行缓存

验收标准：

- `factory_scheduler.py` 体积显著下降
- 单次运行可以被独立测试，不依赖循环调度
- `strategy_manager.factory_run_once` 可以明确传入当前 db，而不是隐式重新加载全局 db

### P2：收口 repository 与 gateway 依赖

目标：应用层不再直接面向动态对象和可选方法拼装。

实施项：

1. 审计当前所有 `_call_optional_async` 使用点，按“硬依赖/软依赖”分类。
2. 把关键硬依赖提升为显式 contract：
   - `save_daily_snapshot`
   - `save_strategy_factory_run`
   - `save_strategy_task_run`
   - `update_strategy_task_run`
   - `save_strategy`
   - `save_strategy_quality_report`
3. 把可选增强能力集中包装到 gateway，例如：
   - event evidence persistence gateway
   - market internals snapshot gateway
4. 应用层不再直接用 `hasattr(db, ...)` 判断关键流程能力。

验收标准：

- 关键路径依赖缺失时，在运行前或阶段入口即显式报错
- `_call_optional_async` 数量明显下降
- repository contract 与实际 db adapter 对齐

### P3：收口兼容层和 runtime proxy

目标：旧包不再决定新包主路径行为。

实施项：

1. 梳理当前必须保留的 patch-point，分为：
   - 仅测试需要
   - 运行时真实需要
2. 让应用层默认使用新包本地实现。
3. compat shell 仅在旧路径导入或显式 fallback 时介入。
4. 把 runtime proxy 从“主运行依赖”降为“边界兼容工具”。
5. 对高风险 patch-point 单独补契约测试。

验收标准：

- 新包主路径在不加载旧根包时可完整跑通
- compat 相关测试通过
- 旧根包被移除时，只有旧调用方失败，不会把新主路径拖垮

### P4：候选流水线服务化

目标：让候选生成、门禁、去重、提交形成清晰的业务链。

实施项：

1. 为候选定义统一对象模型，例如：
   - `CandidateSpec`
   - `CandidateEvaluation`
   - `CandidateDedupDecision`
   - `CandidateSubmissionDecision`
2. 把以下步骤串成明确流水线：
   - spawn
   - autonomy enrichment
   - gate-0/1/2
   - dedup
   - gate-3 submission
3. 区分“策略记录写入”和“实验记录写入”的事务边界。
4. 统一 refresh_existing / spawn_revision_from_existing 的语义与状态流转。

验收标准：

- 候选在每一阶段的字段变化可追踪
- `submitter` 不再承担过多策略数据拼装职责
- `quality_gate`、`backtest`、`dedup`、`submit` 之间的契约更稳定

### P5：读模型与产品接口收口

目标：把产品读接口建立在稳定读模型上，而不是运行结果拼装上。

实施项：

1. 为 `factory_status` / `factory_runs` / `factory_run_detail` 定义稳定 DTO。
2. 将运行时 result、持久化 snapshot、产品 view model 分层。
3. BFF 只做轻量归一化，不再补很多语义。
4. 如有必要，新增 run projection 或 summary 表，减少产品层对原始大 JSON 的依赖。

验收标准：

- BFF 的 normalize 逻辑显著减少
- 前端拿到的数据契约稳定
- run summary 与 detail 可做版本化演进

## 六、建议的目录调整

建议最终收敛到类似结构：

```text
packages/strategy-factory/src/strategy_factory/
  api/
    contracts.py
    facade.py
    dto.py
  application/
    scheduler.py
    cycle_runner.py
    run_models.py
    services/
      snapshot_service.py
      factor_research_service.py
      readiness_service.py
      task_orchestrator.py
      candidate_pipeline.py
      submission_service.py
      elimination_service.py

    research_tasks.py
    run_result.py
    constants.py
  infrastructure/
    repository_adapter.py

    compat_shell.py
```

不要求一步到位，但建议按照这个方向逐步迁移。

## 七、实施顺序与工期建议

建议按 4 个 Sprint 做，而不是一次性大修。

### Sprint 1：运行状态可信化

范围：

- run status / stage status 模型
- autonomy 阶段状态修正
- summary 字段补齐
- `factory_run_once(db)` 语义修正

产出：

- 工厂运行状态可信
- 线上排障成本下降

### Sprint 2：scheduler 与 cycle runner 拆分

范围：

- 抽出 `FactoryCycleRunner`
- scheduler 变薄
- stage helper 迁移

产出：

- 单次运行逻辑可独立测试
- 后续服务化改造成本下降

### Sprint 3：依赖与兼容层收口

范围：

- repository/gateway contract 对齐
- compat 介入点后移
- 减少 `_call_optional_async`

产出：

- 新包主路径更独立
- 兼容逻辑更可控

### Sprint 4：候选流水线与产品读模型整理

范围：

- candidate object model
- 提交流水线梳理
- run DTO/view model 稳定化

产出：

- 工厂主链更容易持续演进
- BFF/前端接口更稳定

## 八、风险与控制措施

### 风险 1：兼容层一动，测试和旧调用方一起炸

控制措施：

- 保留 compat 契约测试
- 每删一个 patch-point，先确认是否仅测试依赖
- 不在同一阶段同时删 compat 和改主链

### 风险 2：状态语义调整后，产品层会看到“更多失败”

控制措施：

- 这不是坏事，是把“隐性失败”显性化
- 先在 run detail 中暴露，再决定是否在首页摘要收敛展示
- 需要同步更新 BFF 的状态映射说明

### 风险 3：抽 service 后，代码文件更多，短期阅读成本上升

控制措施：

- 通过统一 run model 和明确 service 命名控制复杂度
- 让“复杂度显式化”，替代今天的“复杂度隐藏在大文件里”

### 风险 4：没有统一验收口径，重构会变成纯结构整理

控制措施：

- 每一阶段都绑定可验证的 contract、状态字段和测试集
- 没有新增验收指标的重构，不进入高优先级

## 九、测试与验收计划

重构过程中建议维护 4 组测试：

1. compat contract tests
   - 确认旧导入路径、旧 patch-point 仍工作

2. cycle runner tests
   - 验证单次运行的阶段顺序、阻断规则、失败语义

3. gateway / repository tests
   - 验证关键依赖缺失时的显式失败和错误信息

4. manager / BFF integration tests
   - 验证 `factory_status`、`factory_run_once`、`factory_runs`、`factory_run_detail`

建议新增验收指标：

- `run_success_rate`
- `run_partial_rate`
- `hard_failure_rate`
- `stage_degraded_count`
- `task_failure_ratio`
- `persistence_failure_count`
- `compat_fallback_invocation_count`

## 十、第一批建议直接开工的任务

如果现在就开工，我建议先做下面 8 个任务：

1. 定义 `FactoryRunResult`、`StageResult`、`RunStatus` 数据模型。
2. 修正 autonomy stage 的 `ok/status` 语义。
3. 给 `strategy_manager.handle_factory_run_once()` 显式传入当前 `db`。
4. 从 scheduler 提取 `FactoryCycleRunner` 原型。
5. 提取 `ReadinessService`。
6. 提取 `TaskOrchestrator`，承接 `_run_autonomy_batches()`。
7. 统计并分类全部 `_call_optional_async` 调用点。
8. 新增“主路径不依赖旧根包”的回归测试。

## 十一、完成标准

满足以下条件，可认为这轮重构完成：

1. `strategy_factory` 主路径在不依赖旧根包 patch surface 的情况下可运行。
2. `StrategyFactoryScheduler` 不再承担单次运行的全部业务细节。
3. 工厂运行状态能准确表达 `success / partial / skipped / failed`。
4. 关键路径依赖已通过 contract 明确，不再靠大量 `hasattr` 和动态降级拼接。
5. compat 层保留在边界，不再深度参与应用层主逻辑。
6. BFF 与 MCP 入口 contract 保持稳定，现有产品面不需要大改即可继续使用。

## 十二、建议的决策口径

这次重构建议按下面的口径来管理，而不是按“是否继续拆包”来管理：

- 不是“把代码挪到独立目录”就算完成
- 而是“让工厂主路径真正可控、可观测、可演进”才算完成

换句话说，当前策略工厂已经完成了“独立包化”的前半程，但还没有完成“系统收口”的后半程。后续重构的重点，不是再造一套新系统，而是把已经存在的系统整理成一个可信的工程产品。
