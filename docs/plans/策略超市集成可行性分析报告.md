## 二、MCP 工具链真实实现质量审查

### 2.1 因子分析工具链

| 工具 | 源文件 | 实现质量 | 详细说明 |
|---|---|---|---|
| `get_factor_library` | `tools/quant.py` | 元数据 | 返回硬编码字典，8 个因子：momentum/trend/reversal/volatility/value/quality/growth/size |
| `calculate_factor` | `services/factor_calculator.py` | 中 | 技术因子标准（momentum = 价格变化率，volatility = 年化波动率，trend = 线性回归斜率）；基本面因子为启发式打分（quality = `(min(ROE/20,1) + max(1-debt_ratio,0) + min(profit_growth/50,1))/3`），非学术因子模型 |
| `calculate_factor_ic` | `services/factor_analysis.py` + `services/validation.py` | 高 | Pearson IC + Spearman Rank IC（scipy.stats，`calculate_ic_dual`）；行业/市值/Beta 中性化（OLS 截面回归 `np.linalg.lstsq`，行业哑变量 `pd.get_dummies`）；Bootstrap IC 置信区间（向量化重采样，实现在 `validation.py:244-326`）；IC 时间序列（多 forward period 滚动计算） |
| `backtest_factor` | `services/factor_analysis.py` | 高 | 滚动分组回测（按因子值排序分五档），多空净值曲线，交易成本扣除（佣金+滑点），涨跌停/停牌过滤 |
| `validate_factor_oos` | `services/validation.py` | 高 | Walk-Forward Validation（滑动 train/test 窗口）；Purged K-Fold CV（引用 de Prado，带 purge gap）；Bootstrap IC CI；综合评级 A/B/C/D |
| `factor_robustness_check` | `tools/quant.py` | 高 | 多窗口 IC 稳定性（5/10/20/60 天）；参数敏感性分析；子样本一致性检验（宇宙对半分割）；加权综合评分（`quant.py:1567-1725`） |

**结论**：因子分析管线是整个系统中实现质量最高的模块。IC 计算、中性化、OOS 验证、稳健性检验全部是真实的 scipy/numpy 实现。但因子公式本身（尤其是 quality/growth）过于简化。

### 2.2 回测引擎

| 组件 | 源文件 | 实现质量 | 详细说明 |
|---|---|---|---|
| 策略库 | `services/backtest/strategies.py` | 中 | 4 个硬编码策略：ma_cross/momentum/rsi/buy_and_hold。Numba JIT 编译加速。无策略接口/工厂模式，无用户自定义策略框架 |
| 执行模型 | `services/backtest/engine.py` | 中 | 单持仓全仓进出，收盘价成交。JIT 路径在信号产生的同一根 K 线成交（存在 look-ahead bias）。无部分成交、无仓位管理 |
| 滑点模型 | `services/slippage.py` | 高 | 三种模型：FixedSlippageModel（固定费率）、VolumeBasedSlippageModel（成交量相关）、MarketImpactModel（简化 Almgren-Chriss：`permanent + temporary impact`）|
| 涨跌停过滤 | `services/backtest/engine.py` | 高 | 区分主板(10%)、创业板/科创板(20%)、ST(5%)，过滤零成交量（停牌） |
| 参数优化 | `services/backtest/engine.py` | 中 | 网格搜索，目标函数 `sharpe * (1 - max_drawdown)` |
| Walk-Forward | `services/backtest/engine.py` | 高 | 滑动 train/test 窗口优化 |
| Monte Carlo | `services/backtest/engine.py` | 中 | 从历史均值/标准差生成随机收益路径 |

**关键缺陷**：
- **Sharpe 计算路径差异**：JIT 路径（`strategies.py`）执行 `returns = returns[returns != 0]` 过滤零收益日后再算标准差，排除了持仓不变的平盘日，人为降低了波动率分母，导致 Sharpe 向上偏差；mask 路径（`engine.py::_simulate_trades_from_masks`）仅过滤 `eq_prev > 0`（防除零），保留零收益日。两条路径对同一策略可能产出不同 Sharpe，策略横向比较失真
- **win_rate 统计口径不统一**：momentum/rsi 策略及 mask 路径将买入和卖出都计入 `trades` 分母（单边成交计数），`win_rate = wins / trades` 导致胜率被稀释约 2x；而 `_backtest_ma_cross_jit` 仅在买入时递增 trades（近似正确），`_backtest_ma_cross_with_trades_jit` 使用 `wins / (trade_count // 2)` 按完整交易回合计数。口径不统一使不同策略的胜率不可直接比较
- JIT 路径使用扁平化的单一 `total_cost_rate`（`_compute_slippage_rate` 用 `np.nanmean(prices)`/`np.nanmean(volumes)` 对整个序列均值化估算一次），不是逐笔动态滑点。该均值化处理对高波动阶段、流动性分层和冲击成本不敏感，回测成交假设偏乐观

### 2.3 组合优化

| 方法 | 源文件 | 实现质量 | 详细说明 |
|---|---|---|---|
| equal_weight | `services/portfolio_optimization.py` | 完整 | `1/N` 等权 |
| risk_parity | 同上 | 高 | 最小化 `Σ(risk_contrib_i - target_i)²`，scipy SLSQP 求解，正确的边际风险贡献计算 |
| mean_variance | 同上 | 高 | 最大化 `w'μ - λ·w'Σw`，`risk_aversion` 参数可外部传入（默认 1.0），scipy SLSQP |
| black_litterman | 同上 | 高 | 教科书级实现：逆优化隐含收益 `π = δΣw_mkt` → P/Q 观点矩阵 → `Ω = diag(PτΣP')` → BL 后验均值 |
| max_sharpe | 同上 | 高 | 最小化负 Sharpe `-(w'μ - rf) / √(w'Σw)`，单资产权重上限 35%（不可行时自动放宽） |

- 协方差矩阵全部使用 `np.cov(returns_matrix)` 纯样本协方差，无 Ledoit-Wolf 收缩估计，当股票数接近观测天数时矩阵不稳定
- `risk_model.py` 的 `calculate_barra_risk` 方法（L66-111）有完整实现（构建因子暴露矩阵、计算因子风险贡献和特质风险），但该方法未被工具层直接调用，实际使用场景有限
- 压力测试工具层实现是 `sum(weight * 0.30)` 固定百分比乘法，`risk_model.stress_test` 有更好的实现（行业分类冲击+PE 利率敏感度）但工具层未调用

## 三、报告一「商品化与AI推荐」逐项深度对照

### 3.1 流批一体实时因子计算（Kafka + Flink + DolphinDB）

**报告要求**：四种因子计算范式——无状态因子（消息到达即计算）、滑动窗口因子（时序引擎增量聚合）、有状态因子（内存状态+新事件推导）、流水线因子（级联流处理）。全部基于事件驱动流处理，毫秒级延迟。

**代码快照实际（2026-02-21）**：所有因子计算都是同步请求-响应函数。`factor_calculator.py` 中 `calculate_momentum` 就是 `(closes[-1] - closes[-period]) / closes[-period]`，接收 Python list 返回 float。每次调用从 TimescaleDB 全量取数据再计算，无流处理、无增量计算、无状态管理。

**差距本质**：报告描述的是持续运行的计算引擎（数据到达即触发），代码实现的是按需计算的函数库（用户请求时才计算）。这不是"缺一个组件"，而是架构范式完全不同。

**落地评估**：
- A 股日频场景（收盘后更新）：TimescaleDB Continuous Aggregates + pg_cron 定时任务可替代 Flink，因子值写入 `factor_values(code, factor_name, date, value)` 新表。不需要 Kafka/Flink。**可行，中等工程量**
- 分钟级因子（报告提到的 VWAP 偏离度）：需要实时行情推送源 + 流处理引擎。当前架构无法支撑。**不可行，需重建基础设施**
- 毫秒级高频因子：完全超出当前架构能力范围。**不建议尝试**

### 3.2 因子存储中心（Factor Store）

**报告要求**：Redis 在线层（毫秒级 QPS）+ Parquet 离线层（批量回测），消除训练-服务数据倾斜。

**代码快照实际（2026-02-21）**：`CommonCacheService` 已实现 Redis + 内存双层缓存，但缓存的是 API 响应（如因子库列表 TTL 3600s），不是因子值本身。因子计算结果不持久化——`factor.service.ts` 的 `calculateFactor` 调用 MCP 后直接返回，没有写入任何存储。

TimescaleDB schema 中有 `kline_1d`、`financials`、`stock_quotes` 等原始数据表，但没有 `factor_values` 表。每次请求因子 IC 时，`factor_analysis.py` 都要重新从 klines 计算因子值、计算前向收益、做中性化回归、再算 IC。同一个因子在回测和展示中可能因数据窗口不同产生不同值——正是报告警告的"训练-服务数据倾斜"。

**落地评估**：在 schema.py 新增 `factor_values` hypertable，因子计算后写入。Redis 缓存最新一期因子值作为在线层。这是增量改动，不需要新基础设施。**可行，中等工程量**

### 3.3 情感提示工程与大五人格映射

**报告要求**：MIND-SAFE 多层安全对话框架，NLP 提取情感极性，大五人格→因子权重映射，RAG 检索因子存储，CoT 推理链。

**代码快照实际（2026-02-21）**：系统 prompt（`chat.tools.ts`）全文仅约 14 行功能性指令：

```
你是 AIASK 智能股票分析助手。你可以调用工具获取实时行情...
回答规则：1. 先调用工具获取相关数据...
如果当前工具列表中没有你需要的工具，请调用 _request_tools...
```

无情绪评估指令、无人格分析框架、无情感映射逻辑。`UserContextService` 注入的用户上下文仅有：模拟盘总资产/盈亏、自选股列表、投资组合名称、风险偏好（三档下拉框：激进/稳健/保守）。

`analyze_stock_sentiment` 实际公式 `50 + price_change*100 + (volume_ratio-1)*20`——零 NLP。`calculate_fear_greed_index` 工具层不传参数，永远返回 50。

**落地评估**：
- 第一步（零代码改动）：扩展系统 prompt，加入情绪评估指令。例如："分析用户消息中的情绪状态（焦虑/贪婪/理性），映射为风险厌恶系数 λ（焦虑→5.0，贪婪→0.5，理性→2.5），调用 optimize_portfolio 时传入对应 risk_aversion。" **可行，低成本**
- 第二步（中等改动）：修复 `calculate_fear_greed_index`（传入实际市场数据）；扩展 Settings 页风险偏好为多维问卷；在 UserContextService 中注入问卷结果。**可行，中等工程量**
- 第三步（高成本）：接入外部 NLP API 做真实情绪分析，或用 LLM 的 function calling 在对话中动态评估。**可行但效果依赖 LLM 能力，需大量实验**
- 完整 MIND-SAFE 框架 + RAG 检索因子存储：需要向量数据库集成（schema 中已有 `stock_embeddings` 表但未用于因子检索）+ 多轮安全对话逻辑。**高工程量**

### 3.4 RRF 混合排名引擎

**报告要求**：`RRF_score(d) = Σ 1/(k + rank_i(d))`，子排名包括夏普比率、最大回撤、用户好评率，k=60 平滑常数。

**代码快照实际（2026-02-21）**：无任何排名系统。无策略列表、无排序逻辑、无评价数据模型。

**数据源可用性**：回测引擎输出 `total_return`/`sharpe_ratio`/`max_drawdown`/`win_rate`；因子分析输出 `ic`/`rank_ic`/`ic_ir`。这些可直接作为 RRF 子排名维度。缺少用户评价数据。

**落地评估**：RRF 算法本身约 20 行代码。真正工作量在：(1) 策略商品数据模型（PostgreSQL 新表 `strategies`/`strategy_metrics`/`strategy_reviews`）；(2) 定时运行回测/IC 并持久化结果；(3) 用户评价系统。**算法可行且简单，配套系统中等工程量**

## 四、报告二「实时收益与评价」逐项深度对照

### 4.1 实时 NAV 引擎 + 公司行动处理

**报告要求**：实时按市价计值、除权除息处理、拆股调整、多空头寸。

**代码快照实际（2026-02-21）**：`paper_trading.py` 的 P&L 计算是 `(current_price - avg_cost) * quantity`。无公司行动处理。`Position.add` 方法存在双倍计数 bug（`self.quantity += quantity` 执行两次）。回测引擎也不处理公司行动——直接使用传入的 close 价格序列。

所有模拟交易状态纯内存，DB schema 定义了四张表但代码从未引用。

**落地评估**：
- 日频 NAV：TimescaleDB 物化视图 + 定时任务计算每日持仓市值。公司行动数据从 AKShare `stock_dividents_cninfo` 获取。**可行，高工程量**
- 毫秒级 NAV：需要实时行情推送 + WebSocket 基础设施。**不可行**
- 前置条件：必须先修复 Position.add bug 并实现模拟交易持久化

### 4.2 滑点与 TCA

**报告要求**：买卖价差、市场冲击、佣金归因、PRIIPs 合规滑点方法论。

**代码快照实际（2026-02-21）**：三种滑点模型已实现（Fixed/VolumeBased/MarketImpact）。但存在两个问题：
1. 回测 JIT 路径使用扁平化单一 `total_cost_rate`（`_compute_slippage_rate` 用整个序列均价/均量算一次），不是逐笔动态滑点。只有 advanced mask 路径才逐笔调用滑点模型
2. 前端模拟交易页的费用计算（佣金 0.025% min 5 元、印花税 0.05%、过户费 0.001%）只是展示估算，MCP 端 paper_trading 未使用这些费率

**落地评估**：滑点模型代码已有，需要：(1) 从回测引擎中抽取为独立服务；(2) 应用到模拟交易订单执行；(3) 统一前后端费率参数。**可行，中等工程量**

### 4.3 IC/IR 指标与信号衰减

**报告要求**：Pearson IC、Spearman Rank IC、IR、主动管理基本定律 `IR = IC × √BR`、信号衰减可视化。

**代码快照实际（2026-02-21）**：
- `calculate_ic_dual`：Pearson IC + Spearman Rank IC + 行业/市值/Beta 中性化 + Bootstrap CI ✓
- `factor_decay`：在 1 到 max_period 天的 forward return 上逐一计算 Spearman IC，计算半衰期 ✓
- `ic_ir`：代码中是 `mean_ic / std_ic`（IC 的信息比率），不是 Grinold 定律的 `IC × √Breadth` ✗
- 前端可视化：无。IC 结果只在聊天中以 KPI 卡片或表格形式展示

**落地评估**：IC/衰减分析管线已完备。缺少的是：(1) 前端策略详情页的 IC 衰减折线图（用现有 LineChart）；(2) Grinold 定律可在展示层计算（Breadth = 策略覆盖标的数）。**低工程量**

### 4.4 样本外前向验证

**报告要求**：系统记录实时信号，100% 基于前向数据生成排名（Collective2 模式）。

**代码快照实际（2026-02-21）**：`validation.py` 实现了 Walk-Forward + Purged K-Fold + Bootstrap，但都是历史数据上的模拟 OOS。无"信号记录表"，无定时任务记录策略每日信号。

**落地评估**：需新建 `strategy_signals(strategy_id, date, code, signal, score)` 表 + 定时任务 + 事后前向收益计算。Walk-Forward 代码可复用为验证逻辑。**中高工程量**

### 4.5 社交跟单（CopyTrader）

**报告要求**：比例分配、跟单止损（CSL）、明星策略师等级体系、毫秒级信号同步。

**代码快照实际（2026-02-21）**：零社交功能。模拟交易是单用户系统，无"策略师"概念，无信号发布/订阅，无跟单关系管理。`RiskMonitor.check_drawdown` 可作为 CSL 基础，但只是检查函数不自动触发平仓。

**落地评估**：需从零构建独立子系统——策略师注册→信号发布→跟单订阅→比例复制→CSL 自动断开。涉及资金安全，容错要求极高。**极高工程量，本质上是独立产品**

### 4.6 组合优化 λ 参数与情绪映射

**报告要求**：`min w'Σw - λ⁻¹ w'μ`，λ 由 AI 根据用户情绪动态控制。

**代码快照实际（2026-02-21）**：`portfolio_optimization.py` 的 `mean_variance` 目标函数：
```python
def objective(weights):
    portfolio_return = np.dot(weights, expected_returns)
    portfolio_variance = np.dot(weights, np.dot(cov_matrix, weights))
    return -(portfolio_return - risk_aversion * portfolio_variance)
```
`risk_aversion` 参数确实存在且可外部传入。ChatService 的 tool-calling 循环中 LLM 可调用 `optimize_portfolio` 并传入该参数。但当前系统 prompt 无此指令。

**落地评估**：纯 prompt 工程，零代码改动。在系统 prompt 中添加情绪→λ 映射指令即可。效果取决于 LLM 指令遵循能力。**低成本，高不确定性**

### 4.7 协方差矩阵估计

**报告隐含要求**：稳健协方差估计（收缩估计、因子模型协方差）。

**代码快照实际（2026-02-21）**：全部使用 `np.cov(returns_matrix)` 纯样本协方差。`risk_model.py` 的 `barra_risk_decomposition` 是空壳接口。

**落地评估**：引入 `sklearn.covariance.LedoitWolf` 替换 `np.cov`，约 5 行代码。**极低工程量**

### 4.8 合规风控

**报告要求**：报单频率断路器（300 笔/秒、20000 笔/日）、KYC 适当性管理。

**代码快照实际（2026-02-21）**：BFF 有 `RateLimitGuard`（IP+路径级别，登录 5/min，注册 3/min，默认 60/min），但不是交易频率限制。Settings 页有 `riskPreference` 三档选择，无正式 KYC 问卷。

**落地评估**：交易频率限制可在模拟交易订单提交路径添加计数器。KYC 问卷需新建页面+数据模型+策略推荐联动。**中等工程量**

### 4.9 IP 保护

**报告要求**：信号混淆、API 隔离、虚拟黑盒。

**代码快照实际（2026-02-21）**：无 IP 保护机制。但 MCP 架构天然提供代码隔离——策略代码在 Python 服务端运行，用户通过 BFF API 只能获取输出信号，看不到源码。

**落地评估**：信号混淆（对公开展示添加噪声）是应用层逻辑。MCP 架构已提供基础隔离。**中等工程量**

## 八、结论

两份报告描述的是一个完整的「下一代量化策略交易平台」愿景。经过对项目代码的逐行审查，核心结论如下：

**可以直接落地的**：AI 情绪→组合优化 λ 映射（现有 tool-calling + risk_aversion 参数天然支持）、IC/信号衰减展示（分析管线已完备）、RRF 排名（数据源已有）、协方差收缩（5 行代码）。

**需要中等工程量但完全可行的**：因子存储持久化、因子库扩展、策略商品化数据模型、电商化 UI、滑点服务化。现有代码提供了坚实的基础。

**需要谨慎评估的**：模拟交易持久化（当前纯内存且有 bug）、日频 NAV 引擎（需要公司行动处理）、策略生命周期管理（多角色审核流程）。回测引擎的 Sharpe/win_rate 口径不统一和滑点均值化估算问题需在策略超市上线前修复，否则策略横向比较和收益展示的可信度不足。

**不建议在当前架构上尝试的**：毫秒级流处理（用 TimescaleDB 定时任务替代）、完整社交跟单系统（独立产品级工程量）。

项目最强的三个技术支撑点是：因子 IC 分析管线（scipy 统计、中性化、Bootstrap、OOS 验证）、组合优化器（教科书级 Black-Litterman/风险平价/均值方差）、ChatService 的多轮 tool-calling 架构。这三者的组合为报告中最核心的「AI 情绪感知→动态策略推荐」提供了现成的执行管线。

最大的四个风险点是：情绪分析模块工具层与服务层能力不对齐（`fear_greed_index` 工具层不传参数，AI 推荐可解释性链路断裂）、模拟交易纯内存无持久化（策略超市的收益展示无法建立在重启丢数据的系统上）、RiskMonitor 仅检测不自动处置（策略超市"可托管运行"的成熟度不足）、回测引擎统计口径不统一（Sharpe/win_rate 路径差异导致策略比较失真）。前端图表已在 5 个分析页面集成，核心交易页面（stock/backtest/portfolio）的图表接入工作量低于预期。
