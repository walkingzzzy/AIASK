## 2. 为什么先用 300 只验证（而不是直接上 5000）

## 3. 如何扩展到全市场 5000+ 只

### 3.1 扩展机制（已就绪，无需改代码）
扩展只需调整启动参数 `--universe-limit`：

```bash
# 当前：300 只小范围验证
python scripts/factories/run_strategy_factory_quality_session.py --universe-limit 300

# 未来：全市场扩展（覆盖全部 ~5217 只）
python scripts/factories/run_strategy_factory_quality_session.py --universe-limit 5217
# 或设一个大于总量的值，自然覆盖全市场
```

**机制说明**（`scripts/factories/run_strategy_factory_quality_session.py`）：
- `--universe-limit N`（`:2373`）：>0 且**不传** `--codes` 时，走 dispatch 默认 universe 模式，覆盖全市场前 N 只
- 判定分支（`:329`）：`use_dispatch = universe_limit > 0 and not codes`
- dispatch 配置（`:336-338`）：`dispatch_run_mode=True` + `dispatch_default_universe=True` + `dispatch_default_universe_limit=N`
- 脚本注释建议：中等规模验证 200-500（`:2373`）

### 3.2 扩展前必须解决/评估的事项

#### A. 单轮耗时（关键约束）— 已用 session.log 实测修正
- ⚠️ **区分两个口径**：
  - 策略工厂**阶段**耗时（仅 spawn→backtest→dedup→submit）：约 **264s**（v8 报告值）
  - **完整 cycle** 耗时（含孵化 /paper trading /post-cycle）：session.log 实测 **1034.8s 与 1055.9s（≈17～17.5min/轮）**
- 因此扩展耗时估算必须以**完整 cycle ≈17min** 为基准，而非 264s
- 300 只完整单轮 ≈17min → 24h 约 **80 轮**（pause 20s + cycle 17min）
- 5000 只（×17 倍候选）若 LLM 产能不变，完整 cycle 可能 **1～1.5 小时/轮**，24h 仅 ~16～24 轮
- **决策点**：前向证据积累靠轮数 × 交易日，轮数从 80→~20 会显著拖慢 effective_n 累积节奏，扩展前需评估是否接受

#### B. LLM 产能与超时
- 当前 300 只已出现 `partial_infra` 退化：`cooldown_skip=54`、`pipeline_timeout=3`、`no_executable_specs` 空规格回退
- 5000 只候选量级放大约 17 倍，LLM 调用压力同比上升 → 超时冷却、本地 fallback 占比可能恶化
- **决策点**：是否需要提高 LLM 并发/超时容忍，或保持因子挖掘降频（每 10 轮）以让出产能

#### C. 数据新鲜度与覆盖
- dispatch 全市场需要这 5000+ 只都有足够的 K 线/财务数据落库，否则候选生成会退化
- **决策点**：扩展前先跑数据新鲜度检查（`check_db_freshness` / `check_p0_1_data_readiness`），确认全市场覆盖率

#### D. 预算轨道与池容量
- 300 只时：active_pool=3451、paper_active=300、formal_slots=12、observe_slots=24
- 5000 只时 paper/observe 池会显著膨胀，需评估 `deferred_budget_queue` 堆积与池消费速率是否匹配

### 3.3 建议的渐进扩展路径
不要从 300 直接跳 5000，建议分档验证单轮耗时与产能拐点：

```
300（当前，已验证证据链贯通）
  → 500（验证脚本推荐上限，确认耗时仍可控）
  → 1000（观察 LLM 退化是否加剧、单轮是否破 30min）
  → 2000（评估池容量与预算轨道是否堆积）
  → 5217（全市场，最终目标）
```

每升一档观察：单轮耗时、`partial_infra` 退化频率、`no_executable_specs` 占比、observe 诊断单是否持续增长、池消费 vs 堆积。

## 4. 与"全市场"无关、必须靠运营时间积累的慢变量

即使扩展到 5000 只，以下指标**不会因为标的变多而立即改善**，它们是真实运营时间过程：

- **前向覆盖（forward_coverage）**：新提交样本当前=0.00，需纸面交易跨**交易日**真实结算才能累计
- **effective_n / formal 转正**：需 warmup 期真实积累纸面交易证据，代码无法凭空补齐
- **formal 准入质量门**：`post_cost_sharpe`、`win_rate`、`profit_factor` 及多重检验（deflated_sharpe/pbo/white_reality_check）必须由真实交易质量穿透，扩大标的只增加候选基数，不保证质量达标

扩展标的范围解决的是**候选多样性与基数**问题；**质量与前向证据**仍需时间。两者不能混淆。

---

## 5. 结论

1. **当前明确是小范围测试**：300 只 / 全市场 ~5.7%，目标是验证证据生产链贯通，已达成。
2. **扩展路径已就绪**：只需调 `--universe-limit`，无需改代码。
3. **扩展是有约束的决策**：单轮耗时、LLM 产能、数据覆盖、池容量是 4 个必须先评估的关卡，建议 300→500→1000→2000→5217 渐进。
4. **不要对扩展抱有不切实际的预期**：标的变多 ≠ 质量达标 ≠ formal 转正，后者需运营时间积累真实前向证据。

## 7. 重要语义澄清：`gate_3_passed=0` ≠ "G3 拦住所有策略"

> 背景：运行中多轮日志出现 `gate_3_passed=0`，易被误读为"G3 门槛把所有策略都拦死了"。经代码核验，**这是显示口径误解，G3 当前并未拦截提交**。

### 7.1 现配置：observe-first 模式，G3 不再是放行闸门
session 启动时的真实环境变量（`run_strategy_factory_quality_session.py:264, 270, 257`）：
```
STRATEGY_FACTORY_OBSERVE_FIRST_ENABLED            = "1"   # observe-first 开启
STRATEGY_FACTORY_GATE3_RECORD_ONLY_ENABLED        = "0"
INCUBATION_FACTORY_GATE3_RECORD_ONLY_INTAKE_ENABLED = "0"
```

### 7.2 机制：候选走 evidence_scoring，全部放行进 observe 池
`candidate_pipeline.py:67-153` 的逻辑：
- observe-first 开启后，候选走 **`evidence_scoring` 模式**，不是传统 `quality_gate` 拦截
- 候选不被 G3 拦住，而是**全部标记 `observe_first_intake=true` → 路由到 `observe_incubation` 轨道**（`:400-402`）
- 日志里的 `gate_3_passed` 是**旁路统计字段**（`:354` 从 submit_result 读），报告"这批候选里有几个达到传统严格 G3 标准"，**不是放行数量**

### 7.3 实证：passed 波动但 submitted 稳定 → 证明 G3 不拦截
| 轮次 | gate_3_passed | submitted |
|---|---|---|
| 1 | 3 | 14 |
| 2 | 0 | 17 |
| 3 | 0 | 16 |
| 4 | 1 | 15 |
| 5 | 4 | 10 |

- `gate_3_passed` 在 0~4 间波动，但 `submitted` 始终 10~17
- 若 G3 真在拦截，passed=0 时 submitted 应趋近 0 —— 实际没有，**证明候选照常提交进 observe 池**
- `gate_3_passed=0` 的真实含义：**这批进 observe 的候选，0 个达到旧严格门标准**（质量统计，非拦截结果）

### 7.4 真正的影响：质量筛选被延后，不是消失
- ❌ 担心的"G3 拦住所有策略" → 未发生，submitted 一直正常
- ✅ 实际发生 → 候选全进 observe 池，但统计质量普遍弱（win_rate<0.4 / weak_wf_ic_ir / weak_pkf_ic / weak_bootstrap_ci_lower）
- **observe-first 把质量门从"提交时"推迟到"observe→formal 转正时"**。同一批质量标准在转正时仍会拦——problem 没消失，只是换了位置
- 这解释了为什么 observe 池在增长（incubating 14→21）、formal 转正却=0：候选进得来，但质量不足以转正

- **方向错配 = 命中率低的同一病根**：momentum 配下跌标的 → 信号与趋势相反 → 前向收益为负

### 9.3 根因（已代码核验）
`stock_strategy_matrix_parts/normalizers.py` 的 legacy 选族路径 `_intrinsic_families_for_row`：
- `_base_family_order` 只看**全市场 fear_greed 指数**（fg≥60 给所有标的塞 momentum），**完全不看个股方向**
- 已有的方向过滤在 `stock_strategy_router.py`，但受 `STOCK_FIRST_ROUTER_ENABLED` 控制、默认关闭，没生效

### 9.4 修复：legacy 路径加个股方向闸（软过滤，不重蹈 G3 全拦）
- 新增 `_apply_direction_gate`（normalizers.py）：在 legacy 选族出口按个股 trend/reversal 剔除方向矛盾 family
  - 下跌/弱势（trend<0.15 且 reversal≥0.30 或当日跌）→ 剔除趋势族（momentum/ma_cross/growth_factor/breakout/sector_breakout/volatility_breakout/rotation_balanced）
  - 上涨（trend≥0.35）→ 剔除纯反转族（mean_reversion_short/gap_fill，保留 rsi）
  - **方向信号缺失/中间地带 → 不干预**（诚实降级，不误伤震荡/缺数据标的）
  - 剔除后空 → 兜底 multi_factor（候选不枯竭）
- toggle `STRATEGY_FACTORY_DIRECTION_GATE_ENABLED` 默认 ON（修 bug 的缺省行为），可紧急关闭
- 不动 router 路径（已有自己的过滤），只修 legacy fallback
