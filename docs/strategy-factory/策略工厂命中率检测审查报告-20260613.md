# 策略工厂命中率检测审查报告

审查日期：2026-06-13  
更新日期：2026-06-13，补充“流程是否可行、当前问题、严格验收口径”审查结论。  
审查范围：`packages/strategy-factory` 为主，追踪到命中率闭环实际依赖的 `packages/akshare-mcp`、`packages/aiask-quant-core`、`packages/agent`、`desktop`。  
边界声明：本报告只审查当前代码如何体现命中率；未修改策略工厂、孵化工厂、Agent、Desktop 的业务代码。

## 1. 总结论

当前代码里，“策略工厂命中率”不是一个单一字段，而是三层指标共同体现：

1. 回测胜率 `win_rate`：策略工厂候选进入提交/观察前的回测质量指标，属于前置筛选质量，不等于真实投后命中率。
2. 前向观察命中率 `primary_hit_rate` / `hit_rate_by_regime` / `skill_lcb`：策略进入孵化或观察后，按真实前向收益验证信号方向，这是最能回答“AI 生成策略到底命中多少”的主口径。
3. 单笔交易预测命中率 `direction_hit_rate` / `target_touch_rate` / `trade_prediction_score_v2`：策略工厂冻结每个候选的机器可验证 `trade_prediction_contract`，后续由孵化工厂生成 outcome，再由 Quant Core 聚合方向命中率和评分下界，作为更细粒度的预测命中率与晋升门依据。

因此，面向验收或展示时，建议把“命中率”拆成两个主看板：

| 看板 | 核心字段 | 证明的问题 |
| --- | --- | --- |
| 策略级前向命中率 | `primary_hit_rate`, `primary_effective_n`, `primary_skill_lcb`, `recent_primary_hit_rate`, `hit_rate_by_regime` | 生成策略在真实前向收益窗口内是否方向命中 |
| 交易预测命中率 | `direction_hit_rate`, `target_touch_rate`, `trade_prediction_score`, `score_lcb_95`, `score_version=trade_prediction_score_v2` | 每个冻结交易预测是否在目标日/盘中路径上命中 |

`backtest_metrics.win_rate` 只能作为候选质量预筛，不应单独作为“策略工厂已完成后的真实命中率”。

### 1.1 流程可行性判断

当前命中率链路在架构上是可行的：策略工厂负责生成候选并冻结 `trade_prediction_contract`，Quant Core 负责保存预测与 outcome，孵化工厂负责日线/盘中验证和前向命中率报告，Agent/Desktop 负责只读查询与展示。

但从代码审查看，它目前更接近“命中率观测链路”，还不是严格的“命中率验收链路”。原因是：v2 outcome 可能被查询条件饿死，矩阵聚合分母会混入 partial/缺数据样本，目标价缺失会把方向可判定预测降为 partial，交易预测落库失败不会硬失败，晋升门默认 diagnostic-only，Desktop 又会在样本很少时给出较乐观的状态。

因此，当前流程可以用来发现和展示命中率趋势，但不宜直接作为“策略工厂已经用命中率完成质量闭环”的最终证明。若用于验收，应把主口径限定为 `score_version=trade_prediction_score_v2`、`score_status=ok`、`data_quality_status=ok` 的有效样本，并同时披露 partial 数、数据缺口数、有效样本数和 LCB。

## 2. 代码链路审查

### 2.1 回测胜率：前置质量，不是真实命中率

策略工厂回测过滤链路会计算并保留 `win_rate`：

- `packages/strategy-factory/src/strategy_factory/application/backtest_filter_parts/reporting.py`
  - `_trade_profile_from_metric` 按闭合 round-trip 盈亏计算 `wins / pnl_values`，输出 `win_rate`、`profit_factor`、`breakeven_win_rate` 等交易画像指标。
  - `_build_backtest_metrics_contract` 将 `win_rate` 写入 `backtest_metrics_contract`。
- `packages/strategy-factory/src/strategy_factory/application/backtest_filter_parts/policy.py`
  - 组合投资曲线聚合时，按交易数量加权聚合组件 `win_rate`。
- `packages/strategy-factory/src/strategy_factory/application/backtest_filter_parts/models.py`
  - Gate-2 软评分把 `win_rate` 纳入质量分：`>=0.45` 加 10 分、`>=0.38` 加 6 分、`>=0.30` 加 2 分。
  - 该逻辑明确是“软预筛”，用于降低交易质量双低候选通过概率，而不是作为真实命中率证明。
- `packages/strategy-factory/src/strategy_factory/application/backtest_filter_parts/normalizers.py`
  - 候选会写入 `backtest_outcome`、`backtest_metrics`、`backtest_metrics_contract`，同时汇总 `passed_count`、`failed_reason_counts`。

检测含义：

- 可以检测候选生成质量：回测中有多少策略历史胜率达标。
- 不能证明投后命中率：它仍是历史回测/候选筛选指标，存在样本、过拟合、回测窗口偏差。

### 2.2 诊断观察：低质量候选是否保留样本

策略工厂并不是简单“低胜率全部入观察”。测试明确约束：

- `packages/strategy-factory/tests/test_diagnostic_observation_admission.py`
  - `win_rate_0_312_0_400` 默认不进入 diagnostic observation。
  - `win_rate_0_372_0_400` 这种接近阈值的失败原因可以进入 diagnostic observation。
  - `weak_wf_ic_ir`、`weak_pkf_ic`、`weak_bootstrap_ci_lower`、`period_robustness_below_threshold`、`trade_count_3_10` 可以进入诊断观察。
  - 但硬拒绝、数据缺失、重复、样本太少、回撤过大、read-only、refresh_existing 等情况不会进入诊断观察。

检测含义：

- 命中率样本池不是“所有失败候选”，而是经过硬排除和诊断准入后的观察样本。
- 文档或看板必须区分 `formal_incubation`、`observe_incubation`、`diagnostic_observation`、`paper_observation` 等 lane，否则容易高估或低估策略工厂效果。

### 2.3 交易预测合同：把 AI 判断冻结成可验收对象

策略工厂通过 `trade_prediction_contract` 把生成时的预测固化：

- `packages/strategy-factory/src/strategy_factory/application/trade_prediction_contract.py`
  - 必填字段包括 `strategy_id`、`stock_code`、`prediction_as_of`、`target_trading_date`、`direction`、`confidence`、`horizon`、`evidence_refs`、`contract_version`、`contract_source`。
  - `direction` 规范为 `up|down|neutral`。
  - `freeze_trade_prediction_contract` 会校验并生成稳定 `contract_hash`。
  - 模块注释说明 P0 只做归一化、校验和稳定哈希，outcome scoring 属于后续阶段。
- `packages/strategy-factory/src/strategy_factory/application/services/submission_coordinator.py`
  - 提交候选时，如果 `trade_prediction_contract_status == ready` 且有 `contract_hash`，调用 `save_strategy_trade_prediction`。
  - 保存 payload 的 `prediction_status` 为 `pending`，metadata 记录来源、candidate_id、submission_lane。
- `packages/aiask-quant-core/src/aiask_quant_core/storage/sqlite/strategy_trade_prediction.py`
  - `save_strategy_trade_prediction` 要求 `strategy_id`、`stock_code`、`prediction_as_of`、`target_trading_date`、`direction`、`contract_version`。
  - 已存在同一 `prediction_id` 时，`contract_hash` 不一致会拒绝，避免事后篡改预测。

检测含义：

- 如果没有 ready 的 `trade_prediction_contract`，后续无法做严格预测命中率检测。
- `contract_hash` 是“预测前置冻结”的关键证据，能防止结果出来后改预测。

### 2.4 交易预测 outcome：方向命中率和 v2 评分

后续 outcome 由孵化工厂的交易预测验证器写入：

- `packages/akshare-mcp/src/akshare_mcp/services/incubation_factory/trade_prediction_verifier.py`
  - `DAILY_SCORE_VERSION = trade_prediction_score_daily_v1`。
  - `INTRADAY_SCORE_VERSION = trade_prediction_score_v2`。
  - 日线评分 `_daily_outcome`：
    - `direction=up` 时，目标日 `close-open` 收益大于 flat threshold 为 `direction_hit=True`。
    - `direction=down` 时，目标日收益小于负阈值为命中。
    - `direction=neutral` 时，绝对收益在 flat threshold 内为命中。
    - `trade_prediction_score = 0.55*direction + 0.25*target_touch + 0.20*risk_proxy`。
  - 盘中 replay `_score_intraday`：
    - 输出 `score_version=trade_prediction_score_v2`。
    - 评分由方向命中、目标触达、风险代理、入场窗口、出场窗口、time bucket 命中率组成。
  - `verify_pending` 会读取 `target_trading_date <= today` 且尚未有 daily outcome 的 pending prediction，并写入 daily 和可选 intraday outcome。
- `packages/aiask-quant-core/src/aiask_quant_core/storage/sqlite/strategy_trade_prediction.py`
  - `save_strategy_trade_prediction_outcome` 保存 `score_version`、`score_status`、`trade_prediction_score`、`outcome_json`、`data_quality_status`。
  - `aggregate_trade_prediction_matrix` 按 `family/stage/regime/event/factor` 等维度聚合：
    - `direction_hit_rate = direction_hit_n / sample_n`
    - `target_touch_rate = target_touch_n / sample_n`
    - `score_avg`
    - `score_lcb_95`

检测含义：

- 严格展示交易预测命中率时，应优先筛选 `score_version=trade_prediction_score_v2`、`score_status=ok`、`data_quality_status=ok`。
- `daily_v1` 可以作为诊断，`v2` 才是晋升门默认要求的评分版本。

### 2.5 晋升门：命中率/评分是否足够

策略工厂有交易预测晋升门：

- `packages/strategy-factory/src/strategy_factory/application/trade_prediction_promotion_gate.py`
  - 默认要求 `score_version=trade_prediction_score_v2`。
  - 默认 `min_sample_n = 30`。
  - 默认 `min_score_lcb_95 = 0.55`。
  - 会识别 `partial_daily_only`、`partial_intraday_missing`、`insufficient_samples`、`post_hoc_rejected` 等 partial 状态。
  - 会识别 `daily_bar_missing`、`intraday_missing`、`partial_gap`、`invalid_ohlc` 等数据质量缺口。
  - 如果环境变量 `STRATEGY_TRADE_PREDICTION_PROMOTION_GATE_ENABLED` 未开启，返回 `diagnostic_only=True`，不会硬阻断晋升，但仍输出诊断原因。
- `packages/strategy-factory/tests/test_trade_prediction_promotion_gate_p4.py`
  - 默认 disabled 时，即使 v2 缺失也只是诊断。
  - enabled 时样本不足会 hard block。
  - enabled 时 partial/data gap 会 hard block。
  - enabled 且 30 个 v2 ok 样本、LCB 达标时通过。

检测含义：

- 真正“用命中率挡晋升”需要明确打开 `STRATEGY_TRADE_PREDICTION_PROMOTION_GATE_ENABLED=1`。
- 若未开启，系统仍能展示命中率诊断，但晋升不会被 v2 评分硬阻断。

### 2.6 策略级前向命中率：主验收口径

孵化工厂负责对策略信号做真实前向收益验证：

- `packages/akshare-mcp/src/akshare_mcp/services/incubation_factory/forward_verifier.py`
  - 不同策略类型映射到不同 primary/secondary horizon：
    - 高频：5/10
    - 中频：10/20
    - 低频：20/40
  - 对每条信号读取 `forward_returns` 和 `direction`。
  - primary 命中规则：
    - `forward_return > 0` 且方向为正，命中。
    - `forward_return < 0` 且方向为负，命中。
  - 输出：
    - `primary_hit_rate`
    - `secondary_hit_rate`
    - `recent_primary_hit_rate`
    - `primary_skill_lcb`
    - `secondary_skill_lcb`
    - `recent_primary_skill_lcb`
    - `coverage_ratio`
    - `forward_ic`
    - `forward_sharpe`
    - `hit_rate_by_regime`
  - `skill_lcb` 使用 Wilson lower bound 减去 0.5 随机基线，样本少于 5 时返回 0。
- `packages/akshare-mcp/src/akshare_mcp/services/incubation_factory/hit_rate_matrix.py`
  - 将 `ForwardVerifier.verify` 结果聚合为 `strategy_type × holding_bucket × regime_dimension × regime_label` 矩阵。
  - 低于 `DEFAULT_MIN_CELL_N = 5` 的 cell 标为 `insufficient_samples`，不伪造命中率。
  - 对可用 cell 按样本量加权合并 `hit_rate`，再重算 `skill_lcb`。
- `packages/akshare-mcp/src/akshare_mcp/services/incubation_factory/hit_rate_reporter.py`
  - `_aggregate_overall`：`total_hits = round(primary_hit_rate * primary_effective_n)`，整体 `hit_rate = total_hits / total_signals`。
  - 报告包括 `overall`、`by_family`、`by_stage`、`trend`、`matrix`、`trade_predictions`。
  - 报告通过 `save_strategy_domain_event` 落库为 `event_type=incubation_factory.hit_rate_report_generated`。
- `packages/akshare-mcp/src/akshare_mcp/services/incubation_factory/runner.py`
  - Phase 5 调用 `HitRateReporter.generate`。
  - 运行日志会输出整体 `hit_rate`。

检测含义：

- 这是策略级命中率的核心闭环。
- 推荐验收标准至少包含：
  - `primary_effective_n >= 20` 才做策略级初步判断。
  - `coverage_ratio >= 0.5` 才避免前向收益覆盖不足。
  - `primary_skill_lcb > 0` 表示相对 50% 随机基线有正下界。
  - `recent_primary_skill_lcb >= 0` 或更高阈值用于检查近期退化。

### 2.7 生命周期质量归因：预测弱还是执行弱

孵化/生命周期共享逻辑还会区分预测质量和执行质量：

- `packages/akshare-mcp/src/akshare_mcp/services/strategy_lifecycle_shared/execution_quality_parts/execution_metrics.py`
  - `_build_signal_quality_payload` 会整理 `hit_rate`、`hit_rate_lcb`、`skill_lcb`、`recent_hit_rate`、`stability_gap`、`sample_count`。
  - `_classify_prediction_quality`：
    - `primary_skill_lcb <= 0` 或 recent skill LCB < 0 判为 `weak`。
    - `primary_effective_n < 20` 或 coverage < 50% 判为 `insufficient_evidence`。
    - `primary_skill_lcb >= 3%`、recent skill LCB >= 1%、effective_n >= 60、coverage >= 75% 可构成 strong 证据。
  - 同时输出 `execution_win_rate`、`fill_rate`、`signal_to_fill_ratio`、`diagnosis`，用于区分“预测没命中”还是“执行转换差”。

检测含义：

- 如果策略级前向命中率高但 paper/live 执行收益差，应看执行质量字段。
- 如果 `primary_skill_lcb <= 0`，即使 paper 执行没问题，也说明预测质量本身偏弱。

## 4. 建议检测步骤

### 4.1 策略级命中率检测

1. 运行孵化工厂周期，确保 Phase 5 `hit_rate_report` 已生成。
2. 查询最新 `incubation_factory.hit_rate_report_generated` domain event。
3. 检查：
   - `hit_rate_dashboard.overall.hit_rate`
   - `hit_rate_dashboard.overall.total_signals`
   - `hit_rate_dashboard.overall.avg_skill_lcb`
   - `hit_rate_dashboard.by_family`
   - `hit_rate_dashboard.matrix`
4. 对每个 family/type/regime/bucket：
   - 样本不足时只标 `insufficient_samples`，不要解读为低命中。
   - `skill_lcb > 0` 才视为相对随机基线有正证据。
   - 同时看 `recent_primary_hit_rate` / `recent_primary_skill_lcb`，避免历史好但近期退化。

### 4.2 交易预测命中率检测

1. 确认策略提交时有 ready 的 `trade_prediction_contract` 和 `contract_hash`。
2. 查询 pending prediction：
   - `GET /v1/desktop/trade-predictions/status`
3. 运行或等待 `TradePredictionDailyVerifier.verify_pending` 写入 outcome。
4. 对严格验收查询：
   - `GET /v1/desktop/trade-predictions/matrix?score_version=trade_prediction_score_v2`
   - 只认可 `score_status=ok`、`data_quality_status=ok` 的样本。
5. 检查：
   - `sample_n >= 30`
   - `direction_hit_rate`
   - `target_touch_rate`
   - `score_avg`
   - `score_lcb_95 >= 0.55`
   - `partial_count == 0`
   - `data_quality_gap == 0`

### 4.3 晋升门检测

1. 默认状态下，交易预测晋升门是诊断模式，不硬拦截。
2. 若要让命中率成为晋升硬门，设置：
   - `STRATEGY_TRADE_PREDICTION_PROMOTION_GATE_ENABLED=1`
3. 期望行为：
   - v2 缺失：出现 `trade_prediction_score_v2_missing`。
   - 样本不足：出现 `trade_prediction_insufficient_samples`。
   - 数据缺口：出现 `trade_prediction_data_quality_gap`。
   - LCB 不达标：出现 `trade_prediction_lcb_below_threshold`。
   - 满足 30 个 v2 ok 样本且 LCB >= 0.55：通过。

## 5. 关键风险与解释边界

1. 不要把 `backtest win_rate` 当最终命中率。它是历史回测过滤字段，主要用于候选质量。
2. 策略级命中率依赖 `strategy_signal_evidence.forward_returns` 覆盖率；coverage 不足时，命中率不可靠。
3. `skill_lcb` 比裸 `hit_rate` 更适合验收，因为它考虑样本数和随机基线。
4. `trade_prediction_score_daily_v1` 可以诊断，但严格晋升门默认看 `trade_prediction_score_v2`。
5. `trade_prediction_score_v2` 依赖 intraday bars；缺分钟线会产生 `partial_intraday_missing`，这不是预测失败，而是数据质量缺口。
6. 当前晋升门默认 diagnostic-only；如果没有打开环境变量，系统会展示诊断原因但不会硬阻断晋升。
7. 命中率报告位于孵化工厂链路，策略工厂负责生成和冻结预测、提交观察/孵化；完整闭环必须跨 Strategy Factory、Incubation Factory、Quant Core、Agent/Desktop 一起看。

### 5.2 严格验收口径建议

用于对外或内部验收时，建议把“命中率”拆成三个数字同时展示：

1. 全部 outcome 样本数：用于说明系统实际产生了多少验证记录。
2. 有效样本数：仅包含 `score_status=ok` 且 `data_quality_status=ok` 的样本，这是主命中率分母。
3. 排除样本数：包含 partial、pending_market_data、daily_bar_missing、intraday_missing、invalid_ohlc 等，必须单独披露，不能混入主命中率解释。

推荐主判定口径：

- 交易预测主口径：`score_version=trade_prediction_score_v2`、`score_status=ok`、`data_quality_status=ok`、有效样本数 `>= 30`、`score_lcb_95 >= 0.55`。
- 策略级主口径：`primary_effective_n >= 20`、`coverage_ratio >= 0.5`、`primary_skill_lcb > 0`，同时检查 `recent_primary_skill_lcb` 是否退化。
- 展示口径：任何 `sample_n < 30`、`partial_count > 0`、`data_gap_count > 0` 的命中率都应标为诊断态，而不是通过态。

## 6. 最小验收清单

用于判断“策略工厂命中率已经可检测”：

- [ ] 每个正式或观察候选都能看到 `trade_prediction_contract_status=ready`，或有明确 reject reason，不能静默缺失合同。
- [ ] Quant Core 中存在 `strategy_trade_predictions` 记录，且 `contract_hash` 稳定不可变。
- [ ] `_persistence_dlq`、prediction 保存失败、outcome 保存失败均有可查询告警，避免“策略已提交但无预测样本”。
- [ ] 到达目标日后存在 `strategy_trade_prediction_outcomes`，且 daily 与 v2 outcome 的补算互不阻塞。
- [ ] v2 outcome 的 `score_status=ok`、`data_quality_status=ok` 有效样本数达到验收阈值；partial 和数据缺口不进入主命中率分母。
- [ ] `aggregate_trade_prediction_matrix` 能输出 `direction_hit_rate`、`target_touch_rate`、`score_lcb_95`，并能解释这些指标使用的是全部样本还是有效样本。
- [ ] 孵化工厂 `hit_rate_report_generated` 报告能输出 `overall/by_family/by_stage/matrix`。
- [ ] 策略级 `primary_effective_n`、`coverage_ratio`、`primary_skill_lcb` 达到最小解释阈值，且最近窗口没有明显退化。
- [ ] 若要把命中率作为晋升硬门，`STRATEGY_TRADE_PREDICTION_PROMOTION_GATE_ENABLED=1` 必须在验收环境明确开启。
- [ ] Desktop 或 Agent API 能读取同一批 status/outcomes/matrix，且展示中明确区分诊断态、通过态、partial 和数据质量缺口。

## 7. 一句话结论

策略工厂本身通过 `win_rate` 做候选前筛，通过 `trade_prediction_contract` 固化可验收预测；真正体现“策略工厂命中率”的核心证据在后续孵化/观察闭环中形成，但当前代码还存在 v2 补算、有效样本分母、partial 口径、软失败持久化和晋升门默认诊断模式等问题，因此现阶段可用于观测命中率，不应在未修正口径和开关前直接作为严格晋升验收证明。
