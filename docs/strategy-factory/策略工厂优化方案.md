## 1. 优化清单（按优先级）

### P0 ｜ 修复 `_evaluate_statistical_admission` db/klass 签名 bug

**问题**：`trade_profile.py::_run_statistical_gate` 用 `db=db, klass=klass` 调用 `_evaluate_statistical_admission`，但后者签名只接受 `(strategy, profile, gate_payload, *, admission_level, attempt_adjustment)`。每个 candidate 都会抛 `TypeError: got an unexpected keyword argument 'db'`，被外层 except 吞成 warning，**导致补充统计门禁（walk_forward_ic_ir / purged_kfold_ic / bootstrap_ci_lower / param_sensitivity / period_robustness）从未真正生效**。

**影响范围**：每条 Gate-3 评估的 candidate；本次 session 11×16 ≈ 176 次失效调用。

**修复方案**：选择以下任一种（推荐 B）：
- A. 让 `_evaluate_statistical_admission` 接受可选 `db`、`klass` 关键字（前向兼容）
- B. 在 `_run_statistical_gate` 中删掉 `db=db, klass=klass`，改为传入构造好的 `gate_payload`
- C. 把统计门改成异步、把 `db` 用作真实数据源（最大改造，能让统计门真正消费回测时间序列）

**改动量**：A/B ≈ 10 行；C 是大重构。

**验证**：跑一次工厂，确认日志里 `statistical_gate_exception_typeerror` 警告消失；DB 里 `gate_3.supplemental_statistical_gate.passed` 出现真实通过/失败统计。

---

### P1 ｜ 显著拉高 LLM 命中率（target_context_blocked 二次治理）

**现状**：BULK 矩阵每轮抽 20 个 stock-strategy task，但其中 ~15 个因为 target_symbols 命中"市值降序前 N 名"以外、又触发 *cache miss → 重建 universe* 失败而走 `_build_blocked_research_context`。PR-S23 已在 reuse cache 路径修了一刀，但 **`_load_universe_rows` 这一层在 SQL `ORDER BY market_cap DESC NULLS LAST` 下，5,517 只 NULL 全排在末尾**，by-code 补救必须真正生效到底。

**已落地（PR-S23）**：
1. `list_stocks_by_codes(codes)` by-code 取股票元数据
2. `_build_research_context` 在 universe_rows 装载完成后，把 task.target_symbols 缺失项 by-code 补回
3. `_reuse_shared_research_context` cache miss target 时不再 short-circuit，让上层重走完整路径

**待优化**：
1. **填充 stocks.market_cap**：跑一次全量行情同步把 market_cap 写回（5517 只 ≈ 几分钟）。这条做完后，市值降序排列才有意义。
2. **research universe 不再用 limit=300**：对 BULK task，应该按 task.target_symbols ∪ task.focus_industries ∪ "前 N 大市值代表" 拼一份"针对性 universe"，避免每次都拉前 300。
3. **添加埋点**：在 `_load_universe_rows` 调用结束时记录 `target_symbols_in_universe / target_symbols_recovered_by_code / target_symbols_still_missing`，写入 `external_provider.research_context_universe_recovery`，方便监控修复效果。

**预期收益**：每轮 LLM 命中数从 3–4 提到 12–15（占 task 池 50%+）。

---

### P2 ｜ LLM 单 task 超时治理

**现状**：每轮 4–8 个 task 因 `task_timeout_local_fallback` 被强制降级。`STRATEGY_FACTORY_RESEARCH_TASK_TIMEOUT_SEC=180` 这个上限在网关 P95 ≥ 30s 时会被触发；BULK 路径里 fan-out 4 次 + staged pipeline 多阶段，180s 跑不完是常见情况。

**改动方案**：
1. **分级超时**：snapshot/event task 用 180s（细致但快）；BULK stock-strategy task 用 360s（粗糙、token 大）。需要 `_factory_scheduler_loop_parts/policy.py::_compute_task_timeout` 按 task_source 分支取值。
2. **降低 fan-out**：把 `STRATEGY_FACTORY_LLM_FAN_OUT_COUNT=4` 在 BULK 路径下改为 2，单 task 总耗时减半，超时压力立刻缓解。
3. **网关并发节流**：`STRATEGY_LLM_MAX_CONCURRENCY=2`（实测下游 `ai.centos.hk` 单 token RPS 约 1，再高就 429）。当前 `STRATEGY_FACTORY_BACKTEST_CONCURRENCY=10` 没问题，但 LLM 并发要保守。
4. **跳过重试**：发生 `task_timeout_local_fallback` 时记录 `skip_reason='task_timeout'`，不要再降级到 rule path 跑一遍同样的 candidate，应该直接 abort 让下一轮重新 plan。

**预期收益**：每轮再多挽回 4–6 个 LLM task，配合 P1 后总 LLM 命中可达 18–20 / 29。

### P3 ｜ Gate-3 拒绝原因结构性治理

**现状**：本次 session 168 条 rejected，主要原因（每轮 11 条 candidate 中）：
- `expectancy_0.0000_<=_0`：≈10/11（**91%**） — 期望值非正
- `win_rate < 0.45–0.55`：≈3/11
- `trade_density > 1.2`：≈1–2/11
- `validation_grade_d_not_allowed_for_incubation`：D 级评分

**根因分析**：
1. 真正的策略质量问题（参数空间没探明 / market 价格信号 + cost 模型互相吃掉了 alpha）
2. 评分体系问题（实测 multi_factor 把 commission=0.025% + slippage_bps=6.0 + market_impact_bps 累计到 implementation_shortfall=11.6 bps，对短反转单边 8% 止损的小幅 alpha 来说致命）
3. 阈值过严（`payoff_ratio_min=0.8` 在 trade_count=20 的样本下统计意义不足，不应作为 hard fail）

**改动方案**：
1. **参数搜索**：让 quality_gates 的 reject 反馈真正回写到 spawner 的 `param_search_space`（PR-S21 已埋管道，但实测 `feedback_metrics.zero_signal_ratio=0` 表明反馈没流通）。
2. **执行成本分级**：本次 5,204 只全市场覆盖里包含大量小盘股（ADV < 1M 股），应该按 `liquidity_bucket` 给不同 slippage_bps（mid=6, micro=15, large=3），现在统一 6.0 不合理。
3. **门禁阈值分级**：`expectancy_min=0` 这种 hard fail 在低 trade_count（20）下噪声很大，应该改成 `expectancy_min` 软约束 + `cohort_effective_trials >= 30` 才计入。
4. **revise 路径**：当前 `business_admission_decision: revise` 实测有出现，但都直接 reject 没真正进入 revise 循环。应实现 PR-S20 文档里描述的 "1 次 revise → 重跑 backtest"。

**预期收益**：Gate-3 通过率从 9% 提到 25–35%，每轮 submitted 从 0.2 提到 2–4。

### P4 ｜ BULK 矩阵吞吐治理（每轮 0.13% → 1%+）

**现状**：每轮 plan 15,322 个 task，但只跑 20 个，按当前节奏跑完全市场矩阵需要 766 轮 ≈ 32 小时。

**改动方案**（按风险递增）：
1. **简单版**：把 `STRATEGY_FACTORY_BULK_STOCK_MATRIX_MAX_TASKS_PER_RUN` 从 20 调到 50（实测每轮 130s 中 60s 给 LLM、40s 给 backtest，余量足够），单轮 task 数翻 2.5 倍。
2. **中等版**：把 `STRATEGY_FACTORY_RESEARCH_TASK_CONCURRENCY` 从 10 调到 20（CPU 负载实测 < 30%），并行度翻倍。
3. **彻底版**：BULK 矩阵走独立的并行 worker pool，把 LLM 调用从主流程剥离（生产/消费模式），主流程只消费已生成的 candidate。这是大改造，建议放到 PR-S25+。
4. **shard 滚动**：当前 `cursor_resume_from_run_id` 已经有，但 `selected_shard_ids` 每轮只取 1 个 shard。改成"每 5 轮换 shard，每轮取 1 个 shard 内的 50 个 task"，让同一个 shard 在不同 family 上多角度生成。

**预期收益**：吞吐率从 0.13% 提到 1.5%（每轮 50/3,330 batch），全市场矩阵跑完时间从 32h 缩到 ~5h。

### P5 ｜ 数据基础治理（市值/估值/行业 regime）

**现状**：实测三大评分组件全为 0：
- `size_score: 0.0`（全表 market_cap NULL）
- `valuation_score: 0.0`（PE/PB 没装回到 stocks 表，实测两列存在但值缺失）
- `sector_regime_score: 0.0`（hot_sectors / cold_sectors 都是空数组）

`topn_equity_portfolio` 的 score_quality 因此被标 `degraded`，挑出的 Top 20 完全靠 factor_alignment + stock_profile 两个量。

**改动方案**：
1. **market_cap 同步**：每次启动跑一遍 `update stocks set market_cap = ... from quotes` 触发器，或在 `bulk_stock_matrix_loaded_stock_count` 那一步把 market_cap 顺手写回。
2. **PE/PB 同步**：从 financials 表 join 回 stocks 表，至少把最新一期写进 stocks.pe_ratio / pb_ratio。
3. **sector_regime 计算**：调用现有的 `factor_research.py::_compute_sector_regime`，把结果落到 snapshot.hot_sectors / cold_sectors（实测 fear_greed_index=52 但 hot_sectors 是空，明显是上游断了）。

**预期收益**：topn `score_quality` 从 `degraded` 变 `healthy`，submitted 候选的市场代表性增强，Gate-3 的 benchmark_comparison 能算 oos_cagr 了（现在 oos_cagr=0.0166 但 benchmark=null）。

### P6 ｜ 监控与可观测性

**现状**：实测后才发现，要看清"工厂跑得怎么样"得 join 多张表 + 解析 stages JSON，运维成本很高。

**改动方案**：
1. 新建 `view_strategy_factory_run_summary` SQL view，把每轮的 elapsed / candidate_spawned / gate3_passed / submitted / llm_attempt / llm_skip_reason_counts 等核心字段扁平化。
2. 用 desktop UI（已有的 InspectorPanel）加一个 "策略工厂实时面板"，每 30s 拉一次最新 run，画出：
   - 每轮 LLM 调用次数（柱状）
   - 每轮 submitted/draft/rejected 累计（折线）
   - target_context_blocked 占比（线）
   - factor_alignment_score 活跃度（线）
   - submitted 策略的 type 分布（饼）
3. 加 alerting：连续 3 轮 submitted=0 → 告警；LLM POST 200 比例 < 95% → 告警。

**改动量**：view 1 张 + 前端面板 1 个 ≈ 1 天工作量。

## 3. 这次"实测能跑通"是因为什么

为了避免下次再踩同样的坑，把这次让工厂"从 0 LLM 调用跑到 63 次 LLM 调用"的关键决策记一下：
1. **LLM 没被调用 ≠ key 失效 ≠ BULK_LLM_ENABLED=0**。每个层都要单独验证：先 curl 网关、再 provider 直调、再看 stages 里 `external_llm_status_counts`、最后才看 task gating 链路。
2. **`shared_generation_context` cache reuse 是隐藏 short-circuit**：上游某个阶段缓存了一次 blocked context，下游所有 task 复用都直接走 blocked。任何"研究上下文"层 fix 都得在 reuse 路径同时改一次。
3. **市值降序 + NULL LAST + 全表 NULL = LLM 永远拿不到 BULK target 数据**。这是个隐性的依赖：LLM 路径假设 universe SQL 拉到的就是"覆盖度足够的样本"，一旦 stocks.market_cap 失修，整条 LLM 链路就熄灯。

下次再调"为什么 LLM 没跑"，按 1 → 3 顺序排查，能比这次省 2 小时。
