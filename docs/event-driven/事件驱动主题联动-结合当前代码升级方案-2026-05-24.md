## 1. 总体结论

事件驱动方向正确，但当前项目不是“从零实现”。仓库里已经出现了主题图、事件注入、任务生成、目标股动态数量、暴露度构建、回归模型、manager action 等半落地能力。真正的开发重点是把这些能力接成一条可审计、可回滚、可灰度的闭环：

`事件情报/人工注入 -> 统一事件信封 -> 主题图传播 -> 主题暴露股票池 -> event_driven 研究任务 -> Gate -> 提交/孵化 -> outcome/lineage -> 回归修正`

本版基于代码复核与深度审查，修正四个前置假设：

- 主题节点、主题边、事件注入、事件任务 lineage、主题暴露度等 SQLite schema/DAO 已经部分迁移到 `packages/aiask-quant-core/src/aiask_quant_core/storage/sqlite/`；`packages/akshare-mcp/src/akshare_mcp/storage/sqlite/` 是兼容壳，不应在其中重复造 schema。
- **本仓库当前是 TDX-only 数据源**（`docs/data/TDX数据源规范.md` 第 2 节明文规则、`packages/akshare-mcp/src/akshare_mcp/data_source/quotes.py` 默认 `DATA_SOURCE_KEEP_LEGACY_FALLBACK=0`）。原参考方案与上一版本中以 Tushare Pro `fina_mainbz / stock_basic / index_classify / ths_member / daily_basic` 为基底的暴露度设计在当前项目不成立。`tools/finance.py / fund_flow_*.py / macro.py / utils.py` 中残留的 Tushare 调用属于迁移过渡期债务，不是新方向。
- `factory_event_*` 虽然已进入 strategy manager contract，但 Agent `tool_risk.CONFIRM_REQUIRED_STRATEGY_ACTIONS` 与 `execute_confirmed_action()` 尚未覆盖这些 action，Desktop 写操作会被 intent 创建或确认执行链拦住。
- 旧 `LocalEventDrivenResearchEngine` 与新 `event_injections` 必须有明确 cutover 节点；不能让 cluster/signal 与 injection 两套事件永远并行而无统一口径。

当前缺口集中在七处：

- 事件语义未统一：`manual_event` / `auto_event` 与下游大量 `event_driven` 判断冲突。
- 确认执行链未闭合：`factory_event_*` 已是 manager action，但 Agent intent 白名单和执行器都未完整接入。
- 暴露度数据通道不全：本地 TDX 概念/行业板块基底已就绪（`tdx_relation` 87,632 行 / `block_stocks` 17,725 行，2026-05-21~05-23 同步），但缺 `upsert_theme_exposure`、`list_company_concept_blocks` / `list_industry_blocks` DAO，缺概念板块成员稀释项与流动性过滤；`market_blocks.block_type` 在生产中是 `'tdx'` 占位、`_sync_relation/_sync_sector_basic` 未写 `tdx_data_completeness`，需要在 PR-B2 内修补。`fina_mainbz` 在 TDX-only 下不再作为目标。
- 主链路/Gate 未贯通：事件任务生成存在，但下游很多地方仍固定 `limit=12` 或只识别 snapshot/旧 event path。
- 前端缺运营入口：现有 `EventConsolePanel` 是只读 domain events viewer，不是策略工厂事件触发台。
- outbox/幂等策略未落地：优先复用已有 `strategy_domain_events` append-only 表（生产已 5,783 行）做 v1 outbox 基底，而不是新建同质表。
- 批量写性能未解决：`ThemeExposureBuilder` 目前是双层循环逐条 await，6000 标的 x 200 主题会不可接受。

## 3. 事件情报层设计

### 3.1 统一事件信封

新增统一事件契约 `EventIntelligenceEvent`。实现时可以映射到当前 `strategy_factory_event_injections`，不一定马上新增 Python dataclass，但所有入口必须使用同一语义。

必备字段：

| 字段 | 含义 |
| --- | --- |
| `event_id` | 稳定事件 ID，前缀区分来源：`manual_`、`news_`、`macro_`、`market_`、`local_theme_` |
| `source` | `manual`、`news_llm`、`macro_shock`、`market_anomaly`、`price_inference` |
| `event_type` | 事件分类，见 3.2 |
| `time` | 事件发生或被确认的时间 |
| `valid_from` / `valid_until` | 事件有效窗口 |
| `confidence` | 置信度，0~1 |
| `intensity` | 强度，0~1 |
| `primary_themes` | 直接受影响主题，含 `theme_code` 与方向 |
| `evidence` | 摘要、来源 URL、发布时间、抽取依据、人工备注 |
| `dedupe_key` | 去重键，建议 `source + event_type + normalized_title + summary_hash + valid_from_date` |
| `status` | `pending_review`、`active`、`paused`、`expired`、`rejected`、`completed` |

建议采用 CloudEvents 风格字段映射：

- `id -> event_id`
- `source -> source`
- `type -> event_type`
- `time -> time`
- `data -> evidence + primary_themes + horizon`

注意：`normalized_title` 容易因新闻标题微调而变化，`dedupe_key` 必须加入摘要 hash 或人工 canonical key，避免同一事件被重复触发。

### 4.4 主营业务匹配项的替代策略

原参考方案与上一版本（v1/v2）的暴露度公式中存在 0.30 权重的"主营业务匹配（基于 Tushare `fina_mainbz`）"。在 TDX-only 现状下：

- TDX `tqcenter` SDK **没有等价于 `fina_mainbz` 的"按业务条线/产品拆分主营业务收入"接口**。`get_financial_data` 中的 FN358/FN359 仅有"主营业务收入(内/外销)"二元字段；`TDX_LOCAL_CLIENT_DATA_GUIDE.md:34, 503` 实测确认免费版 FN 字段无法作为真实财务来源。
- v1 暴露度公式必须放弃 `fina_mainbz` 路径，采用以下任一替代策略（建议组合 (a) + (b)）：
  - (a) 把 0.30 权重重分配到行业匹配（0.40 → 0.55）+ 名称别名匹配（0.20 → 0.35），保留 0.10 给流动性/市值过滤。
  - (b) 把"主营业务匹配"重命名为"概念板块匹配"，数据来源换成 `tdx_relation(block_type='概念')` 与 `block_stocks`，权重保留 0.30；同概念板块视为有主营业务暴露。
  - (c) 推迟到 v2：等项目接入第三方主营业务数据（同花顺/万得等）后再启用。在 v1 阶段直接走 (a) 或 (b)。

本方案在 §6 Phase 6 选 (a) + (b) 组合：先把"概念板块匹配"做进 v1 公式（权重 0.30，数据来源 `tdx_relation` + `block_stocks`），未来若引入更细的主营业务源再细分。

### 4.5 事件证据数据策略

新闻、政策、公告类证据**与行情数据完全解耦**：不进 `kline_*` / `tdx_*` / `stocks` 等行情表，只落到 `strategy_factory_event_injections.evidence` 与 `strategy_factory_event_injections.rationale` JSON 字段。证据条目仅保存：

- 来源名称。
- URL。
- 发布时间。
- 事件摘要（不超过预设字节上限，参照 `strategy_factory_json_budget.py`）。
- 抽取出的主题、方向、强度、置信度。
- 去重键。

不要在本地长期保存大段版权文本。新闻/公告抽取来源在 v1 阶段**仅支持人工注入**；自动化新闻流接入作为 v2 单独立项，且接入时必须不违反 §4.3 禁令（即不引入 Tushare/AKShare 公告流，需要项目独立选型）。

## 5. 目标架构

### 5.1 分层

1. 事件情报层
   输入包括人工事件、新闻抽取、宏观/商品 shock、市场异动和旧价格倒推事件。输出统一 `EventIntelligenceEvent`。

2. 事件存储与 outbox 层
   `strategy_factory_event_injections` 保存业务事件。v1 优先复用 `strategy_domain_events` 作为 append-only outbox 基底，增加或旁路维护 `dedupe_key`、`processed_at`、`attempts`、`error` 等消费状态。消费者必须按 `event_id + theme_code + target_symbols_signature` 幂等。

3. 主题图传播层
   `theme_graph.py` 读取 `strategy_factory_theme_nodes` / `strategy_factory_theme_edges`，输出 `ThemeImpact`。

4. 主题暴露股票池层
   `ThemeExposureBuilder` 基于本地缓存生成 `(symbol, theme_code, exposure_score)`，`target_basket.py` 只负责选择，不负责实时拉数。

5. 研究任务层
   事件任务统一为 `task_source="event_driven"`，`event_source` 区分来源。目标股数量由 `target_count_resolver` 决定。

6. Gate 与提交层
   Gate 不改变核心质量判断，只接收新的 target contract。lineage 记录 Gate 通过和提交结果。

7. outcome 与回归层
   outcome 标注进入样本池；回归模型先生成建议和冲突报告，不默认覆盖人工锁定边。

### 5.2 新旧路径共存与 cutover

- 旧路径：`LocalEventDrivenResearchEngine.refresh()` 当前继续写 `strategy_factory_event_clusters` / `strategy_factory_event_signals`。
- 新路径：人工/新闻/宏观事件写 `strategy_factory_event_injections`。
- PR-C 后新增适配层：把旧 `local_theme_*` / price inference event 归一化成 `EventIntelligenceEvent` 视图，scan 层统一按 `event_source="price_inference"` 消费。
- PR-E 之前旧 cluster/signal 表仍保留写入；PR-E 后默认 scan 不再直接消费 cluster/signal，只消费归一化事件视图；PR-H 后评估是否停止旧表写入或改为只做审计归档。
- scan 合并顺序固定为：`manual > macro_shock > news_llm > price_inference > snapshot`。
- `_DEFAULT_THEME_LIBRARY` 只作为 seed/fallback，不作为运行时主数据源。

- 概念板块覆盖度有偏：单个概念板块成员可达 1,200 只（`880904.SH 机器人概念`），暴露度公式必须叠加权重衰减或流动性过滤，避免单概念污染目标池。

实施内容：

- 复用已有 TDX 表（已由 `services/tdx_sync_service.py` 写入，无需新建 schema）：
  - `tdx_relation`：股票×板块归属，`block_type ∈ {行业,概念,风格,地区,指数}`。生产已有 87,632 行。
  - `block_stocks` + `market_blocks`：板块成分股与板块元信息（`stock_count / leader_code / weight`）。**注意 `market_blocks.block_type` 在生产中是 `'tdx'` 占位，只代表"该板块由 TDX 同步出来"，不代表"概念/行业"；所有 `block_type` 判断必须走 `tdx_relation`。**
  - `stocks`：股票基础信息（含 `tdx_industry / tdx_region / list_status / market_cap / turnover_rate`）。
  - `tdx_stock_extra`：每日扩展指标，提供市值/换手/涨幅等流动性过滤字段。
- 新增 DAO：
  - `list_company_concept_blocks(symbol, limit, block_type=None)` → 返回 `[{symbol, block_code, block_name, block_type, gp_num}]`，从 `tdx_relation` 读取，默认按 `block_type='概念'` 过滤。
  - `list_industry_blocks(symbol)` → 从 `tdx_relation(block_type='行业')` 读，作为暴露度行业匹配项的精确数据源（弥补 `stocks.industry` 字段粒度不一致的问题）。
  - 这两个 DAO 命名为"本地查询接口"，明确不触发任何外部 API。
- 检查与文档：
  - 在 `docs/data/TDX数据源规范.md` 第 5 节补一行映射，把"概念板块匹配"对应到 `tdx_relation(block_type='概念')`。
  - 在 `_sync_relation` 与 `_sync_sector_basic` 结尾补 `save_tdx_data_completeness(...)`，记录 `tdx_relation / block_stocks / market_blocks` 的最近同步时间和行数。生产实测当前这三项不在 `tdx_data_completeness`，无法监控新鲜度。
  - 用 `scripts/probe_event_driven_data_readiness.py` 在每次 release 前实测一次本地数据基底，结果写入 release notes。
- 不允许做的事：
  - 不新增 `strategy_factory_company_mainbz` 表。
  - 不新增 Tushare `fina_mainbz` 同步任务。
  - 不在事件触发链路实时调用 tqcenter SDK 拉板块数据；如需更新，走现有 TDX 同步任务。

验收：

- `list_company_concept_blocks` 与 `list_industry_blocks` 在临时 SQLite + 真实 adapter 初始化下能返回 mock 数据。
- 当 `tdx_relation` / `block_stocks` 为空时返回空列表 + 日志告警，不阻塞 Phase 1–5。
- 暴露度 v1 公式（§6 Phase 6）能在没有主营业务数据的情况下正常评分。

### Phase 6：暴露度与回归闭环

目标：事件主题能落到可交易股票池，长期通过 outcome 修正主题边。所有数据访问只走本地 TDX 表（§4.1/§4.2）。

实施内容：

- `ThemeExposureBuilder` 数据来源全部改为本地 TDX 表：
  - 股票池与基础属性：`stocks`（含 `tdx_industry / tdx_region / list_status / market_cap / turnover_rate / dividend_yield`）。
  - 行业归属：`tdx_relation(block_type='行业')`，弥补 `stocks.industry` 粒度不一致的问题。
  - 概念板块归属（替代主营业务匹配）：`tdx_relation(block_type='概念')` + `block_stocks`，由 Phase 0.5 的 `list_company_concept_blocks` 提供。
  - 每日流动性 / 市值 / 估值过滤：`tdx_stock_extra` 88 字段每日快照（市值、换手率、近 N 日涨跌幅、连板天数等）。
  - 历史 K 线：`kline_1d`，仅供 `historical_beta` 选配项使用。
- 暴露度 v1 评分（按 §4.4 决策选用 (a)+(b)，主营业务匹配项替换为概念板块匹配）：
  - 行业匹配 0.40：基于 `tdx_relation(block_type='行业')` 与主题节点 `industry_tags`。
  - 名称/别名匹配 0.20：基于 `stocks.stock_name` 与主题节点 `aliases`。
  - 概念板块匹配 0.30：基于 `tdx_relation(block_type='概念')` 与主题节点 `industry_tags / aliases`；同概念板块视为有主题暴露。**概念板块成员数差异极大（生产实测最大 1,200，最小可低于 50）**，公式必须叠加成员稀释项：`concept_score *= clamp(log10(150 / max(1,member_count)), 0, 1)` 或等效衰减，避免大盘性概念（机器人概念、人工智能、新能源车）把上千只股票全打成同一暴露。
  - 流动性/市值过滤 0.10：基于 `tdx_stock_extra` 与 `stocks.list_status`，对低流动性、退市、停牌、近 30 日成交不达标的股票降分或剔除。
- v2 可选项：当项目接入第三方主营业务数据源（同花顺/万得/通达信付费数据包等）时，再把"主营业务匹配"作为新 0.30 权重项独立加入，方案不在 v1 内承诺。
- `historical_beta` 在 v1 仍为附加字段；后续若启用，从本地 `kline_1d` + 主题代理指数（建议使用 `market_blocks.leader_code` 或同概念板块成分等权指数）计算。
- `ThemeExposureBuilder` 必须改成批量写：
  - 使用单事务分批 `executemany` 或 adapter batch API。
  - SQLite 保持 WAL、`synchronous=NORMAL`、合理 `busy_timeout`。
  - 每批建议 500~2000 行，避免 120 万次逐条 await。
  - 输出 `rows_scanned`、`rows_written`、`batch_count`、`elapsed_seconds`、`industry_coverage`、`concept_block_coverage`。
  - **耐久性折中说明**：`synchronous=NORMAL` 在 WAL 模式下，断电/系统崩溃时可能丢失最近若干未 fsync 的事务（参见 SQLite 官方与社区共识）。本方案接受该折中，因暴露度行可在下一次定时刷新中重建。事件驱动主链路的关键写入（`event_injections` / `event_task_lineage` / `factory_event_approve`）仍走默认 `synchronous=FULL` 的会话，不共享暴露度构建的低耐久性配置。
- `ThemeResponseRegression` weekly off-hours 跑，默认只写报告和建议。
- `manual_locked=1` 的 edge 不覆盖方向、幅度、置信度。
- sign conflict 需要人工确认，不自动写回。

验收：

- 任一 seed theme 能返回 exposure 股票池；公式中任何一项数据缺失（例如某主题没有匹配的概念板块）能落到 evidence 字段，不静默丢失任务。
- 低流动性、退市、停牌股票被流动性/市值过滤项剔除，不进入事件目标池。
- 全量 exposure 刷新耗时有上限目标和进度报告，不再是逐条 await 小时级任务。
- 回归结果可展示 `updated_count`、`sign_conflicts`、`skipped_locked`。
- `ThemeExposureBuilder` 不调用任何 Tushare/AKShare/eFinance/Baostock API；如需扩展数据，必须先经 `docs/data/TDX数据源规范.md` 修订。

## 8. 运维与风控规则

- 所有写操作必须通过 ActionIntent。
- `intensity >= 0.8`、`scope=market`、`primary_themes >= 10` 必须双人审核。
- 事件暂停或过期后不得生成新任务。
- 删除主题节点只能 soft delete。
- 新闻/政策证据只存摘要和 URL，不存长篇原文。
- outbox 消费必须幂等，publisher v1 用单 worker 轮询，避免多消费者并发扫 SQLite 热点表。
- 业务事务内只写 DB 与 outbox，不调用外部 API。
- 回归模型默认不开自动覆盖，只给建议。
- 动态目标股数默认关闭，先完成 5a 再开 5b；5a 期间上游事件任务也必须硬限制到 12。
- `LocalEventDrivenResearchEngine` cutover 前后必须有双写/只读归一化说明，避免统计口径分裂。
- `ThemeExposureBuilder` 必须批量写入，禁止 6000 x 200 规模逐条 await。
- **数据源边界**：本方案的所有实施 PR 必须遵循 `docs/data/TDX数据源规范.md` 第 2 节优先级规则。不允许新增 Tushare/AKShare/eFinance/Baostock/外部 HTTP 数据同步任务、本地缓存表或事件触发期实时调用。仅在以下两种情况例外：(a) 用户主动设置 `DATA_SOURCE_KEEP_LEGACY_FALLBACK=1` 的迁移过渡场景；(b) 项目独立选型并修订 TDX 数据源规范后再立项。任何新增"主营业务深度数据"等非 TDX 路径必须按这两条之一明确签署。
- **服务解耦边界（非常重要）**：仓库已通过公共库 `aiask-quant-core` 把 `strategy-factory` 与 `akshare-mcp` 解耦：
  - `strategy-factory` 包对 `akshare_mcp` **零导入**（`grep "from akshare_mcp" packages/strategy-factory/src` 必须始终为 0），`pyproject.toml` 也不允许声明 `akshare-mcp` 依赖。
  - `akshare-mcp` 可以单向 import `strategy_factory`，但反过来不可以。
  - 共享 schema、DAO、契约类型（`StrategyFactoryRepository` 协议、`BacktestEngine`、`RiskModel`、`compile_strategy_blueprint` 等）一律落到 `aiask-quant-core`。
  - 跨包能力（factor_mining_factory / factor_pool_gateway / incubation runtime / quant_manager_callable）由 host 进程在启动期通过 `strategy_factory.infrastructure.mcp_services.configure_runtime_services(...)` 注入；strategy-factory 内部只调用 `_required("provider_name", call=True)`，**不写死 import 来源**。
  - **本方案任何 PR 在改 `packages/strategy-factory/src/**/*.py` 时**：
    - 不允许新增 `from akshare_mcp...` 或 `from akshare_mcp.tools.managers...`；
    - 不允许新增 `from packages.akshare-mcp...`；
    - 需要 host 才能提供的能力（如 tdx_sync 状态、Tushare proxy 等）一律走 configure_runtime_services 注入新 provider，由 akshare-mcp `server.py` 启动时 register。
  - **本方案对 `aiask-quant-core` 的 schema/DAO 改动**（PR-B1 已落地的 outbox / approver 字段 / theme_exposure DAO，以及后续 PR-B2 的 concept_blocks DAO）必须保留向后兼容：列追加用 `IF NOT EXISTS`、不删除既有列、ON CONFLICT 用 COALESCE 避免覆盖既有审批/Gate 字段。
  - 任何违反上述边界的改动会让 strategy-factory 失去独立部署能力，PR 评审第一项就要拒。
