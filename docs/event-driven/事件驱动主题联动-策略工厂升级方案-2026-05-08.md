## 0. 本方案与既有整改的关系

本方案不替代 `策略工厂/策略工厂整改详细清单.md` 里的 WP0~WP11。它只解决一件事：

**目前策略工厂的"机会扫描" 只能从价格倒推主题，不能从外部事件推演主题。**

因此它是 WP1（任务约束）与 WP5（事件验证口径）上游的一块新能力，结构上并联于 `MarketOpportunityScanner`，复用下游的 `target_alignment_contract`、Gate-1/Gate-2/Gate-3、孵化与前端展示。

### 2.1 数据源可行性评估（2026-05-14 修订）

官方 AKShare 文档显示，A 股全市场与主题暴露所需的基础数据是可接入的，但当前策略工厂还没有把这些数据组织成“事件 → 主题 → 股票池”的在线链路：

- 股票清单：`stock_info_a_code_name()` 单次获取沪深京 A 股代码和简称，可作为全市场 universe 基础表。参考：https://akshare.akfamily.xyz/data/stock/stock.html
- 行业与板块：`stock_board_industry_name_em()` / `stock_board_industry_cons_em()` 可提供行业板块与成分股，是主题暴露的第一层映射。参考：https://akshare.akfamily.xyz/data/stock/stock.html
- 主营业务与主营构成：`stock_zyjs_ths()`、`stock_zygc_em()`、`stock_profile_cninfo()` 可提供主营业务、产品类型、主营构成、经营范围，适合补 `main_business_match`。参考：https://akshare.akfamily.xyz/data/stock/stock.html
- 新闻、公告、研报：`stock_news_em()`、`stock_zh_a_disclosure_report_cninfo()`、`stock_research_report_em()` 可作为事件证据与主题文本证据来源，但需要额外做去重、可信度、时效与版权/缓存治理。参考：https://akshare.akfamily.xyz/data/stock/stock.html

### 2.3 新旧事件路径的共存契约

现状代码里有 **`LocalEventDrivenResearchEngine.refresh()`**（基于价格相对强度倒推，写 `strategy_factory_event_clusters` / `strategy_factory_event_signals`）。本方案新增的手动注入路径会写 `strategy_factory_event_injections`。两条路径必须共存且不互相覆盖：

- `MarketOpportunityScanner.scan()` 先读 `strategy_factory_event_injections`（manual / macro_shock / news_llm），再读 `strategy_factory_event_clusters`（price_inference）。
- 同一主题同时被两条路径覆盖时，task 生成按 **source 优先级** 合并：`manual > macro_shock > news_llm > price_inference`；`scope=market` 的 manual 事件优先级最高。
- `event_id` 前缀强制区分：`manual_*` / `macro_*` / `news_*` / `local_theme_*`（已有），禁止跨命名空间。
- `_DEFAULT_THEME_LIBRARY` 保留作为 seed 来源的代码副本，但运行时**只从 DB 读**；读到为空时才降级到硬编码，避免 PR-1 尚未 seed 时主链路崩溃。

## 4. 决策 A：动态目标股数

### 4.1 代替常量的公式

取消 `OPPORTUNITY_TARGET_SYMBOLS_PER_TASK = 8` 作为唯一来源，改为按事件/主题上下文动态计算：

```python
def resolve_target_count(
    *,
    confidence: float,       # 0..1
    intensity: float,        # 0..1
    theme_breadth: str,      # "narrow" / "medium" / "broad"
    task_source: str,        # "manual_event" / "auto_event" / "snapshot"
    feature_flag_target_max: int = 30,   # 未开 flag 时必须传 12
) -> int:
    base_by_breadth = {"narrow": 5, "medium": 10, "broad": 18}
    base = base_by_breadth.get(theme_breadth, 10)

    evidence = confidence * 0.55 + intensity * 0.45  # ∈ [0,1]
    stretch = evidence ** 1.3                         # 非线性放大
    dynamic = base + stretch * 12                     # 最多额外 +12

    # manual 加成 **在 clamp 之前**生效，避免强事件时奖励被 30 截断
    if task_source == "manual_event":
        dynamic += 3

    # 快照任务保持克制（不允许超过 12）
    if task_source == "snapshot":
        dynamic = min(dynamic, 12)

    # flag 未开时，事件任务也不得越过 12，防止 PR-5 未部署就先爆 Gate
    upper = max(3, min(feature_flag_target_max, 30))
    return max(3, min(upper, int(round(dynamic))))
```

关键修正：

1. `manual_event` 的 +3 加成移到 clamp 之前，避免强事件被 30 截断后奖励失效。
2. 新增 `feature_flag_target_max` 参数，调用方必须传入 `OPPORTUNITY_TARGET_SYMBOLS_MAX`（开 flag 后 30）或降级值 12。未开 flag 时，即使 `resolve_target_count` 被意外调用，也不会返回超过 12 的值，避免"PR-5 未部署 + PR-6 被提前开"的最坏组合直接打爆 Gate。
3. 区间 `[3, 30]`，但真正能到 30 的只有 `broad + evidence>=0.9 + manual_event`，典型情况仍在 5-20 之间。

### 4.2 "12 → 30" 迁移节奏（强制分阶段）

原来的"PR-5 一次性把 12 改到 30"在实操上不安全，因为 Gate-3 报告、前端 target preview、governance artifact 里有大量 `limit=12` 的 hard assumption，且 `quality_gates_parts/evaluation.py:229` 的 `target_symbol_count_exceeds_12` 判断会直接拦截。拆成三个阶段：

**阶段 5a（同 PR，但先部署）**：让 12 变成"默认值"而不是"硬上限"
- 引入 `domain/target_limits.py:resolve_target_symbol_limit(ctx)`，单一入口
- 所有 `limit=12` 调用点改为 `limit=resolve_target_symbol_limit(ctx)`，默认仍返回 12
- 新增 `target_alignment_contract.max_candidate_target_symbols` 参与 quality gates 判断
- **此阶段 max 仍是 12**，不改观测上的任何数字，跑 1 周回归

**阶段 5b（同 PR，灰度切换）**：逐步放量
- 开 `STRATEGY_FACTORY_DYNAMIC_TARGET_COUNT_ENABLED=true`
- `resolve_target_symbol_limit` 对 `task_source in {"manual_event","auto_event"}` 返回 `OPPORTUNITY_TARGET_SYMBOLS_MAX`（30），快照仍返回 12
- 监控 Gate-1 队列深度、`BACKTEST_CODE_CONCURRENCY` 饱和度、单任务 P95 回测时长 3 天
- 如回测 P95 翻倍以上、或 `BACKTEST_CODE_CONCURRENCY` 饱和率 > 90% 持续 1 小时，自动回退阶段 5a（通过 flag 切换，无需回滚代码）

**阶段 5c（独立 PR，可选）**：快照任务从 8 改到 12
- 完全独立，只在需要时触发

这三步必须按顺序，不能合并。

### 4.3 下游一致性硬约束

改 `OPPORTUNITY_TARGET_SYMBOLS_PER_TASK` 是起点，不是终点。同一改动必须同时放宽：

| 位置 | 当前值 | 需要的改动 |

| `quality_gates_parts/evaluation.py` | `len(target_codes) > 12` 直接拒绝 | 改为读取 `target_alignment_contract.max_candidate_target_symbols` 或 `OPPORTUNITY_TARGET_SYMBOLS_MAX`，事件路径上限 30，快照路径仍可保持 8/12 |
| `targets_parts/selection.py` / `matching.py` | 多处 `_normalize_target_codes(..., limit=12)` | 引入 `target_limit` 参数，由 research_task / event impact 传入，默认保持 12 |
| `backtest_filter.py` / `backtest_filter_parts/*` | 多处 `_extract_target_codes_from_payload(..., limit=12)` | 改为 `resolve_candidate_target_limit(candidate)`，事件任务允许 30，但实际 evaluated codes 可抽样 |
| `candidate_contract_parts/*` / `submission_gate/runner_parts/*` | 多处 target 归一化 limit=12 | 统一接入 `target contract v2`，避免生成时 30 只、提交时被截断成 12 只 |
| `research_plane_contract.py` / `governance_plane_contract_parts/*` | artifact 只 compact 前 12 只 | 保留完整 `target_symbols`，UI preview 可只展示前 20 |
| `GATE1_REPRESENTATIVE_COUNT` | 4（max 8） | 改为按任务 `target_count` 自适应：`max(2, min(target_count // 2, 10))` |
| `BACKTEST_CODE_CONCURRENCY` | 4（max 12） | 放宽到 max 20，且随 `target_count` 缩放 |
| `_build_strategy_panels(sample_size=6)` | 6 | 改为 `min(max(target_count, 6), 20)` |
| `_apply_target_symbol_policy(limit=8)` 调用点 | 8 | 改为传入 `target_count` |
| `_compact_task_metadata_value` 的 `preview[:8]` | 8 | 改为 `preview[:20]` |

PR-5 的验收标准不是“公式能返回 30”，而是 `target_count=30` 在 candidate contract、Gate、backtest、submission、artifact、前端预览中不被截断，也不会触发 `target_symbol_count_exceeds_12`。

### 4.4 theme_breadth 从哪里来

存在 `strategy_factory_theme_nodes.breadth` 字段（见 §6.2 schema）。每个主题节点定义三档：

- `narrow`：3-8 只龙头（白酒、航空等集中度高的）
- `medium`：8-15 只（航运、新能源）
- `broad`：15-30 只（银行保险、高股息、周期资源）

首次由运营填，后续可以被 "事件-主题响应回归模型"（§7）反向修正。

### 6.5 图遍历算法

事件触发一个或多个 primary theme → BFS 遍历 `strategy_factory_theme_edges`，最多 `max_depth=2`，沿途衰减：

```python
async def propagate_event_to_themes(db, event: NormalizedEvent, max_depth: int = 2):
    impacts: dict[str, ThemeImpact] = {}
    frontier = [
        (
            pt["theme_code"],
            normalize_direction_sign(pt.get("direction") or event.direction),
            event.confidence,
            event.intensity,
            0,
            0,
        )
        for pt in event.primary_themes
    ]
    while frontier:
        theme, dir_sign, conf, mag, lag, depth = frontier.pop()
        # 合并到 impacts 里，取较强的一条
        existing = impacts.get(theme)
        if existing is None or mag > existing.magnitude:
            impacts[theme] = ThemeImpact(theme, dir_sign, mag, conf, lag, depth)
        if depth >= max_depth:
            continue
        edges = await db.list_theme_edges(source=theme, is_active=True)
        for edge in edges:
            new_dir = dir_sign * edge["direction_sign"]
            new_mag = mag * edge["magnitude_factor"]
            new_conf = conf * edge["confidence"]
            if new_mag < 0.15 or new_conf < 0.25:
                continue       # 衰减到阈值以下就不再传导
            frontier.append((
                edge["target_theme_code"], new_dir, new_conf, new_mag,
                lag + edge["lag_days"], depth + 1
            ))
    return list(impacts.values())
```

`normalize_direction_sign()` 必须把 `"positive" / "negative" / "neutral" / +1 / -1 / 0` 统一为 `+1 / -1 / 0`。UI、API、DB 可以保留字符串方向，但图算法和回归结果内部只使用数值符号。

## 7. 决策 D：事件-主题响应回归模型

这是本方案最硬的一块。目标是把 `strategy_factory_theme_edges` 里的 `direction_sign / magnitude_factor / lag_days / confidence` 从 "人工拍脑袋" 变成 "数据驱动 + 人工审核"。

### 7.1 模型定位

- **不是预测模型**：不是用来预测"下次原油飙升会怎样"，而是 **用历史数据拟合"主题 A 的显著变动之后，主题 B 在 T+k 天的收益"**
- **不是 alpha 模型**：不直接用于交易，只用来修正主题图的参数
- **属性**：可解释优先、稳定优先、样本量足够优先

### 7.2 变量定义

**因变量 y**：目标主题 T 在事件后 `horizon` 天的累计超额收益（相对大盘 CSI 300）

$$ y_{T,t,k} = \sum_{i=1}^{k} (r_{T,t+i} - r_{market,t+i}) $$

- $r_{T,t}$ = 主题 T 的成分股等权日收益（或按市值加权）
- $k$ ∈ {1, 3, 5, 10, 20}（交易日）

**自变量 X**：主题 S 的 "异常日"标志 + 强度

$$ X_{S,t} = \{ \text{shock}_{S,t}, \text{magnitude}_{S,t}, \text{direction}_{S,t} \} $$

其中：

- `shock_{S,t} = 1` 当且仅当 $|r_{S,t} - \mu_S| > 2 \sigma_S$（20 日滚动 z-score > 2）
- `magnitude_{S,t}` = z-score 的绝对值（截断到 5）
- `direction_{S,t}` = sign($r_{S,t} - \mu_S$)

**控制变量**：大盘动量、恐贪指数、北向资金流向

### 7.3 模型方程（按 edge 做）

对每条 `(source_theme, target_theme, horizon)` 组合，拟合：

$$ y_{T,t,k} = \alpha + \beta \cdot \text{direction}_{S,t} \cdot \text{magnitude}_{S,t} + \gamma \cdot X_{controls,t} + \delta \cdot r_{T,t} + \epsilon $$

关键差异（相对 v0）：

- **新增 $\delta \cdot r_{T,t}$ 项**：控制 target 主题在 shock 日的"被动同向反应"，避免"当日同涨"被误记为联动强度。对 `horizon=1` 尤其重要。
- **shock 窗口按主题性质自适应**：价格型主题用 z-score(20d)；慢变量（利率敏感、地产周期、宏观）用 z-score(60d) 或 60d 分位数 > 90%。在 `strategy_factory_theme_nodes` 加 `shock_detection_profile ∈ {fast, medium, slow}` 字段驱动。
- **CSI 300 作为基准但不是唯一选择**：对防御/红利主题应改用 `中证红利 000922`，对科技主题改用 `科创 50`；在 node 表加 `benchmark_index_code` 字段，默认 CSI 300。

输出：

- `direction_sign` ← sign($\beta$)
- `magnitude_factor` ← |$\beta$| / baseline（baseline 取所有显著 edge 的 95 分位数）
- `lag_days` ← argmax over k of |$\beta_k$|
- `confidence` ← min(R²_adjusted, 1 - p_value, 0.95) × min(n_samples/100, 1)
- **样本重叠惩罚**：如果 (source, target) 的成分股重叠 > 30%（例如都在银行板块），把 confidence 再乘 0.7，防止"自相关被当成联动"

### 7.4 数据要求

| 项目 | 最低要求 | 推荐 |
| --- | --- | --- |
| 历史 K 线 | 3 年 | 5 年以上 |
| 样本事件数（每条 edge） | 20 次以上 shock | 50+ |
| 主题成分股覆盖 | 每主题 ≥ 5 只 | ≥ 10 只 |
| 市场基准 | 按主题性质选择（CSI 300 / 中证红利 / 科创 50） | 同上 |
| 成分股重叠 | source∩target ≤ 50% | ≤ 30%（否则 confidence 惩罚） |

如果某条 edge 的样本不足 20，置 `confidence_source='manual'`，不用模型结果。

### 7.5 样本偏差与 A 股特殊性（必读）

A 股的统计特性决定了上述回归不能直接套用标准事件研究法，必须显式处理：

- **涨跌停截断**：单日 ±10%（创业板/科创板 ±20%）的硬限制会让 shock 日的收益被截断。处理：shock 识别用"连续 2 日 z-score 合成"替代"单日 z-score"，避免首日触停导致低估。
- **停牌日**：主题成分股有停牌时，等权日收益不能简单用 `NaN.fillna(0)`，应该按当日存活股票重算权重；停牌股超过成分 30% 的交易日直接剔除。
- **ST/退市股污染**：计算 $r_{T,t}$ 时剔除当前为 ST / 已退市 / 上市不足 250 日的股票。
- **IPO 事件污染**：新股上市首 20 日不纳入样本，避免首日暴涨被当 shock。
- **因果方向模糊**：如果 source 和 target 同属一个申万一级行业（例如 `refinery` 和 `petrochemical`），必须额外在方程里加 `industry_common_factor` 控制变量，或者把这条 edge 标为 `relation_type='same_sector_comovement'`，前端展示时提示运营"这不是真正的跨主题联动"。
- **节假日对齐**：A 股和商品期货（WTI、布伦特）交易日不同步。如果 shock source 是商品，需要把 source 收益按 A 股交易日 forward-fill，避免春节期间累积的海外波动在节后首日被当成单日 shock。

这些处理不做，回归结果在 Gate 层面会表现为"置信度高但实际方向错"。

### 7.6 实现位置

**代码位置**：`packages/strategy-factory/src/strategy_factory/application/research/theme_response_regression.py`（新文件）

**接口**：

```python
class ThemeResponseRegression:
    async def build_theme_returns(self, db, theme_code: str) -> pd.Series:
        """加载主题成分股，算等权日收益"""

    async def detect_shocks(self, returns: pd.Series, z_threshold: float = 2.0) -> pd.DataFrame:
        """返回 shock_date / magnitude / direction"""

    async def fit_edge(
        self,
        source_theme: str,
        target_theme: str,
        horizons: list[int] = [1, 3, 5, 10, 20],
    ) -> EdgeRegressionResult:
        """拟合一条 edge，返回 beta / r_squared / best_horizon / n_samples"""

    async def run_full_update(self, db) -> dict:
        """遍历所有 active edge，批量拟合并写回 strategy_factory_theme_edges（confidence_source='regression'）"""
```

**运行频率**：每周日盘后（或每月首次），写入 `strategy_factory_theme_edges.last_regression_at`。

**门槛**：

- 只覆盖 `n_samples >= 20` 的 edge
- 如果回归结果 `|beta| < 0.1` 或 `p_value > 0.1`，保持人工值
- 如果回归和人工值符号相反，标记 `evidence.sign_conflict=true`，触发人工复核，先不覆盖

### 7.7 blended 模式

允许一部分 edge 的 confidence 是人工和回归的混合：

```python
blended_confidence = (
    manual_confidence * manual_weight
    + regression_confidence * regression_weight
)
```

默认权重：manual=0.3, regression=0.7；样本量 < 50 时 manual=0.6, regression=0.4。

### 7.8 回归结果的展示

在 §5 的前端触发台里加一个 "关系诊断" 面板：

- 当前触发的主题 impact 列表
- 每条 impact 旁边显示 `confidence_source: manual / regression / blended`
- 点击可以下钻看：历史 shock 样本数、R²、最近一次回归时间、β 的 95% CI

### 7.9 事件事后标注闭环

用户在事件结束后填 `actual_outcome`（§5.1 区块 3），这个数据进入回归模型的 "事件样本库"，下次更新回归时权重更高。

样本累积后，跑一个简单的二分类 "预测事件-主题关系准确性"：

- 输入：event_type / primary_themes / confidence / source
- 输出：actual_outcome 是否匹配预期方向
- 输出：每个 event_type 的"触发可信度修正系数"

这层是自我校准机制，先不在 v1 实现，先把数据留着。

## 8. 股票池构造（Layer C 细化）

### 8.1 主题暴露度

对每只股票、每个主题，算一个 `exposure_score ∈ [0, 1]`：

```python
exposure_score = (
    0.40 * sw_industry_match(stock, theme)          # Tushare index_classify + concept_detail
    + 0.25 * name_alias_match(stock, theme)          # Tushare stock_basic name 字段（已同步到本地）
    + 0.20 * main_business_match(stock, theme)       # Tushare fina_mainbz（白名单内，需新增同步到本地表）

)
```

第一、二项可以用本地已同步的股票池字段（名称、行业、板块）先落地；第三项使用 Tushare Pro `fina_mainbz` 接口（白名单内），需要在 `sync_daily/financial_sync.py` 中新增同步任务，首次全量拉取后缓存到本地 `strategy_factory_company_mainbz` 表（每季度更新）；第四项直接读本地 K 线数据。

### 8.2 基础数据与预计算

- **数据来源**：Tushare Pro `fina_mainbz`（主营业务构成）+ `concept_detail`（概念成分）+ `index_classify`（申万行业）+ 本地 `daily` 表（K 线），全部通过 `sync_daily/` 同步到本地 SQLite
- **离线任务**：每日盘后跑 `build_theme_exposure_matrix`，输出 `strategy_factory_theme_exposure`（新表）
- **字段**：`(symbol, theme_code, exposure_score, industry_match_level, beta, updated_at)`
- **规模**：5000 股票 × 60 主题 = 30 万行，SQLite WAL 模式下 batch upsert 约 3-6 秒完成

### 8.3 事件发生时的股票选择

```python
async def resolve_target_basket(impact: ThemeImpact) -> TargetBasket:
    rows = await db.list_theme_exposure(
        theme_code=impact.theme_code,
        min_exposure=0.3,
        limit=50,
    )
    # 按 exposure_score 降序，但保留行业分散
    selected = apply_industry_diversification(
        rows,
        max_per_industry=3,  # 提高到 3（vs 现在的 2）
        target_count=30,     # 先拿宽一点，resolve_target_count 再裁
    )
    # 对 negative impact 的主题，排除已经大跌的股票（避免"加空"）
    if impact.direction_sign < 0:
        selected = [r for r in selected if r["return_20d"] > -0.15]
    return TargetBasket(
        theme=impact.theme_code,
        symbols=[r["symbol"] for r in selected],
        weights=compute_exposure_weighted(selected),
        evidence={
            "exposure_rule_version": "v1",
            "avg_exposure_score": mean(r["exposure_score"] for r in selected),
            "industry_breakdown": count_by_industry(selected),
        }
    )
```

```
STRATEGY_FACTORY_THEME_GRAPH_ENABLED=true                (第 2 步，PR-3 上线后)

  └── 打开图遍历，但 preview-only，依然不入队

STRATEGY_FACTORY_MANUAL_EVENT_ENABLED=true               (第 3 步，PR-6 上线后)
  ├── 依赖 THEME_GRAPH_ENABLED=true
  ├── 依赖 DYNAMIC_TARGET_COUNT_ENABLED=true （如需 >12 只目标）
  └── 真正驱动 task，进 Gate

STRATEGY_FACTORY_DYNAMIC_TARGET_COUNT_ENABLED=true       (第 4 步，PR-5 阶段 5b)
  └── 独立于事件路径，可以单独开给 auto_event

```

## 13. 风险和护栏

| 风险 | 护栏 |
| --- | --- |
| 运营误操作，触发高强度错误事件，导致工厂大量生成错误 task | 强制双人审核 + `intensity >= 0.8` 强制 pending_review |
| 主题图形成循环传导，算力失控 | `max_depth=2` + 衰减阈值 `magnitude < 0.15` 剪枝 |
| 回归模型样本不足导致 confidence 异常 | `n_samples >= 20` 硬门槛 + sign_conflict 人工审核 |
| 动态目标股数放大下游回测压力 | `GATE1_REPRESENTATIVE_COUNT` / `BACKTEST_CODE_CONCURRENCY` 同步调整 + 按 target_count 自适应 |
| 事件触发后无法撤销 | 每个事件保留 "pause / expire" 操作，任务进 Gate 前可以拦 |
| feature flag 配置错误 | 所有 flag 默认 false，只有经过验证才开 |
| `event_engine.py` 的旧自动识别路径和新手动路径冲突 | 通过 `strategy_factory_event_injections.source` 明确区分，task 生成时打标签，不合并 |
| 历史回测事件样本有选择偏差 | 回归模型结果 `confidence_source='regression'` 时保留 manual 值备份，允许一键回滚 |

## 17. 运营 SOP

工具做出来还不够，运营侧需要明确的操作手册。

### 17.1 事件触发 SOP

**触发前检查清单**：
1. 事件是否已在 `strategy_factory_event_injections` 中存在（按 `event_name + valid_from` 去重）
2. 主要主题是否都在图中（否则先走 theme-graph 页面补节点）
3. 方向是否与历史同类事件一致（查 `event_type + primary_theme` 的历史命中率）
4. 当前活跃事件数是否 ≥ `STRATEGY_FACTORY_MANUAL_EVENT_MAX_ACTIVE`（默认 20），超了要先暂停低优先级

**提交规范**：
- `intensity >= 0.8` 必须附评论说明依据（新闻链接、指标数值、对照历史案例）
- `scope=market` 必须由 `strategy_lead` 触发
- `horizon` 保守起见，第一次触发取下限（`swing_1_5d` 而不是 `macro_1m`）

**触发后监控**（24 小时内）：
- 查看 `/strategy-market/event-impact/:eventId`，确认至少 3 个 task 进入 Gate-1
- 如果 24 小时后 Gate-1 通过率为 0%，暂停事件并人工复盘
- 如果 Gate-3 通过率异常高（> 历史 3 倍），同样暂停，可能方向反了

### 17.2 事后标注 SOP

事件 `valid_until` 到期后 5 个交易日内必须完成标注：

- `positive`：主要主题的超额收益方向和预期一致，且 |超额| > 3%
- `negative`：方向相反，或 |超额| > 3% 的反向
- `mixed`：主题之间方向分化
- `no_effect`：|超额| < 1%

标注时必须填：
- 主要主题的实际超额收益数字（相对主题选定的基准指数）
- 最强支持证据（一句话）
- 是否发现了预期外的连带影响（会反向修正 theme_graph）

超过 10 个交易日未标注的事件，scheduler 自动打 `outcome='no_label'` 并跳出回归样本。

### 17.3 主题图维护 SOP

每周一早会做一次图巡检：
- 检查上周 `sign_conflict=true` 的 edge 列表，人工裁决保留或翻转
- 检查 `last_regression_at > 30 天` 的 edge，决定是否停用
- 新增节点前先查重（aliases 重叠 > 50% 视为重复）
- 删除节点要检查 `factory_event_task_lineage` 中是否有引用，有引用只能 `is_active=false` 不能删
