## 项目数据架构现状

- **主数据源**：Tushare Pro（`.env` 中 `TUSHARE_TOKEN` 已配置）
- **降级备选**：AKShare（`stock_news_em` 等少数接口在用）
- **同步引擎**：`packages/akshare-mcp/sync_daily/`（`engine.py` → `stock_sync.py` / `financial_sync.py` / `market_sync.py`）
- **本地存储**：SQLite（`~/.aiask/akshare_mcp.sqlite3`）
- **白名单管理**：`src/akshare_mcp/config/tushare_proxy_whitelist.json`（63 个已验证接口）

## 对升级方案各 PR 的影响

### PR-4（主题暴露度离线计算）

**数据来源变更**：

原方案 §8.1 的 `exposure_score` 公式中：
- `sw_industry_match` → 使用 Tushare `index_classify` + `concept_detail`（白名单内）
- `name_alias_match` → 使用 Tushare `stock_basic` 的 `name` 字段（已同步到本地）
- `main_business_match` → 使用 Tushare **`fina_mainbz`**（白名单内，关键新增）
- `historical_beta` → 使用本地已同步的 K 线数据（`daily` 表）

**实现路径**：
1. 在 `sync_daily/financial_sync.py` 中新增 `_sync_mainbz` 方法，调用 `ts_pro.fina_mainbz()`
2. 数据缓存到本地 `strategy_factory_company_mainbz` 表（每季度更新一次）
3. PR-4 的 `theme_exposure_builder.py` 直接读本地表，不实时调用 Tushare

**频率限制注意**：
- Tushare Pro 频率限制约每分钟 200 次
- 5000 只股票首次全量拉取 `fina_mainbz` 需要约 25 分钟
- 应在 off-hours 一次性拉取，后续每季度增量更新

### PR-7（事件-主题响应回归模型）

**数据来源**：
- 主题成分股收益 → 本地 `daily` 表（已同步）
- 市场基准（CSI 300 等）→ 本地 `index_daily` 表（已同步）
- 无需额外调用外部 API

### PR-1/PR-3/PR-6（事件注入/传播/任务生成）

**无数据源依赖变更**：这些 PR 操作的是策略工厂内部的主题图和事件表，不直接调用外部数据接口。

## 关键结论

1. **方案完全可行**：主题暴露度计算的核心数据（`fina_mainbz` + `concept_detail` + `index_classify` + 本地 K 线）全部在 Tushare Pro 白名单内
2. **不需要实时调用外部 API**：`sync_daily/` 已把 K 线、财务指标同步到本地 SQLite，暴露度计算直接读本地数据
3. **架构优势**：项目已有完整的同步引擎框架，PR-4 只需新增一个 sync task
4. **AKShare 仅用于 Tushare 白名单缺失的边缘场景**（新闻、BDI 指数）

## 原 §2.1 的修正说明

原文档 §2.1 中引用的 AKShare 接口（`stock_zh_a_spot_em`、`stock_board_industry_cons_em`、`stock_zyjs_ths`、`stock_zygc_em` 等）应理解为**降级路径**，不是主路径。实际实现时：

- 优先使用 Tushare Pro 对应接口（`stock_basic`、`concept_detail`、`fina_mainbz`）
- 仅在 Tushare Pro 白名单缺失时降级到 AKShare
- 项目中 `data_source/__init__.py` 的 `DataSource` 类已实现"Tushare → AKShare"的优先级降级逻辑
