## 二、各模块诊断

### 2.1 DSL 编译器 (`factor_candidate_compiler.py`)

#### 健康状态：🟡 良好但受限

**设计亮点：**
- 基于 Python AST 的白名单校验，只允许 `Expression`/`BinOp`/`UnaryOp`/`Call`/`Name`/`Constant` 节点
- `eval()` 执行时 `__builtins__={}` 隔离，防止任意代码执行
- 复杂度评分机制（上限 80），防止过拟合表达式
- 完整的编译产物：引用字段、函数调用、未声明字段、复杂度统计

**支持的 DSL 语法：**

```
字段 (13个): open, high, low, close, volume, amount, returns_1d, return_5d,
            return_20d, momentum_20d, momentum_60d, volatility_20d, volume_ratio_5_20

函数 (13个): abs, clip, delta, delay, log1p, max, min, rank, sign,
            ts_mean, ts_rank, ts_std, zscore

运算符: +, -, *, / (二元), +, - (一元)
```

**诊断问题：**

| 编号 | 严重度 | 问题 | 影响 |
|------|--------|------|------|
| C-01 | 🔴 高 | 搜索空间过窄：仅 13 字段 × 13 函数 | 无法表达换手率、市值、行业、基本面因子 |
| C-02 | 🟡 中 | 缺少条件表达式 | 无法构建 regime-switching 因子 |
| C-03 | 🟡 中 | 缺少关键时序算子：`ts_max`, `ts_min`, `ts_corr`, `ts_cov`, `ewma` | 限制了因子多样性 |
| C-04 | 🟡 中 | `eval()` 仍有理论风险 | 若未来 Python 版本新增 AST 节点类型可能绕过 |
| C-05 | 🟢 低 | 无除零保护 | `Div` 运算可能产生 inf/nan（下游有 dropna 兜底） |

---

### 2.2 LLM Provider (`factor_llm_provider_parts/`)

#### 健康状态：🟢 工程化程度高

**设计亮点：**
- 完整的生命周期管理：smoke_check → generate → mark_success/failure → rebuild
- 兼容性冷却机制（compatibility_cooldown_sec=300s）：provider 返回不兼容结构时自动熔断
- SSE 流式解析回退：当 provider 返回 `text/event-stream` 时自动切换到流式解析
- Pydantic 模型校验（`FactorCandidateModel`）确保结构化输出
- 并发控制（Semaphore=3）、重试退避（retry_count=2, backoff=1s）

**配置参数：**

```python
FactorLLMConfig:
  enabled: FACTOR_LLM_ENABLED (default: False)
  base_url: FACTOR_LLM_BASE_URL
  api_key: FACTOR_LLM_API_KEY
  model: FACTOR_LLM_MODEL
  temperature: 0.2
  max_tokens: 1800
  timeout_sec: 45.0
  retry_count: 2
  compatibility_cooldown_sec: 300.0
  smoke_check_ttl_sec: 300.0
```

**诊断问题：**

| 编号 | 严重度 | 问题 | 影响 |
|------|--------|------|------|
| L-01 | 🟡 中 | 单一 provider 架构 | 无法做多模型 ensemble 或 A/B 测试 |
| L-02 | 🟡 中 | temperature=0.2 偏保守 | 因子挖掘需要创造性，低温度导致生成同质化 |
| L-03 | 🟡 中 | max_tokens=1800 可能不够 | 8 个候选 × ~200 token/个 + analysis 容易截断 |
| L-04 | 🟢 低 | 无 prompt 版本管理 | system_prompt 硬编码，无法做 prompt 迭代实验 |
| L-05 | 🟢 低 | 无生成结果缓存 | 相同上下文重复调用时无法复用 |

### 2.3 本地规则回退 (`llm_alpha.py`)

#### 健康状态：🟡 可用但非真正"挖掘"

**设计亮点：**
- 零外部依赖，保证系统可用性
- `TextSignalPipeline`：基于 40 词情绪词典的可解释文本信号
- 根据市场状态（趋势/高波动）动态调整因子优先级排序
- 完整的因子评估工具：IC 计算、Alpha 衰减检测、因子组合优化

**因子模板池（硬编码）：**

```
1. Momentum_20_60_Spread    — 中期与短期动量差
2. Volatility_Adjusted_Return — 收益按波动率归一
3. Short_Term_Reversal_5D   — 短期反转
4. Trend_ZScore_20          — 价格相对均线标准分
5. Price_Volume_Synergy     — 量价共振
6. Volume_Price_Divergence  — 量价背离
7. Intraday_Range_Pressure  — 日内振幅压力
8. Gap_Continuation         — 隔夜跳空延续
9. Turnover_Pressure        — 换手压力
10. Text_Sentiment_Signal   — 文本情绪信号
```

**诊断问题：**

| 编号 | 严重度 | 问题 | 影响 |
|------|--------|------|------|
| R-01 | 🔴 高 | 因子池固定（~10个模板） | 无法真正"挖掘"新因子，只是从固定池中选择 |
| R-02 | 🔴 高 | 公式语法与 DSL 不兼容 | 本地生成的 `close.pct_change(60)` 需二次转换为 DSL |
| R-03 | 🟡 中 | 情绪词典过于简单（40词） | 无法处理隐含情绪、反讽、行业术语 |
| R-04 | 🟡 中 | `evaluate_factor()` 计算单股票时序 IC | 非横截面 IC，统计意义有限 |
| R-05 | 🟢 低 | `scipy.stats` 在函数内部 import | 首次调用有冷启动延迟 |

### 2.4 Prompt 构建 (`factor_prompt_builder.py`)

#### 健康状态：🟢 信息丰富

**设计亮点：**
- 多维度上下文注入：K线摘要、财务快照、估值、另类因子、新闻/公告/研报标题、资金流
- 明确的 DSL 合约（`dsl_contract`）：告知 LLM 可用字段、函数、语义约束
- 记忆上下文注入：历史成功/失败/重复案例
- 数据源链追踪（`source_chain`）：记录每个数据来自哪个接口

**Prompt 结构：**

```
System: "You are a quantitative equity factor researcher for A-share markets..."
        - 输出格式约束（纯 JSON）
        - DSL 语义约束（单股票时序，非横截面）
        - 记忆学习指令

User:   "Research context:\n{request_payload}\n\nGenerate the best candidate factors..."
        - context_rows: 每只股票的市场/财务/新闻上下文
        - dsl_contract: 可用字段和函数
        - memory_context: 历史案例
```

**诊断问题：**

| 编号 | 严重度 | 问题 | 影响 |
|------|--------|------|------|
| P-01 | 🟡 中 | 上下文过长（8股 × 多维度 ≈ 4000+ token） | 对小模型不友好，可能超出有效注意力窗口 |
| P-02 | 🟡 中 | 缺少宏观环境信息 | 无大盘状态、行业轮动、利率环境 |
| P-03 | 🟡 中 | `non_dsl_context` 隔离依赖 LLM 自律 | LLM 可能在 expression_dsl 中引用非法字段 |
| P-04 | 🟢 低 | 无 prompt 压缩/摘要机制 | 当股票数多时 token 浪费 |

### 2.5 验证流水线 (`validation.py` + `factor_validation_pipeline.py`)

#### 健康状态：🟢 学术级水准

**设计亮点：**
- **Walk-Forward 滚动验证**：train_window=60, test_window=20, 滑动步长=20
- **Purged K-Fold CV**：n_folds=5, purge_gap=5，参考 de Prado (2018)
- **Bootstrap IC 置信区间**：非参数 Bootstrap，支持 full/fast 模式
- **多重检验校正**：
  - Deflated Sharpe Ratio (DSR)
  - Probability of Backtest Overfitting (PBO)
  - White Reality Check
  - Hansen Superior Predictive Ability (SPA) Test
- **前视偏差审计**（lookahead_audit）
- **相似度冗余惩罚**（与 5 个基准因子对比）
- **成本容量评估**
- **并行执行**：ProcessPoolExecutor 加速验证

**评级体系：**

```
总分 = 横截面IC(20) + OOS(20) + 稳健性(15) + 治理(40) + 执行(10)
     - 冗余惩罚(8) - 前视偏差惩罚(20) - 多重检验惩罚(18)

A级 (≥75): promote → 注册表晋升
B级 (≥60): review  → 人工审核
C级 (≥45): watch   → 观察池
D级 (<45): reject  → 拒绝
```

**诊断问题：**

| 编号 | 严重度 | 问题 | 影响 |
|------|--------|------|------|
| V-01 | 🔴 高 | `min_cross_section=3` 过低 | 3 只股票的横截面 Rank IC 无统计意义（学术标准 ≥30） |
| V-02 | 🔴 高 | 验证数据与生成数据相同 | 用同一批 K 线生成又验证，存在信息泄露 |
| V-03 | 🟡 中 | 仅日线粒度 | 无法验证日内因子或高频信号 |
| V-04 | 🟡 中 | 成本模型简化 | 固定滑点假设，未考虑非线性冲击 |
| V-05 | 🟡 中 | 基准因子只有 5 个 | 冗余检测覆盖不全（缺少 size/value/quality 基准） |

### 2.6 记忆与去重 (`factor_research_memory.py`)

#### 健康状态：🟡 创新但精度有限

**设计亮点：**
- 自建 128 维哈希向量（SHA1 随机投影），无需外部 embedding 服务
- 多层相似度融合：词法 Jaccard + 向量余弦 + 代码重叠度
- 边类型分类：`duplicate` / `failure_pattern` / `success_pattern` / `family_neighbor` / `semantic_neighbor`
- 记忆标签系统：status、family、grade、recommendation、unstable 等

**相似度阈值：**

```
≥ 0.985 或表达式完全相同 → duplicate（阻断）
≥ 0.92 且历史失败        → failure_pattern（警告）
≥ 0.92 且历史成功        → success_pattern（参考）
≥ 0.75 且同家族          → family_neighbor（提示）
其他                     → semantic_neighbor
```

**诊断问题：**

| 编号 | 严重度 | 问题 | 影响 |
|------|--------|------|------|
| M-01 | 🔴 高 | 哈希向量无法捕捉语义相似性 | 表述不同但语义相同的因子可能漏检 |
| M-02 | 🔴 高 | 缺少因子值层面的相似度 | 表达式不同但产生高相关因子值的候选未被识别为重复 |
| M-03 | 🟡 中 | 外部 embedding 服务可选 | 未配置时退化为纯哈希向量，质量大幅下降 |
| M-04 | 🟢 低 | 向量维度固定 128 | 对于大规模因子库可能不够 |

## 三、系统级问题

### 3.1 🔴 因子搜索空间过窄

**现状**：13 字段 × 13 函数，LLM 在有限语法空间内提出假设
**对比**：WorldQuant BRAIN 支持 100+ 算子；遗传规划可搜索任意深度表达式树
**影响**：系统本质是"LLM 在受限空间内猜测 → 统计验证"，而非自动化搜索

**建议**：
1. 扩展字段集：加入 `turnover`、`market_cap`、`pe_ratio`、`pb_ratio`、`roe`、`industry_dummy`
2. 扩展函数集：加入 `ts_max`、`ts_min`、`ts_corr`、`ewma`、`if_else`、`cross_rank`
3. 考虑引入遗传规划（GP）作为第三种生成模式

### 3.2 🔴 缺少因子正交化

**现状**：验证流水线只检查与 5 个基准因子的相似度
**影响**：连续生成 10 个动量变体因子，它们之间高度相关但都能通过验证
**建议**：在注册表层面维护活跃因子池的协方差矩阵，新因子入池前检查增量信息比

### 3.3 🔴 验证数据与生成数据未隔离

**现状**：用同一批 K 线数据构建 prompt 上下文（LLM 看到了数据特征）又用来验证
**影响**：LLM 可能根据看到的数据特征"定制"因子，导致过拟合
**建议**：
1. Prompt 中只提供 T-60 之前的数据摘要
2. 验证使用 T-60 到 T 的数据（真正的 OOS）
3. 或者使用不同股票池：生成用 A 池，验证用 B 池

### 3.4 🟡 无增量学习机制

**现状**：记忆系统只注入历史案例摘要到 prompt
**影响**：无法从验证结果中学习"什么样的因子结构更容易成功"
**建议**：
1. 维护"因子结构 → 验证结果"的映射表
2. 定期分析成功因子的共性特征（家族、复杂度、持有期分布）
3. 将分析结果作为 meta-prompt 注入

### 3.5 🟡 横截面样本量不足

**现状**：`min_cross_section=3`，验证时可能只用 3-5 只股票
**影响**：Rank IC 的 t 统计量在小样本下无意义
**建议**：将 `min_cross_section` 提升至 20-30，或在报告中明确标注样本量不足的警告

### 3.6 🟡 缺少经济学意义验证

**现状**：只验证统计显著性，不验证经济学合理性
**缺失项**：
- 因果推断：alpha 还是风险溢价？
- 容量评估：能承载多少资金？
- 衰减预测：alpha 半衰期多长？
- 交易约束：T+1、涨跌停、停牌

## 五、优先修复建议

### P0 — 立即修复（影响结果可靠性）

1. **提升横截面最小样本量**：`min_cross_section` 从 3 提升至 20
2. **隔离生成与验证数据**：prompt 上下文使用 T-60 前数据，验证使用近期数据
3. **增加因子值相关性去重**：在记忆系统中加入因子值 Pearson/Spearman 相关性检查

### P1 — 短期优化（提升挖掘效率）

4. **扩展 DSL 字段集**：加入 turnover、market_cap、pe_ratio 等 10+ 字段
5. **扩展 DSL 函数集**：加入 ts_max、ts_min、ts_corr、ewma、if_else
6. **因子正交化检查**：新因子入池前检查与活跃池的增量信息比
7. **提升 LLM temperature**：从 0.2 提升至 0.4-0.6，增加多样性

### P2 — 中期演进（架构升级）

8. **引入遗传规划（GP）**：作为第三种生成模式，自动搜索表达式树
9. **多模型 ensemble**：支持多个 LLM provider 并行生成，取并集
10. **增量学习机制**：从历史验证结果中提取成功因子的结构特征
11. **经济学意义验证**：加入容量评估、衰减预测、因果推断模块

### P3 — 长期方向（系统重构）

12. **分钟线/Tick 级验证**：支持高频因子验证
13. **非线性成本模型**：基于订单簿的冲击成本估计
14. **LLM-as-Judge**：用 LLM 评估因子的经济学合理性
15. **多 Agent 辩论**：生成 Agent + 质疑 Agent + 仲裁 Agent

## 六、附录：关键代码路径

```
# 完整因子挖掘一次调用的代码路径：

1. quant_manager(action="llm_factor_mining")
   → tools/managers/quant_mgr_generation.py::handle_llm_factor_mining()

2. 构建 prompt
   → services/factor_prompt_builder.py::build_factor_mining_prompt()
   → 加载 K线、财务、新闻、资金流、另类因子
```
