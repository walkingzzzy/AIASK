### 0.1 核心发现：G3 没有全拦,真正的断点在"孵化调度只认 incubating 状态"

**结论:G3 通过率 52%、入池 25 个,但全天只有 2 个策略变成 `incubating` 状态、建了 2 个 paper_account。**
"全拦"的真实含义不是"G3 拦截",而是**入池策略绝大多数停在 `submitted` 状态,
没有流转到 `incubating`,导致孵化/纸面交易循环只反复处理那 2 个老策略。**

### 0.2 真正的根因:双孵化通道 + 调度器 status 不匹配（已代码级证实）

`admission_authority.py` 的状态机决定 final_status,**只有一个分支给 `incubating`**:

| 分支(行) | 条件 | submission_lane | final_status |
|---------|------|----------------|-------------|
| `:161-164` | `formal_track_eligible`(严格门全过+budget=formal) | formal_incubation | **`incubating`** |
| `:103-107` | wide_intake observe(G3未过宽进) | observe_incubation | `submitted` |
| `:128-138` | live_candidate 但 runtime 未就绪 | observe_incubation | `submitted` |
| `:173-176` | runtime_bootstrap observe | observe_incubation | `submitted` |
| 其余 | research/deferred | deferred_submission | `submitted`/`rejected` |

两条互不连通的孵化通道:
- **formal 通道**:`final_status=incubating` → `PaperTradingBridge.on_strategy_incubated`(建 paper_account)
  → `PaperTradingScheduler._load_incubating_strategies` **只查 `status='incubating'`**(`paper_trading_scheduler.py:128`) ✅ 有人消费
- **observe 通道**:`final_status=submitted` + lane=observe_incubation
  → `lifecycle_coordinator.py:579-592 _enqueue_paper_observation`
  → `incubation_gateway.ensure_account(stage="paper")`(另一套账户,**status 不是 incubating**)
  → 由**独立的 incubation_factory** `intake.py:204 _list_paper_observation_strategies`(查 `stage='paper'`)消费

**断点:`PaperTradingScheduler` 与 `IncubationIntake` 是两个查询口径不同的消费者。**
strategy_factory 自带的 PaperTradingScheduler 只认 `incubating`,
**完全看不到 observe 通道的 `submitted`/stage=paper 策略**。
observe 策略能否被处理,完全依赖 incubation_factory 进程是否在跑 + `paper_intake_enabled()`。

### 0.3 为什么只有 2 个进 formal(incubating)

`formal_track_eligible` 要求 `strict_incubation_ready`(incubation 级评估零 blocker),
即必须过 `MIN_GRADE=S`(`start_three_factories.sh:41`) + incubation 档 IC≥0.02 等全部严格门。
实测评级分布 **B:13 / C:14 / D:2,零个 S 级** → 几乎无策略能命中 formal 分支
→ 全天仅 2 个侥幸进 incubating。这是 0.1 的"只有 2 个"的直接原因。

## 一、问题陈述（注:以下为初版基于"全拦"假设的推断,已被第零节修订）

策略工厂运行后，**所有生成的策略在 G3 环节全部被拦住**，无一进入孵化阶段。
用户三连问：

1. 为什么 G3 把所有策略全部拦住了？

## 二、根因总览

"全拦"**不是单一开关**，而是 **5 个独立机制叠加**，任意一个都足以拦死全部策略。
更关键的是：**启动脚本把其中 3 个保险同时打到最严档**，形成闭环死锁。

| 编号 | 机制 | 代码位置 | 代码默认 | 启动脚本设定 | 是否当前生效 |
|----|------|---------|---------|------------|------------|
| A | gate3 record-only(只记录不放行) | `_runtime_toggles.py:231-232` | `True` | `=1` | ✅ 生效 |
| B | 预测契约非 ready 即硬拒 | `entry.py:203` / `normalizers.py:461` | 恒拦 | — | ✅ 生效 |
| C | 交易预测晋升门硬拦 | `trade_prediction_promotion_gate.py` | `False`(仅诊断) | `=1`(变硬拦) | ✅ 被脚本激活 |
| D | 最低验证评级 = S 级 | `_runtime_toggles.py:225-228` | `"S"` | `="S"` | ✅ 生效 |
| E | 交易感知评级上限 = C 级 | `trade_profile.py:83-85` | 硬上限 | — | ✅ 生效(与D构成数学死锁) |

**最致命的是 D + E 组合**：准入要求 ≥ S 级(`order["S"]=4`)，
而纯交易策略经 `_derive_trade_aware_validation_grade` 评级，**数学上限只能到 C 级(`order["C"]=1`)**。
`validation_grade_at_least("C","S")` 恒为 `False` → **任何纯交易策略都不可能达标，100% 被拦**。

### 机制 C — 交易预测晋升门被启动脚本激活成硬拦

**代码**：`trade_prediction_promotion_gate.py`

**但启动脚本激活了它**(见第四节)，于是：

### 机制 D + E — 评级门数学死锁（最隐蔽、最致命）

**机制 D**：`_runtime_toggles.py:225-228`

**机制 E**：`trade_profile.py:83-85`，交易感知评级的**数学上限**：

评级序：`GRADE_RANKS = {"D":0,"C":1,"B":2,"A":3,"S":4,"SS":5,"SSS":6}`

→ **任何纯交易策略数学上不可能通过准入，100% 被拦**，与 A/B/C 完全独立。

**research 层例外**：`trade_profile.py:205-208` research 级别直接返回空 blockers(永远放行)，
但 `incubation`/`live` 级别被 D+E 拦死 → **没有任何策略能升到 incubation 以上** → 全拦。

## 四点五、observe-first 为何形同虚设（机制交互与执行顺序）

启动脚本开了 `STRATEGY_FACTORY_OBSERVE_FIRST_ENABLED=1`，设计意图是"观察优先放行"。
代码里也确有一条观察赦免通道 `maybe_grant_provisional_incubation`
(`quality_reporting_parts/policy.py:6`，在 `entry.py:153` 调用)。
**但它对纯回测/纯交易候选被三重断路，赦免给了也拿不到、或拿到又被收回**：

**断路 1 — 候选资格门槛(policy.py:15-22)**
```python
if gate.get("passed"): return gate
if not is_factory_provisional_candidate(strategy): return gate   # 需 tags 含 factory/auto_generated 且为技术/AI原型类型
if not has_only_statistical_gate_failures(gate): return gate     # ★ 关键断路
if not risk_report: return gate
```

**断路 2 — 失败码白名单(normalizers.py:243-255)**
`has_only_statistical_gate_failures` 要求 `reason_codes` **全部**匹配 5 个统计前缀：
```
walk_forward_ic_ir / purged_k_fold_ic / bootstrap_ci_lower / parameter_sensitivity / multi_period_ic
```
而纯回测候选的失败码是 `trade_prediction_contract_not_ready`、
`validation_grade_..._below_minimum_s_for_incubation` —— **不在白名单**
→ 返回 False → 断路 1 第三行 `return gate`(原样返回 `passed=False`)，**赦免根本不触发**。

**断路 3 — 即便赦免成功也被机制 B 覆盖(执行顺序)**
`entry.py` 执行序：`:153 provisional 赦免`(设 `passed=True`) → **再到** `:203 机制 B`。
机制 B 检查 `trade_prediction_contract_status != "ready"` 时**无条件覆写** `"passed": False`
(`entry.py:211`)。所以即使某候选侥幸通过断路 1/2 拿到 `provisional_pass=True`，
也会在 :203 被打回 False。

**结论**：observe-first 在实现上**形同虚设**——观察赦免要么因失败码不在白名单而不触发，
要么触发后被后置的机制 B 撤销。这就是"observe-first 开着却仍全拦"的原因，
也是根治时**机制 B 必须改成不覆盖 `provisional_pass`** 的硬性理由。

## 五、回答三个问题

1. **为什么全拦**
   = A(默认 record-only 不放行) + B(纯回测候选预测契约恒 rejected) +
   D&E(评级门数学死锁，C 级 < S 级要求) + C(脚本激活晋升门硬拦)。
   五重叠加，任一即可全拦。

2. **为什么要拦**
   设计意图是风控 / 反过拟合：hard_constraints 红线(回撤>50%、负收益、零交易)、
   要求"可交易的预测契约"、要求统计可信的盈利证据(LCB 95%)。**动机正确**，
   但把"晋升级证据"误用为"准入级硬条件"，并叠加了不可达的评级上限。

3. **为什么没进孵化就要求证明赚钱能力**
   = 机制 C 的**位置/激活时机错误** + 机制 D&E 的**评级错配**：
   赚钱证据(30+ 预测样本、LCB≥0.55)本应在孵化期产生、晋升时校验，
   却被启动脚本在准入期就激活；同时评级门要求纯交易策略达到它数学上不可能的 S 级。
   → 未孵化策略拿不出它不可能有的证据，自锁。

## 六、根治方案（代码 + 启动脚本两端，从逻辑上杜绝）

**总原则**：保留风控红线(hard_constraints)，把"盈利证据"要求**移回它本该在的晋升阶段**；
准入阶段只看回测健康度 + 结构契约；纯交易/纯回测候选以**观察(diagnostic)身份**进孵化，
由孵化期积累真实 direction/confidence/预测样本，晋升门再用积累证据判定盈利能力。

> 口径确认：用户已选定机制 B 采用「降级为观察身份放行」，不采用「准入即自动兜底 direction/confidence」(避免注入虚假预测语义污染晋升证据)。

### 改动 1 — 机制 A：record-only 默认翻转
**文件**：`_runtime_toggles.py:232`
- `default=True` → `default=False`
- 理由：record-only 是诊断/灰度用途，不应是常态默认。

### 改动 2 — 机制 B（核心）：预测契约非 ready 时分级处理，不再硬拒
**文件**：`submission_gate/runner_parts/entry.py:203-217` 与 `normalizers.py:445-462`

**判定条件(可直接落地)**：在 entry.py:203 的分支前，先对契约失败做"缺失 vs 损坏"分类。
依据 `freeze_trade_prediction_contract` 已返回的 `reject_reasons`(`trade_prediction_contract.py:743-749`)：
- `missing:<field>` = 派生缺失(纯回测候选无预测语义) → **可降级放行**
- `invalid:contract_version` / `invalid:direction` / `invalid:confidence` = 显式契约字段非法 → **仍硬拒**

```
status = trade_prediction_contract_status
reject_reasons = semantic_runtime_context.get("trade_prediction_contract_reject_reasons") or []
has_invalid = any(str(r).startswith("invalid:") for r in reject_reasons)
contract_source = (semantic_runtime_context 或 contract).get("contract_source")
is_derived = (contract_source == "derived_from_legacy_contract")

if status == "ready":
    pass                                   # 正常放行,不变
elif has_invalid:
    passed = False                         # 损坏契约仍硬拒(保留)
else:  # 全为 missing:* 且 is_derived 的派生缺失
    # 不再覆写 passed;保留统计门结果
    diagnostic_only = True
    review_mode = "incubation_only"
    warnings += ["trade_prediction_contract_not_ready", *reject_reasons]
    # 关键:不得把 trade_prediction_contract_not_ready 加进 hard_fail_reasons
```

**两处必须同步改，否则无效**：
1. `entry.py:203-217`：把无条件 `"passed": False` 改为上面的分级；
   **且不得覆写已有的 `provisional_pass=True`**(否则四点五断路 3 仍在)。
2. `normalizers.py:445-462` `_resolve_semantic_runtime_context`：
   `if trade_prediction_contract_status != "ready": hard_fail_reasons.append(...)`
   改为仅在 `has_invalid` 时加 `hard_fail_reasons`，否则加 `warnings`。
   (此处 hard_fail_reasons 会被上层 `_gate_a_payload`/`_gate_b_payload` 当 reject blocker，必须降级)

### 改动 3 — 机制 D&E：放宽准入评级（已定值）
**定值决策**：`MIN_VALIDATION_GRADE` 由 `"S"` 改为 **`"C"`**。
理由：交易感知评级数学上限为 C(`trade_profile.py:85`)，设 C 可让满足交易证据(evidence_score≥5.0)
的策略恰好达标进 incubation；低于 C(即 D/无评级)仍被拦，保留对劣质策略的过滤。

- **代码侧**：`_runtime_toggles.py:226` `os.getenv("STRATEGY_FACTORY_MIN_VALIDATION_GRADE", "S")` → 默认 `"C"`。
- **启动脚本侧**：四个脚本里的显式 `="S"` 同步改 `="C"`(见改动 5)。
- **不改** `trade_profile.py:85` 的 C 上限：保持交易策略评级语义不变,仅放宽准入门。
- `incubation`/`live` 仍可保留更高 committee/promotion 阈值(`_review_gate_thresholds`)，
  本改动只确保策略**能进 incubation 观察**，不降低后续晋升标准。

### 改动 4 — 机制 C：晋升门留在晋升阶段，准入期不激活
**文件**：启动脚本
- 准入期不应 `STRATEGY_TRADE_PREDICTION_PROMOTION_GATE_ENABLED=1`；
  该门应仅在孵化后的 live-ready 晋升评审生效(代码默认 False 即正确语义)。
- 若需保留晋升期硬拦，确保它只作用于已积累 30+ 样本的孵化后策略。

### 改动 5 — 启动脚本全面核查
**文件**：`start_three_factories.ps1` / `.sh` / `scripts/factories/run_three_factories.py` /
`run_three_factories_24h.ps1`
- `STRATEGY_FACTORY_GATE3_RECORD_ONLY_ENABLED` → 不设或 `0`
- `STRATEGY_FACTORY_MIN_VALIDATION_GRADE` → `C`/`D`(见改动 3)
- `STRATEGY_TRADE_PREDICTION_PROMOTION_GATE_ENABLED` → 准入期不设(见改动 4)
