#### Q1 深入诊断（2026-06-12，代码级根因，非"质量太差"）
逐层用真实数据排除假设：
1. **数据量充足**：factor_ic_history 63 个因子，57 个 IC 历史 ≥60 行（满足 strict 的 min_ic_history_rows=60）。
2. **截面充足**：validation universe 实测 4173 只合格股票、抽样 300 只（MIN=120），无 warnings。
3. **历史质量够**：用 factor_ic_history 算，strict 门下 **21 个因子全项达标**（ic_ir≥0.25 等）。
   → 推翻"因子质量太差"假设：明明有 21 个合格因子，active 却是 0。
4. **真正根因 = 鸡生蛋死锁**（代码定位）：
   - `factory._validate_batch`(factory.py:393) 对候选做**当轮实时严格验证**，要求 grade A/B
     且 `_has_admissible_ic_evidence`。
   - `evaluate_validation_evidence`(quality.py:165) 要求 `ic_history_rows ≥ 60`，
     而该值取自 `persisted_outputs.ic_history_rows`(factor_validation_pipeline.py:419-429)——
     **是本轮验证窗口新产生的 IC 天数，不是 DB 累计**。
   - 单轮 lookback=220bars / horizon=10d，`cross_section.dates` 最多几十天 < 60
     → `ic_history_rows_below_min` → evidence 不过 → 即使 grade A/B 也被拦 → validated=0。
   - 即：**要进 active 需 ≥60 行本轮 IC，但本轮 IC 不可能一次产 60 行** → 与孵化 effective_n 死锁同构。
- 结论：这是**代码级晋升死锁**，不是质量问题。修法方向：`evidence` 校验的 `ic_history_rows`
  应读 **DB 累计历史**（factor_ic_history 该因子总行数），而非本轮新增；或对"已有充足历史"的因子
  走累计评估路径。属可修的代码缺陷。
