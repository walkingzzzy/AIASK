## 6. 发现的问题

### P-1（核心待观察）：observe 池仍未见 formal 转正，auto_promoted=0
- 现象：前 7 轮 `incubating` 恒为 2、`auto_promoted=0`、`stage_counts` 全是 `warmup×302`；
  同时 `observe_active` 单调增长（2587→2630，每轮 +7）。
- 强化判断（7 轮证据）：observe 池**只进不出且单调膨胀**。这与历史"旧问题 C"形态一致，
  但根因不同——修复后 remediation 能补 runtime 契约，但历史 2600+ 存量样本绝大多数仍
  不满足完整 formal readiness（缺真实前向证据 / strict gate / measured profile），故转正恒 0。
- 风险：若放任，observe 池规模将随轮次无限增长。这是比"单轮不转正"更明确的**系统性容量问题**。
- 待观察：warmup 自适应门（low/medium bucket 降到 30/45）需 observe 样本积累足够前向样本后才生效；
  本验证窗口（30 轮）内每轮仅 +7 新样本，存量样本的前向证据增长缓慢，**预计 30 轮内难见首个转正**。
  这是诚实预期，不是修复失败——转正需真实运营时间积累。

### P-2：LLM endpoint partial_llm 降级
- 现象：`factory_result.success=False, error=status=partial_llm`。工厂仍产出候选（rule-first 生成兜底），
  但 LLM 增强部分降级。
- 影响：不阻断漏斗（spawned/submitted 正常），但 LLM 候选质量增量受限。属外部 endpoint 稳定性，非本次修复范围。

### P-3：round_NNN.json 不含 gate_3 明细（记录局限）
- 现象：round json 的 `factory_result.data` 只存 `{elapsed_seconds, run_id, status}`，gate_3 明细仅在运行日志。
- 影响：逐轮 json 无法独立复盘 gate 数据，需结合 `logs_verify30.log`。本文档已从日志补齐。

### P-4：recompile remediation 阶段在真实 session 缺可观测日志（我的代码缺陷）
- 现象：`_run_recompile_remediation` 正常路径不打 info 日志（仅异常时 warning）。
  冒烟 dry_run 实测它有效（scanned=50/recompiled=6），但真实 session 日志里**无法确认它每轮真扫了多少、补了多少**。
- 影响：remediation 这种有副作用的阶段缺乏可观测性，无法从日志验证 30 轮里它的实际效果。
- 处置：属我新增代码的可观测性缺陷，应补一行 info 日志（scanned/recompiled/promoted）。
  已记录，待用户确认后修（用户当前选择"先记录"）。
- 备注：不影响孵化侧记录（incubation_result 的 verification/pipeline/backlog 完整）。
