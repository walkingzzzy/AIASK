# 面向 AI 调用的 MCP 服务优化方案

日期：2026-04-01

## 1. 背景与核心判断

本方案面向的是“给 AI 调用的 MCP 服务”，不是单纯面向人的量化平台或网页产品。因此，评估重点不应只看“有没有功能”，而应看：

- AI 能否低成本发现正确工具。
- AI 能否稳定拿到结构化、可验证、可追溯的结果。
- AI 能否安全地把多个工具串成闭环工作流。
- 写操作、风控、审计、幂等、降级信息是否对 AI 明确可见。

基于当前仓库代码和 2026-04-01 的补充联网检索，我的综合判断是：

1. 当前仓库并不缺少大量股票/量化功能，真正的主要欠缺是“AI 友好的 MCP 服务标准化与工作流产品化”。
2. 现状更像“功能丰富但接口表面过厚、契约不完全统一、质量与来源信号分散”，导致 AI 调用成本高、误用概率高、可验证性不足。
3. 股票分析、数据质量、预测分析、因子挖掘、交易策略上的短板仍然存在，但更适合被表述为“MCP 服务对 AI 暴露的欠缺”，而不是传统平台意义上的“没有能力”。

以下结论中，涉及“行业成熟做法”的部分，属于我基于源码证据与官方文档的综合推断。

## 3. 当前真正的欠缺

### 3.1 从 MCP 视角看的核心欠缺

| 维度 | 当前情况 | 实际欠缺 | 对 AI 调用的影响 |
| --- | --- | --- | --- |
| Tool 表面设计 | 大量能力挂在 `quant_manager`、`strategy_manager` 等 manager 下 | tool 过粗，AI 需要先学 action 词典再学参数细节 | 误选 action、漏参数、规划成本高 |
| 契约一致性 | 已有 manager contract 与 `normalize_manager_payload` | 仍有不少 manager / helper 保留自定义 `_normalize_kwargs` 或签名差异 | AI 对不同 manager 的调用心智不统一 |
| 结果结构化 | 局部已有 `trace_id`、`source_chain`、quality meta | 核心工具尚未形成统一结果信封与统一 schema | AI 难以稳定解析、比较、重试与追踪 |
| Tool 可发现性 | 有 `search.py` 和 `resource://server/capabilities` | 缺少“面向 AI 的工具目录”，没有统一给出必填参数、示例调用、副作用级别、时效性、输出 schema | AI 发现工具后仍然不会放心调用 |
| Resources / Prompts | 已有少量资源与 prompt | 相比工具规模仍偏轻，不能充分承载“上下文对象”和“标准工作流模板” | AI 需要靠自然语言猜测，而不是消费服务端准备好的上下文 |
| 写操作语义 | 局部有确认与审计，例如 live trading | 缺少跨 manager 的统一 side-effect 级别、幂等键、审计回执 | AI 难以安全执行写操作 |
| 工作流产品化 | 现有能力多为原子工具或 manager action | 缺少面向 AI 的显式 workflow tools | 工作流编排大量依赖模型临场发挥 |
| 评测与治理 | 有质量门、部分验证与回放 | 缺少专门针对“AI 调用正确率”的 eval harness | 难以量化优化是否真的让 AI 更会用 |

### 3.2 领域视角下的实际欠缺

| 领域 | 当前实现 | 实际欠缺 | MCP 化改造方向 |
| --- | --- | --- | --- |
| 股票分析 | 已有决策、行情、基本面、研究工具 | `packages/akshare-mcp/src/akshare_mcp/tools/_decision_buy.py` 仍含 `logit(score,confidence,volatility)` 与 `decision_threshold_bucket_backtest_proxy` 这类启发式/代理证据 | 把“结论”拆成结构化证据树、置信度、替代情景、证据来源链 |
| 数据质量 | 已有 response-level quality meta、validators、data sync | 更像响应元信息与校验辅助，尚未形成 dataset contract / expectation / checkpoint / data docs 级闭环 | 默认输出 dataset_id、quality_score、validation_run_id、修复建议 |
| 预测分析 | 已有轻量概率校准服务 | `packages/akshare-mcp/src/akshare_mcp/services/probability_calibration.py` 明确写了“轻量实现，生产建议用 `CalibratedClassifierCV` + isotonic/sigmoid” | 建立统一 calibration / uncertainty / lineage 契约 |
| 因子挖掘 | 是当前最强方向之一 | fallback、默认 universe、候选治理、研究记忆虽然存在，但还没完全抽成“AI 直接调用的因子工作流产品” | 提供候选生成-验证-入池-回放的一键 workflow tool |
| 交易策略 | 已有工厂门禁、运行态、评审与孵化 | 统计门槛、成交模型、成本假设与晋级标准仍偏轻；`cost_model.py` 默认回测 `slippage_bps=0`、`market_impact_bps=0` | 把执行现实性、成本模型、promotion gate 做成显式可调用对象 |

## 4. 关键源码证据

### 4.1 manager 契约已写，但执行层尚未完全一体化

- `packages/akshare-mcp/MCP_MANAGER_CONTRACT.md`
  - 已规定统一签名：`action + params + kwargs + code`。
- `packages/akshare-mcp/src/akshare_mcp/tools/manager_protocol.py`
  - 已提供统一归一化与 meta 构造。
- 但从 manager 搜索结果看，多个 manager / helper 仍保留自定义 `_normalize_kwargs`，且 `strategy_manager` 的签名形式与统一契约并不完全一致。

这说明：规范已经有了，但真正做到“所有 AI 入口一致”还差最后一层收口。

### 4.2 output schema 的实践还没有覆盖核心业务工具

- 从仓库搜索结果看，`output_schema` 的显式使用主要集中在：
  - `packages/akshare-mcp/src/akshare_mcp/tools/skills_registry.py`
- inspected core managers / major tools 中，尚未看到同等普遍程度的 `outputSchema` / `structuredContent` 设计。

这意味着：当前最值得优先做的，不是继续加更多工具，而是把高价值工具的输出模式做成 MCP 原生友好格式。

### 4.3 局部质量与来源信号已有良好基础

- `packages/akshare-mcp/src/akshare_mcp/tools/data_quality.py`
  - 已支持 `quality_flags`、`source_chain`、`minimum_quality_threshold` 等。
- `packages/akshare-mcp/src/akshare_mcp/tools/_decision_buy.py`
  - 已有 `trace_id`、`source_chain`、`prediction_quality`。
- `packages/akshare-mcp/src/akshare_mcp/tools/market/kline.py`
  - 已把数据源链路与质量状态带回结果。

这说明：仓库不是“没有 provenance”，而是“provenance 还没变成服务默认面”。

### 4.4 研究与策略闭环已有雏形，但默认约束还偏轻

- `packages/akshare-mcp/src/akshare_mcp/services/factor_scheduler.py`
  - 仍使用固定 `DEFAULT_UNIVERSE` / `DEFAULT_FACTORS`。
- `packages/strategy-factory/src/strategy_factory/application/quality_gates.py`
  - Gate-1 依赖 representative stocks + `avg_sharpe`。
- `packages/akshare-mcp/src/akshare_mcp/services/cost_model.py`
  - execution 默认 `slippage_bps=5.0`、`market_impact_bps=3.0`。
  - backtest 默认 `slippage_bps=0.0`、`market_impact_bps=0.0`。
- `packages/akshare-mcp/src/akshare_mcp/services/pit_utils.py`
  - PIT 工具存在，但直接集成仍偏少。

这说明：当前更像“研究可跑通”，但距离“AI 可安全复用的标准化生产工作流”还差一层制度化封装。

## 5. 补充联网检索后的外部基线

以下链接均为 2026-04-01 检索到的官方或一手来源。

### 5.1 MCP 官方规范给出的直接启发

- MCP Tools（latest 2025-11-25）
  - `tools/list` 支持分页。
  - tool 定义支持 `inputSchema`、`outputSchema`、`annotations`、`execution.taskSupport`。
  - `structuredContent` + `outputSchema` 能显著提高客户端和 LLM 的可解析性。
- MCP Resources（latest 2025-11-25）
  - resources / templates / content blocks 支持 `audience`、`priority`、`lastModified` 注解。
  - `resources/list_changed` / `resources/templates/list` 可提升动态发现体验。
- MCP Prompts（latest 2025-11-25）
  - prompts 是 user-controlled 的。
  - prompt 参数、embedded resources、annotations 都是标准能力。
- MCP Security Best Practices
  - 明确强调 confused deputy、token 透传、SSRF、scope minimization 等风险。
  - 对于敏感操作，应把权限边界、确认、最小授权和服务端治理做清楚。

对本仓库的直接含义是：

1. 不能只做“能调通的 tool”，还要做“AI 易发现、易验证、易治理的 tool”。
2. 不能只返回文本，应该系统性提供 `structuredContent` / `outputSchema` / annotations。
3. 不能只靠 prompt 约束高风险操作，必须把 side-effect 语义做进协议层。

### 5.2 数据质量与 PIT 基线

- Feast 官方文档强调 point-in-time correct joins，并通过 `get_historical_features` 复现过去时点的特征状态，还强调 TTL 相对事件时间而不是当前时间。
- Feast 官方教程中直接把“用 Great Expectations 验证历史特征”列为实践路径。
- Great Expectations 官方文档强调数据验证工作流的基本模式：定义 Expectations、运行 Validations、通过 Checkpoint 执行动作，并更新 Data Docs。

对本仓库的直接含义是：

1. `pit_utils.py` 不应只在少数路径被显式使用，而应成为预测/回测/因子验证工具的默认能力。
2. 数据质量不应只停留在 response meta，而应升级到 dataset contract、validation run、checkpoint result、可读报告。

### 5.3 预测分析与不确定性基线

- scikit-learn 官方文档明确将 `CalibratedClassifierCV` 作为标准概率校准方案，支持 `sigmoid` 与 `isotonic`，并通过交叉验证保证校准数据无偏。
- MAPIE 官方文档强调 conformal prediction / prediction intervals / prediction sets / risk control，可对回归、分类、时间序列提供分布无关的不确定性估计。

对本仓库的直接含义是：

1. 当前轻量 `probability_calibration.py` 很适合作为 MCP 内部快速实现，但不应成为最终生产级默认路径。
2. 对 AI 暴露的预测工具，应默认带出 calibration report、coverage / interval / set size 等不确定性指标，而不是只给单点概率。

### 5.4 因子与研究工作流基线

- Qlib Workflow 官方文档强调 workflow / task / record / recorder 的实验管理思路。
- RD-Agent 官方仓库强调自动化 data-driven R&D、可执行因子/模型实现、trace viewing、量化场景多 agent 协同。
- AlphaAgent（arXiv:2502.16789v2，2025-06-09）强调：
  - originality enforcement
  - hypothesis-factor alignment
  - complexity control
  - 目标是降低 alpha decay 与 crowding

对本仓库的直接含义是：

1. 因子挖掘不应只暴露“生成一个候选因子”，而应显式暴露“研究轨迹、原创性、复杂度、验证结果、入池状态、衰减风险”。
2. 若服务目标是给 AI 调用，那么“trace artifact”与“研究留痕对象”本身就应该是 MCP 资源，而不是只存在数据库或日志里。

### 5.5 策略执行与现实建模基线

- QuantConnect 官方文档强调：
  - event-based / timeslice 模型用于防止 look-ahead bias。
  - slippage model 可定制，默认 brokerage model 也会设置相应行为。
  - equity fill model 对开盘/收盘撮合、bid/ask、tick / quote / trade bar 有明确细则。

对本仓库的直接含义是：

1. `backtest` 默认零滑点/零冲击虽然便于研究，但不应作为 AI 默认看到的“可信现实假设”。
2. 策略与执行工具需要把 fill assumption、slippage assumption、market impact assumption 显式结构化返回给 AI。

### 5.6 试验追踪与模型治理基线

- MLflow Tracking 官方文档强调 run / experiment / dataset / model checkpoint 的统一追踪。
- MLflow Model Registry 官方文档强调 model lineage、model version、alias、tag、annotation、champion 指针等治理能力。

对本仓库的直接含义是：

1. 当前的 `model_registry` / `champion_challenger` 方向是对的，但还需要把 dataset、run、artifact、model、strategy 的关系打透。
2. AI 调用结果必须能返回“这次结论来自哪个 run / dataset / model / validation”。

## 6. 优化原则

### 原则 A：先做 AI 友好的薄封装，不要一上来拆光所有 manager

优先在现有能力之上加一层“窄工具 + 统一结果契约 + 工作流工具 + 目录资源”，而不是先进行大规模内部重构。

### 原则 B：默认返回结构化对象，而不是让 AI 从文本里猜

高价值工具应优先补齐：

- `inputSchema`
- `outputSchema`
- `structuredContent`
- `meta.trace_id`
- `meta.source_chain`
- `meta.quality`
- `meta.side_effect`
- `meta.idempotency_key`
- `meta.degraded`

### 原则 C：把“研究闭环”做成服务对象，而不是隐藏在隐式流程里

AI 需要的不是更多 action 名，而是更少但更完整的工作流接口。

### 原则 D：默认 no-leakage / provenance-first / safe-write

PIT、质量校验、审计、幂等、确认门禁应成为默认行为，而不是可选附加项。

## 7. 分阶段优化方案

### 7.1 P0（1-2 周）：先把 AI 可调用性做对

#### P0-1 新增面向 AI 的窄工具

保留现有 manager，但新增一批高频 workflow tools：

- `analyze_stock_workflow`
- `factor_candidate_workflow`
- `strategy_review_workflow`
- `prediction_diagnosis_workflow`
- `data_quality_workflow`

目标是把“AI 最常走的 5 条路径”从多次 manager/action 试探，收敛为少量标准入口。

#### P0-2 新增 Tool Catalog 资源

新增类似 `resource://server/tool-catalog` 的资源，按工具输出：

- tool 名称与用途
- 必填参数
- 参数示例
- 返回 schema 摘要
- side-effect 级别
- freshness expectation
- 失败码与重试建议
- 常见调用顺序

当前 `resource://server/capabilities` 只能给出能力总览，不足以让 AI 正确选择与正确调用。

#### P0-3 统一结果信封

把所有核心工具统一为：

```json
{
  "success": true,
  "data": {},
  "error": null,
  "error_code": null,
  "meta": {
    "trace_id": "tool:action:timestamp",
    "source_chain": [],
    "quality": {},
    "side_effect": {
      "level": "read_only|stateful|external_write|trade_risk"
    },
    "idempotency_key": null,
    "degraded": false,
    "latency_ms": 0
  }
}
```

重点不是换字段名，而是让 AI 可以跨工具稳定解析。

#### P0-4 统一写操作语义

对所有 stateful / write / external tools 统一补齐：

- `dry_run`
- `confirm_token` / confirmation policy
- `idempotency_key`
- `audit_event_id`
- `side_effect.level`
- `side_effect.target`

不要只在个别 live trading 场景做确认门禁。

#### P0-5 资源与提示词补强

新增资源：

- `resource://workflow/stock-analysis-guide`
- `resource://workflow/factor-governance-guide`
- `resource://workflow/strategy-promotion-guide`
- `resource://run/{run_id}`
- `resource://dataset/{dataset_id}/quality`

新增 prompts：

- `stock-analysis`
- `prediction-diagnosis`
- `factor-registry-review`
- `strategy-promotion-review`

#### P0-6 建立 AI 调用评测

构建 tool-calling eval harness，最少覆盖：

- 发现正确工具
- 参数是否正确
- 是否选择了安全模式
- 是否能够识别 degraded / fallback
- 是否能把多步 workflow 串起来

### 7.2 P1（1-2 个月）：把质量、PIT、lineage 做成默认能力

#### P1-1 PIT 默认化

对以下工具默认接入 PIT 语义：

- 因子验证
- 特征构造
- 预测训练 / 预测诊断
- 回测
- 策略评审

所有相关结果带出：

- `as_of`
- `event_time`
- `feature_time_window`
- `pit_passed`

#### P1-2 建立统一 run / dataset / model / strategy lineage

建议引入统一 lineage 记录层，最少标记：

- `run_id`
- `parent_run_id`
- `dataset_id`
- `validation_run_id`
- `model_id`
- `factor_candidate_id`
- `strategy_id`
- `promotion_review_id`

这样 AI 的每次结论都能回溯到对象级证据。

#### P1-3 概率校准与不确定性标准化

把预测返回升级为：

- calibrated probability
- raw probability
- calibration method
- calibration sample size
- ECE / Brier / reliability summary
- prediction interval / prediction set
- coverage target / realized coverage

#### P1-4 因子工作流标准化

给因子挖掘补齐下列结构化字段：

- originality score
- crowding proxy
- complexity score
- hypothesis alignment
- validation summary
- registry status
- decay monitor status

#### P1-5 策略现实性增强

将以下对象显式化：

- fill model
- slippage model
- market impact model
- liquidity gate
- promotion gate threshold

让 AI 不会把“研究态通过”误解为“可上线执行”。

### 7.3 P2（2-3 个月及以后）：平台化与生态对齐

#### P2-1 选择性引入外部成熟组件

可选集成：

- Feast：feature / PIT / historical retrieval
- Great Expectations：Expectation / Validation / Checkpoint / Data Docs
- MLflow：experiment tracking / model registry / dataset linkage
- MAPIE：conformal uncertainty

注意：这一步是可选的平台增强，不是 P0 的前置条件。

#### P2-2 引入更强的衰减与监控治理

包括：

- factor decay monitor
- crowding monitor
- model drift / calibration drift
- strategy runtime health
- online/offline consistency check

#### P2-3 构建“研究对象资源层”

把 factor / model / dataset / strategy / review / experiment 真正做成可订阅、可读取、可组合的 MCP resources，而不是零散 API 返回值。

## 9. 验收标准

如果优化成功，至少应达到以下效果：

1. AI 在不阅读超长 manager help 的前提下，能发现并正确调用高频工作流工具。
2. 高频任务在 1-3 次调用内完成，而不是靠多轮试错。
3. 所有核心结果都能稳定返回统一结构化 meta。
4. AI 能明确知道某个结果是否 degraded、是否走了 fallback、是否满足最低质量门。
5. 所有写操作都带 side-effect 等级、确认机制、审计回执与幂等键。
6. 因子、预测、策略相关结论都能追溯到 run / dataset / model / review。
7. 回测与执行的现实假设对 AI 是显式可见的。

## 10. 排期建议

建议采用“两层推进”：

- 第一层：P0 薄封装
  - 先让 AI 好用、稳定、安全。
- 第二层：P1/P2 平台化
  - 再逐步把 PIT、lineage、quality、uncertainty 和更强治理沉到底层。

不建议一开始就做“全量 manager 重构”。更高 ROI 的做法是：

1. 先在现有仓库上补 AI-facing facade。
2. 再把被 facade 证明稳定的契约慢慢下沉到所有 manager。
