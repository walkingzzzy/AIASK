## 一、结论先行

这次代码核验后的结论很明确：

1. 当前策略工厂不是“缺一套工厂主链”，而是“主链已经存在，但候选语义、验证协议和提交口径还不够硬”。
2. 旧文档里若继续把问题定义成“没有 governed pool / 没有 warmup / Gate-1 仍是裸 `strategy_type + params` / Gate-2 仍完全是单票聚合 / dedup 只能看参数相似度”，都会误导后续改造。
3. 当前最核心的结构性问题不是少几个模块，而是下面三件事同时存在：
   - 同一候选在 `research_task`、`target_symbols`、`stock_pool`、`candidate_contract`、提交落库数据之间仍会被多次重算、补字段、放宽目标池。
   - `trade_rule_validation`、`event_trade_validation`、`factor_rank_validation` 仍然存在 mixed / fallback 语义，尚未做到严格分轨。
   - 组合级验证虽然已经有 `portfolio_engine` 路径，但覆盖不稳定；部分关键路径仍允许 `proxy_aggregation`、合成事件样本或统计 fallback 参与决策。
4. 因此，本方案不应再按“从零建设工厂”来写，而应改成“收紧现有主链、消灭语义漂移、关闭 fallback 缺口”。

## 四、当前实际问题清单

### P0-1 `research_task` 到最终 `target_symbols` 仍会发生语义漂移

**代码事实**

- `targets.py::_normalize_research_task_contract()` 对 snapshot 任务默认使用：
  - `target_symbol_policy = prefer_intersection`
  - `universe_expansion_policy = allow_market_fallback`
- `targets.py::_apply_target_symbol_policy()` 明确允许：
  - `candidate_retained_without_intersection`
  - `fallback_candidate_universe`
  - `fallback_research_symbols`
- `akshare-mcp/services/_strategy_generators_context.py::_build_research_context()` 中，如果 `task_target_symbols` 在 `universe_rows` 里没有命中，`filtered_rows` 会继续沿用广义扫描结果，而不是直接阻断该任务。
- `akshare-mcp/services/_strategy_generators_specs.py::_external_candidate_to_spec()` 又会把 `research_context.candidate_universe_symbols` 作为 `fallback_symbols` 参与二次 target resolution。
- 与之相对，`stock_strategy_matrix.py::_build_task()` 已经把 bulk stock matrix 路径做成了 `strict_intersection + forbid`，说明问题并不在 bulk 路径，而在 snapshot / external LLM / shared context 路径。

**实际后果**

- 研究任务要求的目标池、生成候选实际使用的目标池、最终提交到数据库里的目标池，不一定是同一个对象。
- 当前代码虽然已经有 `target_alignment_contract`，但它还不是所有路径的唯一真源。
- 目标池漂移会直接放大后续 Gate-1 / Gate-2 / dedup / submit 的语义不一致。

**直接改造**

1. 以 `target_alignment_contract` 为唯一约束源，禁止 snapshot 定向任务继续默认走 `prefer_intersection + allow_market_fallback`。
2. 对 `targeted_snapshot` 任务，默认改成严格模式：
   - `target_symbol_policy = strict_intersection`
   - `universe_expansion_policy = forbid`
3. 对 `event_targeted` 任务，保持 `strict_intersection` 主语义，但保留当前代码已经存在的 `allow_same_theme_only`：
   - 允许的扩池仅限显式 `same_theme_symbols` / `theme_members`
   - 不再允许回退到 market universe / candidate universe
4. 若确实允许扩池，必须通过显式字段声明，不再依赖默认值或隐式 fallback。
5. `shared research context` 在定向任务目标池未命中时，应返回 `blocked_by_target_universe`，而不是回退到广义候选池。

**验收**

- 任意定向任务都能稳定追溯 `research_task.target_symbols == resolved_target_symbols == submitted_target_symbols`。
- `constraint_check.expansion_reason` 不再高频出现 `candidate_retained_without_intersection` / `fallback_candidate_universe`。

### P0-2 候选合同已经存在，但还不是全链路唯一真源

**代码事实**

- `candidate_contract.py` 已有：
  - `build_portfolio_candidate_contract()`
  - `build_candidate_contract_hash()`
  - `build_candidate_identity_signature()`
  - `build_factory_backtest_assumptions()`
- `quality_gates.py` 和 `backtest_filter.py` 已经开始围绕 contract/hash 做 Gate-1 / Gate-2。
- 但后续链路里仍存在多次再归一化 / 再构造：
  - `akshare-mcp/services/_strategy_llm_provider_normalize.py::_normalize_candidate_payload()` 会先规范 `target_symbols`、`stock_pool`、`constraint_check`。
  - `akshare-mcp/services/_strategy_generators_specs.py::_external_candidate_to_spec()` 会再次执行 target resolution，并重写 metadata。
  - `strategy-factory/application/_submitter_actions.py::_build_strategy_data()` 会把 `existing_params` 和当前 candidate merge 后再次重建 `candidate_contract_snapshot` / hash / identity。
  - `submission_gate.py` 在缺失时还会再次回算 `candidate_contract_snapshot` / hash。

**实际后果**

- 现在的问题不是“没有统一合同”，而是“统一合同存在，但多个阶段都还保留二次推导权”。
- 一旦某条路径在 normalize、spec compile、submit merge 的某一层补了默认值或保留了历史字段，就会出现“同名候选，不同交易对象”的问题。

**直接改造**

1. 在 candidate 进入 Gate-0 后就产出单一 `resolved_candidate_envelope`，至少包含：
   - `normalized_research_task`
   - `resolved_target_symbols`
   - `resolved_stock_pool`
   - `candidate_contract_snapshot`
   - `candidate_contract_hash`
   - `candidate_identity_signature`
2. Gate-1、Gate-2、Gate-3、submit、quality report 的新主链优先读取这份 envelope，不再各自重建。
3. 在历史策略 contract backfill 和 refresh 兼容桥接完成前，`_build_strategy_data()` 仍保留：
   - `existing_params` merge
   - `research_task` 归一化
   - refresh / legacy 路径的 contract snapshot 重建
4. 待 envelope 成为唯一真源、且旧策略回填完成后，再把 `_build_strategy_data()` 收窄为 persistence-only adapter。

**验收**

- 下游代码不再出现“如果缺失就重算 contract/hash”的分支。
- `candidate_contract_hash` 在生成后到落库前保持稳定不变。
- 历史策略 refresh 不会因为 envelope 改造丢失字段或破坏既有 contract 兼容路径。

### P0-3 `validation_profile` 已经存在，但 Gate-3 仍然 mixed / fallback

**代码事实**

- `submission_gate.py::run_submission_quality_gate()` 已经按 `profile` 分流：
  - `factor_rank_validation`
  - `trade_rule_validation`
  - `event_trade_validation`
  - `macro_regime_validation`
- 但 trade 主路径仍有两个实际问题：
  - 如果缺少 trade validation audit，会直接退回 `statistical_fallback`。
  - 就算走了 trade primary，仍然会合并 supplemental statistical gate。
- 这意味着 `trade_rule_validation` 和 `event_trade_validation` 还没有做到“只由交易协议决定主结论”。

**实际后果**

- 当前系统已经有 profile 概念，但不同 profile 的主判定边界不够硬。
- 一些本应因为交易审计缺失而失败的候选，仍可能通过统计 fallback 留在流程里。

**直接改造**

1. 先把下列信号提升为一等观测字段，再决定硬切范围：
   - `trade_validation_audit_missing`
   - `gate_protocol = *:statistical_fallback`
   - `supplemental_statistical_gate`
2. 分阶段收紧 trade 类 profile：
   - `live_ready_review` / `formal_incubation` lane 先改成“缺 audit 即 fail”
   - `research` lane 仅允许把 `statistical_fallback` 作为临时研究审计，不能据此声称可进入 incubation / live-ready
3. supplemental statistical gate 保留，但只进入 audit/report，不得覆盖主通过与否。
4. `gate_protocol` 必须显式区分：
   - `trade_primary`
   - `trade_primary_with_supplemental_audit`
   - `statistical_fallback_research_only`
   - `hard_fail_missing_trade_audit`

**验收**

- incubation / live-ready 路径中，不再出现“统计 fallback 通过、交易证据缺失”的通过样本。
- `quality_report` 能清晰区分主判定协议与辅助审计协议。

### P0-4 事件验证仍允许用合成样本补洞

**代码事实**

- `backtest_filter.py::_build_event_sample_metrics()` 在拿不到真实事件样本时，会进入 `_build_minimal_event_samples()`。
- 这条路径会用 target / representative / fallback 的回测结果拼装 `sample_driven_minimal` 样本。
- 后续 `event_window_metrics` 仍会带出 `event_sample_count`、`event_anchor_count`、`traceable_to_event_samples = True`。

**实际后果**

- 从结果结构上看，候选像是“有事件样本验证”。
- 但这类样本实际上可能只是从回测结果合成出来的最小替代物，并不是真正的事件研究数据集。

**直接改造**

1. `sample_driven_minimal` 只能作为审计告警，不能满足 `event_trade_validation` 的准入条件。
2. `event_trade_validation` 必须显式要求：
   - 真实 `event_id`
   - 真实时间锚点
   - 真实事件样本集合
3. 若只拿到了 minimal samples，应标记为 `event_audit_incomplete` 并直接 fail。

**验收**

- 事件类候选不再通过合成样本拿到主通过结论。
- `event_sample_source` 为 `auto_context_minimal` 的候选只能进入研究态，不得进入 incubation / live-ready 分流。

### P1-1 组合级回测路径已经存在，但覆盖仍然不稳定

**代码事实**

- `backtest_filter.py::_run_portfolio_engine_summary()` 已存在。
- `_test_one()` 已经分别尝试：
  - `target_portfolio_metrics`
  - `combined_portfolio_metrics`
- 同时仍保留：
  - `metrics_source = portfolio_engine | proxy_aggregation`
  - representative layer 永远是 `proxy_aggregation`
- 对多标的候选，如果 primary layer 没拿到真实 portfolio engine 结果，会在 Gate-2 失败为 `portfolio_engine_required`。

**实际后果**

- 当前系统并不是“没有组合级路径”，而是“组合级路径存在，但不是所有主判定都稳定走这条路径”。
- 系统会先消耗一轮回测资源，再在 Gate-2 末端发现组合级结果缺失。

**直接改造**

1. 对多标的候选，把“是否具备 portfolio engine 能力”前移到 Gate-0 / Gate-1 前。
2. 只要 profile 是 target-only / multi-name，primary metrics 就必须来自 portfolio engine。
3. representative layer 保留为辅审层，不再参与 trade 类 profile 的主通过判定。

**验收**

- 多标的候选不会再在 Gate-2 末端才以 `portfolio_engine_required` 失败。
- trade 类候选的 primary metrics 来源稳定为 `portfolio_engine`。

### P1-2 shared research context 仍可能把广义市场上下文带进定向任务

**代码事实**

- `akshare-mcp/services/_strategy_generators_context.py::_build_research_context()` 默认先做广义 universe scan。
- 当 `task_target_symbols` 过滤没有命中时，并不会直接阻断，而是继续沿用广义扫描上下文。
- `_reuse_shared_research_context()` 和 `_build_symbol_frame_cache()` 都会复用：
  - `candidate_universe`
  - `symbol_insights`
- `_strategy_generators_external.py::_build_synthetic_market_frame()` 甚至会直接用 `symbol_insights + candidate_universe` 合成市场帧。

**实际后果**

- 即使任务本身是定向的，LLM/DSL 预编译阶段仍可能拿到广义市场背景。
- 这会放大 candidate universe 对定向任务的“软扩池”效应。

**直接改造**

1. 把 research context 明确拆成：
   - `task_target_context`
   - `market_background_context`
2. 对定向任务：
   - frame cache 只允许使用 `resolved_target_symbols`
   - 不允许 silently 回退到 `candidate_universe` 和 `symbol_insights`
3. 若定向任务目标池无数据，应阻断该任务，而不是制造 synthetic broad-market frame。
4. 非定向 snapshot / broad research 路径仍可保留 `market_background_context`，但要和定向任务的 target context 明确分流。

**验收**

- 定向任务的 LLM prompt、DSL preflight、frame cache 都只围绕目标池工作。
- `research_context_summary` 能区分“target context 命中”“targeted blocked”“broad context fallback”。

### P1-3 dedup 已经比旧版本强很多，但 identity contract 仍未完全吃透存量策略

**代码事实**

- `deduplicator.py` 已有：
  - `build_candidate_identity_signature()`
  - `refresh_existing`
  - `spawn_revision_from_existing`
- 但 `existing_identity_signature` 只有在存量策略具备显式 contract 字段时才有效。
- 否则仍会退回：
  - `task_signature`
  - `target_overlap`
  - 参数相似度阈值

**实际后果**

- 对已经有完整 contract 的新候选，dedup 语义相对较好。
- 对历史数据、旧策略或 contract 字段不全的策略，仍可能出现“应 revision 却 refresh”、“应独立候选却被判重复”的情况。

**直接改造**

1. 对历史策略做一次 contract backfill：
   - `candidate_contract_snapshot`
   - `candidate_contract_hash`
   - `candidate_identity_signature`
   - `target_pool_id`
2. dedup 主判定改成优先比较：
   - `candidate_identity_signature`
   - `candidate_contract_hash`
   - `lineage.target_pool_id`
3. `task_signature` 与 `target_overlap` 退为辅判定，不再作为主语义来源。

**验收**

- `refresh_metrics_only` 的触发必须建立在 identity 不变前提下。
- `spawn_revision_from_existing` 的触发主要由 identity / lineage 变化决定，而不是仅靠相似度阈值。

### P2-1 governed pool / warmup / allocation 已经落地，剩余问题是硬化而不是重建

**代码事实**

- `cycle_runner.py`、`readiness_service.py`、`_factory_scheduler_loop.py` 已有：
  - startup warmup
  - readiness score
  - governed pool runtime state
  - refresh trigger

  - governed candidate pool
  - model registry lineage
  - budget feedback
  - `stock_family_allocation`

**正确的改造方向**

- 不再把“实现 governed pool / warmup / stock family allocation”写成新增任务。
- 剩余工作应是：
  - 强化这些模块之间的唯一语义边界
  - 明确 fallback 时的运行状态
  - 建好针对 drift / fallback 的监控指标

**验收**

- 文档与任务拆解里不再出现“从零建设 governed pool 主链”的表述。
- `governed_candidate_pool_active`、`runtime_state`、`allocation_source_mode` 都成为一等指标。

### P2-2 运行观测层已经存在，但还没有把关键 fallback 模式暴露成一等信号

**代码事实**

- `strategy_ai.py` 已经对：
  - `strategy_generation_experiments`
  - `strategy_task_runs`
  - `strategy_factory_runs`
  做了 JSON 压缩 / summary 化落库。
- 这说明观测底座存在，但当前 summary 仍未把下列关键语义稳定暴露出来：
  - `resolved_target_source`
  - `event_sample_source`
  - `event_study_mode`
  - `trade_validation_audit_missing`
  - `alignment_contract_reject_reasons`
  - `portfolio_engine_required`

**实际后果**

- 运行面能看到“工厂跑了”，但不容易直接看出“到底是 target drift、trade audit 缺失、event sample 合成，还是 portfolio engine fallback”。

**直接改造**

1. 把上述 fallback / reject / drift 字段提升为 stage summary 的固定字段。
2. 工厂 run detail 必须能直接回答：
   - 为什么被挡
   - 挡在什么协议
   - 是否因为 fallback 触发了保守失败

**验收**

- 不再需要翻原始 payload 才能判断本轮失败究竟属于 target drift、event minimal sample 还是 trade audit 缺失。

---

### P3-1 runtime / paper 反馈回路已经起步，剩余问题是从“建议权重”升级到“硬调度权”

**代码事实**

- `factor_research.py::_load_budget_feedback()` 已经读取：
  - incubation metrics
  - runtime alerts
  - risk events
- 这些反馈已经进入：
  - family feedback
  - target pool feedback
  - generator mode feedback
  - stock family allocation budget

**实际问题**

- 当前反馈回路更像“调权重”和“调 penalty”，还不是硬门禁。
- 某个 family / target pool / generator mode 即便运行时风险很差，也未必会被明确冷却或暂停。

**直接改造**

1. 在现有 feedback 之上增加：
   - cooldown
   - suppress
   - target_pool freeze
   - generator_mode freeze
2. 让调度层直接读取这些状态，而不只是消费一个柔性 multiplier。

**验收**

- 高告警 family / target pool 不只是“预算变小”，而是能被明确抑制出现在下一轮生成计划里。

## 五、更新后的 P0-P3 路线

### P0：先收紧语义，不再继续重写底座

1. 固化 `target_alignment_contract` 为唯一 target 约束源：
   - `targeted_snapshot` 禁止默认扩池
   - `event_targeted` 仅保留显式 same-theme 扩池，不再允许 market fallback

3. 分阶段将 trade 类 profile 改成“缺 audit 即 fail”，先收紧 incubation / live-ready，再关闭 `statistical_fallback` 主判定通道。

### P1：收紧验证对象，避免 broad context 和 proxy 混入主结论

1. 将组合级 capability 检查前移，避免多标的候选走到 Gate-2 末端才失败。
2. 对定向任务禁用 broad market context fallback。
3. 对历史策略补齐 identity contract，收紧 dedup / refresh / revision 语义。

### P2：把已有底座改成可运维、可诊断的主链

1. 不再重建 governed pool / warmup / allocation，只做硬化和监控。
2. 将 drift / fallback / protocol mismatch 提升为 run summary 的一等信号。

### P3：把现有 feedback loop 从柔性建议升级为硬调度策略

1. runtime / paper 的负反馈可以直接触发 cooldown / suppress / freeze。
2. 调度层对 family / target pool / generator mode 具备明确的停启权。

## 九、最终判断

当前策略工厂的真实状态可以概括为：

```text
主链已存在
  + warmup / readiness / governed pool / allocation 已接线
  + candidate contract / hash / identity / Gate-1 / Gate-2 / Gate-3 已存在
  + dedup refresh / revision / submit lane / live-ready / multiple-testing 已存在
  - 但 research_task 到 submitted strategy 的语义仍会漂移
  - 但 validation_profile 仍 mixed / fallback
  - 但组合级验证与事件验证仍允许 proxy / minimal sample 参与主结论
```

所以，下一轮改造的正确方向不是“继续补更多工厂模块”，而是：

1. 让 target 语义收紧到唯一真源。  
2. 让 candidate contract 成为全链路唯一对象。  
3. 让 trade / event / factor 三类验证协议彻底硬分轨。  
4. 让 portfolio engine 与真实事件样本成为主判定前提，而不是可选增强项。  

只有这样，策略工厂才会从“已经能跑的研究候选工厂”，升级成“语义一致、验证一致、提交一致的真实策略工厂”。
