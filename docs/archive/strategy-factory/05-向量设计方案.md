# 向量设计方案（现状兼容与分期演进）

> 本文档只描述两类内容：
> 1. 当前仓库已经存在的向量能力与接入边界；
> 2. 基于当前工厂主链路整理出的向量判重与检索演进方案。

## 2026-03-21 校准补充

- 当前向量层的正确定位是“**辅助去重与辅助画像证据层**”，而不是策略定义正确性的主判据。
- 在策略对象、目标池约束和质量门禁口径尚未补齐之前，不能让向量相似度承担本应由 `target_symbol_policy`、行为语义、交易成本与容量约束负责的判断。
- 因此向量方案的短期重点应是“解释性更强、误杀更少、与主链一致”，而不是优先追求持久化向量库规模和 ANN 指标。

## 1. 文档定位与边界

- 本文档属于 `策略工厂/` 下的**落地方案文档**，用于排期、评审与后续实施。
- 任何涉及 `pgvector/HNSW`、策略交易行为 embedding、跨会话持久化向量库的内容，默认都属于**中长期规划**，不能写成当前已实现。
- 当前判断一律以以下代码为准：
  - `packages/akshare-mcp/src/akshare_mcp/services/vector_search.py`
  - `packages/akshare-mcp/src/akshare_mcp/services/strategy_factory.py`
  - `packages/akshare-mcp/src/akshare_mcp/services/vector_platform.py`
  - `packages/akshare-mcp/src/akshare_mcp/storage/timescaledb/strategy.py`
  - `packages/akshare-mcp/src/akshare_mcp/tools/vector.py`

## 2. 当前代码基线

### 2.1 当前已实现的向量能力

当前仓库已经存在“向量检索 + 策略画像”两层能力，它的真实定位应表述为：

- 面向 **K 线形态 / 收益率序列 / 技术特征** 的相似度检索
- 当前支持的向量化方法：`price_volume`、`ohlc`、`returns`、`technical`
- 当前支持的相似度：`cosine`、`euclidean`、`correlation`
- 当前支持的检索后端：`python`、`index`
- 其中 `index` 当前仍是**进程内 `pattern_cache` 字典索引**，不是数据库向量库
- 额外存在 `find_similar_patterns_dtw()`，用于不同长度序列的 DTW 相似匹配
- `StrategyVectorPlatform.build_strategy_profile()` 已能在策略提交通过后构建画像
- `save_strategy_vector_profile()` / `save_vector_index_registry()` 已提供轻量持久化与索引登记能力

### 2.2 当前已接入的边界

当前策略工厂主链路里：

1. `StrategySpawner.spawn()` 生成候选
2. `StrategyAutonomyService.generate_factory_candidates()` 补充 AI 候选
3. `BacktestFilter.filter()` 做初筛
4. `Deduplicator.deduplicate()` 以参数相似度为主判，并对可疑候选做向量复筛
5. `StrategySubmitter.submit()` 在质检通过后构建策略画像并登记索引元数据

这意味着：**向量能力已经进入工厂主链路，但当前只承担“可疑候选复筛 + 轻量画像”的角色。**

### 2.3 当前不应写成已实现的事项

- 基于 `pgvector/HNSW` 的持久化向量检索
- 候选级跨批次持久化向量指纹与 ANN 检索
- 策略交易行为向量、文本 embedding、LLM 语义向量
- 向量结果参与生命周期晋级/淘汰决策

## 3. 设计目标

本方案的目标不是新增一套独立向量平台，而是围绕**工厂去重 + 策略画像复用**做增量接线：

1. 巩固当前“参数主判 + 可疑候选向量复筛”的去重链路
2. 保留“为什么命中重复”的结构化原因，便于审查和调参
3. 继续复用现有 `vector_search.py` 与 `vector_platform.py`，避免引入新的平行系统
4. 只有当候选规模、持久化与查询性能成为瓶颈时，才升级到 `pgvector/HNSW`

## 4. 向量对象分层设计

## 4.1 已实现：行情形态向量

这是当前仓库中最早落地、且最直接参与相似检索的向量对象。

| 对象 | 当前状态 | 主要来源 | 用途 |
|:-----|:---------|:---------|:-----|
| 行情形态向量 | 已实现 | `VectorSearchEngine.kline_to_vector()` | 表达最近 N 日价格、成交量、收益率、技术特征 |
| 检索结果对象 | 已实现 | `find_similar_patterns()` | 返回 `code / similarity / klines / source` |
| DTW 相似结果 | 已实现 | `find_similar_patterns_dtw()` | 支持不同长度时间序列相似比较 |

该层的优点是：

- 复用现有数据即可生成
- 与 `search_by_kline` 已有返回结构兼容
- 可以直接服务于工厂“候选是否和历史策略过于相似”的第一阶段判断

局限也需要明确：

- 它描述的是**市场行为片段**，不是完整策略语义
- 它不能单独表达因子构成、持仓约束、风险预算、调仓行为

## 4.2 已实现：策略画像与索引登记（轻量持久化）

当前仓库已经有轻量持久化的策略画像层，主要由 `StrategyVectorPlatform` 与存储层承接：

| 对象 | 当前状态 | 主要来源 | 用途 |
|:-----|:---------|:---------|:-----|
| 策略画像 | 已实现 | `build_strategy_profile()` + `save_strategy_vector_profile()` | 保存 `strategy_id / profile_type / vector_method / metric / embedding / signature / metadata` |
| 索引登记 | 已实现 | `save_vector_index_registry()` | 保存索引版本、后端、样本数、状态与元数据 |
| 相似画像查询 | 已实现 | `find_similar_profiles()` | 面向画像层做相似策略查询 |

该层当前的真实定位是：

- 为策略提交后的画像审计与相似画像查询提供基础数据
- 为向量索引版本管理留出轻量登记能力
- 仍不是跨会话 ANN 向量数据库，也不等于完整行为向量平台

## 4.3 远期规划：策略行为向量（研究方向）

这是研究蓝图中更高级的方向，只建议保留为长期规划。

可能来源包括：

- 因子暴露序列
- 仓位变化序列
- 调仓频率与持有期分布
- 信号命中率与回撤行为
- 模拟盘或真实前向阶段的收益路径

在当前仓库里，上述字段既没有稳定抽取链路，也没有持久化向量表，因此**不能作为当前方案承诺**。

## 5. 判重流程设计

## 5.1 当前流程

当前工厂去重应继续保持：

1. 参数相似度为主判
2. 对可疑候选触发向量复筛
3. 输出重复命中的阈值、原因、匹配对象与后端信息
4. 不把当前轻量复筛写成“全量持久化向量平台”

## 5.2 当前已落地的两阶段口径

当前实现已经是“两阶段去重”的轻量版本：

1. **粗筛：参数维度去重**
   - 快速过滤名称、类型、关键参数高度重叠的候选
2. **复筛：形态向量去重**
   - 仅对参数接近但未达主阈值的可疑候选生成行为片段并做相似度比较
   - 以 `vector_search.py` 的 `index` 或 `python` 后端做相似度比对
3. **判定输出**
   - 返回 `duplicate_level`、`matched_strategy_id`、`similarity`、`metric`、`vector_method`、`reason`

建议的判重结果口径：

- `exact_parameter_duplicate`
- `high_vector_similarity_duplicate`
- `parameter_close_but_vector_diverged`
- `unique_candidate`

## 5.3 当前接入点与可继续增强的位置

当前已经直接在 `Deduplicator.deduplicate()` 内接入向量复筛，而不是新增平行服务：

- 复用当前工厂调度位置，不改变主链路顺序
- 已在该步骤内部追加“向量复筛”分支
- 命中结果继续回写到提交前的审查上下文中

后续如果继续增强，优先考虑：

- 重复命中历史策略 ID
- 命中来源（`python` / `index` / `python_fallback`）
- 阈值配置快照
- 与 `strategy_vector_profiles` 的画像结果做更紧密的审查联动

## 6. 数据模型草案

## 6.1 运行时对象草案：候选向量指纹

建议文档层先采用如下契约：

- `candidate_key`
- `strategy_type`
- `snapshot_date`
- `vector_method`
- `metric`
- `window_length`
- `vector_values`
- `parameter_signature`
- `environment_tags`

说明：该对象**当前不要求落库**，优先保证与 `vector_search.py` 的输入输出兼容。

## 6.2 当前轻量持久化表：`strategy_vector_profiles` / `vector_index_registry`

当前仓库已经存在两张与向量相关的轻量持久化表：

- `strategy_vector_profiles`
  - 主要字段：`strategy_id`、`profile_type`、`vector_method`、`metric`、`vector_dim`、`embedding`、`signature`、`backend`、`index_version`、`metadata`
- `vector_index_registry`
  - 主要字段：`index_name`、`backend`、`status`、`profile_type`、`vector_method`、`metric`、`sample_count`、`index_version`、`metadata`

这两张表当前的作用是：

- 保存轻量策略画像与索引登记信息
- 支撑画像审计、相似画像查询与运行记录
- **不应被表述为 `pgvector/HNSW` 级别的持久化 ANN 向量库**

## 6.3 远期持久化建议

若后续进入 PostgreSQL 向量检索阶段，可参考 `pgvector` 官方能力：

- 向量列可建模为 `vector(n)`
- HNSW 可作为 ANN 索引方案
- 归一化向量更适合配合 cosine distance
- 带过滤条件检索时要注意召回下降与索引参数调优

但在当前仓库阶段，只需把这些内容作为**演进依据**，不作为现状说明。

## 7. 分期实施建议

### 7.1 短期

1. 保持 `Deduplicator` 现有参数去重主路径
2. 为重复命中追加结构化原因与阈值说明
3. 明确候选生成阶段使用的行情窗口口径，并让画像摘要更易被审查报告消费

### 7.2 中期

1. 让画像结果、去重命中结果与工厂审查上下文更紧密联动
2. 继续复用进程内 `pattern_cache`，并评估跨批次画像复用收益
3. 将命中结果更完整地写入提交审查上下文、运行摘要与上层展示

### 7.3 远期

1. 评估是否需要把现有 `strategy_vector_profiles` 进一步升级为更强的 ANN 向量存储
2. 评估是否升级为 `pgvector/HNSW`
3. 评估是否引入策略行为向量与跨周期复检

## 8. 验证要求与风险

## 8.1 验证要求

后续若实施向量去重，至少需要覆盖：

- 正常流程：候选可生成向量并完成相似度比较
- 边界条件：行情窗口不足、向量长度不一致、候选池为空
- 降级流程：`index` 失败时是否正确回退到 `python`
- 结果解释：是否能输出命中原因、阈值和匹配对象

## 8.2 关键风险

- 当前 `index` 只是进程内缓存，重启后不保留
- 行情形态向量不能替代完整策略语义，误判风险需要靠双阶段判重降低
- 若直接跳到持久化向量库，会引入额外表结构、索引维护和参数调优成本

## 9. 最终口径

策略工厂当前关于向量能力的统一表述应为：

> **仓库已经具备独立的行情形态向量检索与轻量策略画像能力，且 `Deduplicator` 已对可疑候选使用 `vector_search.py` 做复筛；当前仍不是全量持久化 ANN 平台，短期重点应放在解释性、画像复用与阈值稳定性，中长期才评估 `pgvector/HNSW` 与更完整的策略行为向量。**

这也是后续所有实施、排期与评审应采用的统一口径。
