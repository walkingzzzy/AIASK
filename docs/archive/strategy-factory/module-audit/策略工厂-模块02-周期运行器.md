# 策略工厂模块 2：周期运行器（FactoryCycleRunner）

> 代码位置：
> - 主类定义：`packages/strategy-factory/src/strategy_factory/application/cycle_runner.py`
> - 核心 `run()` 方法：`cycle_runner_parts/normalizers.py`（~1000 行）
> - 治理流水线：`services/candidate_pipeline.py`（CandidatePipeline）

---

## 代码审计结论

- 准确性状态：基本准确。
- 代码证据：`cycle_runner.py` 组装 `FactoryCycleRunner`；`cycle_runner_parts/normalizers.py` 实现 `run()` 主流程；`services/candidate_pipeline.py` 执行 Gate/Backtest/Dedup/Submit；`run_models.py` 定义阶段状态与 run summary。
- 已实现能力：runtime enabled/readiness 阻断、startup warmup、market snapshot collect、factor research、research plane、governance plane、CandidatePipeline、elimination、run artifacts、stage_results、read_only 透传。
- 过时/夸大描述：文档对阶段耗时追踪的描述需要收敛为“有 stage status/summary，但缺统一阶段级 duration 字段”；Generation 内部已对 autonomy 失败做降级记录，但 `run_generation()` 整体异常仍可能导致周期失败。
- 仍然成立的问题：collect/factor/generation/governance/elimination 缺统一 stage-level timeout；主阶段仍串行；空候选仍会进入 CandidatePipeline 初始化路径；readiness 阻断后的自动修复仍有限。
- 建议优先级：P0 补 readiness authority 与 research/governance plane；P1 阶段 timeout 和失败隔离；P3 阶段耗时与 artifact 分层。下方优化建议中的代码块为概念示例。

## 职责

周期运行器执行**一次完整的策略工厂周期**，从收集市场数据到提交策略、淘汰旧策略。它不拥有调度状态，由调度器创建并传入 `FactoryRunContext`。

## 数据结构

```python
@dataclass(slots=True)
class FactoryRunContext:
    db: Any                    # 数据库连接
    factory_pkg: Any           # 工厂包引用（含 Spawner/BacktestFilter/Deduplicator/Submitter 等）
    runtime_adapters: Any      # MCP 运行时适配器
    start: datetime            # 运行开始时间
    trace_id: str              # 追踪 ID（如 "strategy_factory:a1b2c3d4e5f6"）
    run_id: str                # 运行 ID（如 "factory_run_1715760000_abc12345"）
    execution_mode: str        # "legacy_primary" / "v2_primary" / "shadow_readonly"
    engine_version: str        # 引擎版本
    parity_role: str           # "primary" / "shadow"
    read_only: bool            # 是否只读模式（shadow 运行时为 True）

@dataclass(slots=True)
class FactoryCycleOutcome:
    result: dict[str, Any]                    # 完整运行结果
    persistence_failures: list[dict[str, Any]] # 持久化失败记录
```

## `run()` 方法完整阶段流程

```python
async def run(self) -> FactoryCycleOutcome:
```

### 阶段 0：运行时检查

```python
if not is_factory_runtime_enabled():
    # 直接返回 SKIPPED 状态，不执行任何阶段
    results["status"] = "skipped"
    return FactoryCycleOutcome(results, [])
```

### 阶段 1：Warmup（启动预热）

```python
warmup_result = await scheduler._run_startup_warmup()
# 执行预热任务（core_market / factor_context 类型）
# 状态：completed / skipped / failed / partial
results["stages"]["warmup"] = warmup_result
```

### 阶段 2：Collect（收集市场快照）

```python
collector = factory_pkg.DataCollector()
snapshot = await collector.collect(db)
snapshot["factory_run_id"] = run_id
snapshot["trace_id"] = trace_id

# 注入调度器累积的 family 历史表现（P2-D 反馈）
snapshot["family_gate_feedback"] = scheduler._family_gate_feedback

results["stages"]["collect"] = {
    "date": snapshot["date"],
    "fear_greed_index": snapshot["fear_greed_index"],
    "fg_level": snapshot["fg_level"],
    "listed_count": snapshot["listed_count"],
    "incubating_count": snapshot["incubating_count"],
    "degraded": snapshot["degraded"],
    "completion_ratio": snapshot["completeness"]["completion_ratio"],
}
```

### 阶段 3：Factor Research（因子研究）

```python
factor_gateway = scheduler._get_factor_research_gateway()
factor_research = await self._build_factor_research_artifact(factor_gateway, db, snapshot)
snapshot["factor_research"] = factor_research

results["stages"]["factor_research"] = {
    "active_factor_count": ...,
    "active_family_names": [...],
    "preferred_strategy_types": [...],
    "family_preference_order": [...],
    "stock_family_allocation_count": ...,
    "degraded": ...,
}
```

失败时降级为空因子研究（`factor_source_mode: "error_fallback"`），不阻断后续阶段。

### 阶段 4：Readiness（就绪检查）

```python
readiness = self._build_factory_readiness(snapshot, factor_research)
snapshot["factory_readiness"] = readiness

# 如果就绪检查不通过 → 整个周期 SKIPPED
if not readiness["can_proceed"]:
    results["status"] = "skipped"
    results["summary"]["skip_reason"] = "readiness_blocked"
    return FactoryCycleOutcome(results, persistence_failures)
```

就绪检查评估：
- 运行时是否启用
- 因子数据是否新鲜
- governed 候选池是否可用
- 就绪分数是否达标（≥ 0.55）

### 阶段 5：Generation（策略生成）

```python
generation = await self._research_runner.run_generation(db, snapshot)
candidates = generation.generated_candidates  # 合并后的候选列表

results["stages"]["spawn"] = {
    "count": len(generation.local_candidates),
    # + spawn_report 详情
}
results["stages"]["autonomy"] = {
    "generated_count": len(generation.autonomy_candidates),
    "external_llm_status": ...,
    # + autonomy_stage 详情
}
```

`ResearchPlaneRunner.run_generation()` 内部：
1. `Spawner.spawn(snapshot)` → 本地规则候选
2. `get_adaptive_candidates(db, preferred_types, snapshot)` → 自适应参数候选
3. `TaskOrchestrator(scheduler).run(db, snapshot)` → LLM 自主任务候选
4. 合并 + 应用策略配置文件 + 自动命名 + A 股规则注入 + 无效代码过滤

### 阶段 6：Governance（治理流水线）

由 `CandidatePipeline` 统一编排：

```python
pipeline_run = await CandidatePipeline(factory_pkg, scheduler).run(
    candidates, snapshot, db, read_only=self._context.read_only
)
passed = pipeline_run.passed       # Gate-1/2 通过的候选
unique = pipeline_run.unique       # 去重后的候选
submit_result = pipeline_run.submit_result  # 提交结果
```

`CandidatePipeline.run()` 内部流程：

```
candidates
    │
    ▼ (优先路径：run_gated_submission_pipeline)
Gate-0 + Gate-1 + Gate-2 → passed
    │
    ▼
Deduplicator.deduplicate(passed, db) → unique
    │
    ▼
Submitter.submit(unique, snapshot, db) → submit_result
    │
    ▼
build_governance_plane_artifact() → governance_plane
```

三种执行路径（按优先级）：
1. **统一提交流水线**（`run_gated_submission_pipeline`）：Gate + Dedup + Submit 一体化
2. **统一门禁**（`run_gated_filter`）：Gate 一体化，Dedup + Submit 分开
3. **传统路径**：BacktestFilter.filter → Dedup → Submit 分开执行

产出的 stage 记录：
```python
results["stages"]["quality_gate"] = quality_gate_report
results["stages"]["backtest"] = backtest_report
results["stages"]["deduplicate"] = deduplicator.get_last_report()
results["stages"]["submit"] = submit_result
```

### 阶段 7：Elimination（淘汰检查）

```python
eliminator = factory_pkg.EliminationChecker()
eliminated = await eliminator.check(db, snapshot["fg_level"])

results["stages"]["elimination"] = {
    "count": len(eliminated),
    "items": eliminated,
}
```

### 阶段 8：汇总与收尾

```python
elapsed = (scheduler._now() - start).total_seconds()
results["status"] = "success"
results["elapsed_seconds"] = elapsed

# 构建完整 summary（调用 build_success_run_summary）
results["summary"] = build_success_run_summary(
    trace_id, snapshot, candidates, passed, unique, eliminated,
    spawn_report, submit_result, quality_gate_report, backtest_report,
    autonomy_summary, factor_research_summary, readiness_summary, ...
)

# 附加研究平面和治理平面摘要
results["summary"] = self._apply_research_plane_summary(results["summary"], research_plane)
results["summary"] = self._apply_governance_plane_summary(results["summary"], governance_plane)

# 附加运行合约（run_header, artifacts, stage_results）
return FactoryCycleOutcome(self._attach_result_contracts(results), persistence_failures)
```

## 已识别的优化方向

> 以下为经过代码审计和行业最佳实践对比后识别的改进点，按优先级排列。

---

### 优化 1：缺少阶段级超时保护（🔴 高优先级）

**现状问题**：`run()` 方法中各阶段（collect、factor_research、generation、governance、elimination）均无独立超时控制。如果某个阶段（如 LLM 调用或数据库查询）挂起，整个周期将无限等待。

- 调度器层面的超时仅在研究任务级别（`_generate_for_research_task`），不覆盖 collect/elimination 等阶段
- 一个挂起的 `DataCollector.collect()` 或 `EliminationChecker.check()` 会阻塞整个工厂

**建议方案**：为每个阶段添加可配置的超时：

```python
from ..domain.constants import _resolve_pipeline_stage_timeout

async def run(self) -> FactoryCycleOutcome:
    # ...
    # 阶段 2：Collect（带超时）
    collect_timeout = _resolve_pipeline_stage_timeout("collect", legacy_default=60.0)
    try:
        snapshot = await asyncio.wait_for(
            collector.collect(db),
            timeout=collect_timeout,
        )
    except asyncio.TimeoutError:
        results["stages"]["collect"] = {"status": "timeout", "timeout_sec": collect_timeout}
        # 降级处理或提前终止
        ...

    # 阶段 7：Elimination（带超时）
    elimination_timeout = _resolve_pipeline_stage_timeout("elimination", legacy_default=30.0)
    try:
        eliminated = await asyncio.wait_for(
            eliminator.check(db, snapshot.get("fg_level", "neutral")),
            timeout=elimination_timeout,
        )
    except asyncio.TimeoutError:
        eliminated = []  # 降级：跳过淘汰检查
        results["stages"]["elimination"] = {"status": "timeout", "count": 0}
```

**影响**：防止单阶段挂起导致整个工厂周期卡死；超时后可降级继续或快速失败。

---

### 优化 2：阶段间缺少并行化机会（🔴 高优先级）

**现状问题**：所有阶段严格串行执行。但部分阶段之间不存在数据依赖，可以并行：

- `_run_startup_warmup()`（阶段 1）与 `DataCollector.collect()`（阶段 2）无数据依赖
- `EliminationChecker.check()`（阶段 7）与 `CandidatePipeline.run()`（阶段 6）无数据依赖（elimination 检查的是已有 listed 策略，不依赖本轮候选）

**建议方案**：

```python
async def run(self) -> FactoryCycleOutcome:
    # 阶段 1+2 并行：warmup 和 collect 同时执行
    warmup_task = asyncio.create_task(scheduler._run_startup_warmup())
    collect_task = asyncio.create_task(collector.collect(db))
    warmup_result, snapshot = await asyncio.gather(warmup_task, collect_task)

    # ... 阶段 3-5 串行（有数据依赖）...

    # 阶段 6+7 并行：governance 和 elimination 同时执行
    governance_task = asyncio.create_task(
        CandidatePipeline(factory_pkg, scheduler).run(candidates, snapshot, db, ...)
    )
    elimination_task = asyncio.create_task(
        eliminator.check(db, snapshot.get("fg_level", "neutral"))
    )
    pipeline_run, eliminated = await asyncio.gather(governance_task, elimination_task)
```

**影响**：典型周期耗时从 ~105s 降低到 ~75-85s（warmup+collect 并行节省 ~10s，governance+elimination 并行节省 ~10-20s）。

---

### 优化 3：缺少阶段级耗时追踪（🟡 中优先级）

**现状问题**：只记录了整体 `elapsed_seconds`，没有记录每个阶段的独立耗时。无法识别性能瓶颈在哪个阶段。

**建议方案**：

```python
async def run(self) -> FactoryCycleOutcome:
    stage_timings: dict[str, float] = {}

    # 阶段 2：Collect
    t0 = scheduler._now()
    snapshot = await collector.collect(db)
    stage_timings["collect"] = (scheduler._now() - t0).total_seconds()

    # 阶段 3：Factor Research
    t0 = scheduler._now()
    factor_research = await self._build_factor_research_artifact(...)
    stage_timings["factor_research"] = (scheduler._now() - t0).total_seconds()

    # ... 每个阶段同理 ...

    # 最终写入结果
    results["stage_timings"] = stage_timings
    results["summary"]["stage_timings"] = stage_timings
    results["summary"]["slowest_stage"] = max(stage_timings, key=stage_timings.get)
    results["summary"]["slowest_stage_seconds"] = max(stage_timings.values())
```

**影响**：快速定位性能瓶颈；支持基于历史数据的自适应超时设置；为容量规划提供数据支撑。

---

### 优化 4：Generation 阶段失败不降级（🟡 中优先级）

**现状问题**：如果 `ResearchPlaneRunner.run_generation()` 抛出异常，整个周期直接标记为 `failed`。但 generation 内部有多个独立来源（Spawner、adaptive、TaskOrchestrator），部分失败时应该降级而非全部失败。

**当前代码**：generation 异常被外层 `try/except` 捕获 → 整个周期 failed。

**建议方案**：

```python
# 在 run() 中对 generation 阶段做细粒度错误处理
try:
    generation = await self._research_runner.run_generation(db, snapshot)
    candidates = list(generation.generated_candidates)
except Exception as exc:
    logger.warning("StrategyFactory: generation stage failed, attempting degraded mode: %s", exc)
    # 降级：仅使用 Spawner 本地规则生成
    try:
        spawner = factory_pkg.StrategySpawner()
        candidates = list(spawner.spawn(snapshot) or [])
        generation_degraded = True
    except Exception as spawner_exc:
        # Spawner 也失败 → 空候选继续（跳过 governance，只做 elimination）
        candidates = []
        generation_degraded = True

    results["stages"]["spawn"] = {"count": len(candidates), "degraded": True, "error": str(exc)}
```

**影响**：LLM 服务不可用时仍能产出本地规则候选；避免因 TaskOrchestrator 超时导致整个周期浪费。

---

### 优化 5：空候选时仍执行完整 Governance 流水线（🟡 中优先级）

**现状问题**：即使 generation 阶段产出 0 个候选，仍然会执行完整的 `CandidatePipeline.run()`（包括 BacktestFilter、Deduplicator、Submitter 的初始化和调用）。

**建议方案**：

```python
if not candidates:
    # 短路：跳过 governance 流水线
    results["stages"]["quality_gate"] = {"status": "skipped", "reason": "no_candidates"}
    results["stages"]["backtest"] = {"status": "skipped", "reason": "no_candidates"}
    results["stages"]["deduplicate"] = {"status": "skipped", "reason": "no_candidates"}
    results["stages"]["submit"] = {"status": "skipped", "reason": "no_candidates"}
    passed, unique, submit_result = [], [], {}
else:
    pipeline_run = await CandidatePipeline(factory_pkg, scheduler).run(...)
    # ...
```

**影响**：空候选场景下节省 ~5-15s（避免无意义的 K 线预加载、向量搜索初始化等）。

---

### 优化 6：Elimination 与当前周期提交存在竞态（🟡 中优先级）

**现状问题**：阶段 7（Elimination）在阶段 6（Submit）之后执行。如果本轮刚提交的策略立即被 promote 到 `listed` 状态（理论上不会立即发生，但存在边界情况），可能被同一轮的 Elimination 检查到并淘汰。

**建议方案**：

```python
# 方案 A：Elimination 排除本轮提交的策略
eliminated = await eliminator.check(
    db,
    snapshot.get("fg_level", "neutral"),
    exclude_ids=set(submit_result.get("submitted_ids") or []),
)

# 方案 B：Elimination 移到 Generation 之前（与 Governance 并行）
# 这样 elimination 检查的是上一轮之前的策略，不受本轮影响
```

**影响**：消除理论上的竞态条件，确保新策略有足够的孵化观察期。

---

### 优化 7：结果结构过于庞大（🟢 低优先级）

**现状问题**：`results` 字典包含大量冗余和重复信息（如 `summary` 中重复了 `stages` 中的数据，`governance_plane` 和 `research_plane` 包含完整的 artifact 数据）。单次运行结果可能达到数百 KB。

**建议方案**：

```python
# 分层存储：核心结果 + 详细 artifacts 分开持久化
results_core = {
    "run_id": ...,
    "status": ...,
    "elapsed_seconds": ...,
    "summary": ...,  # 精简版
    "stage_statuses": {stage: status for stage, status in ...},
}

results_detail = {
    "stages": ...,           # 完整阶段数据
    "research_plane": ...,   # 研究平面
    "governance_plane": ..., # 治理平面
}

# 核心结果写入主表（快速查询）
await db.save_strategy_factory_run(results_core)
# 详细数据写入 artifact 表（按需加载）
await db.save_strategy_factory_run_artifact(results_detail)
```

**影响**：减少内存占用和数据库写入量；加快运行记录查询速度。

### 优化 8：缺少分布式追踪集成（🟢 低优先级）

**现状问题**：虽然有 `trace_id` 字段，但仅用于日志关联，没有集成 OpenTelemetry 等分布式追踪系统。无法可视化阶段间的调用链和耗时分布。

**建议方案**：

```python
from opentelemetry import trace

tracer = trace.get_tracer("strategy_factory.cycle_runner")

async def run(self) -> FactoryCycleOutcome:
    with tracer.start_as_current_span(
        "factory_cycle",
        attributes={"run_id": self._context.run_id, "trace_id": self._context.trace_id},
    ) as root_span:

        with tracer.start_as_current_span("stage.collect") as span:
            snapshot = await collector.collect(db)
            span.set_attribute("snapshot.date", snapshot.get("date"))
            span.set_attribute("snapshot.listed_count", snapshot.get("listed_count", 0))

        with tracer.start_as_current_span("stage.factor_research") as span:
            factor_research = await self._build_factor_research_artifact(...)
            span.set_attribute("active_factor_count", ...)

        # ... 每个阶段一个 span ...
```

**影响**：可视化完整的周期执行链路；快速定位慢阶段和异常；支持跨服务追踪（如 LLM 调用链）。

### 优化 9：Readiness 阻断后缺少诊断信息传递（🟢 低优先级）

**现状问题**：当 `readiness.can_proceed = False` 时，周期直接返回 SKIPPED，但不会尝试任何修复动作。连续多轮 SKIPPED 时，调度器仍按正常间隔触发，浪费资源。

**建议方案**：

```python
if not readiness["can_proceed"]:
    # 1. 记录连续 skip 次数
    self._consecutive_skips = getattr(self, "_consecutive_skips", 0) + 1

    # 2. 如果连续 skip >= 3，建议调度器延长间隔
    if self._consecutive_skips >= 3:
        results["summary"]["scheduler_hint"] = {
            "action": "extend_interval",
            "reason": "consecutive_readiness_blocks",
            "consecutive_skips": self._consecutive_skips,
            "suggested_multiplier": min(2.0, 1.0 + self._consecutive_skips * 0.3),
        }

    # 3. 尝试自动修复（如刷新因子数据）
    if "factor_stale" in readiness.get("blockers", []):
        await self._attempt_factor_refresh(db, snapshot)

    return FactoryCycleOutcome(results, persistence_failures)
```

**影响**：减少无效运行；为调度器提供自适应间隔的信号；自动修复常见阻断原因。

### 优化总结

| # | 改进项 | 影响 | 实现难度 | 优先级 |
|---|---|---|---|---|
| 1 | 阶段级超时保护 | 防止单阶段挂起卡死整个周期 | 中 | 🔴 高 |
| 2 | 阶段间并行化 | 周期耗时降低 20-30% | 中 | 🔴 高 |
| 3 | 阶段级耗时追踪 | 定位性能瓶颈 | 低 | 🟡 中 |
| 4 | Generation 降级模式 | LLM 不可用时仍能产出 | 低 | 🟡 中 |
| 5 | 空候选短路 | 避免无意义的 pipeline 执行 | 低 | 🟡 中 |
| 6 | Elimination 竞态消除 | 避免新策略被误淘汰 | 低 | 🟡 中 |
| 7 | 结果结构精简 | 减少内存和存储开销 | 中 | 🟢 低 |
| 8 | 分布式追踪集成 | 可视化执行链路 | 中 | 🟢 低 |
| 9 | Readiness 阻断诊断 | 减少无效运行 | 低 | 🟢 低 |

建议从 #1（阶段级超时）和 #2（并行化）开始实施，这两项对系统稳定性和性能的提升最为显著。#3（耗时追踪）实现成本极低，建议同步实施以获取优化效果的量化数据。
