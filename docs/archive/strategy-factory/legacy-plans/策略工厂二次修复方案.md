# 策略工厂二次修复方案

> **目标**：在《策略工厂跑偏修复方案.md》P0–P3 落地、LLM 通路真正打通之后，针对**实测 16 轮连续运行**暴露出来的瓶颈，给出可执行的下一阶段修复方案。
>
> **基线**：本地连续运行 16 轮（44 分钟），LLM 累计 63 次 `POST /v1/chat/completions` 全部 200 OK；submitted=3 / draft=14 / rejected=168；`target_context_blocked` 占 ~86%；`statistical_gate_exception:TypeError` 每轮触发；`stocks.market_cap` 全表 NULL（5,517/5,517）。
>
> **范围**：本方案聚焦"工厂跑通了但跑得不够好"的 6 类瓶颈。不重写 G0–G3 的审查阈值与 BULK 调度协议；这两块在前一份方案里已经修过。本方案处理的是上游统计门禁失效、LLM 命中率过低、Gate-3 阈值过严、BULK 吞吐过低、数据基础缺失、可观测性不足。
>
> **不属于本方案**：
> - LLM 网关本身的 SLA / 限流（用户侧资源问题）
> - 因子挖掘 / 行情同步链路（属于另一份运维基线）
> - 北交所/B 股/老三板过滤（属于《策略工厂-选股逻辑修复方案》）

## 2. 为什么会"跑通但跑不好"

### 2.1 第一层：统计门禁签名漂移（R0）

`packages/strategy-factory/src/strategy_factory/application/submission_gate/runner_parts/multiple_testing.py:486` 定义：

```python
def _evaluate_statistical_admission(
    strategy: dict,
    profile: dict[str, Any],
    gate_payload: Optional[dict],
    *,
    admission_level: str = "incubation",
    attempt_adjustment: Optional[dict[str, Any]] = None,
) -> dict[str, Any]:
```

但 `submission_gate/runner_parts/trade_profile.py:575` 调用时传：

```python
result = _evaluate_statistical_admission(
    strategy,
    profile,
    db=db,        # ← 不是被调函数的关键字
    klass=klass,  # ← 同上
)
```

每次抛 `TypeError`，被 `except Exception` 兜底吞成 `statistical_gate_exception:TypeError` warning，结果是：

- `gate_3.supplemental_statistical_gate.passed` 永远是 `False`（因为没真正算）
- `wf_ic_ir / pkf_ic / bootstrap_ci_lower / param_sensitivity` 这些字段在 multiple_testing payload 里永远缺失
- 由于 `supplemental_statistical_gate_failed` 是 warning 而非 reject reason，主门禁还能通过，所以工厂"看起来在跑"

这说明历史上有一次签名漂移没同步到调用方，CI 也没拦下来。

### 2.2 第二层：LLM 入口被"market_cap 全表 NULL"间接拦截（R1）

LLM 调用链：

```
generate(snapshot, research_task)
  → _build_research_context(db, research_task)
    → _load_universe_rows(db)  -- ORDER BY market_cap DESC NULLS LAST LIMIT 300
    → if task.target_symbols not in universe_rows:
         → _build_blocked_research_context()
         → status = 'blocked_by_target_universe'
  → if blocked:
       → 'external_provider.status' = 'skipped_target_context_blocked'
       → return []   # LLM 永远不被调用
```

证据链：

1. `RESEARCH_UNIVERSE_SCAN_LIMIT = 300`（`strategy_spec/constants.py:19`）
2. SQL：`ORDER BY market_cap DESC NULLS LAST, code`
3. `stocks.market_cap` 全表 5,517/5,517 NULL
4. NULL 全部排到末尾，前 300 实际是按 stock_code 字典序的"看起来像茅台、中石油、招商银行的子集"
5. BULK matrix 从 5,204 只里抽出来的 target（多数是 market_cap=NULL 的中小盘）必然不在前 300
6. 即使 PR-S23 已经在 reuse cache 路径修了一刀，`_reuse_shared_research_context` 又会先 hit blocked cache → 把 blocked context 传下去 → 永远 short-circuit
7. 实测每轮 21–25/29 task 走这条死路

### 2.3 第三层：BULK task 超时（R2）

`STRATEGY_FACTORY_RESEARCH_TASK_TIMEOUT_SEC=180` 单 task 超时：

- LLM 网关 P95 ~30s
- staged pipeline 多阶段 fan-out，`STRATEGY_FACTORY_LLM_FAN_OUT_COUNT=4`
- 4 个 fan-out × 30s = 120s 起步，加上 prompt 构造、parsing、重试，180s 经常不够

被超时挂掉的 task 会：

```python
# _factory_scheduler_loop_parts/policy.py:188
retry_task["disable_external_llm"] = True
retry_task["external_llm_skip_reason"] = "task_timeout_local_fallback"
retry_task["disable_pipeline_staged"] = True
```

→ 第二次 retry 直接走 rule path，等于这个 task 的 LLM 预算白浪费。

### 2.4 第四层：Gate-3 阈值与短样本噪声打架（R3）

每轮 candidate 平均 trade_count=20，但 Gate-3 的硬阈值假设大样本：

| 阈值 | 当前值 | 实测中位数 | 问题 |
|---|---|---|---|
| `expectancy_min` | 0 | 0.0000 | trade_count=20 时 expectancy 噪声 ±0.005，0.0000 在 hard fail 边界 |
| `win_rate_min` | 0.45–0.55 | 0.30–0.50 | n=20 时 win_rate 标准误约 ±0.11，0.45 hard fail 概率 50% |
| `trade_density_max` | 1.2 | 1.0–1.4 | 当前 candidate 持仓窗口 8–24 天，trade_density 自然在 1.0–1.5 |
| `validation_grade_d_not_allowed_for_incubation` | hard | 91% 评 D | D 是兜底等级，整批被一刀切 |

加上 §2.1 的 supplemental_statistical_gate 全失效，相当于：

- 主门禁阈值过严 → 拦掉 91%
- 补充门禁本应该挽救边缘案例 → 因为 bug 完全没运行
- → submitted 9% 是当前阈值与样本不匹配的产物，不是工厂质量问题

### 2.5 第五层：BULK 吞吐配置过保守（R4）

```text
STRATEGY_FACTORY_MAX_BULK_RESEARCH_TASKS=20
STRATEGY_FACTORY_BULK_STOCK_MATRIX_TASKS_PER_SHARD=50
STRATEGY_FACTORY_BULK_STOCK_MATRIX_MAX_TASKS_PER_RUN=20
STRATEGY_FACTORY_RESEARCH_TASK_CONCURRENCY=10
```

实测每轮 task 实际耗时 130–185s，单轮 LLM 时间占用 60–100s，CPU 利用率 < 30%，说明 task 数和并发都还有 2–3 倍余量。

`bulk_stock_matrix_planned_task_count = 15,322`，按当前 20 task/轮 + 5 分钟/轮节奏，跑完一轮全市场矩阵需要 766 轮 = 32 小时；按市场时段 5 min 间隔算实际 64 小时。

### 2.6 第六层：基础数据缺失（R5）

```sql
-- 历史 PR 已经把 stocks 表建好，但全量行情同步的回写从未做过
SELECT COUNT(*) FROM stocks;                                     -- 5517
SELECT COUNT(market_cap) FROM stocks;                            -- 0
SELECT COUNT(pe_ratio) FROM stocks;                              -- 0
SELECT COUNT(*) FROM stock_quotes WHERE close_price IS NOT NULL; -- 有数据
SELECT COUNT(*) FROM financials;                                 -- 有数据
```

财务数据进了 `financials` 表，行情数据进了 `stock_quotes` 表，但 `stocks` 表的 `market_cap / pe_ratio / pb_ratio` 三个汇总列从未被回写。

这导致：

- §2.2 的 LLM 路径全表无法按市值排序
- topn 评分的 size/valuation/sector_regime 三个组件全 0
- benchmark_comparison.benchmark_oos_cagr 永远是 null（因为算不出 baseline）

### 2.7 第七层：可观测性差（R6）

要弄清"工厂跑得怎么样"，必须 join `strategy_factory_runs` + `strategies` + 解析 `stages` JSON 路径，没有现成 view，没有面板。本次定位"为什么 LLM 没被调用"花了 2 小时，主要原因就是 `external_llm_status` 这层指标埋深在 stage summary 里、UI 完全看不到。

## 3. 修复方案

### R0 ｜ 统计门禁签名 bug

#### R0.1 复现路径

```
Gate-3 (admission)
  └─ trade_profile.py::_run_statistical_gate(db, strategy, profile, klass)
       └─ _evaluate_statistical_admission(strategy, profile, db=db, klass=klass)
            └─ TypeError: got an unexpected keyword argument 'db'
       └─ except Exception:
            └─ warning = "statistical_gate_exception:TypeError"
            └─ result = {"passed": False, "reason": "statistical_gate_error: ..."}
```

#### R0.2 修复方案（推荐方案 B）

**方案 A**：让 `_evaluate_statistical_admission` 接受可选 `db / klass` 关键字（前向兼容）。
- 改动量：1 文件 5 行。
- 风险：极低；db/klass 仅作为预留参数不影响现有逻辑。
- 缺点：bug 的根源（**为什么调用方要传 db**）被掩盖。

**方案 B（推荐）**：在 `_run_statistical_gate` 中删掉 `db=db, klass=klass`，改为调用前先用 db/klass 把 `gate_payload` 构造好再传入。
- 改动量：1 文件 8 行；可能需要新增一个 helper `_build_statistical_gate_payload(db, strategy, klass)`。
- 风险：低；保持 `_evaluate_statistical_admission` 纯函数语义。

**方案 C**：把统计门改成异步、把 `db` 用作真实数据源（最大改造，能让统计门真正消费回测时间序列）。
- 改动量：跨 5+ 文件、需要重新设计 `wf_ic_ir / pkf_ic / bootstrap_ci_lower / param_sensitivity` 的真实计算路径（当前 payload 里这些字段全是 0）。
- 风险：高；需要新一轮的 G2/G3 验收。
- 缺点：超出"修 bug"范畴，应作为单独项目 R0+。

**最终选择**：先做方案 B（让现有代码不再抛 TypeError），同时把 §2.1 暴露出来的"补充统计门禁字段全 0"问题拆到 R3 里讨论（因为 R3 要重新校准阈值，正好顺手）。

#### R0.3 改动文件

| 文件 | 改动 |
|---|---|
| `packages/strategy-factory/src/strategy_factory/application/submission_gate/runner_parts/trade_profile.py` | `_run_statistical_gate` 中删除 `db=db, klass=klass`，新增 `_build_statistical_gate_payload(db, strategy, klass)` helper 用于把 supplemental metrics 凑齐再传入 |
| `packages/strategy-factory/src/strategy_factory/application/submission_gate/runner_parts/multiple_testing.py` | 不动（保持纯函数语义） |
| `packages/strategy-factory/tests/test_statistical_admission_gate.py` | 新增：用 mock `gate_payload` 验证 `_evaluate_statistical_admission` 被调用一次、返回结构正确、不抛 TypeError |

#### R0.4 验收

- 跑一次工厂（`--once`），日志里 `grep -c "statistical_gate_exception_typeerror"` → 0
- DB 查 `gate_3.supplemental_statistical_gate.passed` 至少有 `True/False` 两类，不再 100% `False`
- 单测覆盖：`pytest packages/strategy-factory/tests/test_statistical_admission_gate.py -v` 通过

#### R1.2 market_cap 回填

来源：`stock_quotes` 表里有最新一天的 `close_price`，加上 `total_share`（如果存在）就能算 market_cap。

```sql
-- 写一个回填脚本（单次执行），把最新一天 close * total_share 写回 stocks.market_cap
UPDATE stocks
SET market_cap = (
    SELECT q.close_price * COALESCE(q.total_share, q.float_share)
    FROM stock_quotes q
    WHERE q.stock_code = stocks.stock_code
    ORDER BY q.trade_date DESC
    LIMIT 1
)
WHERE stocks.market_cap IS NULL;
```

如果 `stock_quotes` 没有 `total_share`，需要从 `financials` 或 akshare 增量同步把 share count 补回来。

## 6. 这次"实测跑通"的复盘要点

> 把这次让工厂"从 0 LLM 调用跑到 75 次 LLM 调用"的关键决策记下来，防止下次再踩。

### 6.1 关键发现（按时间线）

1. **`STRATEGY_FACTORY_BULK_LLM_ENABLED=1` 不等于 LLM 真的会被调用**：BULK_LLM_ENABLED 只控制 `bulk_stock_matrix` 一类 task，对 snapshot/event task 不生效；snapshot 路径里有自己的"target_context_blocked"门，把 LLM 拦在调用之前。
2. **`load_dotenv()` 用 `os.environ.setdefault()` 而不是 `os.environ.update()`**：意味着 inline `env VAR=1 python ...` 会被尊重；但反过来如果脚本的 dotenv 用 `override=True`，inline env 就会被无声覆盖。每次启动后必须 `grep STRATEGY_FACTORY_BULK_LLM_ENABLED /proc/$PID/environ` 确认。
3. **LLM gateway 的 403 不一定持久**：`urllib` ping 拿到 403 可能是瞬时风控，curl 立刻 200 OK；不能据此判定 key 失效，要至少 3 次失败才判失。
4. **`shared_generation_context.research_context` 是个隐藏 short-circuit**：上游某轮缓存了 blocked context，下游所有 task reuse 都直接走 blocked。任何"研究上下文"层修复都得在 reuse 路径同时改一次。
5. **市值降序 + NULL LAST + 全表 NULL = LLM 永远拿不到 BULK target 数据**：这是个隐性依赖，LLM 路径假设 universe SQL 拉到的就是"覆盖度足够的样本"，一旦 `stocks.market_cap` 失修，整条 LLM 链路就熄灯。
6. **`task_timeout_local_fallback` 不是错误而是设计**：出现这个 skip_reason 不代表工厂坏了，但代表 LLM 配额白浪费。要优化但不要恐慌。
7. **stage summary 字段藏得很深**：`external_llm_status_counts` 在 `stages.autonomy.external_llm_status_counts`，但日志里完全不出现，必须查 `strategy_factory_runs.stages` 才能看到。这是 R6 监控面板的强需求。

### 6.2 下次排查"为什么 LLM 没跑"的标准流程

```
1. curl 网关：是否 200 OK？           — 排除 LLM 网关问题
2. provider 直调：是否能拿到 candidates？ — 排除项目内 provider 配置问题
3. DB 查 stages.autonomy.external_llm_status_counts：分布是什么？
   - 全 skipped_target_context_blocked → R1 路径问题
   - 全 skipped (timeout)              → R2 超时问题
   - 全 disable_external_llm           → 调度器 disable 链路问题
   - 0 attempts                        → task 根本没进 LLM 路径
4. 日志 grep "POST https://"：HTTP 调用次数是否 > 0？
   - 0 次 → 项目内 short-circuit
   - > 0 次但 DB 显示 0 → 埋点丢了
5. 单测：直接调用 _build_research_context 用 BULK target 看返回的 status
```

### 6.3 不变量（这些条件不满足就不要排查 LLM）

- `STRATEGY_LLM_ENABLED=1` 且 `STRATEGY_LLM_API_KEY` 有效
- `factor_llm_provider_health_status=ready` 且 `external_llm_provider_health_status=healthy`
- `STRATEGY_FACTORY_RUNTIME_ENABLED=1`
- 至少一个 task 的 `disable_external_llm != True`

任意一项不满足，先把它修了再谈 LLM。
