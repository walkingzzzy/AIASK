## 一、方案依据

本方案以以下文档作为权威输入，不再并行维护多套口径：

1. `510300沪深300ETF定投回测正式报告.md`
2. `510300沪深300ETF定投回测第一版报告.md`
3. `策略工厂/策略工厂孵化阶段命中率重构方案.md`
4. `策略工厂/strategy-factory-高置信度交易决策引擎重构方案.md`

本方案的基本判断如下：

1. 当前策略工厂并不缺“候选生成能力”，缺的是“研究级准入协议”。
2. 当前系统已经有语义合同、委员会评审、孵化统计、执行审计、向量治理等资产，但这些资产没有被收口成统一主门。
3. 510300 两份研究报告已经给出了比现有工厂更严谨的默认研究标准，尤其是在 OOS、成本敏感性、多重检验、现金池调度和业务硬门槛方面。
4. 修复方向应当是“收口与前移”，而不是重写整个工厂。

## 二、结论先行

### 2.1 当前问题的本质

当前策略工厂的核心问题，不是不会生成策略，而是生成结果在进入 `submit` 之前仍然更像“可讨论的信号原型”，而不是“可正式审查的完整交易策略”。  
这会带来四类断层：

1. `evidence -> hypothesis -> trade plan -> DSL -> backtest -> submit` 之间并未形成单一真源。
2. 提交前的质量门更偏结构评审和局部回测，不是完整的研究级 admission gate。
3. 孵化阶段虽然已经积累了不少命中率与执行统计，但 `signal quality` 与 `execution quality` 仍然没有明确拆门。
4. 生成器、reviewer、bandit、向量记忆和后验失败反馈之间没有形成真正可追溯的闭环学习。

### 2.2 目标状态

目标状态不是让工厂“生成更多策略”，而是让工厂做到以下四点：

1. 每个候选在进入回测前，都必须先编译成完整、可追溯、不可静默补洞的 `ExecutableStrategySpec`。
2. 每个候选在进入孵化前，都必须先通过一次研究报告级的 Gate B 审核包。
3. 每个孵化中的策略，都必须同时回答两个问题：
   - 它的信号是否还有统计优势。
   - 它的统计优势是否真的转成了执行收益。
4. 每个推广或拒绝结论，都必须能反查到：
   - 为什么生成它。
   - 为什么通过或被拒绝。
   - 依据了哪些历史家族证据。
   - 预测与执行是否一致。

## 三、510300 报告给出的默认研究标准

510300 两份报告已经给出一套可直接抽象为工厂默认协议的研究标准。

### 3.1 交易逻辑标准

报告覆盖的不是单一策略，而是一整套可比较、可审查的策略族：

1. 基准定投
   - 固定计划投入。
   - 分红独立复投。
   - 作为所有增强方案的基准对照。
2. 止盈定投
   - 包含 lot 级止盈。
   - 卖出资金回流现金池。
   - 后续月度定投优先消耗现金池，而不是额外放大杠杆。
3. `MA + RSI` 趋势过滤增强家族
   - 不是只定义“信号条件”，而是定义完整的动态仓位和入场/降仓语义。
   - 需要按家族做 walk-forward、参数折叠和稳定性比较。

### 3.2 执行语义标准

报告对执行时钟的约束非常明确，工厂默认协议必须对齐：

1. 前收形成信号。
2. 次日开盘执行风险腿交易。
3. 同日收盘重建现金池。
4. 分红路径独立于日常现金池。
5. 成本评估必须显式给出 `0/5/10 bps` 敏感性。

### 3.3 评价体系标准

510300 报告要求工厂默认输出以下指标，而不是只输出总收益或单次回测分数：

1. `CAGR`
2. `Max Drawdown`
3. `0/5/10 bps` 成本敏感性
4. `cash sleeves` 调度结果
5. 家族级 walk-forward 结果
6. `WFV OOS IC`
7. `Purged KFold OOS IC`
8. `PBO`
9. `White p-value`
10. `SPA p-value`
11. 家族级 OOS CAGR / OOS MDD 聚合比较
12. 家族级 business admission decision

### 3.4 业务门槛标准

510300 正式报告已经给出当前最清晰的硬门槛：

- `OOS CAGR >= 2 x benchmark OOS CAGR`
- `OOS MDD <= benchmark OOS MDD`

这应当被定义为策略工厂当前的默认业务准入门槛。  
如果未来某个资产类别、频率或策略类型要调整门槛，只能通过显式覆写 `ResearchValidationContract` 参数实现，不能绕开主流程另起一套链路。

## 四、现状审计结论

基于现有实现与既有重构文档，本次修复方案认定当前工厂已有能力与缺口如下。

### 4.1 已有资产

当前系统已经具备以下可复用资产：

1. `StrategySpec`、`candidate_contract`、`semantic_contract` 与 `governance_plane_contract` 已经形成一条“候选语义 -> 提交门禁 -> 治理工件”的基础链路。
2. `MultiAgentStrategyReviewer` 已经能对结构、风险、语义一致性、compiled DSL 完整性做初筛，更接近 Gate A 子模块，而不是纯风格 reviewer。
3. `submission_gate` 已经支持 walk-forward、多重检验、防过拟合验证、admission stage 评估与 family-level proxy 检验，但其默认协议尚未与 510300 研究协议完全对齐。
4. `signal_tracking.py`，已经具备 `hit_rate_lcb`、`skill_lcb`、`recent_skill_lcb`、`effective_n`、`stability_gap` 等高置信度统计基础。
5. `strategy_lifecycle_shared.py` 与 `incubation_pipeline.py` 已经实际产出 `signal_quality`、`execution_quality`、`execution_audit_gate_status`、`promotion_ready`、`hard_gate_result` 等孵化与推广判断结果。
6. `trace_id`、signal snapshot、execution lineage、trade audit summary 与 round-trip 覆盖统计已经存在，可作为后续 trace contract 的现实起点，而不是从零起表。
7. 向量检索、去重与 feedback 基础设施已经存在，能够支撑历史实验摘要、候选 dedup、family/target_pool/generator_mode 级别反馈控制。

### 4.2 关键缺口

真正缺失的是以下六项收口能力：

1. 没有统一的 `ResearchValidationContract` 来承载 510300 报告级研究协议。
2. 没有把当前 `gate_0 / pre_gate / gate_1 / gate_2 / gate_3` 明确映射成稳定的 Gate A/B/C 语义，导致新方案难以无损接入现有流水线。
3. 关键字段仍允许静默补默认值，导致“看似完整，实则未证实”的候选也能进入后续流程。
4. `submit` 之前虽然已有 admission gate，但还没有把 510300 的家族级研究协议、基准定投对照、`cash sleeves` 与业务硬门槛提升为默认主门。
5. 孵化阶段已经存在 signal/execution 双轴判断，但尚未沉淀成稳定、单一真源的 `SignalQualitySnapshot` / `ExecutionQualitySnapshot` 合同，promotion review 仍混用 legacy readiness 信息。
6. 生成器、reviewer、bandit、向量记忆、孵化反馈和推广审查之间仍缺统一 `prediction_trace_id` 主键链路，现状更像多份 lineage 视图并存而不是单主账本。

## 五、修复总原则

### 5.1 不重写，只收口并版本化

本次修复不推倒现有工厂，而是在已有代码事实上做四个收口：

1. 协议收口：把研究协议和追踪协议提升为一级合同。
2. 流程收口：把 Gate A、Gate B、Gate C 明确映射到现有主链，而不是一次性抹平 `gate_0~gate_3`。
3. 统计收口：把信号质量与执行质量拆成双快照。
4. 反馈收口：把失败原因、家族结论和 trace id 写回生成入口。

### 5.2 先兼容主链，后切默认主链

本轮必须采用版本化/feature flag 灰度，而不是一次性硬切：

1. 先在现有 contract 上增加 `v2` 字段与桥接对象。
2. 先让新 Gate A/B/C 以“补充判断 + 报告扩展”方式并行跑通。
3. 待回归稳定后，再把主判定权从 legacy gate 迁移到新协议。
4. 禁止为了追求协议纯度，直接删除当前 `gate_0~gate_3`、`quality_report`、`governance_plane` 的既有输出。

### 5.3 先服务层，后 UI

本轮只处理服务与协议，不要求优先改 UI。  
UI 展示只在以下对象稳定后再补：

1. `FactoryGateReport`
2. `ResearchValidationArtifact`
3. `SignalQualitySnapshot`
4. `ExecutionQualitySnapshot`
5. `PredictionTraceLedger`

### 5.4 先逻辑账本，后物理账本

本轮不优先重构底层数据库 schema。  
“统一事件账本”先以逻辑主写路径和聚合视图形式收口，待字段语义跑稳后再决定是否下沉成独立表结构。

## 六、目标架构

### 6.1 目标主链

策略工厂主链应重构为以下显式阶段：

```mermaid
flowchart LR
    A["Generate"] --> B["Gate A: Semantic Compile"]
    B --> C["Reviewer Gate"]
    C --> D["Legacy Quality Gates / Fast Screen"]
    D --> E["Backtest Summary"]
    E --> F["Gate B: Research Validation"]
    F --> G["Dedup"]
    G --> H["Submit Incubation"]
    H --> I["Gate C: Incubation Dual Gate"]
    I --> J["Promotion Review"]
```

落地时不应理解为“推翻现有 gate 编号后重写整条流水线”，而应按如下映射渐进收口：

1. 当前 `gate_0 / pre_gate / gate_1` 作为 Gate A 的过渡载体，负责 semantic compile、compile-stable checks 与 reviewer 子判断。
2. 当前 `gate_2 / gate_3` 作为 Gate B 的过渡载体，负责 fast screen、统计 admission、提交 lane 与研究级 admission package 的桥接。
3. Gate C 继续落在 `strategy_lifecycle_shared.py` 与 `incubation_pipeline.py`，通过升级既有 `signal_quality` / `execution_quality` / `hard_gate_result` 合同实现，而不是平行重做一条孵化链。

### 6.2 Gate A：语义与证据编译门

Gate A 的职责不是回测，而是证明“这已经是一套完整交易策略，而不是松散信号描述”。

本阶段应优先复用现有 `semantic_contract`、`StrategySpec`、`MultiAgentStrategyReviewer`、`runtime_playbook_provenance`、`claim_to_trade_plan_map` 等能力，在现有主链上增加稳定语义，而不是从零发明一套并行校验器。

固定检查项应包括：

1. 目标定义是否完整。
2. 预测对象、评估窗口与研究任务是否一致。
3. hypothesis claim 是否映射到 trade plan。
4. trade plan 是否映射到 DSL。
5. 风险规则与执行语义是否可执行。
6. 关键字段 provenance 是否达标。
7. 证据链是否具备 traceability。

Gate A 结论只能是：

1. `pass`
2. `revise`
3. `reject`

Gate A 失败即终止，不允许进入回测。

### 6.3 Gate B：研究级验证门

Gate B 是本次修复的主升级点。  
它必须在 `submit` 之前，产出一份足够接近研究正式报告的 admission package。

但 Gate B 不应直接把 `research_510300_v3.py` 生搬硬套到当前工厂。正确做法是：

1. 抽取 510300 的 `ResearchProtocol` 与 selection gate 口径。
2. 让 `submission_gate` 增加对该协议的显式消费能力。
3. 先把当前通用 admission gate 升级为“可承载 510300 协议的 v2”，再决定哪些资产类别默认采用该协议。

Gate B 固定输出应包括：

1. 基准定投对照结果。
2. 止盈 / `cash sleeves` 调度验证。
3. `60/12/12` walk-forward。
4. `0/5/10 bps` 成本敏感性。
5. `WFV OOS IC`。
6. `Purged KFold OOS IC`。
7. `PBO`。
8. `White p-value`。
9. `SPA p-value`。
10. 家族级 OOS CAGR / OOS MDD 对比。
11. 家族级 business admission decision。

Gate B 的核心对象必须是“家族级 admission decision”，而不是单个参数点的局部得分。

### 6.4 Gate C：孵化期双质量门

Gate C 不回答“这套策略长得像不像好策略”，只回答两个更硬的问题：

1. `SignalQualitySnapshot`
   - 信号是否仍然有统计优势。
2. `ExecutionQualitySnapshot`
   - 统计优势是否真的转化成了交易收益。

Gate C 应明确拆分如下：

#### SignalQualitySnapshot

只看预测质量，不看 realized win rate 的表面好坏。

固定字段应包括：

1. `hit_rate_lcb`
2. `skill_lcb`
3. `recent_skill_lcb`
4. `effective_n`
5. `coverage_ratio`
6. `forward_ic`
7. `stability_gap`

#### ExecutionQualitySnapshot

只看执行转化质量，不把它和信号预测质量混成一个分数。

固定字段应包括：

1. `realized_trade_count`
2. `fill_rate`
3. `round_trip_close_rate`
4. `trade_expectancy`
5. `pnl_conversion_efficiency`
6. `execution_conversion_efficiency`
7. `realized_slippage_vs_model`
8. `missed_trade_ratio`

`win_rate` 只作为辅助描述，不再作为推广主依据。

说明：

1. 当前代码已经存在 `signal_quality`、`execution_quality`、`execution_audit_gate_status`、`promotion_ready` 与 `hard_gate_result`。
2. 本次修复的重点不是从零创建 Gate C，而是把这组现有输出升级为单一、稳定、显式命名的双质量合同，并让 promotion review 只读它们。

## 七、核心合同修复方案

### 7.1 新增 `ResearchValidationContract`

该合同是本次修复的主协议。  
默认字段应包括：

1. `benchmark_spec`
2. `walk_forward_spec`
3. `cost_sensitivity_grid`
4. `execution_timeline`
5. `cash_sleeve_policy`
6. `family_validation_bundle`
7. `business_admission_gate`
8. `trace_contract`

默认参数口径应直接继承 510300 正式报告：

1. `walk_forward = 60/12/12`
2. `cost_sensitivity_grid = [0, 5, 10] bps`
3. `execution_timeline = prev_close_signal -> next_open_risk_leg -> same_close_cash_rebuild`
4. `business_admission_gate = oos_cagr >= 2 x benchmark_cagr && oos_mdd <= benchmark_mdd`

实施要求：

1. `ResearchValidationContract` 应先作为 `strategy_spec` / `validation_profile` / `submission_gate` 的桥接合同引入，而不是要求所有调用方首版就直接改成新对象。
2. 510300 的 `ResearchProtocol` 应视为该合同的首个参考实现，而不是与工厂 admission 并行存在的第二套主门。
3. 合同首版应允许“显式未覆盖”状态，但必须禁止无记录的静默补洞。

### 7.2 生成产物三段化

生成器不应再直接产出可提交 candidate，而应强制拆成三类对象：

1. `StrategyIntent`
   - 回答“这套策略要解决什么问题”。
2. `StrategySpecDraft`
   - 回答“候选草案长什么样”。
3. `ExecutableStrategySpec`
   - 回答“这是不是一套完整、可回测、可提交、可审计的交易策略”。

修复目标是消除“信号原型”和“完整交易策略”之间的断层。

落地约束：

1. 首版可以先以“逻辑层对象”或 envelope 字段形式并存于当前 candidate dict，不要求一次性在所有模块中替换为新类。
2. `ExecutableStrategySpec` 的实现应优先复用现有 `StrategySpec`、`candidate_contract_snapshot` 与 `execution_contract_hash`，避免平行维护两套可执行规范。

### 7.3 provenance 与 completeness 收紧

以下字段不再允许静默补成“看起来完整”：

1. `risk_rules`
2. `execution_assumptions`
3. `cost_sensitivity_grid`
4. `runtime_playbook`
5. `claim_to_trade_plan_map`

这些字段必须显式记录：

1. `provenance = user_asserted | derived | missing`
2. `completeness_score`
3. `hard_failures`

Gate A 的判定原则如下：

1. `missing` 的关键字段直接 `reject`
2. `derived` 但尚未验证的关键字段默认 `revise`
3. `validated` 或 `user_asserted` 的关键字段才允许进入后续阶段

灰度策略如下：

1. 第一阶段先补 `provenance` 记录、`completeness_score` 与 `hard_failures`，但不立即切主拒绝。
2. 第二阶段把关键 `missing` 从 warning 升级为 `revise`。
3. 第三阶段再把明确禁止项升级为 `reject`，以避免直接打断当前生成与回放链路。

### 7.4 新增 `FactoryGateReport`

所有关键 gate 都必须输出统一格式的证据报告，至少包含：

1. `gate_name`
2. `decision = pass | revise | reject`
3. `hard_failures`
4. `evidence_gap_codes`
5. `artifact_ids`
6. `retrieval_context_ids`
7. `trace_ids`
8. `family_outcome_summary`

禁止继续使用单一布尔值表达复杂的质量门结论。

实现上优先升级当前 `gate_artifact.v1` / `governance_plane_contract`，而不是抛弃现有治理平面重新发明平行报告对象。

### 7.5 新增 `TraceContract`

系统必须引入统一 `trace contract`，打通以下对象：

1. `prediction_trace_id`
2. `signal_event`
3. `intended_order`
4. `actual_fill`
5. `position_round_trip`
6. `pnl_event`

之后所有孵化报告、推广审查和失败复盘，只读这条主链，不再混用多份派生统计。

实现顺序应为：

1. 先把现有 `trace_id`、signal snapshot、signal evidence、execution lineage、trade audit summary 统一挂到 `prediction_trace_id`。
2. 再补缺失的 intended order / actual fill / pnl 对齐。
3. 最后再决定是否下沉为单独物理 ledger 表。

## 八、DSL 与执行语义修复方案

当前 DSL 的问题，不是无法表达条件，而是还没有被强制表达“完整交易语义”。

### 8.1 DSL 必须覆盖的动作

AI 生成的 DSL 必须至少能显式表达以下动作：

1. `entry`
2. `add`
3. `reduce`
4. `exit`
5. `rebuild_cash`

### 8.2 DSL 必须覆盖的执行语义

DSL 编译结果必须显式覆盖：

1. 前收信号。
2. 次日开盘风险腿执行。
3. 同日收盘现金池重建。
4. 分红处理路径。
5. 止盈止损。
6. 回撤失效。
7. 滑点补偿。
8. 执行价格基准。
9. 仓位与现金池调度。

### 8.3 claim 到 trade plan 的强映射

任何策略 claim 都必须有明确的 trade plan 映射：

1. 证据声称“趋势增强”，则必须有趋势确认、仓位调整和失效条件。
2. 证据声称“回撤控制”，则必须有减仓、退出或现金切换语义。
3. 证据声称“收益增强”，则必须说明收益来自哪类暴露，而不是只给出触发条件。

## 九、生成器、reviewer 与向量记忆修复方案

### 9.1 生成器目标函数重写

`LLMProxyStrategyGenerator`、`RuleStrategyGenerator`、`BanditParameterOptimizer` 的目标函数应从“局部评分最优”改成“研究级接收率最优”。

新的优化目标应同时考虑：

1. Gate A 通过率
2. Gate B 通过率
3. Gate C 通过率
4. 被拒绝原因分布
5. 家族级通过率

但这里不应从零重写反馈闭环，优先复用现有 `feedback_metrics`、`budget_feedback`、family/target_pool/generator_mode 反馈路由，再把 Gate A/B/C 结论接入这些现有反馈指标。

### 9.2 reviewer 的定位

`MultiAgentStrategyReviewer` 不删除，但定位应调整为：

1. Gate A 的语义评审子模块
2. 负责发现结构缺口、风险规则缺口与目标不对齐
3. 不再承担研究级 admission 的最终主判断

### 9.3 向量体系拆分

当前向量体系应明确拆成两类索引：

1. `dedup index`
   - 继续服务参数/行为去重。
2. `research memory index`
   - 专门存储家族级 OOS 证据、失败模式、执行失真案例、相似任务结论。

### 9.4 生成阶段的强制检索上下文

生成阶段不得只拉轻量 `history_summary`，而应至少同时拉取三类上下文：

1. 最近成功家族
2. 最近被拒家族及拒绝原因
3. 同 regime 的执行失败案例

这些 `artifact_id` 与 `retrieval_context_id` 必须写入 `FactoryGateReport`，形成可追溯证据。

## 十、闭环反馈修复方案

### 10.1 反馈对象

后续所有 gate 输出，都必须回写以下统一字段：

1. `failure_reason_codes`
2. `evidence_gap_codes`
3. `family_outcome_summary`
4. `target_contract`
5. `trace_contract`

### 10.2 闭环目标

闭环不是让生成器“记住高分策略”，而是让它记住以下结构化事实：

1. 哪类候选在 Gate A 经常缺什么。
2. 哪类候选在 Gate B 的 OOS 或多重检验上失败。
3. 哪类候选在 Gate C 是“预测好但执行差”。
4. 哪类候选在某类市场 regime 下存在系统性失真。

### 10.3 100% 可追溯的工程定义

“预测一致性 100% 可追溯”的工程定义是：

1. 每一个 promotion 或 rejection 结论，都能反查 `prediction_trace_id`。
2. 每一个 `prediction_trace_id`，都能反查对应的：
   - hypothesis
   - DSL
   - intended order
   - actual fill
   - round-trip
   - pnl
   - gate failure reason

这不是对未来市场命中率的承诺，而是对系统证据链一致性的承诺。

## 十一、交付路线图

### Phase 1：协议硬化

目标：先把“对象类型、研究协议、trace 协议、gate 报告协议”收口，并以兼容方式挂到现有主链。

#### 交付项

1. `ResearchValidationContract`
2. `StrategyIntent`
3. `StrategySpecDraft`
4. `ExecutableStrategySpec`
5. 字段 provenance 模型
6. `FactoryGateReport`
7. `TraceContract`

#### 完成标准

510300 的三类策略能够在无人工补丁前提下，被编译成完整 `ExecutableStrategySpec`：

1. 基准定投
2. 止盈定投
3. `MA + RSI` 趋势过滤增强策略

额外要求：

1. 不破坏当前 `quality_report`、`governance_plane`、`gate_artifact` 的既有消费者。
2. 新协议默认以 feature flag 或 contract version 灰度，不允许一次性硬切主调用路径。

### Phase 2：Gate B 前移

目标：把研究报告级 admission gate 前移到 `submit` 之前，但通过升级当前 `submission_gate` 实现，而不是平行复制另一条提交流程。

#### 交付项

1. 研究级回测与家族验证包
2. `0/5/10 bps` 成本敏感性
3. 家族级 OOS admission decision
4. 基准定投对照标准化
5. `cash sleeves` 审计结果并入 admission package

#### 完成标准

任何候选都必须先拿到家族级 OOS 审核包，才能进入 dedup 与 incubate。

说明：

1. 首版允许“当前通用 admission + 510300 协议补充报告”并行输出。
2. 待回归稳定后，再把业务硬门槛切换为默认主判定。

### Phase 3：Gate C 收口

目标：把孵化期质量门升级成“双质量门 + trace 账本”，并收口当前 `signal_quality / execution_quality / hard_gate_result` 的多处消费。

#### 交付项

1. `SignalQualitySnapshot`
2. `ExecutionQualitySnapshot`
3. `PredictionTraceLedger`
4. `IncubationDualGate`
5. 推广审查只读双质量快照

#### 完成标准

promotion review 不再直接依赖 legacy readiness score，而只消费：

1. 双质量快照
2. trace ledger
3. hard gate failure codes

兼容要求：

1. `readiness_score` 在过渡期可继续保留为排序辅助。
2. 但 promotion 主判断不得再依赖它覆盖双质量硬门。

### Phase 4：反馈闭环

目标：把家族研究记忆、失败原因、目标合同和 bandit 目标统一回接到生成入口。

#### 交付项

1. 研究记忆检索合同
2. 失败原因反馈合同
3. 目标任务合同反馈
4. 生成器目标重写
5. bandit objective 与 Gate A/B/C 统一

#### 完成标准

任一被拒绝或被推广策略，都能回答：

1. 它为何被生成。
2. 它为何被拒绝或通过。
3. 它引用了哪组历史家族证据。
4. 它的预测与执行是否一致。

## 十三、验收矩阵

### 13.1 研究标准回归

使用 510300 正式报告作为金标准回归集，验证三类策略在新协议下能够：

1. 复现相同交易语义。
2. 在合理容差内复现基准 `CAGR / MDD`。
3. 复现 `cash sleeves` 调度结论。
4. 复现 `0/5/10 bps` 成本敏感性方向。

### 13.2 Gate A 验收

构造“字段齐全但关键字段全靠默认值”的候选，验证：

1. Gate A 必须拒绝或要求 revise。
2. 拒绝原因必须明确指向 provenance/completeness 缺口。

### 13.3 Gate B 验收

构造以下候选，验证 Gate B 必须拒绝：

1. 样本内优秀但 OOS 不达标的候选。
2. `White / SPA / PBO` 失败的候选。
3. reviewer 高分但业务门槛未过的候选。

### 13.4 Gate C 验收

构造以下样本，验证 Gate C 的主判断正确：

1. `signal_quality` 达标但 `execution_quality` 不达标。
2. `win_rate` 高但 `skill_lcb <= 0`。
3. `effective_n` 不足但表面收益较好。

系统必须禁止 promotion，并明确指出问题出在：

1. fill
2. slippage
3. conversion
4. round-trip

### 13.5 向量闭环验收

验证以下事项：

1. 重复策略能被 `dedup index` 识别。
2. 生成器在 drafting 前，必须能检索到最近成功家族、最近失败家族和执行失败案例。
3. 对应 `artifact_id` 能回写到 gate report。

### 13.6 trace 完整性验收

从任一 promotion 或 rejection 结果出发，必须可以反查：

1. `prediction_trace_id`
2. Gate A/B/C artifact
3. 订单与成交事件
4. position round-trip
5. pnl event
6. failure reason code

## 十五、边界与非目标

本轮修复明确不把以下事项作为第一优先级：

1. 不优先改 UI。
2. 不优先重构向量数据库底座。
3. 不优先重写底层数据库 schema。
4. 不优先把所有 legacy score 一次性删除。
5. 不把 `win_rate` 包装成命中率主指标。
6. 不把本方案理解为一次性替换现有 `gate_0~gate_3` 的大爆炸式重写。

本轮唯一优先级是：  
把 510300 报告已经证明有效的研究协议，提升为策略工厂的默认业务准入标准。

## 十六、最终交付要求

本方案落地后，策略工厂必须能够稳定回答以下问题：

1. 这个策略为什么会被生成。
2. 这个策略的 hypothesis 是由什么证据支持的。
3. 这组证据如何被编译成 trade plan 与 DSL。
4. 它在 submit 前是否通过了研究报告级的家族验证。
5. 它在孵化期的信号质量是否仍然成立。
6. 它的预测优势是否成功转成了可实现收益。
7. 它为什么被推广、继续观察或拒绝。

如果系统仍然回答不了上述任一问题，那么它仍然不是“研究级策略工厂”，而只是“能生成候选的策略系统”。
