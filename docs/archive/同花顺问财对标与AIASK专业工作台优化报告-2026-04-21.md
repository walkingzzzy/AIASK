# 同花顺问财对标与 AIASK 专业工作台优化报告

> 文档角色：时点性对标审计 + 产品优化方案  
> 适用范围：`apps/web`、`apps/bff`、`packages/akshare-mcp`，以及同花顺问财桌面 Web 对标  
> 校准说明：问财侧结论基于 2026-04-21 当天通过 Playwright MCP 的真实桌面 Web 深测；AIASK 侧结论基于当前仓库代码与现有页面结构，不等于全部页面已重新跑过实时回归  
> 阅读方式：先看“0. 摘要”和“4. 该学什么 / 不该学什么”，再看“5. 差距矩阵”和“6. 优化路线图”

## 0. 摘要

这份报告的核心结论只有一句话：

- **AIASK 不应该向问财收敛成单入口 AI 产品，而应该继续走“专业工作台”路线。**
- **真正值得借鉴的不是问财的入口形态，而是它把研究结果做成“可继续操作的下一步”。**

问财的强项在于：

1. 把自然语言问题迅速转成选股、搜索、对话、策略、主题研究等任务入口。
2. 把结果页做成可继续筛选、对比、跳转、追问的操作面板。
3. 用推荐问题、推荐条件、推荐视图，持续缩短用户下一步动作成本。

AIASK 当前的强项在于：

1. 页面深度远高于问财，已经覆盖行情、研究、策略、组合、模拟交易、风控、绩效、执行。
2. 已具备 `CopilotDock + AskAiButton + pageContext + pageActions + SSE chat` 的跨页研究副驾驶骨架。
3. 已有 `assistant / search / screener / strategy-market / risk / portfolio / paper-trading` 等专业模块，适合做真正的工作台，而不是消费级单入口问答。
4. 已有 `MCP resources/prompts/tool-catalog + skills registry + strategy_manager + workbench-store` 这套平台层，不需要再为“AI 化”重造一遍底座。

因此本轮建议不是“做一个 AIASK 版问财”，而是：

- 保留多页面专业工作台结构。
- 把 `CopilotDock` 升级成全站研究副驾驶。
- 把 `assistant / search / screener` 的结果页统一成“可继续操作的研究结果”。
- 把现有 `MCP / skills / strategy-factory` surface 更直接地暴露给产品层，而不是新增一层平行系统。
- 学问财的结果组织方式，不学它的入口堆叠、推理泄露和高风险回答处理缺陷。

| 二次条件追加 | AI选股结果页 | 可点击推荐条件如 `a股市值(不含限售股)>100亿元` | 已闭环 | 点击后结果数从 `2265` 降到 `766` |

### 1.3 信息呈现类

问财并不是单一聊天产品，而是“同一产品壳下的多种结果视图”：

- 文本答案：Chat、AI答案 tab、推荐问题回答
- 表格结果：AI选股股票列表、搜索结果列表
- 卡片结果：精选策略、AI看板、主题板块
- 对比结果：多股同列、一问多答
- 来源和聚合：AI搜索 tabs
- 推荐问题和推荐条件：贯穿首页、Chat、结果页
- 会员与登录门槛：`专业版 / 去升级 / 登录 iframe`

### 1.4 前端交互特征

- 导航层级虽然多，但每个入口都对应一种明确任务形态，而不是简单栏目分页。
- 结果页里“下一步动作”非常多：继续筛、继续问、切视图、看策略、看主题、切模型。
- 相比传统财经站，问财的页面更像“任务控制台”，不是“资讯浏览器”。
- 相比纯聊天产品，它没有把所有结果都压平到对话气泡里。

## 2. 问财深测证据与缺陷

### 2.1 已验证通过的关键能力

| 模块 | 深测动作 | 实际结果 |
| --- | --- | --- |
| AI选股 | 输入 `今日成交放量股` | 正常返回股票列表、可视化分析、多股同列等结果 |
| AI选股 | 点击推荐条件 `a股市值(不含限售股)>100亿元` | 条件追加成功，结果数量显著收敛 |
| AI选股 | 点击 `可视化分析` | 进入分析看板，显示估值分位、行业分布、主力资金流向 |
| AI选股 | 点击 `多股同列` | 进入多股对比卡片视图 |
| AI搜索 | 切换 `公告` tab | 激活成功，内容切换为公告结果 |
| AI搜索 | 切换 `图表` tab | 激活成功，无数据时能稳定降级 |
| Chat | 选择历史会话 `什么是市盈率` | 旧会话和完整答案可重新显示 |
| Chat | `股票诊断 -> 诊股报告` | 输入框被自动预填复杂诊断 prompt |
| 投研库 | 打开 `investmentSquare` | 可见主题板块、说明文案、关注数 |
| AI看板 | 打开 `ai-board` | 可见工作台、默认/自定义布局、任务卡片 |
| 精选策略 | 打开 `strategy-list-page` | 可见策略卡、标签、收益和回撤指标 |
| 一问多答 | 打开 `multiChat` | 可见 `问财 / Kimi / 豆包` 多模型模式 |

### 2.2 已发现的正式缺陷

| 严重级别 | 缺陷 | 复现入口 | 影响 |
| --- | --- | --- | --- |
| 高 | 生成阶段泄露内部推理 | AI搜索 `AI答案`、Chat `股票诊断` | 直接暴露内部思考过程，属于高风险产品缺陷 |
| 高 | 高风险请求处理不一致 | `明天一定涨停的股票有哪些` | 没有先拒绝，反而进入预测与搜索链路 |
| 中 | AI选股对宏观问句路由错误 | `大盘今日量能如何` | 被错误解析成个股筛选条件 |
| 中 | Chat skill 模式状态不一致 | `股票诊断 -> 诊股报告` | 已进入诊断模式，但底部标签仍显示 `智能调度` |

### 2.3 对 AIASK 的直接启示

- **必须显式防止推理泄露。**
  问财的真实缺陷说明，“只靠模型自觉不暴露推理”不够。
- **高风险投资请求必须先收敛，再回答。**
  否则会从“智能辅助”滑到“危险承诺”。
- **自然语言路由必须给出可解释边界。**
  宏观问题不应静默转成个股筛选。
- **skill 模式切换必须是全链路一致状态。**
  仅预填 prompt 不够，输入态、模式标签、结果态都要一致。

## 3. AIASK 当前代码能力映射

### 3.1 当前产品形态

AIASK 当前形态不是问财式单入口产品，而是专业工作台：

- 顶层导航由 [`apps/web/components/app-shell.tsx`](../../apps/web/components/app-shell.tsx) 组织为 `看盘 / 研究 / 策略 / 交易 / AI`
- 首页 [`apps/web/app/page.tsx`](../../apps/web/app/page.tsx) 是综合总览工作台
- AI 能力拆分在：
  - [`apps/web/app/assistant/page.tsx`](../../apps/web/app/assistant/page.tsx)
  - [`apps/web/app/search/page.tsx`](../../apps/web/app/search/page.tsx)
  - [`apps/web/app/screener/page.tsx`](../../apps/web/app/screener/page.tsx)
  - [`apps/web/app/chat/page.tsx`](../../apps/web/app/chat/page.tsx)

这意味着 AIASK 的天然方向更接近“研究操作系统”，而不是“财经问答门户”。

### 3.2 已具备但入口分散的能力

| 用户任务 | AIASK 当前代码 | 结论 |
| --- | --- | --- |
| 市场总览与机会发现 | 首页、`market`、`watchlist`、`strategy-market` | 已具备，但缺少统一 AI 串联 |
| 自然语言选股 / 主题搜索 | `screener`、`search` | 已具备，但结果页不够任务化 |
| 个股研究 | `stock`、`research`、`fundamental`、`technical`、`sentiment`、`valuation` | 深度强于问财 |
| AI 决策与诊断 | `assistant`、`chat` | 已具备，但入口分散、结果 contract 不统一 |
| 自选 / 组合 / 风控 / 执行 | `watchlist`、`portfolio`、`risk`、`paper-trading`、`execution` | 明显强于问财消费侧产品 |
| 跨页 AI 联动 | `CopilotDock`、`AskAiButton`、`pageContext`、`pageActions` | 已有骨架，但还没有做成系统能力 |

### 3.5 从代码层再看：MCP / skills / 前后端 / 策略工厂

这一节只讨论当前仓库已经存在的真实能力，不讨论理想设计。

#### 3.5.1 MCP：已经不是“工具调用层”，而是带治理信息的 runtime surface

从代码上看，AIASK 的 `MCP` 不是一个薄封装：

- [`packages/akshare-mcp/src/akshare_mcp/server.py`](../../packages/akshare-mcp/src/akshare_mcp/server.py)
  - 已支持 `full / worker / tool-only` 三种 startup profile
  - 已对 `vector / skills / quant / sentiment / data_sync / factor_profile` 做 lazy import
  - 这说明当前运行时已经在处理“能力完整性”和“启动成本”之间的平衡
- [`packages/akshare-mcp/src/akshare_mcp/tool_registry.py`](../../packages/akshare-mcp/src/akshare_mcp/tool_registry.py)
  - 已能导出工具实现路径、签名、参数和 category
  - 这意味着 MCP surface 本身已经是可审计的，不只是一个黑盒工具池
- [`packages/akshare-mcp/src/akshare_mcp/scenario_coverage_matrix.py`](../../packages/akshare-mcp/src/akshare_mcp/scenario_coverage_matrix.py)
  - 已能把 runtime tool surface 和 coverage matrix 文档做 merge
  - 说明项目里已经有“运行时能力”和“覆盖率基线”之间的治理脚手架
- [`apps/bff/src/data/data.service.ts`](../../apps/bff/src/data/data.service.ts)
  - 已通过 BFF 暴露 `resource://server/tool-catalog`、`resource://governance/system/report` 等 MCP resources
  - 这说明 resources 已经不只是运维资产，理论上可以被产品层直接消费

这里有一个需要写进报告的明确信号：

- [`packages/akshare-mcp/README.md`](../../packages/akshare-mcp/README.md) 当前记录 `tools: 155`
- [`docs/171工具全量对话式深度测试任务.md`](../../docs/171工具全量对话式深度测试任务.md) 当前记录 `运行时工具数: 161`

这不是小问题。它说明当前更值得补的是 `runtime/documentation baseline` 的自动对齐和可见性，而不是重做 MCP 架构。

代码层结论：

- `MCP` 当前缺的不是 transport 或 manager 重写
- 真正缺的是把现有 `tools / resources / prompts / coverage / health` 更明确地接到产品层、测试层和治理层

AIASK 的 `skills` 也不是“写几份 prompt 文档”这么简单：

代码层结论：

- skills 已经有 registry 和执行链

- [`apps/bff/src/chat/chat.service.ts`](../../apps/bff/src/chat/chat.service.ts)
  - 当前会把 provider delta 直接流式转发到前端
- [`apps/bff/src/chat/tools/system-prompt.ts`](../../apps/bff/src/chat/tools/system-prompt.ts)
  - 已有情绪、KYC、合规和审计要求
  - 但没有显式禁止暴露内部推理、规划过程或工具选择中间态

这里的结构性问题已经比较明确：

- [`apps/web/lib/copilot-types.ts`](../../apps/web/lib/copilot-types.ts) 的 `CopilotPageContext`
  目前仍偏“页面摘要对象”
- [`packages/shared-types/src/workspace.ts`](../../packages/shared-types/src/workspace.ts) 的 `WorkspaceSharedContext`
  目前能承载 code、strategyId、conversationId 等基础字段，但仍偏“页面级上下文”

也就是说，AIASK 现在已经有跨页 AI 骨架，但“任务连续性 contract”还没有完全长出来。

代码层结论：

- 前后端现在缺的不是更多页面，也不是更多 MCP tools
- 缺的是一层统一的 `研究结果 contract + 任务上下文 contract + 推荐动作 contract`

#### 3.5.4 策略工厂：已经是一条分布式产品线，不是待建设能力

策略工厂这块，代码证据比初版报告更强：

- [`packages/strategy-factory/README.md`](../../packages/strategy-factory/README.md)
  - 已明确 `packages/strategy-factory` 是当前主实现
  - `akshare_mcp.services.strategy_factory` 主要保留兼容层
- [`策略工厂/README.md`](../../策略工厂/README.md)
  - 已明确主实现、MCP 入口、BFF/Web 消费面的代码路径
- [`apps/bff/src/strategy/strategy.service.core.ts`](../../apps/bff/src/strategy/strategy.service.core.ts)
  - 已不只是简单透传 `strategy_manager`
  - 还承担 cache、normalize、factory runs 状态归一化、自动刷新、observability 读取
- [`apps/web/app/strategy-market/page.tsx`](../../apps/web/app/strategy-market/page.tsx)
  - 已有 capability badges、daily snapshot、factory runs、observability、featured strategies、cart 等产品层能力

这说明当前“策略工厂”并不是一个待立项的缺口，而是一条已经存在的分布式产品线：

- 主实现：`packages/strategy-factory`
- MCP 入口：`strategy_manager`
- BFF 合同层：`apps/bff/src/strategy`
- Web 产品层：`apps/web/app/strategy-market`

代码层结论：

- 策略工厂不该再被当成“未来要做的大功能”
- 当前更该做的是把它接回 `assistant / search / screener / Copilot / 首页任务看板` 这些 AI 研究路径

#### 3.5.5 代码层总判断

从这轮代码核对看，AIASK 当前状态可以明确分成三类：

| 分类 | 代表能力 | 判断 |
| --- | --- | --- |
| 已具备但产品入口分散 | `MCP resources/prompts`、`skills`、`Copilot`、`strategy-market`、`workbench` | 不应重做，只应强化入口与联动 |
| 能力存在但 product contract 偏弱 | `assistant/search/screener`、`pageContext/pageActions`、`chat SSE` | 需要补统一 contract、状态和安全护栏 |
| 当前确实值得新增 | 结果视图切换、推荐下一步、任务型首页看板、skill 内嵌触发 | 适合做增量增强，不需要推翻现有结构 |

## 4. 该学什么 / 不该学什么

### 4.1 值得借鉴

#### 1. 把结果做成“下一步操作面板”

问财真正强的不是“回答一句话”，而是回答之后立刻给你：

- 继续筛
- 切视图
- 看对比
- 看主题
- 看策略
- 继续追问

AIASK 应该把这一点落到：

- `assistant`
- `search`
- `screener`

三个页面的结果 contract 上。

#### 2. 用推荐条件和推荐问题降低下一步成本

问财的结果页几乎总会引导下一步。AIASK 也应该在结果页里补：

- 推荐条件
- 推荐追问
- 推荐跳转
- 推荐研究动作

#### 3. 用工作台承接复杂任务，而不是让用户自己记路径

问财的 `AI看板` 本质上是在做“任务模板化”。AIASK 已有 `workspace-templates` 和 `workbench-store`，完全可以做得更专业。

#### 4. 用主题/策略卡片把抽象概念产品化

问财的 `投研库` 和 `精选策略` 说明一件事：

- 很多用户并不从“股票代码”开始，而是从“主题/策略/问题”开始。

AIASK 也应该允许从：

- 研究主题
- 策略模板
- 风险任务
- 组合巡检

进入后续研究链路。

### 4.2 不建议借鉴

#### 1. 不要改成单入口 AI 门户

AIASK 当前在交易、执行、组合、风控、策略等模块上的深度，本来就是专业工作台优势。收敛成问财式单入口，会削弱现有产品价值。

#### 2. 不要复制问财的多入口重叠语义

问财的 `AI选股 / AI搜索 / Chat / 一问多答 / 投研库 / AI看板` 入口很多，规模够大时成立，但对 AIASK 这种工作台产品来说，过多重叠入口会提高理解成本。

#### 3. 不要允许推理泄露

问财真实暴露了内部推理文本。AIASK 当前 [`apps/bff/src/chat/chat.service.ts`](../../apps/bff/src/chat/chat.service.ts) 会直接把模型 delta 流式透传到前端，因此后续必须显式加防线。

#### 4. 不要对高风险请求做“貌似有帮助”的危险回答

问财在“涨停、保证收益”类问题上处理并不稳定。AIASK 必须优先守住合规和安全边界。

#### 5. 不要为了 AI 气氛牺牲页面职责清晰度

AIASK 当前页面职责是清楚的：

- `assistant` 是决策与诊断
- `search` 是搜索与相似/语义检索
- `screener` 是条件选股
- `research` 是研报公告与研究信息

这个清晰度应该保留。

## 6. 优化路线图

### 6.0 不重构前提

这轮更新建议全部建立在“增量改造”前提下，不建议：

- 不重写 `MCP gateway`、不替换当前 transport / manager 结构
- 不把 `skills` 从现有 registry / executor 体系迁出去
- 不把 `strategy-factory` 从 `package + MCP + BFF + web` 现有分层推倒重来
- 不新增一套平行的 AI 页面体系去覆盖现有 `assistant / search / screener / strategy-market`

建议的边界是：

- 在现有页面和 BFF 合同层上补统一 result/context/action contract
- 用现有 `MCP resources/prompts/skills/strategy_manager` 做产品接入
- 用现有 `workbench-store` 维持跨页任务状态
- 先做“串联和可见化”，后做“局部增强”，不做大迁移

### 6.1 P0：把 CopilotDock 升级成全站研究副驾驶

#### 目标

从“右侧聊天框”升级成“跨页持续研究任务层”。

#### 产品动作

- 从首页、搜索、选股、研究、策略页统一注入：
  - 当前对象
  - 页面摘要
  - 推荐下一步
  - 可执行动作
- Copilot 会话不仅能回答，还要能反向触发：
  - 去研究页
  - 去基本面
  - 去资金流
  - 加入自选
  - 加入工作台

#### 代码触点

- [`apps/web/components/copilot-dock.tsx`](../../apps/web/components/copilot-dock.tsx)
- [`apps/web/lib/copilot-types.ts`](../../apps/web/lib/copilot-types.ts)

## 7. 深度测试体系建议

### 7.1 问财外部平台深测矩阵

继续只用 Playwright MCP，固定覆盖：

- AI选股：
  - 问句解析
  - 二次条件
  - 可视化分析
  - 多股同列
  - 结果跳转
- AI搜索：
  - tab 切换
  - AI答案生成态
  - 无结果降级
  - 资讯类型覆盖
- Chat / 一问多答：
  - 推荐问题
  - 历史会话
  - skill 模式
  - 多轮追问
  - 发送链路
- 非功能：
  - 推理泄露
  - 高风险回答
  - 状态一致性
  - 加载恢复

### 7.2 AIASK 本地对照测试矩阵

按用户任务跑，不按页面孤立冒烟：

1. 从首页发现机会
2. 发起搜索/选股
3. 进入个股研究
4. 调用 AI 总结与统一决策
5. 加入自选 / 工作台 / 策略链路
6. 在 Copilot 中继续追问并执行页面动作

补充一组平台层深测，不再只测页面 happy path：

1. `MCP`：
   校验 `tool-catalog / governance-report / workflow-guide` 是否能被 BFF 稳定读取，health/fallback 是否被正确透出
2. `skills`：
   校验 `/v1/skills` 列表、过滤、触发、执行结果写回 workbench context 是否一致
3. `前后端 contract`：
   校验 `pageContext / pageActions / availableActions / conversationId / workspace context` 在跨页后是否延续
4. `策略工厂`：
   校验 `ranking / capabilities / daily snapshot / factory runs / observability` 是否能被首页、Copilot、策略页交叉消费

### 7.3 AIASK 回归重点

| 优先级 | 回归项 | 原因 |
| --- | --- | --- |
| P0 | Copilot 注入与跨页上下文延续 | 这是专业工作台路线的核心差异点 |
| P0 | `assistant/search/screener` 统一结果 contract | 决定结果页是否真正可操作 |
| P0 | pageActions 执行成功率与回执 | 决定 AI 是否只是“会说”还是“会做” |
| P0 | `strategy-market` 接入 AI 研究链路 | 决定策略工厂是否从独立频道变成任务闭环组成部分 |
| P1 | MCP resources / health / governance 可见性 | 决定平台层是否能被产品和测试体系稳定消费 |
| P1 | skills 嵌入业务页的触发与回写 | 决定 skills 是否真正成为 workflow shortcut |
| P1 | 结果视图切换 | 决定问财式组织能力是否真正落地 |
| P2 | 推理泄露和高风险请求防线 | 防止问财已暴露的问题在本地重演 |

---

## 8. 最终判断

如果只看“AI 入口气势”，问财像更成熟的 AI 产品；  
如果看“完整工作流深度”，AIASK 已经是更专业的投研工作台。

因此 AIASK 这轮最正确的演进方向不是：

- 再做一个更大的 AI 首页
- 再拆更多 AI 菜单
- 把所有结果都塞回聊天框

而是：

- 让现有专业页面更容易被 AI 串起来
- 让结果页更像任务工作台
- 让 Copilot 成为跨页研究副驾驶
- 让 AIASK 保留专业工作台优势，同时吸收问财在结果组织上的产品经验

这才是“学到问财的长处，又不丢掉 AIASK 自己的产品方向”。
