# 四工厂独立化与 MCP 瘦身拆分开发方案

## 文档定位

本文档是四工厂独立化与 `akshare-mcp` 瘦身拆分的唯一 target-state 主方案。它不是现状证明文档，而是把已经核对过的 current-state 事实转成可执行的开发路线、代码迁移矩阵、PR 级实施顺序、测试守门和回滚策略。

当前真实情况继续以 `docs/factory-architecture/01`、`03`、`09`、`12`、`13` 为准；本文档只在这些事实之上定义目标边界和开发计划。凡是本文档里出现的新目录、新模块、新类型，除非特别注明“已存在”，否则都属于 `planned/target` 路径。

## 一、方案结论

- 真正的问题不是 MCP tool catalog 太多，而是 `akshare-mcp` 同时承担了 `MCP host`、`runtime bridge`、`factory owner` 三种角色。
- 四工厂要独立，关键不是先删工具，而是先把“谁拥有运行编排、谁拥有 contract、谁负责 host/integration”反转清楚。
- 本次终态固定为：
  - `strategy-factory` 拥有四工厂运行编排、状态机、公共 runtime contract、health/detail DTO、后台 runtime ownership。
  - `aiask-quant-core` 继续只保留共享存储、回测、验证、风险、signal/position/audit primitive。
  - `akshare-mcp` 收缩为 MCP host、tool/resource/prompt/manager facade、外部数据与 SQLite/provider/integration 层。
- 迁移方式固定为三阶段渐进迁移，不做一次性大搬家，不新增第五个 runtime package，不改现有 CLI 名和 root runner 名。

## 二、当前事实基线

本轮开发计划建立在以下 current-state 基线上：

- 运行拓扑已经固定为 `4 factory supervisor + 1 sidecar`。
- `SignalTracker` 继续是 sidecar，不混回 supervisor。
- `strategy-factory` 已经有公共契约、scheduler、cycle pipeline、readiness/submission/theme-event 骨架，但默认执行路径仍依赖 `akshare-mcp` 注入。
- 四工厂大量真实运行实现仍在 `packages/akshare-mcp/src/akshare_mcp/services/` 下。
- `docs/factory-architecture/12-四工厂真实流程与MCP依赖审计.md` 和 `13-四工厂-MCP能力占用台账.md` 已经形成 current-state 证据台账；本文档在其基础上给出拆分开发计划。

## 四、目标边界与冻结决策

### 4.1 目标边界

- 四工厂以独立进程运行，默认主执行路径不再依赖 `akshare_mcp.server`。
- 四工厂公共 runtime 入口统一落在 `strategy_factory.runtime.*`。
- `strategy-factory` 拥有：
  - 四工厂运行编排
  - phase 状态机
  - sidecar/paper runtime ownership
  - 公共 runtime contract
  - run summary/detail/health DTO
  - `ExecutionUniverseContract` source-of-truth
- `akshare-mcp` 仅保留：
  - MCP server、tool/resource/prompt
  - manager facade
  - 数据抓取、外部平台、SQLite/provider 适配
  - 可选 vector/semantic/LLM/provider
  - 兼容 wrapper 与 compat shim

### 4.2 本轮冻结决策

- 不新增第五个 runtime package。
- `SignalTracker` 继续是 sidecar，不混回 supervisor。
- `run_three_factories.py` 继续只管理 4 个运行体。
- 现有 CLI 名、root runner 名、manager/tool 名先保持兼容。
- `strategy-factory` 继续禁止静态 import `akshare_mcp`。
- `akshare-mcp` 迁移后只允许依赖 `strategy_factory.api.*`、`strategy_factory.runtime.*` 和明确保留的 compat shim。

## 六、公共 runtime 契约设计

### 6.1 canonical 类型与入口

本次迁移后，以下类型和入口必须成为 canonical public surface：

- `strategy_factory.api.runtime.RuntimeAdapters`
- `strategy_factory.api.runtime.build_runtime_adapters(...)`
- `strategy_factory.runtime.factor_mining`
- `strategy_factory.runtime.incubation`
- `strategy_factory.runtime.signal_tracker`
- `strategy_factory.runtime.market_event_ingest`

### 6.2 每个 runtime 入口必须统一提供的能力

| runtime | 必备方法 | daemon 型额外方法 |
| --- | --- | --- |
| `FactorMiningRuntime` | `preflight()`、`status()`、`run_once()` | `run_loop()` 可选 |
| `IncubationRuntime` | `preflight()`、`status()`、`run_once()` | `run_daemon()` |
| `SignalTrackerRuntime` | `preflight()`、`status()`、`run_once()` | `run_daemon()` |
| `MarketEventIngestRuntime` | `preflight()`、`status()`、`run_once()` | `run_loop()` 可选 |

### 6.3 必须回迁到 `strategy-factory` 的契约

- `ExecutionUniverseContract`
- 四工厂 `run summary / detail / health payload`
- `blocked / degraded / pending_evidence / passed` 统一状态枚举
- `SignalTracker` sidecar health contract
- `Market Event bridge payload`
- execution universe 查询参数与结果 DTO
- paper runtime ownership contract

### 6.4 过渡期保留的 compat alias

- `MCPRuntimeAdapters`
- `build_mcp_runtime_adapters(...)`
- `akshare_mcp.adapters.strategy_factory_runtime.build_strategy_factory_scheduler_kwargs(...)`
- `akshare_mcp.adapters.strategy_factory_runtime.configure_strategy_factory_runtime_services()`
- `akshare_mcp.adapters.strategy_factory_runtime.build_strategy_factory_runtime_adapters(...)`

这些 alias 在迁移期间保留，但它们不再拥有 canonical semantics，只能代理到 `strategy-factory` 的新主入口。

## 十一、风险与回滚策略

### 11.1 主要风险

- runtime 命名改造后，现有测试和 manager facade 可能大量依赖字符串 `MCPRuntimeAdapters`。
- `ExecutionUniverseContract` 回迁时，SignalTracker / Incubation / 诊断脚本可能出现双 import 路径并存。
- `MatchingEngine` / `NavEngine` ownership 切换容易出现双跑或漏跑。
- `server.py` 收口过快，会让某些旧部署默认缺少后台服务。

### 11.2 回滚原则

- Phase 1 所有变更都必须保留 compat alias，允许回退到旧 import 路径。
- Incubation paper runtime ownership 切换期继续保留 `INCUBATION_FACTORY_OWNS_PAPER_TRADING` 作为临时回滚开关。
- server 收口期允许短期保留 profile 级兼容桥，但不允许继续扩大 embedded ownership。
- root runner 切换前必须先有 contract snapshot 和 run-once 回归，不能先切入口再补测试。

## 十二、阶段完成定义

### Phase 1 完成定义

- `RuntimeAdapters` 成为 canonical 公共命名。
- `strategy-factory` 拥有 canonical provider registry 与 bootstrap 语义。
- `ExecutionUniverseContract` source-of-truth 回迁完成。

### Phase 2 完成定义

- 四工厂都已有 `strategy_factory.runtime.*` 真实入口。
- 每个 root runner 的 primary path 都直接走 `strategy-factory`。
- 旧 `akshare-mcp` factory service 退化为 compat adapter 或 integration glue。

### Phase 3 完成定义

- `akshare-mcp/server.py` 不再启动 Strategy Factory、SignalTracker、MatchingEngine、NavEngine 等 factory-owned runtime。
- manager facade 只依赖 `strategy_factory.api.*` 与 `strategy_factory.runtime.*`。
- current-state 文档已更新为新的 owner/path，根目录主方案只保留 target-state 与剩余弃用计划。

## 十三、给实施者的直接指令

如果按本方案开始落地，推荐的第一轮实际开发顺序是：

1. 先做 `PR-1` 到 `PR-3`，只解决命名、bootstrap、contract owner，不碰四工厂大块逻辑。
2. 然后按 `Factor Mining -> Incubation -> SignalTracker -> Market Event Ingest` 顺序迁移 orchestration。
3. 每迁完一个工厂，立刻切该工厂 root runner primary path，再收缩对应 manager facade。
4. 最后才收 `server.py` 和兼容脚本，不反过来先砍 host。

这份顺序不能反过来做。否则会先失去运行能力，再去补 contract，风险最高。
