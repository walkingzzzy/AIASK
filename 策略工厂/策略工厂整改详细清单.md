# 策略工厂整改详细清单

> 文档目的：
> - 把“当前策略工厂实现与股票交易策略标准定义之间的偏差”收束为可执行的整改计划
> - 形成可以直接拆分为多个 PR / 工作包 / 测试集的工程清单
> - 为后续代码修改提供统一口径，避免继续在“信号模板”和“完整交易策略”之间混用概念

> 参考依据：
> - MLFactor / Backtest 章节：强调 signal、portfolio construction、transaction costs、turnover 和执行约束是完整策略的一部分
> - Portfolio Optimization Book 8.3：强调 backtest overfitting、data snooping、look-ahead bias、survivorship bias、transaction costs
> - CFA Institute 模型验证框架：强调 model validation 不等于单次 backtest，还应覆盖假设、输入、使用场景、监控与回溯
> - 本轮联网核验（2026-03-21）：补充查阅 White (2000) Reality Check、Hansen (2005) SPA、Bailey & Lopez de Prado 的 Deflated Sharpe Ratio / Probability of Backtest Overfitting、Eckbo / MacKinlay 的事件研究方法、Almgren-Chriss 执行成本模型、TCA best practices，以及 Frazzini / Israel / Moskowitz 与 Novy-Marx / Velikov 关于交易成本与异常可实现性的研究

---

## 1. 先给结论

当前策略工厂已经具备以下能力：

- 能基于 snapshot / event 生成研究任务
- 能通过外部模型或本地 fallback 生成候选 DSL / 规则策略
- 能做 Gate-0 / Gate-1 / Gate-2 / Gate-3 的分层筛选
- 能将部分候选落入孵化、刷新已有策略、沉淀运行记录

但从“股票交易策略”这一标准定义看，当前实现仍然存在以下结构性偏差：

1. 生成结果更接近“信号原型”而不是“完整交易策略”
2. 任务约束、提示词约束、候选归一化、提交门禁之间存在口径不一致
3. 回测对交易成本、滑点、容量、可交易性约束覆盖不足
4. 事件任务验证时混入大量非事件股票，容易稀释策略目标
5. Gate-3 主要按因子式横截面统计口径验证，不完全适配事件型 / DSL 时间序列策略
6. 已记录 LLM 尝试次数，但未对多重检验和数据挖掘偏差做显式修正
7. `strategy_preferences` 过于启发式，但被作为硬门禁使用，容易形成标签偏见
8. `refresh_existing` 的使用场景过宽，容易把“新任务的新策略”错误地收敛成“旧策略刷新”

因此，本次整改的目标不是简单放宽门禁，而是把策略工厂从“AI 候选生成器”升级为“可审计、可验证、可执行的股票交易策略工厂”。

### 1.1 前提修正（基于当前仓库状态）

这份整改清单在执行时，必须同时接受下面几个已经被代码和测试固化的前提：

- `STRATEGY_FACTORY_MIGRATION_PLAN.md` 已明确记录：截至 2026-03-20，`P0-P6` 已完成，当前阶段是 compat 观察期，而不是重新发起迁移工程
- 当前整改对象应默认是 `packages/strategy-factory/` 下的主实现、公共 `facade/contracts` 与其 adapter/bridge；`packages/akshare-mcp/` 下旧路径更多承担 compat / re-export / patch-point 保留职责
- `packages/akshare-mcp/tests/test_strategy_factory_package_migration_contract.py`、`packages/akshare-mcp/tests/test_strategy_factory_module_compat.py` 已把兼容导出和 patch surface 锁定为回归基线
- `packages/akshare-mcp/tests/test_strategy_factory_and_marketplace.py` 已把 `refresh_existing`、event candidate refresh、`strict pass for refresh` 等行为锁定为现状契约
- `packages/strategy-factory/tests/test_quality_gates_runtime_execution.py` 等测试已把 Gate-1 代表股模式和部分门禁行为锁定为现状默认值

## 2. 整改总目标

本次整改要同时达成 6 个目标：

### G1. 统一策略定义

把“策略”明确拆成以下组成部分，并要求工厂生成与验证时全链路携带：

- 研究假设 `hypothesis`
- 标的池 / 股票池 `target_symbols`, `stock_pool`
- 信号规则 `entry`, `exit`
- 持有期 / 再平衡语义 `holding_horizon`, `rebalance_rule`
- 风险规则 `risk_rules`
- 组合与仓位规则 `position_sizing`, `portfolio_constraints`
- 成本与执行假设 `commission`, `slippage`, `tradability`, `capacity`
- 验证协议 `validation_protocol`

### G2. 统一任务约束

研究任务必须明确哪些约束是：

- 提示词层软约束
- 归一化层硬约束
- 提交门禁硬约束

不能再出现“前面要求只在目标池内生成，后面又在归一化时扩池，最后再因为扩池被门禁拦下”的自相矛盾。

### G3. 统一验证口径

不同策略类型必须用不同的主验证逻辑：

- 因子 / 排序类策略：可继续强调 IC / OOS / 稳健性
- 事件驱动 / DSL 交易类策略：必须强调交易表现、成本敏感性、样本外衰减、容量与可执行性

### G4. 降低数据挖掘偏差

必须把 run 级别的尝试次数、候选数、选中数纳入最终质量判断，不能只看幸存策略的单点表现。

### G5. 修正事件任务偏离

事件任务生成的候选必须围绕事件目标池、事件方向和事件证据，不应在回测与验证中被过度稀释成“泛市场通用策略”。

### G6. 补齐审计证据

每个候选都必须能追溯：

- 输入任务是什么
- LLM 被要求输出什么
- 目标股票池是什么
- 最终为何扩池 / 未扩池
- 为何通过 / 未通过各级门禁
- 是新策略、衍生策略还是刷新已有策略

## 3. 当前问题与代码落点

## 3.1 问题 A：策略定义不完整，当前更像“信号模板”

### 现象

- DSL 支持 `risk_rules`，但 `DslRuleStrategy.generate_signals()` 并不使用这些规则
- 回测执行默认单票全仓买入 / 全仓卖出
- 工厂主路径没有系统性带入滑点、可交易过滤、容量约束

### 主要代码位置

- `packages/akshare-mcp/src/akshare_mcp/services/strategy_dsl.py`
- `packages/akshare-mcp/src/akshare_mcp/services/backtest/dsl_strategy.py`
- `packages/akshare-mcp/src/akshare_mcp/services/backtest/engine.py`
- `packages/strategy-factory/src/strategy_factory/application/backtest_filter.py`

### 风险

- 候选策略被误判为“可交易策略”
- 高换手、高冲击成本策略在回测中被高估
- `risk_rules` 只是存档，不是真正参与验证

## 3.2 问题 B：任务约束链路前后不一致

### 现象

- Prompt 明确要求优先与 `research_task.target_symbols` 取交集
- 归一化候选时却会把 candidate 和 research_task 的股票池合并
- 提交门禁随后再处罚 `universe drift`

### 主要代码位置

- `packages/akshare-mcp/src/akshare_mcp/services/strategy_llm_provider.py`
- `packages/akshare-mcp/src/akshare_mcp/services/strategy_generators.py`
- `packages/strategy-factory/src/strategy_factory/application/submitter.py`

### 风险

- 系统制造了可避免的 `候选股票池偏离事件目标池`
- 不是模型“犯错”，而是流水线口径冲突
- 结果难以解释，也难以通过后续优化稳定修复

## 3.3 问题 C：事件策略回测与验证目标被稀释

### 现象

- Gate-1 与 Gate-2 都会混入代表性股票
- Gate-3 又额外混入固定大盘蓝筹股票
- 事件策略不再只验证“是否围绕该事件池有效”

### 主要代码位置

- `packages/strategy-factory/src/strategy_factory/application/quality_gates.py`
- `packages/strategy-factory/src/strategy_factory/application/backtest_filter.py`
- `packages/strategy-factory/src/strategy_factory/application/submission_gate.py`

### 风险

- 事件驱动策略被迫在非事件环境也表现稳定
- 容易把事件型研究扭曲为“弱泛化的通用趋势模板”

## 3.4 问题 D：多重检验偏差未被纳入门禁

### 现象

- 工厂记录了 `external_llm_attempt_count`、`selected_count`
- 但 Gate-3 不考虑“这是从多少次尝试里选出来的”

### 主要代码位置

- `packages/strategy-factory/src/strategy_factory/application/factory_scheduler.py`
- `packages/strategy-factory/src/strategy_factory/application/submission_gate.py`
- `packages/strategy-factory/src/strategy_factory/application/quality_reporting.py`

### 风险

- 出现“越多尝试，越容易抽中偶然好看样本”的幸存者偏差
- 当前门禁会高估 LLM 幸存候选的可信度

## 3.5 问题 E：`strategy_preferences` 来源过于启发式，却被当成硬门禁

### 现象

- `高股息`、`防御` 之类主题直接映射到 `quality_factor/value_factor/ma_cross`
- 提交时再把这些启发式偏好变成硬拒绝条件

### 主要代码位置

- `packages/strategy-factory/src/strategy_factory/application/opportunity.py`
- `packages/strategy-factory/src/strategy_factory/application/submitter.py`
- `packages/strategy-factory/src/strategy_factory/application/event_engine.py`

### 风险

- 标签偏见大于真实研究证据
- 阻挡了可能合理但不在预设标签中的候选

## 3.6 问题 F：`refresh_existing` 语义过宽

### 现象

- 当前只要参数相似、目标池高度重合，就可能刷新已有策略
- 但新事件、新主题、新证据条件下，本应视为新实验

### 主要代码位置

- `packages/strategy-factory/src/strategy_factory/application/deduplicator.py`
- `packages/strategy-factory/src/strategy_factory/application/submitter.py`

### 风险

- 新任务结果被错误并入旧策略历史
- 审计链路混乱
- `refresh_existing but no strict pass` 被频繁触发

## 4. 总体实施顺序

建议按以下顺序推进，不建议跳步：

0. 先确认 compat 契约和 patch-point 不被破坏
1. 先统一对象和口径
2. 再修任务约束与目标池规则
3. 再修回测现实性与事件验证协议
4. 再修 Gate-3 统计门禁
5. 再修 dedup / refresh 语义
6. 最后做观测指标、回归测试和灰度切换

不建议先动：

- 前端展示
- 门禁阈值数值微调
- 单个 prompt 文案的小修小补

因为根问题在于定义和协议，而不是阈值太严或模型不够听话。

额外约束：

- 本轮整改默认在 `packages/strategy-factory/` 主实现上演进，再通过 facade / compat bridge 向旧路径透传
- 若某项修改会破坏 `compat/re-export/patch-point` 现有测试，应把兼容桥接和回归补丁作为同一 PR 的一部分，而不是先破后修

## WP1：统一研究任务约束与目标池政策

### 目标

把 `research_task` 中的约束分成明确的软硬规则，避免提示词、归一化、门禁三层自相矛盾。

### 核心设计

给每个任务增加以下字段：

- `preferred_strategy_types`
- `allowed_strategy_types`
- `target_symbol_policy`
- `universe_expansion_policy`
- `preference_strength`
- `validation_focus`

建议语义如下：

- `preferred_strategy_types`
  - 研究偏好，默认软约束
- `allowed_strategy_types`
  - 允许出现的策略类型集合，默认空表示不限制
- `target_symbol_policy`
  - `strict_intersection`
  - `prefer_intersection`
  - `allow_expansion_with_reason`
- `universe_expansion_policy`
  - `forbid`
  - `allow_same_theme_only`
  - `allow_market_fallback`
- `preference_strength`
  - `soft`
  - `medium`
  - `hard`
- `validation_focus`
  - `event_target_only`
  - `target_plus_representative`
  - `broad_generalization`

### 具体修改项

#### 5.1.1 重命名并细化任务偏好字段

把当前 `strategy_preferences` 演进为：

- `preferred_strategy_types`
- `preference_strength`

并保留兼容读取逻辑，避免旧 run / 测试立即失效。

#### 5.1.2 事件任务显式声明目标池政策

对 `event_driven` 任务默认使用：

- `target_symbol_policy = strict_intersection`
- `universe_expansion_policy = allow_same_theme_only`
- `validation_focus = event_target_only`

#### 5.1.3 snapshot 任务使用较宽松策略

对 `snapshot` 任务默认使用：

- `target_symbol_policy = prefer_intersection`
- `universe_expansion_policy = allow_market_fallback`
- `validation_focus = target_plus_representative`

### 涉及文件

- `packages/strategy-factory/src/strategy_factory/application/opportunity.py`
- `packages/strategy-factory/src/strategy_factory/application/collect.py`
- `packages/strategy-factory/src/strategy_factory/application/event_engine.py`
- `packages/strategy-factory/src/strategy_factory/application/factory_scheduler.py`

### 验收标准

- 同一个任务在 prompt、归一化、提交门禁里的约束语义一致
- event 任务默认不能随意扩池
- snapshot 任务仍允许合理扩池

### 测试要求

- event task contract test
- snapshot task contract test
- 兼容旧字段 `strategy_preferences` 的桥接测试

## WP2：修正外部模型提示词与候选归一化的目标池逻辑

### 目标

让外部模型生成阶段与归一化阶段遵守同一套目标池规则，消除系统自造的 `universe drift`。

### 具体修改项

#### 5.2.1 重写 prompt 中的目标池规则字段

把自然语言提示改成结构化约束，不只写中文句子，还要把策略约束作为 JSON contract 明示：

- `target_symbol_policy`
- `universe_expansion_policy`
- `allowed_strategy_types`
- `validation_focus`

#### 5.2.2 修改候选归一化逻辑

当前 `_normalize_candidate_payload(...)` 会把 candidate 与 research symbols 合并。

应改为：

- 若 `target_symbol_policy = strict_intersection`
  - `target_symbols = candidate_symbols ∩ research_symbols`
  - 如果交集为空，则候选直接标记 `constraint_violation`
- 若 `target_symbol_policy = prefer_intersection`
  - 优先交集
  - 交集为空时才允许 fallback
- 若发生扩池
  - 必须记录 `expansion_reason`
  - 必须记录 `expansion_source`

#### 5.2.3 在 `provider_payload` 中保留约束遵守结果

增加审计字段：

- `constraint_check.target_symbols_before_normalize`
- `constraint_check.target_symbols_after_normalize`
- `constraint_check.expansion_applied`
- `constraint_check.expansion_reason`

### 涉及文件

- `packages/akshare-mcp/src/akshare_mcp/services/strategy_llm_provider.py`
- `packages/akshare-mcp/src/akshare_mcp/services/strategy_generators.py`

### 验收标准

- event task 下，模型给出 8 只股票、任务给出 5 只股票时，若是 strict 策略，只能保留交集
- 不再出现“先提示交集、后归一化并集、再提交处罚”的链路矛盾

### 测试要求

- 新增 `strict_intersection` 单元测试
- 新增 `prefer_intersection` 单元测试
- 新增 `allow_expansion_with_reason` 单元测试

- `hypothesis`

## WP4：升级回测现实性，纳入成本、滑点、可交易性和容量

### 目标

让工厂回测不再只用“佣金 + 单票全仓”的极简口径，而是具备基本交易现实性。

#### 5.4.3 事件策略默认不再单票全仓

- 默认等权

## WP5：重构 Gate-1 / Gate-2 的事件验证口径

### 目标

让事件型任务首先验证“在事件目标池是否成立”，而不是先拿泛市场代表股把信号稀释掉。

联网核验补充：事件研究文献反复强调，事件窗口、估计窗口、污染事件控制和基准选择必须显式定义。若 Gate-1 / Gate-2 过早混入非目标股票，会把“事件是否成立”的问题错误替换为“是否能在泛市场代表股上稳定成立”。

### 具体修改项

#### 5.5.1 Gate-1 分流

将 `gate_1_fast_screen(...)` 改为按任务类型分流：

- `event_driven`
  - 优先只在 `target_symbols` 上计算
  - 必须显式记录 `event_window`、`estimation_window`、`holding_window`
  - 样本不足时再按策略声明决定是否补 representative
- `snapshot`
  - 保留当前 target + representative 模式

#### 5.5.2 Gate-2 分层输出

`BacktestFilter` 必须把以下结果明确拆开：

- `target_layer_metrics`
- `representative_layer_metrics`
- `combined_layer_metrics`
- `event_window_metrics`
- `contamination_summary`
- `primary_validation_layer`

#### 5.5.3 Gate-3 根据 `validation_focus` 选择主层

- `event_target_only`
  - 主判定只看 target layer
- `target_plus_representative`
  - 主判定看 target，代表股只做风险提示
- `broad_generalization`
  - 才允许 combined layer 成为主判定

若 `contamination_summary` 显示同窗内存在高强度混杂事件或目标股票被大量替换，应触发 warning 或人工复核，而不是静默并入 combined layer。

- `packages/strategy-factory/src/strategy_factory/application/quality_gates.py`

- event 策略不会因为代表股表现差就被直接误杀
- snapshot 策略仍能保留泛化验证能力
- event task 的报告能直接看见事件窗口与污染摘要

## WP7：引入多重检验修正与 run 级偏差惩罚

### 目标

让工厂在评估幸存候选时，把“尝试次数”纳入质量判断，降低 data snooping 风险。

联网核验补充：White's Reality Check、Hansen SPA、Deflated Sharpe Ratio 与 Probability of Backtest Overfitting 的共同结论是，不能把“从大量尝试里挑出的最佳候选”按单次独立检验对待。因此本 WP 必须分阶段推进，先做稳健的工程代理，再做正式统计修正。

### 具体修改项

#### 5.7.1 新增 run-level correction context

在提交门禁输入中增加：

- `factory_attempt_count`
- `factory_selected_count`
- `task_attempt_count`
- `task_selected_count`

#### 5.7.2 第一阶段先做简单惩罚模型

先不直接上复杂 DSR，也可以先实现一版简单可靠的惩罚：

- 尝试次数越多，最低 Sharpe / OOS 门槛越高
- 候选越多，Bootstrap 下界要求越严格
- `selected_count / attempt_count` 极低时，增加警告或调高 strict pass 门槛
- `attempt_count` 仅作为代理变量使用，不宣称等价于正式多重检验校正

#### 5.7.3 第二阶段再升级为更正式的修正

预留后续升级空间：

- Deflated Sharpe Ratio
- White's Reality Check
- Hansen SPA
- Probability of Backtest Overfitting（如 CSCV / PBO）
- Bonferroni / FDR 只作为保底对照，不建议替代上述更贴近策略筛选流程的方法

注意：更正式的修正最好放在 `WP5/WP6` 把验证 profile 和主判定层稳定之后再做，否则不同策略类型共用错误分布假设，会造成“形式更复杂、结果更不可信”的假精确。

### 涉及文件

- `packages/strategy-factory/src/strategy_factory/application/factory_scheduler.py`
- `packages/strategy-factory/src/strategy_factory/application/submission_gate.py`
- `packages/strategy-factory/src/strategy_factory/application/quality_reporting.py`

### 验收标准

- 同样表现的候选，在“尝试 5 次”和“尝试 100 次”的 run 中不能被完全同等对待
- run summary 必须输出 attempt-adjusted gate 结果

### 测试要求

- 新增 attempt penalty tests
- 新增 run-level adjustment report tests
- 第二阶段补充 DSR / PBO / Reality Check / SPA smoke tests 或 contract tests

## 10. 建议的落地方式

如果只允许先做一轮最小整改，建议最小集如下：

1. 先修 `target_symbol_policy`
2. 再修 event task 的 target-only 验证，并显式记录 `event_window / contamination_summary`
3. 再把 `strategy_preferences` 从硬拒绝降级为分级建议
4. 再把 `refresh_existing` 拆成 `refresh_metrics_only` 与 `spawn_revision_from_existing`
5. 最后补成本 / 滑点 / 可交易过滤的显式传递，以及最小审计字段

这一最小集能最快改善当前最突出的三类问题：

- 任务偏好与目标池不一致
- event 策略被代表股稀释
- refresh_existing 误判

同时它还能避免两个常见误区：

- 在验证协议尚未分流前，过早引入复杂多重检验统计，导致“形式复杂但主判定对象仍然错位”
- 在 compat 观察期内再次大拆迁移路径，导致整改本身先把现有 patch surface 打碎

## 12. 联网核验补充（2026-03-21）

### 12.1 联网核验后的方法论修正

- `WP7` 不应被简化为“记录一个 `attempt_count` 字段就算完成”。外部研究普遍认为，从大量候选中筛出少数优胜者时，单个 Sharpe / OOS 指标会系统性高估，因此本清单把它改成“第一阶段工程代理惩罚 + 第二阶段正式统计修正”的两段式设计。
- `WP5/WP6` 需要显式采用事件研究思路。事件任务首先要回答的是“在目标事件池与事件窗口中是否成立”，而不是“在被扩充后的泛市场股票里是否还能保持类似统计特征”。
- `WP4` 不能再把现实性假设压缩成 `commission + slippage_bps`。执行成本研究和 TCA 实务都表明，显式费用、冲击、滑点、容量和参与率是不同维度，至少需要最小拆分与审计。

### 12.2 与当前代码状态对齐后的约束

- `STRATEGY_FACTORY_MIGRATION_PLAN.md` 已将独立包迁移标记为完成，当前是 compat 观察期，因此整改应默认以 `packages/strategy-factory/` 主实现为中心推进。
- 现有 compat / re-export / patch-point 契约已被 `test_strategy_factory_package_migration_contract.py` 与 `test_strategy_factory_module_compat.py` 固化，不宜在整改中顺手删除旧桥接。
- `refresh_existing`、event candidate refresh、`strict pass for refresh` 等行为已被 `test_strategy_factory_and_marketplace.py` 固化；`Gate-1` 的代表股默认逻辑也已有独立回归。整改需要做的是“重写判定依据并保留兼容桥接”，而不是“假设这些行为目前不存在”。

### 12.4 排序修正结论

- 优先级上调：`WP8`、`WP11-min`
  原因：当前最影响策略工厂稳定性的，不只是“候选不够好”，而是“偏好被当硬门禁”和“流水线拒绝原因不可审计”。
- 后置但不取消：`WP7` 第二阶段
  原因：若 `WP5/WP6` 尚未把事件型、因子型、交易型验证对象分开，直接上 DSR / PBO / SPA / White RC 容易造成统计口径错配。
- 必须分阶段：`WP4`
  原因：显式/隐式成本拆分与滑点传播应先落地；容量、冲击与 `implementation_shortfall_proxy` 可作为第二阶段增强。
- 不建议重启迁移：整改不是新的 migration 项目，而是对已完成迁移后的主实现做契约收敛和验证修正。
