# 策略工厂系统架构设计文档（现状与分期演进）

> 本文档用于描述当前仓库中“策略工厂”相关能力的真实边界，以及在此基础上的分期演进路径。
> 研究蓝图请参考《策略工厂系统设计与实现》，但该研究报告**不代表当前已实现能力**。

## 1. 文档目标与边界

本文件只回答三个问题：

1. 当前仓库里已经有哪些可证明的能力。
2. 现阶段有哪些明确缺口。
3. 哪些增强项适合短期、中期、远期推进。

### 1.1 当前验证边界

本文中“当前已实现”的判断，主要基于以下证据：
- 当前工作区中的代码结构、模块接线与接口暴露情况
- BFF / Web / MCP 侧可见的策略工厂相关入口与页面
- 历史审计文档、问题清单与部分测试/运行旁证

这不等于已经对所有历史缺陷完成逐项回归验收。
因此凡是来自历史审计、P0 清单或方案文档的条目，除非已在当前工作区中再次核实，否则都应理解为“历史结论，当前状态待重新验证”。


以下能力**当前不应视为已实现**：

- 完整 Event Sourcing / CQRS
- 基于 pgvector/HNSW 的持久化向量去重
- 完整模拟盘 NAV 驱动的孵化晋级闭环
- 工业级 RL / LLM 自治生成工厂
- 工厂级监控大盘与熔断体系

## 2. 当前架构基线

当前仓库已经形成了一个“可运行但仍偏轻量”的工厂闭环，核心逻辑主要位于 `packages/akshare-mcp`。

| 架构层 | 当前代码映射 | 已确认能力 | 当前边界 |
|:-------|:-------------|:-----------|:---------|
| 数据采集层 | `DataCollector` | 采集恐贪、因子 IC、北向资金、融资融券、板块资金流、策略分类计数 | 仍以日级快照为主，无独立数据质量服务 |
| 候选生成层 | `StrategySpawner` + `StrategyAutonomyService` | 启发式候选生成、配额补位、轻量 AI 候选增强（规则/LLM 代理/参数演化） | 仍不是完整自治工厂，实验治理与候选规模仍偏轻量 |
| 初筛与质检层 | `BacktestFilter` + `_run_quality_gate()` | 10 股中位数回测初筛；WF / PKF / Bootstrap / 参数敏感性四步质检；结果已落库到 `strategy_quality_reports` | 仍缺更丰富评级、趋势摘要与自动复检治理 |
| 向量画像与相似检索层 | `vector_search.py` + `vector_platform.py` | 行情形态向量检索、策略画像、索引登记、可疑候选向量复筛 | 仍是轻量检索与画像存储，不是 `pgvector/HNSW` 向量平台 |
| 生命周期与淘汰层 | `strategy_manager.py` + `EliminationChecker` + `incubation.py` | 状态机、提交审核、孵化扫描、红旗淘汰、状态事件审计、孵化账户/指标记录 | 晋级仍主要依据 `strategy_metrics` 与前向收益概览，不是完整 NAV 驱动闭环 |
| 展示与消费层 | BFF `strategy.controller.ts` + Web `strategy-market` 页面 | 已有策略列表、详情、排序、订阅、评价、信号与前向收益接口，并补工厂运行态、审查报告、事件流、孵化概览、运行历史 | 仍偏轻量看板，无完整运营总控台 |

## 3. 当前已实现的工厂闭环

### 3.1 每日工厂流程

`StrategyFactoryScheduler.run_once()` 已能串起如下流程：

1. `DataCollector.collect()` 生成每日市场快照
2. `StrategySpawner.spawn()` 生成候选策略
3. `StrategyAutonomyService.generate_factory_candidates()` 补充 AI 候选
4. `BacktestFilter.filter()` 完成初筛
5. `Deduplicator.deduplicate()` 以参数相似度为主判，并对可疑候选做向量复筛
6. `StrategySubmitter.submit()` 创建策略、提交质检，并在通过后尝试绑定孵化账户与构建策略画像
7. `EliminationChecker.check()` 对已上架策略执行淘汰检查

这意味着：**当前仓库已经具备“从快照到候选、再到提交与淘汰”的自动化主链路。**

### 3.2 验证与状态管理

当前质量门禁与状态管理能力已经比较明确：

- `_run_quality_gate()`：执行 Walk-Forward、Purged K-Fold、Bootstrap、参数敏感性四步验证
- `_save_quality_report()`：把提交质检与复检结果结构化落库
- `LIFECYCLE_TRANSITIONS`：定义当前 9 个生命周期状态与合法流转
- `_lifecycle_scan()`：按 `strategy_metrics` 与 `incubation_overview` 推进 `incubating → listed/deprecated`
- `SignalTracker.run_once()`：生成信号并计算前向收益，为后续淘汰与展示提供数据
- `strategy_manager`：已暴露 `review_report`、`events`、`incubation_overview`、`factory_status`、`factory_runs` 等治理接口

### 3.3 当前已经落库的数据

`storage/timescaledb/strategy.py` 已经支持：

- 策略基础信息与指标
- 质量报告 `strategy_quality_reports`
- 状态事件 `strategy_status_events`
- 工厂运行历史 `strategy_factory_runs`
- 血缘记录 `save_strategy_lineage()`
- 淘汰日志 `save_elimination_log()`
- 每日快照 `save_daily_snapshot()`
- 孵化账户与指标
- 策略向量画像与索引登记

因此当前更准确的架构表述是：

> **已有轻量闭环 + 局部审计能力，但还不是完整的工业化策略工厂。**

## 4. 已知阻塞项与代码缺陷（前置条件）

> 以下问题最初在《策略工厂方案》（`docs/plans/策略工厂方案.md`）和《策略超市集成可行性深度分析报告》（`docs/plans/策略超市集成可行性分析报告.md`）中确认。
> **基线声明**：P0/缺陷清单基于 `master` 分支编制。后续工作区中 P0-1（ImportError）、P0-3（get_limit_up_stats）、D-4（fear_greed_index 工具层）已有修复提交，但尚未合入主分支。**每次排期前应重新核实各项当前状态。**

### 4.1 历史审计中识别的 P0 问题（本节仅作排期背景，当前状态需重新核实）

| # | 阻塞项 | 位置 | 影响 |

### 4.3 对第 3 节“已实现闭环”描述的修正

本节保留的是“历史审计发现过什么”，而不是对当前工作区逐项重新验收后的结论。因此第 3 节的闭环描述应理解为：

> **代码结构与当前测试旁证已经表明，仓库具备可运行的工厂主链路；但历史缺陷条目仍应在每次排期前重新核实是否回归，而不应直接复制为“当前阻塞现状”。**

## 5. 当前确认的主要缺口

对照代码后，当前缺口主要集中在“接线不完整”，而不是“完全没有基础”。

### 5.1 孵化与模拟盘尚未形成完整 NAV 驱动闭环

- `incubation.py` 已能绑定账户、同步信号到模拟订单并记录孵化指标
- `_lifecycle_scan()` 当前仍以 `strategy_metrics` 与多周期前向收益概览为主，不直接读取模拟盘 NAV
- `paper_trading.py` 已被孵化服务部分复用，但尚未成为唯一晋级依据

### 5.2 去重已升级为“参数主判 + 可疑候选向量复筛”，但仍非完整向量平台

- `Deduplicator` 以参数相似度作为主判
- 对参数接近但未达主阈值的可疑候选，已调用 `vector_search.py` 做向量复筛
- 当前仍是轻量进程内/轻量持久化组合，不应写成 `pgvector/HNSW` 级别的持久化 ANN 平台

### 5.3 质量结果与运行态已经对外暴露，但运营视图仍偏轻量

- `_run_quality_gate()` 结果已落库，可经 `review_report` / `review_report_recheck` 查询
- `StrategyFactoryScheduler.status()`、`run_once()`、运行历史已通过 manager/BFF 暴露
- Web 端已有运行历史、趋势与失败聚合，但仍缺更重的运营总控台与干预视图

### 5.4 状态变更已有轻量审计流，但不等于完整 Event Sourcing

- `update_strategy_status()` 已会写入 `strategy_status_events`
- 当前可以按策略查询事件时间线与筛选条件
- 因此应表述为“已有 append-only 状态审计日志”，而不是“已实现完整 Event Sourcing / CQRS”

## 6. 分期演进路线

### 6.1 短期（基于现有代码最容易落地）

适合优先推进的事项：

1. **统一工厂级统计与趋势字段**
   - 生成数、初筛通过率、质检通过率、淘汰数、失败分类继续统一输出
   - 为 BFF/Web 的趋势视图与聚合看板提供稳定契约
2. **丰富质量报告摘要与失败标准化**
   - 补更多 `reason_code`、评分与摘要字段
   - 让复检、审查报告和失败聚合口径一致
3. **孵化/淘汰阈值参数化**
   - 将最小观察窗口、命中率、Sharpe、回撤阈值配置化
   - 降低不同策略类型共用固定阈值带来的误伤
4. **加强运行失败聚合与错误指纹**
   - 让工厂运行历史能更快定位回归与配置问题

### 6.2 中期（已有基础，但需跨模块接线）

1. **让孵化判断进一步靠近真实前向表现**
   - 继续提升 `signal_forward_returns` 多周期指标在晋级/淘汰中的权重
   - 补充基于净值序列的观察指标，但先不强行切换到完整 NAV 驱动
2. **扩展向量画像与跨批次复用**
   - 将历史画像、索引登记与去重摘要更紧密地接入工厂审查上下文
   - 再评估是否需要更强的持久化向量检索能力
3. **增强事件与运行历史查询能力**
   - 扩展事件 metadata、运行阶段摘要与多维筛选
   - 支撑更细粒度的运营排查和审计

### 6.3 远期（研究方向，不建议当前承诺）

1. **完整模拟盘 NAV 驱动的孵化晋级闭环**
2. **基于 `pgvector/HNSW` 的持久化向量去重**
3. **完整 Event Sourcing / CQRS**
4. **真实滑点、延迟、订单簿撮合**
5. **工业级 RL / LLM 自治生成工厂**

这些方向都具备技术可行性，但当前仓库还没有足够接线，文档中应保留为中长期规划。

## 7. 设计原则

1. **代码事实优先**：所有“已实现”描述必须能在仓库中找到对应实现。
2. **增量接线优先**：优先复用已有模块，而不是再造一套平行系统。
3. **先轻量审计，再完整事件化**：先解决可追溯问题，再考虑完整 Event Sourcing。
4. **先进程内接线，再持久化升级**：向量去重可先用现有 `vector_search.py`，再考虑 pgvector。
5. **BFF 扩展遵循现有 NestJS 风格**：新增接口沿用 Controller/Service 分层，不另起体系。

## 8. 联网资料对本方案的影响

本轮联网检索只保留与当前仓库强相关的结论：

- **pgvector 官方文档**：HNSW 确实适合 ANN 检索，但需要索引构建与参数调优，且过滤后召回会下降，所以更适合作为中期能力。
- **NestJS 官方文档**：现有 BFF 的 Controller/Service 写法已是标准模式，后续接口增强应直接沿用。
- **Martin Fowler Event Sourcing**：事件溯源适合审计与回放，但会显著提高复杂度，因此当前建议先做轻量事件日志，而非直接引入完整 CQRS/Event Sourcing 架构。

## 9. 最终判断

当前“策略工厂”的真实定位应表述为：

> **已经具备自动生成、质检、状态流转、信号跟踪、淘汰与展示的基础闭环，但离研究报告中的完整工业化工厂仍有明显距离。**

因此后续所有方案文档应统一采用：

- 当前已实现
- 短期可补齐
- 中期可演进
- 远期研究方向

而不是继续将研究蓝图直接写成现状说明。
