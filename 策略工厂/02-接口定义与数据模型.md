# 接口定义与数据模型（现状、草案与分期边界）

> 本文档只描述两类内容：
> 1. 当前仓库已经存在的接口与数据对象；
> 2. 基于现有代码边界整理出的接口草案与数据模型草案。

## 2026-03-21 校准补充

- 当前接口与数据模型，大多服务于“策略超市条目、工厂候选记录、生命周期事件”这类对象，而不是严格意义上的“完整股票交易策略契约”。
- 若要让策略工厂真正产出可审计、可执行、可回放的股票交易策略，后续必须补齐至少以下字段族：`target_symbol_policy`、`eligible_universe`、`exclusion_rules`、`position_sizing`、`rebalance_rule`、`holding_horizon`、`exit_rule`、`cost_assumption`、`capacity_limit`、`refresh_mode`、`lineage_reason`、`strict_pass_profile`。
- 在这些字段补齐之前，现有 `create / publish / submit` 等接口输入只能视为“候选策略定义”或“超市条目元数据”，不应被误读为完整策略对象。

## 1. 文档使用说明

阅读本文件时请先区分三种状态：

- **已实现**：代码中已存在，可直接调用或查询
- **运行时对象**：代码中会产生，但当前未独立持久化或未通过 BFF 暴露
- **接口草案 / 模型草案**：基于现有能力可以扩展，但当前尚未实现

- 这些接口**当前不能直接对接**。
- 它们之所以保留，是因为现有仓库已经具备部分底层能力，不需要从零设计。
- 后续若要实施，建议仍沿用当前 NestJS Controller/Service 分层模式。

## 4. 数据模型边界

### 4.1 当前已持久化的数据对象（权威清单）

> 本节为策略工厂文档集中**数据持久化状态的唯一权威源**。其他文档引用本节判定某对象是否已落库。

以下对象已经在当前仓库中存在明确落库路径（`storage/timescaledb/strategy.py` 中有对应写入函数）：

| 对象 | 当前状态 | 主要来源 | 说明 |
|:-----|:---------|:---------|:-----|
| 策略基础记录 | 已持久化 | `save_strategy()` | 策略名称、类型、参数、状态、标签等 |
| 策略指标 | 已持久化 | `save_strategy_metrics()` | 多周期收益、Sharpe、MDD、胜率等 |
| 策略血缘 | 已持久化 | `save_strategy_lineage()` | 记录父策略、生成原因、出生环境 |
| 淘汰日志 | 已持久化 | `save_elimination_log()` | 记录淘汰时间、红旗、原因 |
| 每日快照 | 已持久化 | `save_daily_snapshot()` | 记录工厂输入快照 |
| 质量报告 | 已持久化 | `save_strategy_quality_report()` | 记录质检结果、验证/风险摘要、去重说明 |
| 状态事件 | 已持久化 | `update_strategy_status()` / `list_strategy_status_events()` | 记录状态流转审计事件 |
| 工厂运行历史 | 已持久化 | `save_strategy_factory_run()` / `list_strategy_factory_runs()` | 记录 `run_once()` 的摘要、阶段结果与错误信息 |

### 4.2 当前存在但尚未独立持久化的运行时对象

| 对象 | 当前状态 | 主要来源 | 当前边界 |
|:-----|:---------|:---------|:---------|
| 工厂运行摘要 | 运行时对象 + 已持久化历史 | `StrategyFactoryScheduler.run_once()` | 最近一次结果仍保留在进程内，同时历史结果已落 `strategy_factory_runs` |

### 4.3 推荐采用但当前未强制执行的契约格式

当前文档仍建议使用 JSON Schema 表达复杂对象契约，但需要明确两点：

1. 这是**推荐表达格式**，不是当前仓库已接线的运行时校验器。
2. 若后续需要真正执行校验，应在 BFF 或 MCP 入参边界增加对应验证逻辑。

可优先用于文档契约的对象包括：

- 策略元数据
- 质量报告
- 工厂运行摘要
- 事件审计记录

## 5. 建议保留的模型草案

以下模型可以保留为文档草案，但必须标明“未实现”。

### 5.1 质量报告草案

适合短期落地的字段：

- `strategy_id`
- `passed`
- `timestamp`
- `gate_results.walk_forward`
- `gate_results.purged_kfold`
- `gate_results.bootstrap_ci`
- `gate_results.param_sensitivity`
- `reasons`

不建议在第一阶段就加入过多“解释性文本”或复杂评级体系，优先保证与 `_run_quality_gate()` 当前返回值一致。

### 5.2 工厂运行摘要草案

适合直接从 `run_once()` 汇总的字段：

- `run_id`
- `run_time`
- `status`
- `elapsed_seconds`
- `candidates_spawned`
- `candidates_passed_backtest`
- `candidates_after_dedup`
- `submitted`
- `passed_quality_gate`
- `eliminated`
- `error`

若需要详情展示，可继续复用以下对象：

- `snapshot_summary`
- `stages.collect / spawn / filter / deduplicate / submit / eliminate`

若需要最近运行对比视图，可直接复用同一批摘要字段：

- `status`
- `candidates_spawned`
- `candidates_after_dedup`
- `submitted`
- `passed_quality_gate`
- `eliminated`
- `elapsed_seconds`

若需要运行趋势视图，可在前端基于最近多次运行结果直接计算：

- 成功率（基于 `status`）
- 平均耗时（基于 `elapsed_seconds`）
- 最新值相对最早值的变化量

若需要细粒度趋势与筛选，可继续在前端基于同一批运行历史增加：

- 状态筛选（全部 / 成功 / 失败）
- 指标切换（候选生成 / 提交数 / 质检通过 / 耗时）

若需要失败原因聚合，可继续复用同一批运行历史字段：

- `status = failed`
- `error`
- `stages`

若需要错误指纹标准化，可在前端基于 `error` 做轻量规则化归类，例如：

- 超时错误
- 网络连接错误
- 数据库错误
- 配置缺失
- 输入校验错误
- 依赖加载错误

若需要规则命中统计，也可继续基于同一批失败运行结果在前端直接计算：

- 规则命中失败数
- 规则命中率（已命中规则失败数 / 失败总数）
- 未分类错误数量
- 覆盖指纹种类数（仅统计已命中规则的类别）
- 未分类错误示例列表

### 5.3 事件审计记录草案

适合作为中期 append-only 审计表字段：

- `event_id`
- `strategy_id`
- `event_type`
- `from_status`
- `to_status`
- `reason`
- `actor`
- `metadata`
- `created_at`

这里推荐先做“状态变更审计日志”，不要在第一阶段就把文档口径升级为完整 Event Sourcing / CQRS。

## 6. 当前生命周期状态定义（权威源）

> 本节为**策略工厂文档集中状态定义的唯一权威源**。其他文档（01/03/04 及 `docs/plans/策略工厂方案.md`）均应引用本节定义。

状态定义必须以 `LIFECYCLE_TRANSITIONS` 为准：

| 状态 | 当前含义 | 允许去向 | 备注 |
|:-----|:---------|:---------|:-----|
| `draft` | 草稿 | `submitted` | 工厂生成或手工创建 |
| `submitted` | 已提交审核 | `incubating` / `rejected` | 提交后立即进入质检 |
| `rejected` | 审核/孵化拒绝 | `draft` | 可调整后重提 |
| `incubating` | 孵化观察中 | `listed` / `rejected` | 质检通过后进入 |
| `listed` | 已上架 | `deprecated` / `suspended` | 可展示、可订阅 |
| `suspended` | 风险冻结 | `listed` / `deprecated` | 人工或规则冻结 |
| `deprecated` | 已淘汰 | 终态 | 退化/红旗/环境错配 |
| `published` | 已发布（历史遗留态） | `deprecated` / `suspended` / `archived` / `listed` | 见下方说明 |
| `archived` | 已归档 | 终态 | 手工归档 |

### 6.1 `published` 与 `archived` 的定位说明

- **`published`** 是当前代码中保留的历史状态。在策略工厂的自动化流程（`run_once()`）中不会产生此状态——工厂生成的策略走 `draft → submitted → incubating → listed` 路径。`published` 仅用于手工发布场景，后续建议评估是否合并入 `listed`。
- **`archived`** 是手工归档的终态，工厂淘汰流程使用 `deprecated` 而非 `archived`。两者区别是：`deprecated` 由系统自动触发（退化/红旗），`archived` 由人工主动触发。
- `docs/plans/策略工厂方案.md` 中仅使用 `draft/submitted/incubating/rejected/listed/deprecated` 6 个状态，这是工厂自动化流程的最小状态集，与本节 9 个状态不矛盾——差异在于 `published`/`archived`/`suspended` 仅出现在手工操作或风控场景。

### 6.2 与研究报告状态名的映射

文档中不再使用 `UNDER_REVIEW`、`LIVE_CANDIDATE`、`RE_OPTIMIZING` 等研究报告状态名来描述当前系统。研究报告状态名与当前系统的对应关系仅供参考：

| 研究报告状态 | 当前对应 | 说明 |
|:-------------|:---------|:-----|
| `IDLE` / `GENERATED` | `draft` | 合并为草稿态 |
| `UNDER_REVIEW` | `submitted` | 审查=质检 |
| `INCUBATING` | `incubating` | 一致 |
| `FAILED` / `ARCHIVED` | `rejected` / `archived` | 拆分失败与归档 |
| `LIVE_CANDIDATE` | 无对应 | 当前不区分候选与上架 |
| `LIVE` | `listed` | 上架≈上线 |
| `SUSPENDED` | `suspended` | 一致 |
| `RE_OPTIMIZING` | 无对应 | 远期研究方向 |

## 7. 联网资料的落地结论

- **JSON Schema 官方资料**：适合作为对象契约文档格式，因此保留“Schema 草案”是合理的；但当前不能写成“已开启强校验”。
- **NestJS 官方文档**：当前 BFF 路由设计已符合标准，因此任何新增端点都应沿用现有 Controller/Service 结构。
- **Event Sourcing 资料**：事件流非常适合审计，但在当前阶段更合适的做法是先做轻量状态审计表。

## 8. 本文档的最终口径

本文件不再把“接口建议”写成“已存在接口”，也不再把“模型草案”写成“当前事实”。

1. 质量报告落库
