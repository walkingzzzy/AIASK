# 策略工厂因子研究层最小优化方案

> 目标：在**不重构现有策略工厂主链**的前提下，为 `packages/akshare-mcp` 增加一个显式、轻量、可回退的“因子研究层”，解决“已有因子能力分散存在，但未形成主链独立阶段”的问题。
>
> 2026-03-21 校准补充：因子研究层的正确定位是“研究证据整理层”，不是完整策略语义、事件约束或提交门禁的替代品。它可以为 `strategy_preferences`、候选排序、验证侧证提供输入，但不应单独决定候选是否合理。

---

## 1. 方案背景

基于当前仓库真实代码，策略工厂主链为：

1. `DataCollector.collect()`
2. `StrategySpawner.spawn(snapshot)`
3. `StrategyAutonomyService.run_cycle(...)`
4. `BacktestFilter`
5. `Deduplicator`
6. `StrategySubmitter`
7. `EliminationChecker`

当前系统**不是完全没有因子能力**，而是：

- 有独立 `FactorScheduler.run_once()` 负责批量计算因子与 IC
- `DataCollector.collect()` 会把 `factor_ic` / `factor_ic_trend` 汇总进 `snapshot`
- `StrategySpawner._from_factor_ic()` 会用因子摘要直接生成候选策略
- `MarketOpportunityScanner._build_snapshot_tasks()` 会根据 `factor_ic_trend` 生成 `factor_acceleration` 任务
- `LLMAlphaMiner.generate_factor_candidates()` 可在本地 fallback 路径中生成候选因子定义

但当前工厂主链中**没有一个显式的独立阶段**来统一完成：

- 因子发现 / 因子筛选
- 因子有效性摘要
- 因子优先级排序
- 因子到策略生成偏好的结构化映射

这导致因子信息虽然存在，但主要以“快照字段/局部 fallback”的形式分散参与，而不是形成统一的中间产物驱动后续生成。

---

## 2. 当前问题（代码事实）

### 2.1 主链缺少显式因子研究阶段

`StrategyFactoryScheduler.run_once()` 当前没有 `factor_research` / `factor_screening` / `factor_selection` 之类的独立 stage。

### 2.2 因子信息进入生成链的方式偏摘要化

当前工厂主要消费的是：

- `snapshot.factor_ic`
- `snapshot.factor_ic_trend`
- `factor_acceleration` 类型 research task

缺少统一的结构化产物，例如：

- 当前活跃因子列表
- 因子优先级排名
- 因子稳定性/衰减标签
- 因子驱动的推荐策略类型
- 给 LLM / reviewer / spawner 共用的因子证据链

### 2.3 两条生成路径对因子的利用不一致

- monolithic 路径中，`LLMProxyStrategyGenerator._build_research_context()` 会带入 `factor_ic` / `factor_ic_trend`
- staged pipeline 路径中，`strategy_pipeline.py::_build_initial_input()` 当前未显式加入因子研究产物

这会导致不同生成路径对因子的利用深度不一致。

---

## 3. 优化目标

本方案只解决一个核心问题：

**把现有已分散存在的因子能力，收敛为策略工厂主链中一个轻量、统一、可回退的“因子研究层中间产物”。**

明确不做：

- 不重写 `FactorScheduler`
- 不重新发明新的因子计算引擎
- 不把因子研究变成首版硬门禁
- 不改动回测 / 去重 / 提交 / 淘汰语义

---

## 4. 最小可行方案

### 4.1 新增阶段位置

在 `StrategyFactoryScheduler.run_once()` 中插入：

1. `collect`
2. **`factor_research`（新增）**
3. `spawn`
4. `autonomy`
5. `backtest`
6. `deduplicate`
7. `submit`
8. `elimination`

### 4.2 新增阶段职责

新增 `factor_research` 不负责重算因子，只负责：

1. 读取 `snapshot.factor_ic` / `snapshot.factor_ic_trend`
2. 必要时补读最近 `factor_ic_history`
3. 对已有因子做轻量排序、筛选、打标签
4. 生成统一的 `factor_research_artifact`

### 4.3 建议产出结构

建议新增：`snapshot["factor_research"]`，结构示例：

- `active_factors`: 当前激活因子列表
- `ranked_factors`: 因子排序结果
- `positive_rising_factors`: 上升且 IC 为正的因子
- `decay_flags`: 因子衰减标记（首版可选）
- `preferred_strategy_types`: 建议优先生成的策略类型
- `research_rationale`: 人类可读解释
- `source_chain`: 来源链（如 `factor_ic_history -> artifact_v1`）
- `degraded`: 是否降级

首版建议只基于已有 `factor_ic` / `factor_ic_trend` 计算，不强依赖 `LLMAlphaMiner.evaluate_factor()`。

---

## 5. 对现有模块的最小改造点

### 5.1 `factory_scheduler.py`

改造点：

- 在 `collect` 后调用新的 `factor_research` 构建函数
- 将结果写入：
  - `snapshot["factor_research"]`
  - `results["stages"]["factor_research"]`
  - `results["summary"]` 的关键统计字段

### 5.2 新增 `strategy_factory/factor_research.py`

新增轻量服务，例如：

- `class FactorResearchBuilder`
- `async def build(self, db, snapshot) -> dict`

职责仅为“聚合与筛选”，不做大规模新计算。

### 5.3 `spawner.py`

优先读取：

- `snapshot["factor_research"]["preferred_strategy_types"]`
- `snapshot["factor_research"]["positive_rising_factors"]`

若缺失则回退到当前：

- `factor_ic`
- `factor_ic_trend`

### 5.4 `opportunity.py`

将当前基于 `factor_ic_trend` 的 `factor_acceleration` 任务生成，改为优先消费：

- `snapshot["factor_research"]["active_factors"]`

这样 research task 会更稳定，也更容易解释。

### 5.5 `strategy_generators.py` / `strategy_autonomy.py`

把 `factor_research` 作为显式上下文透传给：

- `research_context`
- `research_task.metadata`
- `llm_report` / `generation_stats`

目标是让 rule / LLM / reviewer 看到同一份因子研究结果。

### 5.6 `strategy_pipeline.py`

首版不新增 pipeline stage，但建议把：

- `snapshot.factor_research`

显式加入 `_build_initial_input()`，保证 staged 与 monolithic 两条路径上下文一致。

---

## 6. 分阶段实施建议

### Phase 1：轻量接入（建议先做）

范围：

- 新增 `factor_research_artifact`
- 调度器接入
- `Spawner` / `Scanner` / `research_context` 优先读取 artifact

特点：

- 不改变现有门禁逻辑
- 不减少候选数量上限
- 仅增强解释性与输入质量

### Phase 2：评估增强（可选）

在已有 artifact 基础上，选择性接入：

- `evaluate_factor()`
- `detect_alpha_decay()`
- `get_top_factors()`

但仍建议保持为“增强信号”，而不是硬拦截。

### Phase 3：硬门禁（暂不建议）

只有当以下都验证充分后再考虑：

- 候选质量显著提升
- 候选数不明显下滑
- staged / monolithic 两条路径一致性稳定

---

## 7. 风险控制

### 7.1 避免重复实现因子计算

风险：与 `FactorScheduler` 重叠，导致口径不一致。

控制：

- `factor_research` 首版只消费既有结果
- 不重算基础因子值

### 7.2 避免候选数断崖式下降

风险：如果把 artifact 直接做成硬筛选，会压缩候选池。

控制：

- 首版仅作为增强输入
- 缺失时无缝回退旧逻辑

### 7.3 避免两条生成路径继续分裂

风险：monolithic 与 staged 对因子使用不一致。

控制：

- 同时把 `factor_research` 注入 `research_context` 与 `pipeline initial input`

### 7.4 避免可观测性缺失

控制：

- 在 `run_once().summary` 中增加：
  - `factor_research_used`
  - `active_factor_count`
  - `top_factor_names`
  - `factor_research_degraded`

---

## 8. 推荐验证方式

### 8.1 单元/集成验证

至少补以下测试：

1. `factor_research` artifact 构建测试
2. `Spawner` 优先读取 artifact、缺失回退旧字段测试
3. `OpportunityScanner` 基于 artifact 生成 factor task 测试
4. `Autonomy/LLM research_context` 透传 artifact 测试
5. `run_once().summary` 新字段测试

### 8.2 真实运行验证

使用真实 `get_strategy_factory_scheduler().run_once()` 对比：

- factor artifact 是否生成
- event/snapshot/factor task 分布是否合理
- autonomy 候选是否带有更清晰因子上下文
- 提交前候选数是否明显异常

### 8.3 观察指标

建议重点观察：

- `generated_count`
- `reviewed_count`
- `passed_backtest_count`
- `submitted_count`
- `active_factor_count`
- `factor_acceleration_task_count`
- `top_factor_names`

---

## 9. 实施结论

当前仓库**已经具备进入最小实施的条件**，因为：

1. 插入点明确：`collect` 之后、`spawn/autonomy` 之前
2. 上游依赖已有：`FactorScheduler`、`factor_ic_history`
3. 下游消费点明确：`Spawner`、`Scanner`、`research_context`
4. 风险可控：可做成增强输入而非硬门禁

因此，推荐按 **Phase 1 轻量接入** 开始实施，而不是直接做大规模因子系统重构。

---

## 10. 一句话结论

当前问题不是“没有因子能力”，而是：

**已有因子能力分散存在，但尚未在策略工厂主链中沉淀为统一、显式、可观测的因子研究层。**

本方案的目标，就是以最小改动把这层补出来。
