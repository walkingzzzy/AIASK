# 策略工厂 100 候选/小时优化方案

## 1. 目标与约束

- 目标：1 小时内生成至少 100 个策略候选，且至少 10 个通过质量门禁进入孵化期。
- 约束：不能牺牲质量；必须符合 `策略工厂/EVENT_DRIVEN_FACTORY_REBUILD_PLAN.md`；必须考虑 LLM 成本、速率限制、系统稳定性。

## 2. 基于实际代码的现状诊断

### 2.1 当前吞吐瓶颈是“四层串行”叠加

1. **研究任务串行**
   - `packages/akshare-mcp/src/akshare_mcp/services/strategy_factory/factory_scheduler.py:269`
   - 当前是 `for task in tasks:` 逐个执行 `generate_factory_candidates(...)`，没有 `TaskGroup` / `gather` / `Semaphore`。

2. **单任务内 pipeline 严格串行**
   - `packages/akshare-mcp/src/akshare_mcp/services/strategy_pipeline.py:4-5,109,220-227`
   - 当前固定执行 5 个 Stage：`event_recognition -> theme_propagation -> exposure_mapping -> market_confirmation -> strategy_generation`。
   - 每一阶段都等待上一阶段输出，且共享 `PIPELINE_STAGE_TIMEOUT_SEC`。

3. **候选回测串行，且候选内股票回测也串行**
   - `packages/akshare-mcp/src/akshare_mcp/services/strategy_factory/backtest_filter.py:126-127,170-188`
   - 先对 `candidates` 逐个 `_test_one`，再对 `evaluated_codes` 逐个拉 K 线和回测。

4. **提交/质量门禁串行**
   - `packages/akshare-mcp/src/akshare_mcp/services/strategy_factory/submitter.py:58-60,112`
   - 当前逐 candidate 走 `_submit_one()`，内部还串行执行 `_run_quality_gate()`。

### 2.2 当前配置本身限制了候选总量

- `AUTONOMY_MAX_RESEARCH_TASKS = 5`
  - `packages/akshare-mcp/src/akshare_mcp/services/strategy_factory/constants.py:86`
- `AUTONOMY_CANDIDATES_PER_TASK = 2`
  - `.../constants.py:87`
- 盘中默认调度间隔 900 秒（15 分钟）
  - `.../constants.py:94`
- `PIPELINE_STAGE_TIMEOUT_SEC = 20`
  - `.../constants.py:119`
- `CATEGORY_MINIMUMS` 为固定静态配额
  - `.../constants.py:19-23`

这意味着当前默认配置下，即使单次运行完全顺利，**每轮研究任务上限也只有约 10 个候选的默认规模**，远不足以稳定达到目标。

### 2.3 event-driven 任务还有额外限额

- `packages/akshare-mcp/src/akshare_mcp/services/strategy_factory/opportunity.py:273-296`
- event-driven 任务 `generation_limit` 被压到 `<= 3`。
- `packages/akshare-mcp/src/akshare_mcp/services/strategy_factory/opportunity.py:457`
- 最终任务列表还会被 `tasks[:AUTONOMY_MAX_RESEARCH_TASKS]` 截断。

### 2.4 LLM provider 不是“并发不足”，而是“根本没有 fan-out”

- `packages/akshare-mcp/src/akshare_mcp/services/strategy_generators.py:1108-1123`
  - `request_limits = [max(2, min(int(limit or 3), 3))]`
  - 只有单个 request limit，没有多批并发请求数组。
- `packages/akshare-mcp/src/akshare_mcp/services/strategy_llm_provider.py:860-905`
  - provider 内部是单请求、串行 retry、超时降级，不是多请求并行编排。

## 3. 与事件驱动重构方案的一致性要求

`策略工厂/EVENT_DRIVEN_FACTORY_REBUILD_PLAN.md` 已明确三条硬约束：

1. **主流程尽量只读数据库**（第 11-14 行）
2. **外部抓取前移到 ETL / 同步任务**（第 11-12、88-90、110-129 行）
3. **LLM 只负责结构化摘要与模板化 DSL 生成，不负责自由选股**（第 13、233-246、482-501 行）

因此，本次优化的正确方向不是“给 LLM 更多上下文 + 更长 prompt + 更高 token”，而是：

- 把**吞吐优化放在编排层**
- 把**质量控制放在分级门禁层**
- 把**股票池和任务定义继续留在数据库/规则侧**

## 4. 外部最佳实践提炼

### 4.1 Python asyncio

- Python 官方文档建议用 `TaskGroup` 做结构化并发，用 `Semaphore` 做有界并发。
- 含义：可以并发处理多个研究任务，但必须设置上限，避免数据库、LLM 和回测引擎被打爆。

### 4.2 Anthropic SDK / 高吞吐 LLM 调用

- Anthropic Python SDK支持：
  - `AsyncAnthropic` 并发请求
  - message batches 批量处理
  - 针对 `RateLimitError` 的重试/退避
- 含义：候选生成可以做**多请求 fan-out**，但必须带配额控制、重试和降级策略。

### 4.3 Backtrader

- Backtrader 官方优化文档强调三件事：
  1. 多核并行是最大收益来源
  2. 数据预加载一次，避免每个 worker 反复加载
  3. 返回精简结果对象，而不是完整策略对象
- 含义：回测层要做**共享数据预取 + 并行执行 + 精简结果回传**。

### 4.4 vn.py

- vn.py README 强调：
  - 事件驱动引擎
  - 异步高并发 REST/WebSocket
  - batch feature calculation
  - 面向研究/回测/实盘的一体化流程
- 含义：任务编排应该是事件驱动+异步 IO，而不是在单个串行链路里堆更多规则。

### 4.5 AWS Batch + Airflow

- AWS 官方案例明确建议：
  - AWS Batch 负责并行回测
  - Airflow 负责依赖、重试、调度、监控
  - 通过分层架构把 orchestration 和 compute 分离
- 含义：本项目不一定要直接引入 Airflow，但应该学习它的**任务编排思想**：
  - 配置层
  - 调度层
  - 执行层
  - 结果归档层

### 4.6 补充吸收：旧方案中值得保留的实现级优化项

结合 `策略工厂/策略工厂性能优化方案.md` 的细化审查结果，还应补充四类实现级优化：

1. **LLM / embedding 连接池化**
   - `strategy_llm_provider.py` 与 `text_embedding.py` 当前都存在调用时新建 `httpx.AsyncClient` 的模式。
   - 建议改为进程级复用 client，统一连接池、超时、重试和关闭逻辑。
   - 这类优化不改变任务语义，属于低风险高收益的基础设施优化。

2. **去重链路批量预热**
   - `factory_scheduler.py` 当前是 `backtest -> deduplicate -> submit` 的同步主链路。
   - `deduplicator.py` 在 `_vector_check()` 中会触发 `_build_behavior_klines()`，后者又会调用 `_build_strategy_panels(...)`，成本不低。
   - 建议在去重前先对候选和既有策略做行为缓存预热，再进入逐候选判重。

3. **向量画像/ANN 检索作为后续增强**
   - 当前系统已有 `strategy_vector_profiles`、pgvector 查询接口和 `vector_platform` 能力。
   - 因此后续可把“画像构建并发化、ANN 检索替代部分暴力扫描”作为 Phase 3 增强项。
   - 但其优先级应低于任务并发、分级门禁、回测 worker 化。

4. **Spawner 参数变体扩展**
   - 在不放大 LLM 自由度的前提下，规则候选可以通过参数变体扩展形成更多 seed。
   - 适合作为低成本增产手段，并与快速门禁配套使用。

5. **收益数字仅作为压测目标，不作为承诺值**
   - 旧方案中的数量/耗时提升值可作为 benchmark target。
   - 最终结果仍取决于 DB、LLM 限流、pgvector 是否开启、embedding 是否启用、CPU 资源和候选分布。

## 5. 最终建议：采用“有界并发 + 分级门禁 + 任务驱动生成”

### 5.1 架构层

#### A. 任务级并发（最高优先级）

- 将 `factory_scheduler._run_autonomy_batches()` 从串行改为**有界并发任务池**。
- 推荐：`research_task_concurrency = 4~6`。
- 原则：只并发任务，不并发写同一条实验记录；每个任务内部仍保留 provenance。

#### B. 单任务 pipeline 降长链

- **短期**：保留 5 stage，但允许：
  - task 已带完整证据包时，跳过前 2~3 个 stage
  - 超时后快速 fallback，不占满 20 秒
- **中期**：将 5 段压缩为 2~3 段：
  - `evidence_digest`
  - `confirmation`
  - `strategy_generation`

#### C. 回测与提交分离成独立 worker 池

- 回测过滤和提交不要阻塞 candidate generation 主通道。
- 生成、回测、提交拆成三个 bounded queue：
  - generation workers
  - backtest workers
  - submit workers

#### D. 基础设施和去重链路同步优化

- 为 `strategy_llm_provider.py`、`text_embedding.py` 引入共享 `httpx.AsyncClient`，统一连接池与生命周期管理。
- 在 `deduplicate` 前增加候选/既有策略行为缓存预热，降低 `_build_strategy_panels(...)` 的重复计算。
- 将去重本身也纳入 bounded concurrency，而不是保持纯串行逐 candidate 扫描。

### 5.2 配置层

#### 推荐调整

1. `AUTONOMY_MAX_RESEARCH_TASKS`
   - 当前：5
   - 建议：**12**（盘中）/ **8**（盘后）
   - 理由：要达到 100/hour，在 15 分钟一个周期下，每轮至少需要 25+ 原始候选。

2. `AUTONOMY_CANDIDATES_PER_TASK`
   - 当前：2
   - 建议：**4**
   - 理由：12 个任务 × 平均 3~4 个候选，单轮可到 36~48。

3. `PIPELINE_STAGE_TIMEOUT_SEC`
   - 当前：20
   - 建议：默认降到 **8~10 秒**，并引入 stage-specific timeout。
   - 理由：当前 fallback 已存在，继续让每 stage 持有 20 秒只会拖慢吞吐。

4. `CATEGORY_MINIMUMS`
   - 当前：固定静态最低配额
   - 建议：**不要简单整体调高**，改为：
     - per-cycle 轻量 minimum
     - per-hour diversity target
   - 目标：保证多样性，而不是强行制造低质量 quota-fill 候选。

5. `event_driven` `generation_limit`
   - 当前：上限 3
   - 建议：改为**按 priority 动态 3~6**，高证据任务可放宽。

### 5.3 算法层

#### A. 规则生成器（spawner）

- 当前 `spawner.py` 的 quota fill 目标总量偏低（目标总数 8，fill budget 最高 4）。
- 建议把 spawner 定位为：
  - **低成本 seed generator**
  - 不做最终主产能，只做规则种子和参数变体扩增
- 做法：
  - 每个强信号生成 2~3 个参数变体
  - 将规则候选上限提高到 12~16
  - 进入快速筛选后再决定是否进 LLM 深化

#### B. LLM 生成器

- 当前是单请求 limit，缺少 fan-out。
- 建议改为每任务：
  - 2 个 prompt variant
  - 每个 variant 产出 2 个候选
  - 总计 4 个候选上限
- 并发控制：
  - `llm_global_concurrency = 3~4`
  - `llm_per_task_parallel_requests = 2`
  - rate-limit/backoff/cooldown 保持现有机制并增强指标观测

#### C. 模板库与变体生成

- 强烈建议引入：
  - 事件驱动模板
  - 主题轮动模板
  - 龙头/补涨模板
  - 超跌修复模板
  - 因子增强模板
- LLM 主要负责：
  - 填 DSL
  - 变体化参数
  - 生成研究理由和风险提示
- 不负责：
  - 决定股票池
  - 发明任务主题

#### D. 去重与向量链路

- `Deduplicator` 作为回测后的主流程阶段，应优先做两步优化：
  1. 行为缓存批量预热
  2. 去重阶段 bounded concurrency
- `vector_platform` / `pgvector` / ANN 检索建议作为后续增强能力：
  - 用于缩短画像构建和相似搜索耗时
  - 不替代事件驱动任务定义本身
  - 不应挤占任务并发与分级门禁的优先级

### 5.4 质量控制

#### 分级门禁（必须做）

1. **Gate-0：结构门禁**
   - JSON 合法
   - DSL 可编译
   - 与 research_task 一致

2. **Gate-1：快速筛选**
   - 单股票/少量代表股票快速回测
   - 使用缓存 K 线
   - 只返回精简 metrics

3. **Gate-2：完整回测**
   - 只对 Gate-1 Top 25%~35% 候选执行
   - 可并行多股票验证

4. **Gate-3：提交门禁**
   - 质量门禁 + 风险报告 + 去重 + lineage 落库

#### 通过率目标

- 原始候选：100+/hour
- 通过 Gate-0/1：30~40/hour
- 进入完整回测：15~20/hour
- 进入孵化：10+/hour

## 6. 推荐实施顺序

### Phase 1（最快见效，1~2 周）

- 引入任务级有界并发
- 为 LLM / embedding 引入连接池复用
- 缩短 stage timeout
- 提升任务数与单任务候选数
- 提交/回测改 worker pool

### Phase 2（质量与吞吐兼顾，2~4 周）

- 引入分级门禁
- 回测缓存/预加载/精简结果对象
- 去重行为缓存预热 + 去重并发化
- LLM fan-out + prompt variants
- spawner 参数变体扩展

### Phase 3（与重建方案完全对齐，4~8 周）

- 把 `opportunity.py` 改成真正的事件/主题/暴露驱动任务生成
- 将 LLM 输入改为单任务证据包
- 压缩 pipeline stage
- `vector_platform` 画像构建并发化
- 视环境启用 pgvector / ANN 检索优化

### 实施说明

- 上述阶段中的吞吐和时延收益，应视为**压测目标**而非承诺值。
- 每一阶段落地后都需要单独记录：
  - candidates/hour
  - Gate-1 通过率
  - Gate-2 通过率
  - 平均单任务耗时
  - LLM 请求数 / 超时率 / 429 比例
  - DB 负载与回测队列长度

## 7. 风险与控制措施

1. **LLM 并发过高导致限流/成本上升**
   - 控制全局 semaphore
   - 分盘中/盘后不同配额
   - 盘后可使用 batch 模式，盘中只用 async 并发

2. **并发后数据库/回测资源被打满**
   - generation/backtest/submit 三池分离
   - 每池独立并发上限和熔断指标

3. **候选数量提升但质量下降**
   - 靠分级门禁而不是靠更严 prompt
   - 让完整回测只处理 Top-K

## 8. 最终结论

要达到 `100 candidates/hour`，**不能只调参数**，必须至少同时做四件事：

1. 任务级有界并发
2. LLM fan-out 而不是单请求 limit
3. 回测分级门禁与并行执行
4. 让 event-driven 高证据任务获得更高 generation budget

其中最重要的是：

- **吞吐优化放在 scheduler / worker / backtest orchestration**
- **研究质量继续放在事件驱动任务定义和分级门禁**
- **LLM 继续做受约束的辅助生成，而不是更自由的全市场推理**

这条路线既能提升数量，也不会偏离 `EVENT_DRIVEN_FACTORY_REBUILD_PLAN.md` 的方向。
