## 1. 功能设计

### 1.1 需求背景与价值

| 项 | 内容 |
|---|---|
| 问题陈述 | AIASK 具备文件、终端、外部平台、金融等高风险能力，必须有统一门禁和验收矩阵。 |
| 解决方案 | 按 read-only、config write、local high privilege、external side effect、financial risk、V1 deferred 分类。 |
| 业务价值 | 发布前可量化验证安全边界。 |

| OPS-US-SEC-002 | P0 | 作为审批人，我希望看到动作摘要和风险。 | intent/approval 列出 action/params/rationale。 |

### 1.4 业务规则与边界

| 动作类型 | 规则 | UI |
|---|---|---|
| 只读 | API token 可用 | 正常按钮 |
| 配置写入 | control token 或 confirm | 保存前提示 |
| 本地高权限 | full mode + control token | gated |
| 外部副作用 | preview -> intent -> approval | 创建审批 |
| 金融风险 | read-only/dry-run/intent/blocked | 不实盘交易 |
| V1 deferred | 隐藏或标记 internal | 不跳转 |

## 2. 流程设计

状态机：`read_only -> gated -> intent_created -> pending_approval -> approved|denied|expired -> executed|blocked|failed`。

## 3. 架构设计

前端门禁只做可见性和交互限制；后端 Agent policy、routes、intents、approvals 是权威执行边界。

| 能力 | Endpoint/文件 | Token | 字段 |
|---|---|---|---|
| Intents | `/intents` | control | `intent_id`、`action`、`status` |
| Approvals | `/v1/approvals` | control | `approval_id`、`decision` |
| Tool policy | `tools/policy.py` | N/A | toolset、blocked tokens |
| Health/control | `/health/detailed` | API | `control.token_configured` |

## 5. 前端设计

所有高风险按钮统一显示：动作性质、需要的 token、是否会写入、是否外部投递、是否金融风险、后续审批入口。

## 6. 开发规范

新增按钮必须在 PR 中声明动作分类；新增高风险路径必须补 negative test。

## 7. 错误说明

| 错误码 | 用户提示 | 技术原因 | 处理 |
|---|---|---|---|
| OPS-201 | 需要控制令牌 | control missing | 禁用按钮 |
| OPS-401 | 动作被策略阻断 | policy blocked | 显示 blocked reason |
| OPS-501 | 安全边界缺失 | no intent/approval for side effect | 阻止发布 |

## 8. 功能测试

| 用例编号 | 场景 | 预期 |
|---|---|---|
| TC-SEC-001 | 无 control token | 写入按钮 disabled |
| TC-SEC-002 | 外部发送 | 创建 intent 不直接发送 |
| TC-SEC-003 | live trading | blocked |
| TC-SEC-004 | secret scan | 不展示 key/token |
| TC-SEC-005 | 四工厂 | 不作为 V1 产品入口 |

## 9. 不做什么

- 不用前端判断替代后端策略。
- 不让副作用动作绕过 ActionIntent。
- 不把安全失败写成 warning 后继续发布。

## 10. 代码实证与成熟实现补强

### 10.1 当前代码审计

| 安全点 | 代码证据 | 当前行为 | 文档结论 |
|---|---|---|---|
| Token 状态 | `useAppConnectionSettings.ts`、`AppContextPanel.tsx`、`SettingsWorkspace.tsx` | API token、control token、mock/live、full mode 状态分离 | 文档要区分读 token 和控制 token |
| 通用禁用 | 各页面 `hasControlToken`、`disabled={!hasControlToken}` | Gateway、Jobs、MCP、Plugins、Data sync、Broker sync、Security scan 等写入动作禁用 | 无 token 不发写入请求 |
| 确认动作 | `confirmAction()` | Gateway directory refresh/send、danger action 有确认 | 高风险操作要二次确认 |
| Secret redaction | `shared.tsx`、Models/StockDataSources tests | raw JSON 中 secret-looking 值被 redacted | 文档和 UI 不展示 secret 原值 |
| V1 Scope | `v1Scope.ts`、`routes.ts`、`views.test.ts` | 隐藏 deferred factory tools/views | 四工厂负向是发布门禁 |

### 10.2 发布门禁矩阵

| 风险 | 必须门禁 | 证据 | 失败判定 |
|---|---|---|---|
| Secret | 只显示 env 名/configured/missing/redacted | `ModelsWorkspace.test.tsx`、`StockDataSourcesPanel.test.tsx`、`shared.test.tsx` | DOM/raw JSON 出现 key/token 原值 |
| 外部投递 | confirm + ActionIntent/approval | Gateway/Webhooks tests | 未审批直接投递 |
| 本地高权限 | full mode + control token | Diagnostics/Security tests | 无 token 仍调用 terminal/file/security scan |
| 金融风险 | read-only/intent/blocked | FinancialManager/FinanceLab tests | 出现实盘下单按钮 |
| 四工厂 | deferred/internal/legacy | routes/views/e2e/v1Scope tests | 导航或推荐入口出现四工厂 |

### 10.3 成熟技术采用

OWASP API Security Top 10、OWASP ASVS、Tauri Security 和 RFC 9457 共同形成 AIASK 安全口径：访问控制、错误结构、secret redaction、本地能力边界、审计和负向测试。AIASK 不采用前端自认为安全的绕过策略，后端策略始终权威。

### 11.3 状态和响应式

- `error`：安全检查失败必须显示具体失败项和文件/测试证据，不只写“未通过”。
- `gated`：高风险能力在 UI 上也要显式 disabled，但最终以后端策略为准。
- 窄屏矩阵变分组列表，列字段按“能力、风险、门禁、状态、证据”顺序展示。

## 原有内容保留

## 功能目标

本文件定义第一版发布前必须通过的安全和验收规则。它用于约束 PM、前端、后端和测试团队，避免“页面能点”被误认为“产品可发布”。

## 门禁分级

| 动作类型 | 示例 | 必须门禁 |
|---|---|---|
| 只读 | health、models、sessions、data status、stock radar candidates | API token，错误可见 |
| 配置写入 | 模型配置、数据源配置、profile、plugin/skill | control token，secret redaction |
| 外部副作用 | Gateway send、Webhook trigger、Feishu/Discord/Home Assistant 写操作 | confirm 或 ActionIntent/approval |
| 本地高权限 | 文件写入、patch、终端、浏览器控制、代码执行 | full mode + control token + 工具级说明 |
| 金融风险 | broker sync、financial manager intent、雷达推送/调度 | read-only/dry-run/intent，非投资建议 |
| 四工厂 | Strategy/Factor/Incubation/Factory Events | V1 不展示 |

## 发布验收矩阵

| 检查项 | 通过标准 |
|---|---|
| Typecheck | `npm run typecheck` 通过 |
| Unit tests | `npm test` 通过 |
| Build | `npm run build` 通过 |
| Mock e2e | V1 页面矩阵通过，不要求 live backend |
| Live smoke | 真实 Agent 启动后模型、MCP、数据、金融核心路径通过 |
| 四工厂负向 | 主导航、金融工作台、工作流、工具常驻入口无四工厂 |
| Secret | 页面、测试输出、文档不含 key/token 原值 |
| Token gates | 缺 control token 时写入按钮不可执行 |
| 状态灯 | 模型、MCP、数据源、数据库、Gateway、金融 readiness 有红黄绿 |

## 每个功能的验收模板

开发任务完成前必须写清：

1. 页面/组件路径。
2. 用户目标。
3. API endpoint、method、token、body/query。
4. loading/empty/error/degraded/gated/success。
5. 是否需要 ActionIntent/approval/confirm。
6. 测试文件和 mock 数据。
7. 四工厂负向断言。
8. 是否需要 live smoke。

## 当前已知风险

1. 现有前端和 e2e 仍有 legacy/advanced 入口需要继续和 V1 范围对齐。
2. 旧文档和部分源码中文可能存在编码/乱码显示问题，影响 PM 阅读。
3. Mock e2e 只能证明前端交互，不证明真实 Agent/MCP/数据源生产可用。
4. 后端四工厂能力仍存在，文档和前端要持续防止误回流到 V1。

## 验收规则

1. 没有对应专项文档的功能不得进入产品化开发。
2. 没有 API 合约和测试断言的页面不得标记完成。
3. 只通过单测不能说发布完成，必须至少通过 build 和 mock e2e。
4. 涉及真实数据源/外部平台/模型 provider 的功能必须另列 live smoke。
5. 任何“已实现”说法都必须能回指到代码、测试或可运行验证。

## 详细落地规范

### 问题场景与技术方案

| 问题场景 | 技术方案 | 验收 |
|---|---|---|
| 页面按钮能点但后端拒绝 | 前端 gated + 后端 control token 双保险 | 缺 token 不发写入请求，后端仍拒绝 |
| 高风险动作被当普通动作 | 动作分类决策树 | 每个按钮标注只读/写入/外部/本地高权限/金融风险 |
| mock 被误当 live | mode/readiness 显示 mock/live | PM 演示能看出当前模式 |
| 四工厂能力回流 | route fallback + v1Scope + e2e 负向 | 主导航和金融页无四工厂入口 |
| 文档写了已实现但代码无证据 | 代码证据索引 + 完成定义 | 每个“已实现”回指文件/API/测试 |

### 动作分类决策树

开发任何按钮前必须先回答：

1. 这个按钮是否只读？
2. 是否会写配置、写数据库、写文件、发消息、启动进程、运行代码？
3. 是否会影响外部平台？
4. 是否涉及金融交易、券商、组合、风控、策略生命周期？
5. 是否属于 V1 deferred 的四工厂？

对应处理：

| 判断结果 | 前端处理 | 后端处理 |
|---|---|---|
| 只读 | API token，可直接执行 | structured response |
| 写配置 | control token，按钮 gated | route 校验 control token |
| 外部副作用 | 预览 + confirm/intent | ActionIntent/approval |
| 本地高权限 | full mode + control token | `general_full` policy |
| 金融风险 | read-only/dry-run/intent | risk metadata |
| V1 deferred | 不展示入口 | 后端可保留 |

### 验收分层

| 层 | 要验证什么 | 命令/方法 |
|---|---|---|
| 文档 | 是否有问题-方案、状态机、API、验收 | 人工检查 + `rg` 结构检查 |
| 类型 | 前端类型和 API shape | `npm run typecheck` |
| 单测 | 组件状态、token gate、API 调用 | `npm test` |
| 构建 | 生产包是否能生成 | `npm run build` |
| mock e2e | 页面矩阵、交互、负向边界 | `npm run test:e2e:mock` |
| live smoke | 真实 Agent/MCP/model/data/platform | `npm run test:e2e:live` 或专项脚本 |

### 负向验收清单

每个页面都必须检查：

- 不显示 secret/key/token 原文。
- 不直接导入 Python、MCP server、AKShare manager。
- 不显示四工厂产品入口。
- 不把 mock 显示为 live。
- 不在缺 token 时发送写入请求。
- 不用 raw JSON 墙替代 UI。
- 不让文字溢出或按钮尺寸不稳定。
