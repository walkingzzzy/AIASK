## 1. 功能设计

### 1.1 需求背景与价值

| 项 | 内容 |
|---|---|
| 问题陈述 | 旧文档要求多且散，若不映射，容易在新规范中遗漏或重复。 |
| 解决方案 | 用映射表把旧要求转成 V1 功能编号、开发阶段和验收标准。 |
| 业务价值 | 保留历史审计成果，同时让开发可执行。 |

### 1.2 用户故事

| 编号 | 优先级 | 用户故事 | 成功标准 |
|---|---|---|---|
| PLAN-US-001 | P0 | 作为 PM，我希望知道旧要求是否被保留。 | 每条旧要求有去向。 |
| PLAN-US-002 | P0 | 作为开发负责人，我希望按阶段执行。 | P0-P7 有进入/退出标准。 |
| PLAN-US-003 | P0 | 作为 QA，我希望知道哪些是 deferred。 | 四工厂等范围有明确状态。 |

### 1.3 功能分解与优先级

| 功能编号 | 功能点 | 优先级 | 当前代码依据 | 待开发事项 | 验收标准 |
|---|---|---|---|---|---|
| PLAN-F001 | 旧要求映射 | P0 | 旧文档和主规范 | 持续维护 | 无遗漏 |
| PLAN-F002 | 开发阶段 | P0 | V1 方案 | 与 PR/任务同步 | 每阶段有交付物 |
| PLAN-F003 | Deferred 规则 | P0 | `routes.ts` | 阶段准入检查 | 四工厂不进入 V1 |

### 1.4 业务规则与边界

旧要求不能直接删除；只能映射到 V1、标记 deferred、合并到已有章节，或说明不采用原因。

## 2. 流程设计

流程：`旧文档要求 -> 分类 -> 映射功能编号 -> 指定开发阶段 -> 定义验收 -> README/专项文档同步`。状态机：`unmapped -> mapped -> staged -> implemented -> verified -> retained|deferred`。

## 3. 架构设计

本文件是规划和追踪层，不新增系统架构；所有实际代码事实必须回到 Desktop/Agent/AKShare/Finance packages。

## 4. 功能说明：接口与数据

本文件不定义运行时 API；映射表字段必须包含来源文档、旧要求、V1 功能编号、代码证据、阶段、验收、状态。

## 5. 前端设计

本文件不定义页面 UI；但任何阶段计划若涉及页面，必须引用 `views.ts`、`routes.ts`、`App.tsx` 和 `features/*`。

## 6. 开发规范

阶段任务必须可落 PR：每项至少包含文件、接口、mock、测试、文档更新。

## 开发阶段

### P0 范围冻结

完成内容：

- 冻结 V1 功能列表。
- 冻结不展示范围：Strategy Factory、Factor Factory、Incubation Factory、Factory Events。
- 梳理 `desktop/src/views.ts`、`desktop/src/routes.ts`、`desktop/src/v1Scope.ts`。
- 建立四工厂负向断言。

完成方式：

1. 扫描主导航、快捷入口、Finance Lab、Workflows、Readiness、ToolCatalog。
2. 将四工厂 route fallback 到非产品入口。
3. 保留代码证据，但文案标注 deferred/legacy。

### P1 AI 工作台闭环

完成内容：

- Workbench 新建、发送、模型选择、历史、归档。
- runs/events/artifacts/sources 可追踪。
- AI 回复显示工具调用与证据。

完成方式：

1. 对齐 `/v1/responses`、`/v1/desktop/workbench/summary`、`/v1/runs/*`。
2. 右侧栏实现运行、工具、证据、审批。
3. 补充 Workbench 单测和 mock e2e。

### P2 能力接入

完成内容：

- Models、MCP、Skills、Plugins、Connectors。
- 状态灯、测试按钮、secret redaction。

完成方式：

1. 每个 provider/connector/service 都有红黄绿状态。
2. 变更动作使用 control token。
3. 动态 MCP/插件工具不直接进入模型可见工具列表。

### P3 数据基础

完成内容：

- 股票数据源配置与测试。
- 数据库状态、freshness、同步计划。
- 数据同步按钮进入受控流程。

完成方式：

1. 对齐 `/v1/desktop/stock-data-sources`、`/v1/desktop/data/status`、`/sync-plan`。
2. 展示免费/付费/本地源。
3. stale、empty、fallback 必须可见。

### P4 金融观察与发现

完成内容：

- Market Temperature/热力图。
- Stock Radar 独立页面。
- 金融右侧栏联动。

完成方式：

1. Market Temperature 使用 `agent_market_temperature_*` 工具。
2. Stock Radar 使用 `/v1/desktop/stock-radar/*`。
3. 输出保持非投资建议和数据来源。

### P5 金融研究与工作台

完成内容：

- Finance Lab、Financial Manager、Quant Research、Broker read-only。

完成方式：

1. Quant Research 不跳转 Strategy Factory。
2. Broker 只读展示账户/持仓/订单/分析，不提供交易按钮。
3. Financial Manager 写入动作走 intent。

### P6 自动化与外部联动

完成内容：

- Jobs、Workflows、Gateway、Webhooks、飞书/Discord/Home Assistant 等。

完成方式：

1. 任务创建/修改/删除使用 control token。
2. 外部投递使用 confirm/intent/approval。
3. 失败、重试、目录刷新可追踪。

### P7 发布验收

完成内容：

- typecheck、unit tests、build、mock e2e、live smoke 清单。
- 文档、测试、页面三者一致。

完成方式：

1. 所有新页面有专项文档。
2. 每个页面有 API 合约和状态验收。
3. mock e2e 覆盖页面矩阵。
4. live smoke 单独验证真实 Agent/MCP/数据源。

## 详细落地规范

### 问题场景与技术方案

| 问题场景 | 技术方案 | 验收 |
|---|---|---|
| 旧文档太宽泛 | 按功能拆成专项文档 | 每项能力有单独文档 |
| 旧文档说“已实现”但代码不一定支持 | 以当前代码和 API 为准重写 | 每条结论回指代码 |
| 开发阶段只写目标不写做法 | P0-P7 写清交付物和进入条件 | 每阶段有文件、API、测试要求 |
| 四工厂内容混入 V1 | 标注 deferred，只保留证据 | V1 页面负向检查 |
| 文档和开发脱节 | 文档变更作为开发前置条件 | 没有专项文档不进入开发 |

### 旧文档升级规则

旧文档中的内容不得直接复制为“已实现”。每一条旧要求升级时必须按以下规则处理：

| 旧文档说法 | 新规范处理 |
|---|---|
| “支持某功能” | 拆成用户场景、API、页面、状态、验收 |
| “已有后端能力” | 写出代码路径、route/tool、缺前端什么 |
| “需要前端展示” | 写出信息架构、组件、字段、空态/错误态 |
| “需要验收” | 写出命令、测试文件、mock/live 区分 |
| “策略/因子/孵化/事件” | 标注 V1 deferred，不进入产品入口 |

### 开发阶段进入条件

每个阶段开始前必须满足：

1. 需求对应的专项文档存在。
2. 文档达到 `25-功能文档详细编写标准.md` L4。
3. 代码证据或待开发代码路径已列明。
4. 风险门禁已判断。
5. 负向边界已写入验收。
