## 1. 功能设计

### 1.1 需求背景与价值

| 项 | 内容 |
|---|---|
| 问题陈述 | AIASK 功能覆盖面大，如果没有统一总览，PM、开发和 QA 容易把 mock、后端存在、产品入口和 live 可用混为一谈。 |
| 解决方案 | 用本总览定义 V1 展示范围、代码证据总线、四工厂 deferred 边界和所有专项文档的阅读顺序。 |
| 业务价值 | 让第一版发布范围可评审、可拆解、可验收，避免“想一出是一出”。 |

## 2. 流程设计

| 流程 | 说明 | 异常路径 |
|---|---|---|
| 范围确认 | PM 先读总览和主规范，再进入专项文档 | 发现能力缺证据时标记待开发，不写已完成 |
| 开发拆解 | 开发按功能编号、代码路径、API、测试拆任务 | 发现后端缺 route 时先补 Agent HTTP |
| 发布验收 | QA 按主流程和负向边界执行 | 四工厂命中必须解释为 deferred/internal |

状态机：`draft -> reviewed -> development_ready -> verified -> release_locked`；遇到代码证据缺失进入 `blocked`，遇到四工厂展示则必须进入 `scope_failed`。

## 3. 架构设计

| 层 | 职责 | 代码证据 |
|---|---|---|
| Desktop | UI、路由、状态、mock/live 展示 | `desktop/src` |
| Agent HTTP | Desktop-facing API、intents、approvals、tools | `packages/agent/src/aiask_agent/routes/*` |
| 金融/MCP | 数据、研究、金融工具和外部 server | `packages/akshare-mcp`、`packages/finance-mcp-servers` |
| Deferred | 后端保留但 V1 不展示的工厂类能力 | `packages/strategy-factory`、旧 feature folders |

核心决策：总览只负责产品化范围和证据总线，不替代各专项文档的详细接口和测试。

## 6. 开发规范

新增或修改范围时，先改专项文档，再改代码和测试；不得只改导航或只改文案。

## 10. 代码实证与成熟实现补强

### 10.1 当前代码审计结论

| 维度 | 当前实码事实 | 对文档的影响 |
|---|---|---|
| 前端栈 | `desktop/package.json` 使用 React 18、Vite 6、Tauri 2、React Router、Vitest、Playwright、TanStack Table/Virtual、Lightweight Charts | 所有前端方案必须写成现有栈落地，不能引入未评审框架 |
| 页面挂载 | `desktop/src/App.tsx` lazy 加载 Workbench、FinanceLab、MCP、Gateway、Models、Settings、StockRadar 等页面 | “已存在页面”必须同时具备 view、route、renderer、test 证据 |
| V1 路由边界 | `desktop/src/routes.ts` 的 `V1_DEFERRED_VIEWS` 排除 `strategy-factory`、`factor-factory`、`incubation`、`factory-events` | 四工厂只能作为 deferred/internal/legacy 证据，不进入 V1 正向入口 |
| 工具过滤 | `desktop/src/v1Scope.ts` 过滤 `agent_factory_*`、`agent_factor_factory_*`、`agent_incubation_factory_*` 等工具 | 工具目录和 Workbench 推荐动作也必须遵守 V1 范围 |
| API 分层 | `desktop/src/services/aiaskApi.ts` 叠加 `services/api/ai.ts`、`workbench.ts`、`finance.ts`、`integrations.ts`、`intents.ts`、`ops.ts`、`desktopState.ts` | 文档接口必须写前端方法和 Agent endpoint，不允许只写“调用后端” |
| Agent routes | `packages/agent/src/aiask_agent/routes/*` 覆盖 AI、MCP、Gateway、Jobs、Learning/RL、Data、Finance、Run history、Intents、Approvals | “待开发事项”要落到具体 route 文件或明确无需改后端 |
| 测试现状 | `desktop/e2e/capabilities.spec.ts` 已有 V1 隐藏工厂、Stock Radar、Data Sync、MCP、Gateway、模型、页面矩阵 mock/live smoke | 文档验收不能只写“测试通过”，要说明 Vitest、Playwright mock、live smoke 的边界 |

### 10.2 联网成熟方案采用基线

| 来源 | 官方核验结论 | AIASK 采用方式 | 不采用内容 |
|---|---|---|---|
| OpenAI Tools | 工具调用需要明确工具、输入、输出、错误和状态 | Workbench/Tools 页面展示 `agent_*` 工具证据、side_effect、blocked reason | 不把工具结果藏进纯 Markdown |
| MCP 官方文档 | MCP 是连接 tools/resources/prompts 的协议层 | MCP 页面按 servers/tools/resources/prompts/OAuth 分层，动态工具必须经 Agent facade | 不让 Desktop 或模型直调 raw MCP stateful tool |
| OpenAPI 3.2 / JSON Schema | API 需要 method/path/schema/error 明确 | 每篇功能文档接口表要写 endpoint、method、request、response、错误码 | V1 不强制一次性生成全量 OpenAPI 文件 |
| RFC 9457 / OWASP API Security | 错误和权限要结构化、可解释、可审计 | 采用 `error_code`、trace/audit、token、ActionIntent、approval、redaction 口径 | 不暴露 secret、堆栈和第三方凭据 |
| React / React Router / Vite / Tauri | 前端以组件、路由、构建和桌面安全边界组织 | 保持 `App.tsx`、`views.ts`、`routes.ts`、Tauri Security 的边界 | 不做网页营销页，不让桌面 UI 绕过后端门禁 |
| Vitest / Playwright / Testing Library | 单测测组件行为，E2E 测真实页面流程 | 每个模块必须有 component/API/mock/e2e 或说明 live smoke 前置 | 不把 mock e2e 当生产可用证明 |

### 10.3 文档补强后的最低阅读粒度

每篇专项文档后续都必须能回答：页面在哪里、API 方法在哪里、Agent route 在哪里、mock 在哪里、测试在哪里、哪些按钮只读、哪些按钮 gated、错误码如何显示、secret 如何 redacted、四工厂是否只作为 deferred。无法回答的条目不能写“已完成”，只能写“待开发”或“未核验”。

├── AppSidebar: 只展示 V1 产品入口

## 产品定位

AIASK 第一版应发布为“Agent 驱动的金融研究与自动化桌面工作台”。它不是官网、不是能力陈列墙，也不是策略工厂展示页。用户打开后应该能完成：AI 对话、模型配置、工具调用、MCP/Skills/插件接入、会话追踪、记忆管理、数据源与数据库检查、自动化盯盘、股票雷达、市场温度、金融研究与只读券商分析。

Strategy Factory、Factor Factory、Incubation Factory、Factory Events 不作为 V1 产品入口。当前代码里仍有相关包、类型、API client 或 legacy panel，这是后续版本能力或兼容证据，不等于第一版可见功能。前端验收必须检查主导航、工作流推荐、金融实验室、工具目录常驻入口中不出现四工厂产品入口。

## 标准页面模板

每个功能页面必须包含：

1. 页面目标：用户为什么打开这里。
2. 状态灯：绿色可用、黄色降级/需配置、红色不可用/失败、灰色未启用。
3. 主操作：只读操作、写入操作、副作用操作分区。
4. 证据区：工具调用、API endpoint、来源、时间、错误。
5. 门禁区：token、full mode、ActionIntent、approval、confirm、blocked reason。
6. 空态/错误态：不能只显示“无数据”，要告诉用户下一步。
7. 验收：API 调用、UI 展示、负向断言、安全断言。

## 问题场景与技术方案总览

| 产品问题 | 系统方案 | 技术边界 | 前端要求 |
|---|---|---|---|
| 用户不知道 AIASK 能做什么 | Workbench 默认入口 + 金融工作台 + 集成中心 | Desktop 只编排，不直接执行后端能力 | 首屏显示任务入口、状态和最近历史 |
| AI 对话不可追踪 | session/run/event/artifact/source 全链路 | Agent session store 是来源 | 右侧栏展示运行、工具、证据 |
| 模型经常不可用 | provider status + models + smoke test | 不展示 secret | 红黄绿灯和错误分类 |
| 工具太多且有风险 | `agent_*` facade + toolset policy | raw manager 不可见 | 工具目录按风险分层 |
| MCP/Skills/Plugins 容易失控 | Agent HTTP 管理 + control token | 动态工具不能直接给模型 | 管理、测试、启用分步骤 |
| 金融数据不稳定 | data source status + DB freshness + sync plan | AKShare/TDX/Tushare 属数据层 | 数据源、数据库、同步按钮联动 |
| 自动化会产生副作用 | Jobs + Gateway/Webhook + ActionIntent | 外部投递必须可审计 | 任务模板、运行历史、审批 |
| 金融功能被误认为交易 | read-only/dry-run/intent | 不提供实盘交易入口 | 固定风险提示和只读标记 |
| 四工厂过早展示 | V1 deferred | 后端可保留，前端不展示 | route/view/tool/e2e 负向 |

## 开发落地总流程

1. 先读本目录对应功能文档和 `25-功能文档详细编写标准.md`。
2. 查 `18-代码证据索引.md`，确认已有 route/tool/client/page/test。
3. 如果后端已有能力，优先补 Desktop API client、mock、页面状态和测试。
4. 如果后端缺能力，先补 Agent HTTP route 或 `agent_*` facade，不让 Desktop 直连 Python/MCP/DB。
5. 新增 UI 前先定义状态机、字段、门禁、错误和空态。
6. 新增按钮前必须判断动作类型：只读、配置写入、外部副作用、本地高权限、金融风险、deferred。
7. 新增功能后必须补 Vitest/mock e2e；真实 provider/数据源/平台另补 live smoke。

## 完成定义

一个功能只有同时满足以下条件，才能在开发计划中标记为完成：

- 有专项文档，且达到 `25` 中的 L4 标准。
- 有代码证据或明确待开发代码路径。
- 有 API/工具合约。
- 有状态机和 UI 布局。
- 有 token/intent/approval/blocked 规则。
- 有 mock 和测试策略。
- 不违反 V1 四工厂隐藏边界。
- 中文文档可读，无乱码。
